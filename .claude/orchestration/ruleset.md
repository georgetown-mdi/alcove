# Alcove orchestration ruleset

The rules for CONDUCTING an Alcove session -- one that spawns agents, runs review rounds, dispatches fixes, and reports decisions to the owner. `CONTRIBUTING.md` and `CLAUDE.md` hold what binds every agent; this file holds only what binds the session doing the conducting.

An orchestrating session reads this file before its first `Agent` or `Workflow` call, and again after a context reset. Enforced by `require-orchestration-ruleset-read.mjs`, which refuses that first `Agent` or `Workflow` call until `record-orchestration-ruleset-read.mjs` has recorded a read of this file in the session; the marker and how long a read stands for are in their headers. Seven front doors load it as their first step: `.claude/commands/start-issue.md`, `.claude/commands/light-review.md`, `.claude/commands/assess-review.md`, `.claude/commands/panel.md`, `.claude/commands/docket.md`, `.claude/commands/follow-ups.md`, and `.claude/skills/shortlist-backlog/SKILL.md`.

A spawned agent does not read it. `CLAUDE.md` alone holds the rules that bind it, and a spawn that reads this file pays for rules addressed to its caller.

## Worktrees and checkouts

- A small assess-review fix (under 20 changed lines) goes out as a `sonnet` implementer's exact edit, not inline; anything larger is a full spawn (`.claude/commands/assess-review.md`, Step 3).
- Parallel writing spawns run in their own worktree: pass `isolation:"worktree"` on the `Agent` call as a PARAMETER, never only in the prompt (prose telling the agent it is in one is inert) -- re-read the call for that parameter before submitting a worktree-mentioning spawn. Enforced by `require-declared-worktree-isolation.mjs`. Read-only reviewers may share `/workspace`, diffing by ref. Have the agent run `.claude/scripts/worktree-init.sh` before its first edit, provisioning `node_modules` and re-pointing a fresh `main`-based tree onto `origin/staging`; details in its header.
- A worktree under `.claude/worktrees/` holds work that exists nowhere else until committed, so do not disturb a live one: leave another session's tree alone, retire a finished one with `git worktree remove <path>` (no `--force`) only once every in-flight agent has landed -- a non-isolated agent inherits the session's worktree fence dynamically, so an idle-looking tree may still be in use -- and never switch out of one you have entered while an agent or review Workflow may still run there -- since a non-isolated run's write fence follows the session, switching cuts its shell mid-run and finishes the round read-only. Only a worktree-isolated spawn, or the by-ref flow that never enters a tree, is immune. Enforced by `block-worktree-deletions.mjs` on Bash -- rephrasing around its refusal destroys the tree just the same; details in its header.
- A command against a worktree runs with `env -C <tree> <command>` or `git -C <tree> <args>`, NEVER a leading `cd <tree> && ...`. The Bash tool's directory persists between calls, so that `cd` does not scope the one call: it re-homes the session into the tree for every later call, and the write fence a non-isolated spawn inherits follows the session, so the move lands later spawns -- and the shell of a run already under way -- in a tree that is not theirs. Enforced by `block-worktree-cd.mjs` on Bash; details in its header. If it happened, `cd /workspace` at once.

## Review flow

- Resolving a PR's checklist means re-reading `.github/PULL_REQUEST_TEMPLATE.md` and performing the Docs line's enumeration against the diff; an n/a box is checked with a reason tied to this diff, and a changelog n/a names the class it skips. CI (`npm run check:pr-checklist`) catches only the mechanical tells.
- A `Workflow` `schema` for a long-form agent follows the authoring rules in `.claude/commands/light-review.md`, Authoring a Workflow schema. An agent that exhausts its structured-output retries usually left analysis intact in the rejected attempts; salvage before re-running.
- Review and fixing run BY REF from the primary checkout, keeping several branches in review at once: `/light-review --target <ref>`, then `/assess-review <branch>`, then one implementer per branch pointed at that branch's worktree by absolute path. No step of that flow changes directory or checks anything out.
- Commit before any review round -- reviewers diff by ref and see only commits, so an uncommitted edit is treated as absent -- and a review attests the commit it read: the checklist's Security review line states that sha, and CI (`npm run check:pr-checklist`) fails while it is not the PR head. Re-attesting means reviewing that head; editing the sha alone states a review that did not happen, and the check cannot see it. Details on re-attesting a moved head, the base-sync route needing none, and what voids each: `.claude/commands/assess-review.md`, Step 4. Enforced by `require-clean-tree-for-review.mjs` on `Workflow` calls only (an `Agent`-spawned review is not gated, so hold the rule yourself); details in its header.
- Never self-review a security- or partner-reachable surface: spawn an independent reviewer, even for a small rework -- it alone sees the diff and the issue. Spawn `security-reviewer` and `adversarial-verifier` only under a refutation contract (a named list of claims to refute, one per claim), and only when the diff has adversary-reachable surface -- a test-only, docs-only, or support-script-only diff takes the lens round only, whatever its size -- run as `/light-review --role <name> --claims <file>`. Enforced by `require-review-contract.mjs` on a direct `Agent` spawn of either role. A claim's double quotes mean the quoted text occurs at the target ref and a string the round feeds the surface takes single quotes; enforced by `require-measured-claim-literals.mjs` on the round's `Workflow` call. Details: `.claude/commands/light-review.md`, The refutation contract.
- A gated claim or confirmed review finding has four dispositions: fix it, contest it by measurement, narrow it to what is measured, or record it as a stated limit in the round's dispositions ledger with no board item filed -- default for a confirmed finding that changes no runtime behavior on a user- or partner-reachable surface. Each exit's mechanics: `.claude/commands/assess-review.md`, Step 3.
- A stated limit's home: the dispositions ledger is the record while the session runs. At the branch's merge-ready point, a `limit` on a surface a user or partner can reach is promoted to a limits line in the `docs/spec/` file governing that surface, and its ledger entry records the line as `limitsLine`. A limit on an internal surface or a test guard stays in the ledger alone, its entry marked `"surface": "internal"`. At merge-ready, `.claude/scripts/check-review-ledger-dispositions.mjs` refuses a reachable limit with no limits line the head holds; the entry fields: `.claude/commands/light-review.md`, Step 3 -- Trajectory, ledger, write.

## Models and spawns

- The session model, Fable included, is the owner's choice, never an agent's, reserved for planning a complicated issue, a high-stakes review (new crypto, at-rest, protocol), or adjudicating a gated role round: a Fable spawn needs the owner's explicit per-spawn approval and is never inherited; accept a harness downgrade, never argue it. Enforced by `require-fable-approval.mjs` (`Agent` spawns) and `require-workflow-fable-approval.mjs` (a `Workflow` call naming Fable literally); a committed `Workflow` script's `agent()` call inherits the SESSION model when it omits `model:`, so every one pins a literal tier (`npm run check:workflow-agent-models`).
- Never SendMessage an agent to continue substantive work: the delivered message switches it to the session model on its next turn. Course-correct via TaskStop plus a fresh spawn -- fix rounds are fresh spawns too. Enforced by `block-model-drop-sendmessage.mjs`, whose header carries the `[accept-model-drop]` message override.
- Run at most four writing spawns at once -- implementers, fix agents, and review Workflows -- and one read-only analyst. Hold a spawn while the one-minute load average (`uptime`) is above about eight on the ten-core container, and queue the rest in the continuation brief. Concurrent repo-wide gates starve each other, so a wider fan-out finishes later.
- A completion notification whose note says the agent stopped with background work of its own still running is interim: the harness resumes the agent when that work ends, and the same task id notifies again with the result. Act on that second notification, not the first. The probe behind it: `.claude/hooks/block-sleep-poll.probe.md`.
- Size a spawn's tier after its brief is written, by two questions: does the brief already state the outcome -- which side wins, the exact text, the command order, the pass criterion -- and will a mechanical check (a verifier, a test suite, a hook) decide whether the result is right? Two yeses is a `sonnet` spawn; either no is `opus`. A brief that reads like a checklist is a `sonnet` brief. A brief that mixes a judgment with a mechanical tail is split only when the split is free; otherwise the judgment sets the tier. The exact-edit rule in `.claude/commands/assess-review.md`, Step 3, is one instance.

## Decisions, briefs and reporting

- An orchestration session keeps working: as its pull requests merge it takes the next workable items, and it carries on across compactions of its context. It does not wind down or hand off on its own. What carries the work across a compaction is a continuation brief kept current in a file -- the branches in flight, their review state, and what comes next -- named by path, never pasted into a prompt: a paste enters the context at full width and is re-billed on every call, while a path costs one Read. Decisions surfaced mid-work are parked as Decision items, and the docket (`/docket`) and the filing pass (`/follow-ups`) run ONLY on the owner's trigger -- at the end of the day, or earlier when the owner judges parked items are piling up and blocking work -- never because the session judges it is time.
- Weigh a decision against `.claude/product-principles.md` before recommending: it holds the owner's standing product principles and how a recommendation argues from them.
- NEVER open a decision with AskUserQuestion. A maintainer's decision goes in PROSE -- options, tradeoffs, a recommendation -- the question tool has one place only: relaying a PM consult's NEEDS INPUT round. Hold decisions for the docket; when the owner triggers it, let in-flight agents land first, then present one decision per message, each with its context, the options and their trade-offs, and a recommendation, in plain language (`/docket`), and put follow-ups in a separate message from decisions (`/follow-ups`).
- The board is the only queue, for work and decisions alike, and follow-on work a branch turns up is no exception. When a session files an item, and where work it may not yet file waits, is `.claude/pm/ruleset.md`, Filing and updating items.
- The docket is the only channel for rulings. A session that needs a ruling mid-work files the Decision item and parks it for the next docket, presented as `/docket` does when the owner triggers it, and records the ruling verbatim on the item in the turn it is given.
- A brief handing work to a session on the host embeds the contract in `.claude/orchestration/host-handoff-brief.md`: that session reads `CLAUDE.md` but not this file.
- A rebuild brief permits cherry-picking surviving code with edits; forced re-derivation of code that survived review is a defect in the brief.
- An issue's own deferred design decisions -- Open Questions, or a direction left to the maintainer -- are not the orchestrator's to settle silently. Proceed when obvious, after measuring the quantity in dispute: an immaterial delta is itself the answer, reported in a line. `/panel` answers a technical-judgment question whose answer changes runtime behavior or a public or partner-facing surface. A panel the session runs during orchestration settles the question when every position agrees; proceed on its conclusion. A split panel goes to the owner, and a panel the owner asked for informs the owner's decision and settles nothing. Raise it with the owner for a genuine product, scope, or priority call -- a one-message ask is cheap, not a failure of autonomy.
