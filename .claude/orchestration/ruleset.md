# Alcove orchestration ruleset

The rules for CONDUCTING an Alcove session -- one that spawns agents, runs review rounds, dispatches fixes, and reports decisions to the owner. `CONTRIBUTING.md` and `CLAUDE.md` hold what binds every agent; this file holds only what binds the session doing the conducting.

An orchestrating session reads this file before its first `Agent` or `Workflow` call, and again after a context reset. Enforced by `require-orchestration-ruleset-read.mjs`, which refuses that first `Agent` or `Workflow` call until `record-orchestration-ruleset-read.mjs` has recorded a read of this file in the session; the marker and how long a read stands for are in their headers. The front doors that load it as their first step are the `FRONT_DOORS` list in `scripts/check-rule-ledgers.mjs`, which that check keeps wired.

A spawned agent does not read it. `CLAUDE.md` alone holds the rules that bind it, and a spawn that reads this file pays for rules addressed to its caller.

## Worktrees and checkouts

- A small assess-review fix (under 20 changed lines) goes out as a `haiku` implementer's exact edit, not inline; anything larger is a full spawn (`.claude/commands/assess-review.md`, Step 3).
- Parallel writing spawns run in their own worktree: pass `isolation:"worktree"` on the `Agent` call as a PARAMETER, never only in the prompt (prose telling the agent it is in one is inert) -- re-read the call for that parameter before submitting a worktree-mentioning spawn. Enforced by `require-declared-worktree-isolation.mjs`. Read-only reviewers may share `/workspace`, diffing by ref. Have the agent run `.claude/scripts/worktree-init.sh` before its first edit, provisioning `node_modules` and re-pointing a fresh `main`-based tree onto `origin/staging`; details in its header.
- A worktree under `.claude/worktrees/` holds work that exists nowhere else until committed, so do not disturb a live one: leave another session's tree alone, retire a finished one with `git worktree remove <path>` (no `--force`; a tree git refuses as locked, which an agent that stopped mid-run leaves, is unlocked first by the steps in the hook's header) only once every in-flight agent has reported -- a non-isolated agent writes only under the session's current working directory, so an idle-looking tree may still be in use -- and never switch out of one you have entered while an agent or review Workflow may still run there -- since a non-isolated run's writable directory follows the session, switching cuts its shell mid-run and finishes the round read-only. Only a worktree-isolated spawn, or the by-ref flow that never enters a tree, is immune. Enforced by `block-worktree-deletions.mjs` on Bash -- rephrasing around its refusal destroys the tree just the same; details in its header. A branch is retired with its worktree once `gh pr view <n> --json state,mergedAt,headRefOid` shows its pull request merged and its `headRefOid` equals `git rev-parse <name>` (a tip that differs may hold a commit never pushed, so that branch is listed for the owner, never deleted): a squash merge leaves the local branch's commits off staging, so `git branch -d` refuses it and `git branch -D <literal name>` is the form. The `worktree-agent-*` branch the harness cuts for a worktree-isolated spawn is deleted the same way once its worktree is gone and `git rev-list --count <branch> --not origin/staging origin/main` prints 0; one that prints more may hold work that merged nowhere, so it is listed for the owner, never deleted. GitHub deletes the remote branch at the merge; the local ones are the session's to retire, and a session's follow-ups pass leaves each one deleted or listed.
- A command against a worktree runs with `env -C <tree> <command>` or `git -C <tree> <args>`, NEVER a leading `cd <tree> && ...`. The Bash tool's directory persists between calls, so that `cd` does not scope the one call: it moves the session's working directory into the tree for every later call, and a spawn that is not worktree-isolated writes only under the session's working directory, so the move puts later spawns -- and the shell of a run already under way -- in a tree that is not theirs. Enforced by `block-worktree-cd.mjs` on Bash; details in its header. If it happened, `cd /workspace` at once.
- Sessions on the host share this `.git`, so a `git worktree prune` on either side drops the other side's worktree entries while their directories survive; never run one here while `git worktree list` shows a host path. A tree whose entry was pruned fails every git command, `git worktree repair` included; re-register it with its edits intact by recreating the `.git/worktrees/<id>/` its `.git` file names, with `HEAD` (`ref: refs/heads/<branch>`), `commondir` (`../..`) and `gitdir` (`<tree>/.git`), then `git -C <tree> reset -q`.

## Review flow

- Resolving a PR's checklist means re-reading `.github/PULL_REQUEST_TEMPLATE.md` and performing the Docs line's enumeration against the diff; an n/a box is checked with a reason tied to this diff, and a changelog n/a names the class it skips. CI (`npm run check:pr-checklist`) catches only the mechanical tells.
- A `Workflow` `schema` for a long-form agent follows the authoring rules in `.claude/commands/review-round.md`, Authoring a Workflow schema. An agent that exhausts its structured-output retries usually left analysis intact in the rejected attempts; salvage before re-running.
- Review and fixing run BY REF from the primary checkout, keeping several branches in review at once: `/review-round --target <ref>`, then `/assess-review <branch>`, then one implementer per branch pointed at that branch's worktree by absolute path. No step of that flow changes directory or checks anything out.
- CI is the gate, and it runs only on a pull request. Push a branch and open it as a draft pull request into staging (`gh pr create --draft`) once its implementation commit lands, so CI runs the full set on GitHub while review rounds run by ref on the committed head. The body is the template filled as far as it can be; the Security review line is completed when the PR is marked ready. Implementers do not push or open PRs: the session pushes, opens the draft, watches CI, and dispatches fixes. Read a failure with `gh run view --job <id> --log-failed`; re-run a flaky job with `gh run rerun <id> --failed`, and send a real failure to a fix pass, whose pushed fix reruns CI.
- Mark a PR ready (`gh pr ready <n>`) only when its review rounds are done, CI is green on its head (the next bullet), its checklist is resolved with the Security review line on the head sha, the merge-ready dispositions check run with `--body` passes (`.claude/commands/assess-review.md`, Step 4) -- it refuses a product fix after the last review with neither a fix review nor "not re-reviewed" on that line (its Step 3) -- and, for two or more commits, its squash comment is posted (`CONTRIBUTING.md`, Commit Messages). The PR Checklist workflow skips a draft and runs when it is marked ready, so read that check on a fresh `gh pr view` after `gh pr ready`. The maintainer merges ready PRs; a draft is never his to merge.
- A PR is green only on a fresh `gh pr view <n> --json mergeStateStatus,statusCheckRollup` taken after any watch exits: `gh pr checks --watch` covers only the checks registered when it started, and a path-filtered workflow can register later.
- A stack of branches: CI runs only for pull requests into staging or main, so each stage's draft targets staging, showing the stages below it until they merge, and its body names the branch it is stacked on. After the branch below merges, rebase the stage onto origin/staging and force-push it; CI runs again on the rebased head.
- Commit before any review round -- reviewers diff by ref and see only commits, so an uncommitted edit is treated as absent -- and a review attests the commit it read: the checklist's Security review line states that sha, and CI (`npm run check:pr-checklist`) fails while it is not the PR head. Re-attesting means reviewing that head; editing the sha alone, without the "not re-reviewed" the exact-edit and non-product cases take (`.claude/commands/assess-review.md`, Step 3), states a review that did not happen, and CI's check cannot see it. Details on re-attesting a moved head, the base-sync route needing none, and what voids each: `.claude/commands/assess-review.md`, Step 4. Enforced by `require-clean-tree-for-review.mjs` on `Workflow` calls only (an `Agent`-spawned review is not gated, so hold the rule yourself); details in its header.
- Never self-review a security- or partner-reachable surface: spawn an independent reviewer, even for a small rework -- it alone sees the diff and the issue. Spawn `security-reviewer` and `adversarial-verifier` only under a refutation contract (a named list of claims to refute, one per claim), and only when the diff has adversary-reachable surface -- a test-only, docs-only, or support-script-only diff takes the lens round only, whatever its size -- run as `/review-round --role <name> --claims <file>`. Enforced by `require-review-contract.mjs` on a direct `Agent` spawn of either role. A claim's double quotes mean the quoted text occurs at the target ref and a string the round feeds the surface takes single quotes; enforced by `require-measured-claim-literals.mjs` on the round's `Workflow` call. Details: `.claude/commands/review-round.md`, The refutation contract.
- A gated claim or confirmed review finding has four dispositions: fix it, contest it by measurement, narrow it to what is measured, or record it as a stated limit in the round's dispositions ledger with no board item filed -- default for a confirmed finding that changes no runtime behavior on a user- or partner-reachable surface. Each exit's mechanics: `.claude/commands/assess-review.md`, Step 3.
- A stated limit's home: the dispositions ledger is the record while the session runs. At the branch's merge-ready point, a `limit` on a surface a user or partner can reach is promoted to a limits line in the `docs/spec/` file governing that surface, and its ledger entry records the line as `limitsLine`. A limit on an internal surface or a test guard stays in the ledger alone, its entry marked `"surface": "internal"`. At merge-ready, `.claude/scripts/check-review-ledger-dispositions.mjs` refuses a reachable limit with no limits line the head holds; the entry fields: `.claude/commands/review-round.md`, Step 3 -- Trajectory, ledger, write.

## Models and spawns

- The session model is the owner's choice, never an agent's -- Opus 5.5 at xhigh effort by default, Fable when the owner picks it for a session -- and Fable is otherwise reserved for planning a complicated issue, a high-stakes review (new crypto, at-rest, protocol), or adjudicating a gated role round: a Fable spawn needs the owner's explicit per-spawn approval and is never inherited; accept a harness downgrade, never argue it. Enforced by `require-fable-approval.mjs` (`Agent` spawns) and `require-workflow-fable-approval.mjs` (a `Workflow` call naming Fable literally); a committed `Workflow` script's `agent()` call inherits the SESSION model when it omits `model:`, so every one pins a literal tier and a literal effort (`npm run check:workflow-agent-models`).
- A yes/no premise behind a finding is settled by the session in one call or carried into the security round as a claim; it never enters a fix brief as a conditional redesign branch.
- Run at most four writing spawns at once -- implementers, fix agents, and review Workflows -- and one read-only analyst. Hold a spawn while the one-minute load average (`uptime`) is above about eight on the ten-core container, and queue the rest in the continuation brief. Concurrent repo-wide gates starve each other, so a wider fan-out finishes later.
- A completion notification whose note says the agent stopped with background work of its own still running is interim: the harness resumes the agent when that work ends, and the same task id notifies again with the result. Act on that second notification, not the first. The probe behind it: `.claude/hooks/block-sleep-poll.probe.md`.
- Size a spawn's tier after its brief is written, by two questions: does the brief already state the outcome -- which side wins, the exact text, the command order, the pass criterion -- and will a mechanical check (a verifier, a test suite, a hook) decide whether the result is right? Three answers set the tier: a brief that states the exact edit -- the file, the old text, the new text, and the check that decides it -- is a `haiku` spawn; two yeses is a `sonnet` spawn; either no is `opus`. A brief that reads like a checklist is a `sonnet` brief. A brief that mixes a judgment with a mechanical tail is split only when the split is free; otherwise the judgment sets the tier. The exact-edit rule in `.claude/commands/assess-review.md`, Step 3, is one instance.

## Session lifecycle

A session is always in one of the five states below, and an owner turn naming one -- by its command or by the words listed with it -- means that state and nothing else. Each state's steps live in its command; this section states only what each one means. Entering a state other than Compact-prep, the session writes it to the continuation brief in that turn, so a compaction at any moment resumes into it.

- **Working**, the default, entered with `/orchestrate` (`.claude/commands/orchestrate.md`) at the start and in a new session after `/clear`, and after a compaction when the continuation brief records it. An orchestration session keeps working: as its pull requests merge it takes the next workable items, the large and difficult ones included, and it carries on across compactions of its context. A shortlist short of workable items sends it to survey `docs/ROADMAP.md`, `docs/DESIGN.md` and `docs/notes/` for designs not yet built and to file Decision items for at most a handful of the ripest for a ruling, listing the rest in the continuation brief, never to wind down. It does not wind down or hand off on its own, and an owner turn naming an event to come -- a promotion, an image build, going away for a while -- changes nothing until it names a state below; the owner compacts when he judges it convenient, or when the session asks at the context size the Compact-prep bullet states. What carries the work across a compaction is a continuation brief kept current in a file -- the branches in flight, their review state, and what comes next -- named by path, never pasted into a prompt: a paste enters the context at full width and is re-billed on every call, while a path costs one Read. Decisions surfaced mid-work are parked as Decision items, and the docket (`/docket`) and the filing pass (`/follow-ups`) run ONLY on the owner's trigger, never because the session judges it is time: the docket at the end of the day, or earlier when the owner judges parked items are piling up and blocking work, and the filing pass as the session's last step, since it ends the session. A mid-day docket's rulings are acted on from the session's own record and reach the board in that pass.
- **Wind-down** (`/wind-down`; "wind down", "hold after the last PR lands", "find a natural conclusion", "close out", "wrap up", "finished means finished"): finish everything already started -- every branch, run and host handoff -- to its full conclusion, start no new board item, then report ready with a recommendation and hold until the owner fires the docket. A branch's conclusion is its intended final state -- for an implementation branch, a PR marked ready, its review rounds done and CI green on its head -- never the docket. A limit the day's notes set is counted in PRs, a proxy for token spend, and reaching it is a wind-down.
- **Compact-prep** (`/compact-prep`; "compact", "prepare for compaction"): bring the continuation brief current and print the two short messages the owner needs to compact and resume. Nothing in flight stops and nothing new starts for it. The brief records the state the session was in before the preparation, never Compact-prep itself, and the latest shortlist's candidates not yet taken, and after the compaction `/orchestrate` enters the recorded state. The session also enters it unasked when its context passes 300k tokens, read with `node .claude/scripts/context-size.mjs` each time it brings the continuation brief current. The owner compacts while agents are out: agents in flight keep running, their results arrive after the compaction, and nothing waits for them to land. The 300k trigger is on trial through the next retro, about 2026-11-06.
- **Docket** (`/docket`; "present the docket"): present the parked decisions one per message, and record each ruling and act on it when given; only its board writes wait for the follow-ups pass. `.claude/commands/docket.md` holds the steps and what the bare command carries.
- **Follow-ups** (`/follow-ups`; the filing pass, "a clean break"): the session's last step. File, update or decline the session's potential follow-ups on the board, write the rulings and their consequences, do the housekeeping, and mark the continuation brief closed so the next `/orchestrate` starts from the board, as `.claude/commands/follow-ups.md` sets out. Owner-triggered, like the docket.

After a docket the session is Working again, unless the owner names another state; a follow-ups pass ends it.

## Decisions, briefs and reporting

- Weigh a decision against `.claude/product-principles.md` before recommending: it holds the owner's standing product principles and how a recommendation argues from them. Before presenting a decision, run `node .claude/scripts/find-rulings.mjs` on its subject words, fetch the item's epic siblings and every item its body names, and cite any earlier ruling among them (`.claude/commands/docket.md`, Build the list, step 2); a decision an earlier ruling settles is not presented, and a documented default is the ruling on what the behavior is, so a proposal to change it is presented only with that ruling cited and a changed assumption or new driver the item names.
- A proposal that adds a bound, a refusal, a consent step or a new mechanism on a surface a user reaches -- the CLI, the console, the web app -- states in one line who asked for it and which legitimate use it blocks, whether it is a docket option, a recommendation, a review finding's fix, or a brief. Weigh it against `.claude/product-principles.md` (No invented numbers; Ship the whole feature; No machinery nobody asked for): when nobody asked, the line says so and the recommendation is not to build it. The owner's most frequent correction is agents over-building consent steps, size limits and refusals that make the product hard to use and that no user or partner asked for. A control over content the operator cannot inspect is asked for by the threat model: `CLAUDE.md`, Applications, makes it a hard refusal.
- Before presenting anything as the owner's -- an action, a run, a check, a batch of judgment calls to ratify, a filing -- state in one line why the session cannot do it itself, and do it when the line has no answer. The owner has had to hand back work the session could do: whether to file a follow-up (the session's and the PM's call, `/follow-ups`), a run on another machine (a host handoff, below, tracked by a board item), a batch of judgment calls (the docket's controversy scoring has two independent lenses judge them, and only a line either lens flags is presented: `.claude/commands/docket.md`, Build the list, step 1), and a step that waits on planned work (it goes on the item that plans it, not into a list of action items). Only the owner makes a product, scope or priority call, takes a step that needs his hands or accounts, or does what `CLAUDE.md` reserves to him.
- An explicit owner instruction is followed as given. A route the session judges better is put to the owner in one line before acting, never taken in the instruction's place.
- A step needing the owner's hands that takes more than one action -- a dashboard change, a keychain item, a token to create -- goes to him as a host handoff brief, filled from `.claude/orchestration/host-handoff-brief.md` and given by path, never as a list of steps in a chat message, where it scrolls past. A one-line yes/no or a merge stays in chat.
- NEVER open a decision with AskUserQuestion. A maintainer's decision goes in PROSE -- options, tradeoffs, a recommendation -- the question tool has one place only: relaying a PM consult's NEEDS INPUT round, whose answers the session sends back to that consult. Hold decisions for the docket; when the owner triggers it, let in-flight agents land first, then present one decision per message, each with its context, the options and their trade-offs, and a recommendation, in plain language (`/docket`), and put follow-ups in a separate message from decisions (`/follow-ups`).
- The board is the only queue, for work and decisions alike, and follow-on work a branch turns up is no exception. When a session files an item, and where work it may not yet file waits, is `.claude/pm/ruleset.md`, Filing and updating items.
- The docket is the only channel for rulings. A session that needs a ruling mid-work files the Decision item and parks it for the next docket, presented as `/docket` does when the owner triggers it. A ruling, and an answer the owner gives mid-work outside a docket, is recorded verbatim in the session's own record -- the docket's rulings file under `scratch/` and the continuation brief -- in the turn it is given, and nothing of it reaches the board until the follow-ups pass, which writes every ruling's text and its consequences to their items in one pass (`.claude/commands/follow-ups.md`). A ruled number the owner revises mid-window is recorded the same way in the turn the revision happens, and that pass appends the revision to its item, not only to a docs note.
- A brief handing work to a session on the host is filled from the template in `.claude/orchestration/host-handoff-brief.md`: that session reads `CLAUDE.md` but not this file. An implementer's draft is rewritten into the template, and checked with `bash .claude/scripts/host-handoff.sh --check <brief>`, before it goes to the owner as the launch line in its For the owner section. In that message the session states the result path once and starts `.claude/scripts/wait-handoff-result.mjs` on it in the background, in the form its `--help` gives; it reads the result when the wait exits 0, and never asks the owner to relay it or to say where it is. A wait that exits 124 is started again while the hand-off is still to run.
- An item set aside for a host step gets its handoff brief, and one set aside for a scope or product call gets a Decision item with options and a recommendation, both written in the session that set it aside. The Decision item is parked for the docket, not presented. Before filing it, run `node .claude/scripts/find-rulings.mjs <the question's 2-3 subject words>`: a question a standing ruling answers, or one asking what a default the user docs document is, is not filed, and the ruling is cited on the originating item instead; a proposal to change a documented default is filed only on a changed assumption or a new driver it names.
- A retrospective's reading step lists the agent-memory notes written or changed since the previous retrospective and moves each repository rule into the file that binds its reader, as `CLAUDE.md`, Boards and PM, requires; the store keeps only owner preferences and host-local facts. It also counts, for each rule written to answer an earlier retrospective's cluster of owner corrections, that cluster's corrections in the new window against the earlier count: a rule whose cluster did not shrink is revised or deleted. It also re-tests, on each of boards 9 and 10, every trigger `node .claude/scripts/list-issues.mjs --parked <N>` lists, as `.claude/pm/ruleset.md`, Task template, states: a trigger that fired loses its line and the item is a candidate again; one that cannot be answered yes or no is rewritten or goes to the docket.
- A rebuild brief permits cherry-picking surviving code with edits; forced re-derivation of code that survived review is a defect in the brief.
- An issue's own deferred design decisions -- Open Questions, or a direction left to the maintainer -- are not the orchestrator's to settle silently. Proceed when obvious, after measuring the quantity in dispute: an immaterial delta is itself the answer, reported in a line. `/panel` answers a technical-judgment question whose answer changes runtime behavior or a public or partner-facing surface. A panel the session runs during orchestration settles the question when every position agrees; proceed on its conclusion. A split panel goes to the owner, and a panel the owner asked for informs the owner's decision and settles nothing. Raise it with the owner for a product, scope, or priority call.
