# Relay credential derivation

This document specifies how a party authenticates to the relays an exchange uses: the relay key and exchange id derived from the shared secret, the time-limited TURN credential, a TURN credential minted from a relay provider's API, the relay locator an invitation carries and the relays a run lists, the registrar request proof and the WebSocket relay proof, enrolling and registering the relay key at a registrar, and the web application's relay check.
It does not cover the P-256 authenticated key exchange and the label space the derivations sit in (see [PROTOCOL.md](PROTOCOL.md#p-256-authenticated-key-exchange)), the rotation that replaces the secret each run (see [SHARED_SECRET_ROTATION.md](SHARED_SECRET_ROTATION.md)), the WebSocket relay's own wire protocol (see [WEBSOCKET_RELAY.md](WEBSOCKET_RELAY.md)), the registrar's operating contract (see [infra/relay/README.md](../../infra/relay/README.md#the-registrar)), or the connection fields that name a relay (see [EXCHANGE_REFERENCE.md](../EXCHANGE_REFERENCE.md)).
Intended readers are security auditors, external implementors, and developers.

A party whose WebRTC connection needs a TURN relay uses the relay the invitation names, one its own side controls, or both (see [The invitation's relay locator](#the-invitations-relay-locator) below), and authenticates to it with a credential derived from the invitation's 32-byte shared secret, so no relay password is sent in the invitation or out of band. The relay is coturn, in its `use-auth-secret` mode: it holds a table of shared secrets and accepts a time-limited credential signed under any of them. The reference relay under `infra/relay` holds one entry per exchange in that table, added and removed by its operator's register and revoke scripts, run on the relay host or through its registrar service, and retired by a sweep once the exchange's max-age lapses (`infra/relay/README.md`, Per-exchange keys).

**The relay key.** One key per exchange, which the relay's operator registers as an entry in the relay's secrets table. The key is derived from the exchange's current shared secret, so it changes at each [rotation](SHARED_SECRET_ROTATION.md), and a relay must hold the key derived from the current secret:

```
relay_key = hex(HKDF-SHA-256(ikm = secret, salt = 0x00 * 32, info = "alcove-relay-key-v2", 32))
```

The key is the whole 32-byte output as 64 lowercase hex characters, and the relay stores that string as the entry. coturn keys its HMAC with the stored string's bytes, so the HMAC key is the 64 ASCII hex characters, not the 32 bytes they decode to. This is coturn's behavior rather than anything Alcove controls, so it holds only as far as it has been measured against a real coturn: against coturn 4.18.0, the version `infra/relay/Dockerfile` pins, a credential keyed with the characters was accepted and one keyed with the decoded bytes refused. `infra/relay/verify.sh` repeats that check against each running relay, and a relay on another coturn version must pass it before this paragraph is relied on there. The info string is a single fixed label in the [domain-separation label space](PROTOCOL.md#p-256-authenticated-key-exchange), so the relay's operator, who holds the relay key, learns no other key derived from the secret.

**The exchange id.** A party that enrolls the relay key at a registrar without a token ([Enrolling at a default relay](#enrolling-at-a-default-relay)) enrolls it under an exchange id derived from the same secret:

```
exchange_id = hex(HKDF-SHA-256(ikm = secret, salt = 0x00 * 32, info = "alcove-relay-exchange-id-v2", 16))
```

- **Its form.** 32 lowercase hex characters, within the registrar's id alphabet.
- **Why derived.** Both parties compute it without exchanging anything, and a third party without the secret cannot predict it, so it cannot enroll the id under another key first.
- **What it reveals.** Nothing about the secret or the relay key: the info string is a single fixed label in the [domain-separation label space](PROTOCOL.md#p-256-authenticated-key-exchange). It changes at each rotation, as the relay key does.
- **Test vector.** For the secret of bytes 0x00..0x1f, `exchange_id` = `ef946df1a03b076bd042fa7cf3cea8ed`, computed by OpenSSL's HKDF (`openssl kdf`, with the info string above and a 16-byte output) and held by `packages/core/test/relayCredential.test.ts`.

**The credential.** coturn's time-limited credential format, minted locally from the relay key without contacting the relay:

```
username   = decimal(floor(now_unix_seconds) + ttl) + ":" + label
credential = base64(HMAC-SHA-1(key = utf8(relay_key), msg = utf8(username)))
```

The credential is standard base64 with padding. `label` is chosen by the party minting and is non-empty with no `:`, the separator between it and the expiry. `ttl` is whole seconds from 1 to 3600: one hour, the default of the relay's own `infra/relay/mint-credential.sh`, which is the length of one exchange rather than the life of the key. coturn recomputes the HMAC when the credential is presented to open an allocation, and refuses it once the expiry in the username has passed. A value outside these bounds is refused rather than clamped. Against coturn 4.18.0, the version `infra/relay/Dockerfile` pins, an Allocate presenting a credential past its expiry was refused with `401 Unauthorized`, while an allocation opened before the expiry was refreshed, and its channel bindings renewed, under the expired credential, with data flowing 1,140 s past the expiry, measured 2026-11-10. The expiry therefore bounds when an allocation can be opened, not how long it lasts, and a relayed exchange is not cut at the credential's expiry while the relay keeps the allocation.

HMAC-SHA-1 appears here only because coturn's credential format fixes it; it is not an Alcove security primitive. The credential authorizes use of the relay and nothing else: the exchange's confidentiality and authentication rest on DTLS and the [key exchange](PROTOCOL.md#p-256-authenticated-key-exchange), not on it.

**What the relay key grants.** While the relay key is registered with a relay, holding the exchange's shared secret is equivalent to holding access to that relay: the key is computable from the secret, and the relay, not Alcove, decides which expiries it honors. The 3600-second ceiling above bounds only the credentials Alcove mints; anyone holding the key can mint one with a later expiry. Removing the key from the relay's secrets table is the revocation: coturn then refuses a new allocation under the key, and does not end one already open.

**Compatibility.** The project's TURN relay is coturn, which speaks TURN as coturn does; its one Alcove-specific input is the credential above, and the relay reads no version of it. The version of the relay key and of the exchange id is the `v2` of their labels alone, which no message states. The project's relay keeps the credential of every supported release (the rule of [RELEASES.md, Project-run services](../RELEASES.md#compatibility-policy)) by holding the relay key that release derives. Two builds that derive different keys hold different keys at a relay, and the key exchange's version negotiation does not reach them, since a relay comes before it.

## The invitation's relay locator

A webrtc connection endpoint MAY hold `relay`, the inviting party's relay locator: an object with an optional `turn` list and an optional `stun` list of urls, an optional `websocket` url, an optional `websocketExchangeId`, an optional `registrar` url, and no other key.

- **Grammar.** Each `turn` url and each `stun` url holds the grammar of the connection block's own [`turn`](../EXCHANGE_REFERENCE.md#connectionturn) `url` and [`stun`](../EXCHANGE_REFERENCE.md#connectionstun) entries, one schema for both (`TurnUrlSchema` and `StunUrlSchema` in `packages/core/src/config/connection.ts`).
- **Bounds.** A list present holds 1 to `MAX_RELAY_LOCATOR_URLS` (**8**) urls, each at most `MAX_RELAY_LOCATOR_URL_LENGTH` (**1024**) UTF-16 code units, and the locator names at least one url.
- **Registrar.** `registrar` is the address of a registrar that enrolls the exchange's relay key without a token ([Enrolling at a default relay](#enrolling-at-a-default-relay)): one `https://` url naming a host and an optional port, the rule of [`relay_registrar`](../EXCHANGE_REFERENCE.md#connectionrelay_registrar)'s `url`, at most `MAX_RELAY_LOCATOR_URL_LENGTH` UTF-16 code units. A locator that names it names at least one `turn` url or a `websocket` url. A locator's registrar enrolls the key of its TURN relay, and of its WebSocket relay where it names no `websocketExchangeId`: a CLI run enrolls there when the TURN url it allocates on is one the locator names, or when it dials the locator's `websocket` url under the id derived from the secret ([A command-line party](#enrolling-at-a-default-relay)). A locator does not say which of its relays its registrar serves, so a CLI run that dials the locator's WebSocket relay enrolls at the registrar even where that relay is the inviter's own and the registrar serves only the TURN relay beside it. Host case, a default port and one trailing `/` are normalized away when the url is parsed, so a party holds and mints the url as its origin. A url naming a path, a query, a fragment, a user or port 0 is refused, an empty `?` or `#` included, and the refusal does not repeat it.
- **No credential.** A `username`, `credential`, or any other key on the locator, and a `turn` entry written as an object rather than a url, is refused when the invitation is decoded and when it is minted -- refused, not stripped.
- **Composition.** The inviter composes the locator from relays it uses itself (`relayLocatorFromOwnRelay`): the CLI from its connection's `stun` list and the `url` of each `turn` entry that sets no `username` or `credential` and that its `allowed_relays` keeps (`endpointFromConnection` in `packages/core/src/config/endpointProducer.ts`), the web app from the exchange's own relays (`ownRelay`) and a build's default relay ([Enrolling at a default relay](#enrolling-at-a-default-relay)), each TURN url only where the allowed relays that apply keep it (a saved exchange's own, otherwise those set on the review of the invitation it creates), the default relay's following the exchange's own and named only where the locator has room for it under `MAX_RELAY_LOCATOR_URLS`. Where the default relay is in use and the locator names its TURN url or its WebSocket relay url, the web app also names that relay's registrar as `registrar`; the CLI names none. With the relay switched off, the web app names no registrar, even where the exchange's own relays name the default relay's TURN url and the locator names that url as one of its own (`invitationRelayWithDefault` in `apps/web/src/psi/transport/defaultRelay.ts`), so a CLI party accepting that invitation enrolls nowhere ([A command-line party](#enrolling-at-a-default-relay)). Creating an invitation contacts no registrar. A `turn` entry with a static credential is left out, since the accepting party cannot authenticate to it. So is a `turn` entry that names a provider ([Provider-minted credentials](#provider-minted-credentials)). An inviter with no relay of its own, in a build that names no default relay, names none.
- **The WebSocket relay.** `websocket` is the address of a [WebSocket relay](WEBSOCKET_RELAY.md), in the grammar of the connection block's own [`websocket_relay`](../EXCHANGE_REFERENCE.md#connectionwebsocket_relay) (`webSocketRelayUrlSchema` in `packages/core/src/config/connection.ts`): one `wss://` url naming a host, an optional port and a path, with no user, query or fragment, accepted only as the WHATWG URL parser's `href` gives it back, the trailing slash of an empty path aside, at most `MAX_WEBSOCKET_RELAY_URL_LENGTH` (**1024**) UTF-16 code units. A list in its place is refused. It counts as the one url a locator names.
- **The WebSocket relay an inviter names.** The CLI names its connection's `websocket_relay` (`endpointFromConnection`). The web app names the exchange's own WebSocket relay url (`ownRelay`'s), or, where that names none, a build's default WebSocket relay (`VITE_DEFAULT_RELAY_WEBSOCKET_URL`; `invitationRelayWithDefault` in `apps/web/src/psi/transport/defaultRelay.ts`). A console names the WebSocket relay set with its coordination server instead, which its run states as `websocket_relay` (`ownRelayInvitationLocator` in `apps/web/src/jobContract/signalingServer.ts`). Each names it only where the allowed relays that apply keep it (`webSocketRelayUrlIsAllowed` in `packages/core/src/config/connection.ts`).
- **The WebSocket relay's exchange id.** `websocketExchangeId` is the exchange id the `websocket` relay holds the exchange's relay key under, where the inviter enrolled the key there under an id of its own rather than the one [derived from the secret](#relay-credential-derivation); a party's hello to that relay names it ([The WebSocket relay proof](#the-websocket-relay-proof)). It follows the grammar of [`relay_registrar`](../EXCHANGE_REFERENCE.md#connectionrelay_registrar)'s `exchange_id`: 1 to 128 of `[A-Za-z0-9._-]`, not starting with `-` or `alcove-verify-`, not one or two dots alone, and with no run of 64 hex characters. A refusal does not repeat it. A locator that names it names a `websocket` url. The CLI names its `relay_registrar`'s `exchange_id` beside the `websocket_relay` it names (`endpointFromConnection`), a console names its registrar's exchange id beside the WebSocket relay set with its coordination server (`ownRelayInvitationLocator`), and the web app names a saved exchange's registrar's exchange id (`relayRegistrar`) beside the exchange's own WebSocket relay url on a re-invite (`composeManagedReinvite` in `apps/web/src/psi/managed/managedReinvite.ts`); none names one otherwise. It is not a credential: it names the key the relay checks a proof under.
- **Compatibility.** The field was added to the strict webrtc endpoint without a token `version` bump, while no decoder was deployed; a decoder predating it refuses an invitation that holds it. `registrar` was added to the strict locator without a `version` bump too: a decoder predating it, an earlier web app or CLI build among them, refuses every invitation that names it, as an invitation a build makes with its default relay in use does. `websocket` was added to the strict locator without a `version` bump as well, so a decoder predating it refuses every invitation that names it. `websocketExchangeId` was added the same way, beside `websocket` only, so a decoder predating it refuses an invitation that names it, and one predating `websocket` already refuses every invitation that could. A `registrar` beside a `websocket` url and no `turn` url was admitted without a `version` bump too, so a decoder predating that refuses such a locator. The web app mints one where its default relay is in use and the locator names that relay's WebSocket relay url and no TURN url ([Enrolling at a default relay](#enrolling-at-a-default-relay)).


**Which relay a run uses.** The accepting party keeps the locator on its connection as `invitation_relay` ([EXCHANGE_REFERENCE.md](../EXCHANGE_REFERENCE.md#connectioninvitation_relay)), beside its own `turn` and `stun` rather than in them. Every run, browser and CLI alike, lists every relay it may use: its TURN urls are its own followed by the invitation's, each listed once, and its STUN urls likewise. A browser run reads its own relay from the exchange's own relays (`ownRelay`; `relayForRun` in `apps/web/src/psi/transport/ownRelaySetting.ts`), and its default relay switch from the exchange's own (`defaultRelayOn`), each set under Connection settings when the invitation is created or accepted, or on a saved exchange's page ([MANAGED_EXCHANGE_RECORD.md](MANAGED_EXCHANGE_RECORD.md#persisted-across-runs)). It adds a build's default relay's TURN url, last, once the run has enrolled there ([Enrolling at a default relay](#enrolling-at-a-default-relay)). It lists the default STUN server only where neither the exchange's own relays nor the invitation names a STUN url; otherwise its STUN urls, its own and the invitation's, take the default's place, as a CLI run's do (`buildIceServers` in `apps/web/src/psi/transport/rendezvous.ts`). An acceptor's network address so goes to the STUN servers the invitation names in place of the default, and an acceptor that reaches none of the STUN servers it lists gathers no server-reflexive candidate, which the default might have given it. STUN urls in the invitation relay of a saved exchange replace the default from this version on; the web app shows no notice of this change. An acceptor that cannot reach the STUN servers its invitation names gathers a server-reflexive candidate again once the exchange's own relays list a STUN url it can reach, Google's included, since its own and the invitation's urls are listed together. An acceptor whose web app predates this version still lists Google's server beside the invitation's, so an inviter's own STUN server keeps Google's server out of an exchange only where the acceptor's web app is this version or later. A CLI run reads its own relay from its connection's `turn` entries and `stun` list (`selectRunRelay` in `packages/core/src/relayCredential.ts`), and a url that an own `turn` entry and the invitation both name is listed once, as the own entry. A connection with no `invitation_relay` runs exactly its own lists. A CLI connection's `allowed_relays` ([EXCHANGE_REFERENCE.md](../EXCHANGE_REFERENCE.md#connectionallowed_relays)), and a browser run's allowed relays, a saved exchange's from its record's connection (`managedAllowedRelays` in `apps/web/src/psi/managed/managedExchangeRecord.ts`), an accepted invitation's from the Allowed relays set on its review (`AcceptorLaunch` in `apps/web/src/exchange/useAcceptorExchange.ts`), and a created invitation's from the Allowed relays set on its review before it was created (`GeneratedInvitation` in `apps/web/src/psi/invitation.ts`), then leave out every TURN url no entry names, matching an entry's host without resolving it and, where the entry names a port, the url's port, 3478 for a `turn:` url naming none and 5349 for a `turns:` one (`turnUrlIsAllowed` in `packages/core/src/config/connection.ts`). They leave the STUN urls and the partner's candidates alone. A browser run's list includes the build's default relay, which it does not enroll at where its allowed relays leave that relay out. A run whose every TURN url its allowed relays leave out continues without a relay (`relayPlanForRun` in `apps/web/src/psi/transport/runRelayPlan.ts`, `webRtcDialFrom` in `apps/cli/src/run/prepare.ts`). A CLI run so left warns, naming the setting; where the connection lists no `stun` url, the warning also names the built-in default STUN server (`WERIFT_BUILT_IN_STUN_URI`), which learns the host's public address.

**Which WebSocket relays the allowed relays keep.** An invitation names at most one WebSocket relay url, and the allowed relays keep it by a rule of its own, apart from the TURN urls:

- **The allowed relays.** They keep a WebSocket relay url only where an entry names its host, matching without resolving the host and, where the entry names a port, the url's port, 443 for a url naming none (`webSocketRelayUrlIsAllowed`). A TURN url is kept by its own rule, and a WebSocket relay url is not kept by the TURN rule.
- **The list.** A CLI run lists its connection's `websocket_relay`, then the invitation's `websocket` url (`selectRunRelay`). A browser run lists the exchange's own (`ownRelay`'s), then the invitation's, then a build's default WebSocket relay once its enrollment there confirmed (`relayPlanForRun`). Either lists each url once, less every one its allowed relays leave out, and a browser run leaves out the default relay's url where its enrollment did not confirm, even where another source names it, as it does the default relay's TURN url.
- **The exchange id of each.** A run's proof to each relay it lists names an exchange id decided by the url ([The WebSocket relay proof](#the-websocket-relay-proof)). The url the invitation names takes its `websocketExchangeId`, since the inviter proves to that relay under it. A url of the party's own takes its own registrar's exchange id: the CLI connection's `relay_registrar`, or a saved exchange's `relayRegistrar` in the browser. Any other url, and one with no exchange id named, takes the id [derived from the secret](#relay-credential-derivation), the one an enrollment without a token uses.
- **Dialing them.** A run dials every WebSocket relay it lists as its rendezvous starts, and moves the exchange onto one only when no WebRTC path opens ([WEBRTC_TRANSPORT.md](WEBRTC_TRANSPORT.md#falling-back-to-the-websocket-relay)). A run that sets allowed relays states the WebSocket relay urls they keep and leave out beside the TURN urls, and a run whose connection to the partner does not open names those left out.

**Stated limits of listing every relay.**

- **No preference for a party's own relay.** ICE may carry an exchange over the invitation's relay, the project relay a hosted invitation names among them, where the party's own relay would serve, unless the party's allowed relays leave the invitation's relay out. A party's allowed relays keep its own allocations and enrollments on the relays it names, but the partner may still offer candidates relayed through another, and the exchange may then pass through a relay the party did not name.
- **A CLI run gathers from one TURN url and one STUN url.** A CLI run hands its WebRTC library only the first TURN url and the first STUN url of its list (`buildPeerConfiguration` in `apps/cli/src/connection/webrtc/weriftPeer.ts`), so it gathers relay candidates from the first TURN url it lists (its own first `turn` entry, else the invitation's first url, among those its `allowed_relays` keeps) and server-reflexive candidates from the first STUN url it lists (its own first `stun` url, else the invitation's first). With the first TURN url left out by `allowed_relays`, a CLI run allocates on the first url the setting keeps, a host it does not contact with the setting unset. A CLI run whose connection has its own `turn` entry that its `allowed_relays` keeps allocates only on the first such entry, which is on the invitation's relay only when that entry names one of the invitation's urls; the exchange may still pass through the invitation's relay by way of the partner's relayed candidates. A CLI run enrolls at the registrar the invitation's relay names only when the url it allocates on is one the invitation names and takes the run's derived credential, or when it dials the invitation's WebSocket relay under the id derived from the secret ([A command-line party](#enrolling-at-a-default-relay)); a browser partner enrolls there for its own allocation, so an exchange on a hosted invitation is still enrolled by the party that uses that relay. A url both the connection and the invitation name is the same relay to the run only when it is written identically; an own entry spelled differently is a different relay, allocated on without the invitation's enrollment. A browser run uses every server it lists.
- **Reports name more relays.** What a run states about the relays it uses, its relay credential notice among them, names the invitation's relay beside the party's own, and a report that no relay candidate was gathered means none was gathered from any relay a browser run lists, or from the one TURN url a CLI run gathers from.

**The run credential.** A run that lists the invitation's TURN urls configures each of them with one credential, minted when the run starts (`mintRunRelayCredential`) and, in a CLI run, minted again for each connection attempt after the first while it waits for the partner ([WEBRTC_TRANSPORT.md](WEBRTC_TRANSPORT.md#connection-attempts)): the relay key derived from the stored current shared secret the run holds, `ttl` = 3600, and `label` = `alcove`. It is minted before the key exchange, so it is the current secret's whichever secret the handshake then completes under ([Which secret a handshake uses](PROTOCOL.md#p-256-authenticated-key-exchange)), the key a party's own registrar holds once its registration of that secret has landed. A browser run presents that one credential to every TURN url it lists, its own relay's, the invitation's and the default relay's alike. A CLI run configures each of its own `turn` entries that sets no `username` or `credential` with the same minted credential, and every other entry with its own static pair, whether or not it also lists the invitation's urls; a run holding no shared secret refuses such an entry by its url before anything is dialed. It hands its WebRTC library only the first TURN url it lists, so a CLI run presents a credential to that url alone ([the stated limit](#the-invitations-relay-locator)). The secret rotates on every successful handshake, so each run's credential derives from a different key. Neither the credential nor the relay key is written anywhere. A CLI run that [registers its rotated relay key](#registering-the-rotated-relay-key) also holds the pre-rotation shared secret in memory until the process exits, whether or not the registrar confirmed; it signs the registration with the relay key it derives from that secret, and the one thing it writes is a timestamp in the key file recording that the registrar has not yet confirmed the rotated key. A browser managed run that registers holds the pre-rotation secret the same way, in its own copy of the record read inside the run+rotate lock, until the run ends, and writes the same timestamp into the managed record ([MANAGED_EXCHANGE_RECORD.md](MANAGED_EXCHANGE_RECORD.md#the-pending-relay-registration)).

## Provider-minted credentials

A connection's `turn` entry may name a relay provider in place of a server: `provider`, the provider's TURN key id (`key_id`) and that key's API token (`api_token`), and no url, username or credential (`TurnProviderEntry` in `packages/core/src/config/connection.ts`). `cloudflare` is the one provider. A CLI run mints the entry's servers and credential from the provider's API under the operator's own account, and lists them in the entry's place, so the rest of this document reads them as entries with a static pair (`mintProviderTurn` in `apps/cli/src/connection/webrtc/providerTurn.ts`).

- **The request.** A `POST` to `https://rtc.live.cloudflare.com/v1/turn/keys/<key_id>/credentials/generate-ice-servers`, with the token as its bearer and the JSON body `{"ttl":3600}` (`turnProviderMintRequest` in `packages/core/src/turnProvider.ts`). Every request sets `ttl`, at `RELAY_CREDENTIAL_MAX_TTL_SECONDS` (**3600**), the one-hour ceiling of a relay credential a run presents, inside the 60 to 172800 s the endpoint accepts ([cloudflare-turn-sizing.md](../notes/cloudflare-turn-sizing.md#credential-lifetimes-the-minting-endpoint-accepts)). The key id is 1 to 128 of `[A-Za-z0-9_-]`, so it needs no escaping in the path. Redirects are not followed. A run waits `TURN_PROVIDER_REQUEST_TIMEOUT_MS` (**15000**) for the answer and reads at most 16384 bytes of it.
- **The urls kept.** Of the urls the answer lists, a run keeps each `turns:` url on Cloudflare's own host, `turn.cloudflare.com`, in the grammar of a `turn` entry's url, with the username and credential of the ICE server listing it (`providerTurnServersFromAnswer`), so the relay's TLS certificate is checked against the provider's name. A `turn:` url, a STUN url and a url on any other host are dropped. A run lists the kept url on port 443 first, since a CLI run allocates on the first TURN url alone ([the stated limit](#the-invitations-relay-locator)). An answer that lists no kept url fails the mint.
- **The lifetime.** The answer states none, so a run counts the credential's expiry from just before it sent the request.
- **When a run mints.** Once as the run is prepared, after every refusal decided from local inputs and before the rendezvous. A connection attempt after the first ([WEBRTC_TRANSPORT.md](WEBRTC_TRANSPORT.md#connection-attempts)) mints again only where it would outlast the credential: where less is left of the credential's lifetime than `PROVIDER_TURN_ATTEMPT_LIFETIME_MS`, the longest attempt (1.5 times the 600000 ms attempt budget) and the 30000 ms channel-open budget after it. A credential is not renewed once the partner connects, so an exchange that connects late in a credential's hour can outlast it.
- **The token.** The CLI reads `api_token` from an `@`-file alone, and refuses a token written in the configuration without repeating it. Neither the token nor a minted credential is written to the configuration, the key file, an event, a log line or an error message: a mint's outcome holds a status or a reason, never the answer's text or a network error's message.
- **A failed mint.** A mint that yields no server fails the run before anything is dialed, or ends the wait at a later attempt, naming the provider and, where it answered, the HTTP status. A 401, 403 or 404 is a usage error (exit 64), the token or key id to fix. Any other status, no answer, and an answer with no kept url is a transport failure.
- **Not in an invitation.** An inviter leaves a provider entry out of its invitation's relay locator, as it leaves out an entry with a static credential, since the partner cannot mint under the inviter's account (`endpointFromConnection`).
- **Stated limits.** A run against the real minting endpoint is not recorded for this path: the request and the handling of its answer are tested against a stubbed API. The web application does not mint.

## The registrar request proof

The reference relay's registrar (`infra/relay/registrar.py`; its contract is `infra/relay/README.md`, The registrar) takes one of two credentials in the `Authorization` header. The relay-owner token, under `Bearer`, enrolls an exchange (`POST /exchanges/<exchange-id>`) and is the relay operator's recovery route on `PUT` and `DELETE`. A registrar whose operator allows it also enrolls on a `POST` with no `Authorization` header ([Enrolling without a token](#enrolling-without-a-token)). A rotation (`PUT`) or revocation (`DELETE`) otherwise proves the caller holds the relay key the registrar has registered for the exchange:

```
proof_key = HKDF-SHA-256(ikm = unhex(relay_key), salt = 0x00 * 32, info = "alcove-relay-registrar-v2:proof-key", 32)
message   = "alcove-relay-registrar-v2:request" LF method LF exchange_id LF hex(SHA-256(body)) LF decimal(ts)
mac       = hex(HMAC-SHA-256(key = proof_key, msg = ascii(message)))
Authorization: Alcove-Relay-Proof ts=<decimal(ts)>,mac=<mac>
```

- **The key.** The HKDF input is the relay key's 32 decoded bytes, not the 64 hex characters coturn keys its HMAC with. The proof key is a further derivation under its own label, used with HMAC-SHA-256 rather than coturn's HMAC-SHA-1 over the characters, so nothing signed for the registrar is a coturn credential; the message also starts with a letter, so it never parses as coturn's `<expiry>:<label>` username.
- **The message.** Five ASCII fields joined by LF (0x0A), with no trailing LF. `method` is `PUT` or `DELETE`. `exchange_id` is the path segment as sent, within the registrar's id alphabet `[A-Za-z0-9._-]`. The body hash is the lowercase hex SHA-256 of the raw body bytes as sent, so no JSON is canonicalized; an empty body, a revocation's, hashes the empty string. `ts` is decimal Unix seconds with no leading zero. No field's alphabet admits LF, so the layout parses one way.
- **The header.** `ts` and the lowercase-hex `mac` travel in the one `Authorization` header as `ts=<digits>,mac=<64 hex>`, never in a second header or the body, so a request holds the token or a proof and never both. The scheme name is matched without regard to case; a malformed value is answered 401.
- **Freshness.** The registrar refuses a `ts` more than 300 s from its own clock with 401 and `serverTime`, its clock's Unix seconds, so a caller whose clock has drifted can sign again. Within the window nothing records a proof -- no timestamp column, nonce, or seen-set; the compare-and-swap below bounds a replay.
- **Verification.** Under the table's write lock, the registrar reads the key the exchange holds and checks the MAC under it, and a rotation replaces that key in the same transaction. A proof made under any other key is refused 409, so of two rotations proven under one key only the first lands, and a replayed rotation is refused once the key has moved on. A `PUT` naming the key the exchange already holds is a renewal: its body shows possession of that key, so it is accepted with any well-formed proof inside the window, including one made under the key it replaced. That is how the second party to register a rotated key, whose proof is made under the key its partner has already replaced, renews the row rather than failing. The proof's MAC is not verified on that path: the key bytes in the body are the credential, so only a holder of the current key reaches it. A renewal restarts the row's lapse from the request's time and takes `maxAgeDays` from the body, so a replayed renewal re-applies that same body and restarts the lapse again, and nothing else. A replayed revocation finds no exchange enrolled.
- **A stated limit: any key holder sets the row's lapse.** For a row the relay-owner token enrolled, a rotation or renewal under a proof takes `maxAgeDays` from its body, `null` included. So any holder of the exchange's current relay key, the partner included, can renew the row, or replace its key with one only it holds, with any lapse or none, and keep the row past the exchange's last run. What it gains is use of the relay, not exchange data, and the registrar's journal records each such write with `authority=proof`. The operator revokes an ended exchange with the token. A row enrolled without a token keeps the lapse the registrar fixed at enrollment.
- **What a caller without the key learns.** A `PUT` or `DELETE` with a well-formed proof inside the window that does not verify is answered 409 with a not-enrolled message for an id the registrar does not hold and a does-not-verify message for one it does, so anyone can learn whether an id in the registrar's id space is enrolled. That is accepted so an operator sees which of the two remedies applies: enroll the exchange, or sign under the key it holds.
- **The label.** `alcove-relay-registrar-v2:*` sits in the [domain-separation label space](PROTOCOL.md#p-256-authenticated-key-exchange). Its input keying material is the relay key, not the shared secret, so it gives the relay's operator, who holds the relay key, nothing derived from the secret.
- **Compatibility.** The project's registrar keeps the requests of every supported release, the rule of [RELEASES.md, Project-run services](../RELEASES.md#compatibility-policy). Nothing in a request names a version: the path is `/exchanges/<exchange-id>`, the body holds exactly `key` and `maxAgeDays` (`registrar.py`, the body reader), and the proof's version is its `v2` label alone, which the registrar checks under the one proof key it derives. The two credentials, the tokenless enrollment, the status codes and the answer's members are the wire a supported release depends on. So are the starts of the `error` text that a release matches to name a refusal's cause (`apps/web/src/psi/transport/defaultRelayRefusal.ts`): in a 429, `"this address holds "`, `"this address has sent "` and `"the registrar is answering enrollments without a token from as many addresses as it can"`; in a 503, `"the relay holds as many exchanges enrolled without a token as it serves"`.
- **Connections.** The registrar answers one request on a connection, each answer holding `Connection: close`, and closes the connection after it. A connection's request must arrive whole within a few seconds of the registrar accepting it ([infra/relay/README.md](../../infra/relay/README.md#the-registrar), Bounds on a connection). No address's connections are bounded, so one address opening about 13 connections a second can still hold every connection slot the registrar has (arithmetic from its bounds, not measured), and while it does every other caller is answered 503 or closed unanswered.

## The WebSocket relay proof

A party shows a WebSocket relay that it holds the exchange's relay key with a proof made under a key of its own, derived from the relay key as the registrar proof's key is. The proof is the message and the tag below; how a relay's hello encodes them is specified in [WEBSOCKET_RELAY.md](WEBSOCKET_RELAY.md#the-hello), apart from the key lookup below.

```
proof_key = HKDF-SHA-256(ikm = unhex(relay_key), salt = 0x00 * 32, info = "alcove-relay-websocket-v2:proof-key", 32)
message   = "alcove-relay-websocket-v2:hello" LF role LF decimal(expiry)
tag       = HMAC-SHA-256(key = proof_key, msg = ascii(message))
```

- **The key.** The HKDF input is the relay key's 32 decoded bytes, as for the registrar proof, under a label of its own, and the tag is the whole 32-byte MAC. So a relay's proof is neither a coturn credential nor a registrar proof, and neither of those is a relay's proof: a captured relay hello mints no TURN credential, and a captured TURN credential opens no relay socket. The message starts with a letter, so it never parses as coturn's `<expiry>:<label>` username.
- **The message.** Three ASCII fields joined by LF (0x0A), with no trailing LF. `role` is the party's rendezvous role, `inviter` or `acceptor` (`RENDEZVOUS_ROLES` in `packages/core/src/rendezvousRoles.ts`). `expiry` is decimal Unix seconds with no leading zero, the second from which the relay refuses the proof. No field's alphabet admits LF, so the layout parses one way.
- **The key lookup.** The hello MUST name the key the proof is under, by the exchange id (`exchange_id`, the `<exchange_id>` path segment of the enrollment request; `exchangeId` in `packages/core/src/relayRegistrarClient.ts`) under which the registrar stored the exchange's relay key, so the relay derives and checks one proof key, not one per enrolled exchange. The exchange id is not part of the signed message, since a tag verifies under one key only.
- **The expiry bound.** A party sets `expiry` to the current Unix second plus whole seconds from 1 to 300 (`WEBSOCKET_RELAY_PROOF_MAX_TTL_SECONDS` in `packages/core/src/websocketRelayProof.ts`), the registrar's freshness window. A value outside these bounds is refused rather than clamped. As with the TURN credential, the bound covers only the proofs Alcove makes: anyone holding the relay key can make one with a later expiry, which the proof check accepts and the relay then refuses when it lies more than 305 seconds past its own clock (What a check refuses, below).
- **What a check refuses.** The relay reads a presented message and tag (`parseWebSocketRelayProof`) and checks them under the proof key of a relay key it holds (`checkWebSocketRelayProof`). It refuses a message over 128 bytes, not UTF-8 or not exactly in the layout above, or a tag that is not 32 bytes, as malformed. It refuses a role other than the one the presenting party claims, and an expiry at or before its own current Unix second. It refuses a tag other than the one the proof key makes over the role and the expiry, compared in constant time. It refuses a proof that passes these checks but whose expiry is more than 305 seconds past its own current Unix second: the 300-second longest lifetime and 5 seconds of slack (`RELAY_PROOF_EXPIRY_SLACK_SECONDS` in `packages/websocket-relay/src/protocol.ts`). A party whose clock runs 300 seconds or more behind the relay's cannot present a proof the relay accepts, and one less than that behind is accepted only while the remaining margin has not elapsed. The relay answers a stale proof with its current Unix second, so a party can sign again ([WEBSOCKET_RELAY.md](WEBSOCKET_RELAY.md#the-hello)).
- **Replay.** A captured proof can be replayed until its expiry, at most 300 seconds, which can open a relay socket in that role and take the role's slot first; it exposes no data, since the key exchange still needs the shared secret. The relay's hello does not bind the proof to its connection ([WEBSOCKET_RELAY.md](WEBSOCKET_RELAY.md#the-hello)).
- **The label.** `alcove-relay-websocket-v2:*` sits in the [domain-separation label space](PROTOCOL.md#p-256-authenticated-key-exchange). Its input keying material is the relay key, not the shared secret, so it gives the relay's operator, who holds the relay key, nothing derived from the secret.

**Test vectors.** For the secret of bytes 0x00..0x1f, whose relay key is the `relay_key` of the registrar proof's vectors above, and `expiry` = 1767225900, the proof key and each role's tag are below. They are generated with Node's `crypto` by `packages/core/test/vectors/generate-relay-proof-vectors.mjs` into `relay-proof-vectors.json` beside it, held to that generator by `npm run check:vectors`, and core is held to the file by `packages/core/test/websocketRelayProof.test.ts`. ## Enrolling without a token

A registrar whose operator turns it on (`infra/relay/README.md`, Enrollment without a token) also enrolls an exchange on a `POST /exchanges/<exchange_id>` that holds no `Authorization` header, so a party holding no relay-owner token can enroll the relay key it relays under. The token and proof routes above are unchanged by it.

- **The request.** The body is `{"key": <relay key>, "maxAgeDays": null}`. A body naming any other `maxAgeDays` is answered 400 and nothing is written: the caller does not choose the lapse.
- **The lapse.** The registrar fixes it at 4200 s (70 minutes) after the enrollment, the web application's 10-minute wait for its partner followed by one credential's `ttl` of 3600 s, and states it in the answer: `maxAgeDays` is `null` and `lapsesAt` is that time. A `PUT` under a proof on such a row, a renewal or a rotation, keeps that lapse whatever `maxAgeDays` its body names, so a row enrolled without a token is never extended past it; the key still authenticates until the next sweep removes the lapsed row, up to the sweep's interval later ([infra/relay/README.md](../../infra/relay/README.md#the-registrar)); only the relay-owner token's `PUT`, the operator's recovery route, replaces it.
- **The same key, and another.** An enrollment naming the key the id already holds is answered 200 with the registration as held, its lapse unchanged, so either party, each deriving the key from the same secret, may enroll it. An enrollment naming another key is answered 409, as for the token's, so a caller cannot replace or revoke an exchange whose key it does not hold.
- **The rate limit.** The registrar limits enrollments without a token from each client address within a window, and answers one past the limit 429 with `Retry-After`, the seconds until the window ends, writing nothing. Its values are the registrar's (`infra/relay/README.md`, Enrollment without a token).
- **The cap on each client.** The registrar holds at most a set number of rows enrolled without a token that have not lapsed for each client address, and answers an enrollment of an id not yet held past it 429 with `Retry-After`, the seconds until the first of that address's rows lapses, writing nothing; an enrollment naming the key an id already holds is still answered 200. The cap is a small fraction of the ceiling below at its default, so one address cannot fill the ceiling alone. Its value, and the prefix an IPv6 address counts under, are the registrar's (`infra/relay/README.md`, Enrollment without a token).
- **Any page can spend an address's limits.** The registrar does not check a request's `Origin`, and its CORS answers allow every origin, so any page a browser on a network loads can send enrollments without a token from that network's address. They count against that address's rate limit and its cap, and its own enrollments can then be refused 429 until the window ends or the rows lapse.
- **The ceiling.** The registrar holds at most a set number of rows enrolled without a token that have not lapsed, and answers an enrollment of an id not yet held past it 503 with `Retry-After`, the seconds until the first of those rows lapses, writing nothing; an enrollment naming the key an id already holds is still answered 200. Its value, derived from what each row adds to the relay's authentication of every credential, is the registrar's (`infra/relay/README.md`, Enrollment without a token). Many addresses, each at its cap, can still reach it. At the ceiling, a browser run that could not enroll dials without the default relay, with its other relays or by STUN alone, until rows lapse.
- **The exchange id.** Any id in the registrar's id alphabet. Since any caller may enroll, a third party that learns or guesses an id before the exchange's own party enrolls it can hold it under another key, and that party's enrollment is then answered 409; an id derived from a secret only the parties hold leaves nothing to guess.

## Registering the rotated relay key

The CLI and the web application's managed re-run keep the relay key a registrar holds current by registering the key derived from each rotated secret. Both use one client, `packages/core/src/relayRegistrarClient.ts`; the CLI's side is `apps/cli/src/relayKeyRotation.ts` and the browser's `apps/web/src/psi/managed/managedRelayRegistration.ts`. The console registers nothing. A browser run of a build that names a default relay also enrolls at that relay, one-shot and managed alike, and so does a CLI run that allocates on an invitation relay naming a registrar with the credential it derives, or dials that relay's WebSocket relay under the derived id ([Enrolling at a default relay](#enrolling-at-a-default-relay)).

- **Who registers.** The party that supplies the relay. A CLI run registers only when its connection names a [`relay_registrar`](../EXCHANGE_REFERENCE.md#connectionrelay_registrar) and one of this party's own `turn` entries has its credential minted from the secret. A browser managed run registers only when its record names the registrar it was enrolled at (`relayRegistrar`) and the exchange's own relays (`ownRelay`) name at least one TURN url, every one of which is minted from the secret. The relay the invitation names does not change that, since the run lists its own relay beside it. A run registers its rotated key at its own relay's registrar whatever its allowed relays keep.
- **When.** After a run whose key exchange rotated the secret: once its outputs are written, before the terminal event, or after the failure of a run that failed past the rotation. A browser run registers before it releases the run+rotate lock.
- **A browser re-invite.** A re-invite of a record that names a registrar registers the key derived from the fresh secret the same way, signed under the key of the secret it replaced, after the write that stores the fresh secret and before it releases the run+rotate lock. A registration it does not confirm cannot be retried by a run, since no key the browser holds can sign it: the record states that ([MANAGED_EXCHANGE_RECORD.md](MANAGED_EXCHANGE_RECORD.md#the-pending-relay-registration)), and the remedy is owner-token re-enrollment.
- **The request.** `PUT /exchanges/<exchange_id>` with the body `{"key": <relay key of the rotated secret>, "maxAgeDays": <authentication.token_max_age_days, or null>}` and a proof made under the relay key of the pre-rotation secret. The body always holds `maxAgeDays`.
- **Retries.** Each request has 15 s. No answer, a 408, 429, or 5xx is tried again after 2 s and after 5 s, three attempts in all. A 401 holding `serverTime` is signed again once at the registrar's time. Any other 401, and a 409, is final.
- **What confirms.** A 2xx whose body is the registrar's answer ([infra/relay/README.md](../../infra/relay/README.md#the-registrar)): a JSON object of at most 4096 bytes stating `maxAgeDays`, a whole number or `null`, and `lapsesAt`, a UTC timestamp or `null`. Any other 2xx -- a body over that bound, not JSON, not an object, or missing either field -- confirms nothing and is tried again as an unanswered request is; an enrollment answered so stores no registrar. The removal from a registrar's error text that [a command-line party's enrollment](#enrolling-at-a-default-relay) states applies to the text shown for a registration here too, and a very short `relay_registrar.exchange_id` is replaced wherever its characters occur in the registrar's text.
- **A cancelled browser run.** The run's cancel ends the retries of the registration after the exchange but reaches no request: the attempt under way, or the next one when the cancel lands between attempts, runs to its 15 s and is the last. The pre-rotation secret that signs it is held nowhere else, so a registration abandoned there would leave the registrar holding a key only the relay-owner token can replace. The retry before the next run dials stops at the cancel.
- **No token.** No request on this path holds the relay-owner token, and no refusal leads to one. The token is sent only at enrollment, which asks for it: `alcove enroll-relay`, or the Relay registration section of a saved exchange's page in the browser. Either sends a `POST` to enroll, or a `PUT` as the operator's recovery (`--replace-relay-key`, or the browser's replace choice). The browser holds the token in the form's state from entry until the request settles, and writes it to no storage.
- **The pending record.** The rotation write that stores the rotated secret also stores `relayRegistrationPendingSince`: in the key file of a run that registers ([EXCHANGE_FILE.md](EXCHANGE_FILE.md#the-pending-relay-registration)), or in a managed record that names a registrar, whether or not the run registers ([MANAGED_EXCHANGE_RECORD.md](MANAGED_EXCHANGE_RECORD.md#the-pending-relay-registration)). A confirmed registration removes it. A failure never rolls the secret back.
- **The retry before the next run dials.** A run whose key file or record holds the pending registration registers the current key again before any contact with its partner; a browser record whose pending registration a re-invite left sends nothing and stops the run with the re-enrollment step. A key file or record that still holds the previous secret -- the partner's confirmation of its store not yet read -- signs it under that secret's relay key, which is the key the rotation replaced, so the retry succeeds whether or not the rotation's request landed, provided the registrar holds the key of one of the two secrets. Otherwise it is signed under the current key, since the pre-rotation secret left with the run that rotated, and succeeds only when the registrar already holds the current key, as when the rotation landed and its answer was lost. A refusal ends the run with the re-enrollment step, the shared secret unchanged: exit 77 on the command line, and in the browser a stopped run that records no `lastRun`. An unavailable registrar ends it the same way, with exit 69 on the command line.

## Enrolling at a default relay

A web application build may name a default relay: a TURN url and its registrar's address (`VITE_DEFAULT_RELAY_TURN_URL`, `VITE_DEFAULT_RELAY_REGISTRAR_URL`; [DEPLOYMENT.md](../DEPLOYMENT.md#the-default-relay)). The build offers the relay switched off until the user turns it on for an exchange, or turns it on in every browser run (`VITE_DEFAULT_RELAY_MODE`, `opt-in` or `on`). Switched off, a run reads the relay's urls from one source, the invitation it accepted where that names the relay's TURN url and otherwise the exchange's own relays (`ownRelay`), and uses each of them only where that source names it: the TURN url, and the enrollment below, only where the source names the TURN url, and the WebSocket relay url only where the source names the WebSocket relay url (`defaultRelayForRun` in `apps/web/src/psi/transport/defaultRelay.ts`). A source names a url only where it holds it exactly as the build names it: one written differently for the same server, in another letter case, with its default port written out, or without its `?transport=` parameter, is not the default relay's, so a run listing it from the exchange's own relays enrolls nowhere and the review shows no relay notice for it, though the run still contacts that server. Each browser run of such a build that uses the relay enrolls its relay key there right before it connects, and lists the relay once enrolled; the client is `enrollRelayKeyWithoutToken` in `packages/core/src/relayRegistrarClient.ts`, and the browser's side `apps/web/src/psi/transport/defaultRelay.ts`. The build may also name that relay's WebSocket relay url (`VITE_DEFAULT_RELAY_WEBSOCKET_URL`), whose relay reads the keys the registrar enrolls. A CLI run accepting an invitation such a build made enrolls there too when it allocates on that relay with the credential it derives, or dials its WebSocket relay url under the id derived from the secret (**A command-line party**, below).

- **Who and when.** Every browser run that uses the relay, inviter or acceptor, one-shot or managed, right before it contacts the coordination server; a managed run enrolls after its retry of a pending registration. Each party derives the same key and id from the run's current secret, so the second enrollment repeats the first, and a later run on the same secret repeats it again. A managed run's rotated secret derives a fresh id, so it enrolls anew and renews nothing. A managed acceptor that also waits under its previous secret, on a run using the relay's WebSocket relay url, enrolls that secret's key under that secret's derived id in a second request sent at the same time ([WebRTC rendezvous peer-id derivation](PROTOCOL.md#webrtc-rendezvous-peer-id-derivation)), and where that one fails while the current secret's enrollment confirmed, the run says once that the relay could not be set up for that secret and looks for its partner on that server under the current secret only. Where the allowed relays that apply (a saved exchange's own, otherwise those set on the review of the invitation accepted or created) leave out the default relay's TURN url, the browser does not name that TURN url in an invitation it creates. Where they keep the relay's WebSocket relay url, a run using the relay still enrolls there for that relay alone, and an invitation it creates that names that url names the registrar beside it; where they keep neither url, it neither enrolls there nor names the registrar. Creating an invitation, a one-shot invitation or a managed re-invite, enrolls nothing, and an invitation created with the relay in use names it whatever its registrar would answer ([The invitation's relay locator](#the-invitations-relay-locator)). One created with the relay switched off names no registrar, and names the relay's TURN url or WebSocket relay url only where the exchange's own relays name that url, as one of its own.
- **How long a dial waits.** One attempt, with no retry, for at most 3 seconds (`DEFAULT_RELAY_DIAL_WAIT_MS` in `apps/web/src/psi/transport/defaultRelay.ts`, an arbitrary working value); a run cancelled meanwhile stops waiting.
- **The request.** `POST /exchanges/<exchange_id>`, the id [derived from the secret](#relay-credential-derivation), with no `Authorization` header and the body `{"key": <relay key>, "maxAgeDays": null}`. The registrar fixes the lapse and states it in its answer's `lapsesAt`.
- **What confirms.** As for [a rotated key's registration](#registering-the-rotated-relay-key): a 2xx stating `maxAgeDays` and `lapsesAt`, the answer to an enrollment naming the key the id already holds included. A refusal, an unreachable registrar, and no answer within the wait confirm nothing. A 409 means the id is held under another key.
- **What the run says of a failure.** The run states which failure it met, read from the answer's status and the start of the registrar's `error` text (`apps/web/src/psi/transport/defaultRelayRefusal.ts`): the cap on each client, the rate limit, or the registrar's table of addresses full, each a 429; the ceiling, a 503; no answer, from an unreachable registrar or none within the wait; or any other answer. It states each in a sentence of its own and never repeats the registrar's text, so an answer it does not recognize is stated as a refusal with no reason given. It states the answer's `Retry-After` wait where the answer gives one in seconds, at most 86400 (`MAX_REGISTRAR_RETRY_AFTER_SECONDS` in core, an arbitrary working value well above the registrar's own longest wait, a row's 70-minute lifetime), and no wait otherwise. A managed exchange's scheduled window records the same cause and wait (`defaultRelayRefusal`, [MANAGED_EXCHANGE_RECORD.md](MANAGED_EXCHANGE_RECORD.md#persisted-across-runs)), and the exchange's page states it.
- **What the run lists.** Its ICE servers hold the default STUN server only where neither the exchange's own relays nor the invitation names a STUN url, and those STUN urls in its place otherwise ([Which relay a run uses](#the-invitations-relay-locator)); the default relay adds no STUN url. A confirmed enrollment adds the default relay's TURN url, where the allowed relays keep it, after the TURN urls of the exchange's own relays and the invitation's, under the one credential minted from the secret. An unconfirmed one leaves it out, even where the invitation or the exchange's own relays name it: the run says once, as the enrollment fails, that the relay could not be set up and why ([What the run says of a failure](#enrolling-at-a-default-relay)), and connects with its other relays. A confirmed enrollment also lists the default relay's WebSocket relay url, where the build names one, the run uses it and the allowed relays keep it, after the exchange's own and the invitation's ([Which WebSocket relays the allowed relays keep](#the-invitations-relay-locator)), and an unconfirmed one leaves that url out too. A run with the relay switched off where neither the invitation nor the exchange's own relays name the TURN url enrolls nowhere, and lists the WebSocket relay url, where either names it, as that source's.
- **Managed runs.** The registration of a managed run's own relay, above, is unaffected by it.
- **The key the default relay holds.** The key enrolled is the exchange's relay key, so the default relay's operator holds a key that the exchange's other relays and registrar also accept, until the secret rotates. No separate key is derived for the default relay.

**A command-line party.** A CLI party learns the registrar from the invitation: an invitation such a build makes with the relay in use names it as its relay locator's `registrar` ([The invitation's relay locator](#the-invitations-relay-locator)), and the accepting party keeps it in `invitation_relay`. The CLI's side is `apps/cli/src/invitationRelayEnrollment.ts`, over the same client.

- **Who and when.** A CLI run whose `invitation_relay` names a `registrar` and whose first TURN url, the one it allocates on ([the stated limit](#the-invitations-relay-locator)), is one the invitation names and takes the run's derived credential: the connection has no `turn` entry of its own that its `allowed_relays` keeps, or the first it keeps names that url and sets no `username` or `credential`. A run that lists the invitation's `websocket` url, where the invitation names no `websocketExchangeId`, enrolls there too, since it dials that relay under the derived id (`runEnrollsAtInvitationRegistrar` in `packages/core/src/relayCredential.ts`). It enrolls once per run: after its retry of a pending registration and before its first connection attempt. An acceptor that also waits under its previous secret enrolls that secret's key under that secret's derived id at the same time ([WebRTC rendezvous peer-id derivation](PROTOCOL.md#webrtc-rendezvous-peer-id-derivation)). The attempts after the first while it waits for the partner ([WEBRTC_TRANSPORT.md](WEBRTC_TRANSPORT.md#connection-attempts)) enroll nothing, since they present the same key.
- **A run that does not enroll.** A CLI run whose first TURN url is one the invitation does not name, or is its own `turn` entry setting a `username` and `credential`, and that does not dial the invitation's WebSocket relay under the derived id, contacts no registrar the invitation names, and states on the log that it did not, naming the url it allocates on. One whose `allowed_relays` leaves out every TURN url and the WebSocket relay url the invitation names states that as the reason instead, and one that allocates on no TURN url while it proves to the invitation's WebSocket relay under the invitation's `websocketExchangeId` states that. A browser partner enrolls there for its own allocation, so an exchange on a hosted invitation is still enrolled by the party that uses that relay. An invitation a browser created with the default relay switched off names no `registrar`, even where it names that relay's TURN url because the exchange's own relays name it ([Composition](#the-invitations-relay-locator)), so a CLI run accepting it that allocates on that url enrolls nowhere and states nothing about it. The relay then takes that allocation only where the browser inviter's own run enrolled the key there, which it does before it contacts the coordination server, and refuses it where that enrollment failed.
- **The request and its wait.** The request above, one attempt with no retry, waited on for at most 3 seconds (`INVITATION_RELAY_ENROLLMENT_WAIT_MS` in `apps/cli/src/invitationRelayEnrollment.ts`, an arbitrary working value, the browser's own); a run interrupted meanwhile stops waiting.
- **What the run reports.** A confirmed enrollment, the answer to a same-key repeat included, is stated on the log. A refusal (401 or 409), a 429, a registrar the run cannot reach, and no answer within the wait are each stated as a warning on the terminal and on the event stream under the source `invitationRelayEnrollment` ([CLI_EVENTS.md](CLI_EVENTS.md#warning-sources)), and the run goes on. A run that enrolls both its current and its previous secret states each answer separately, each line naming the secret it is about ([CLI_EVENTS.md](CLI_EVENTS.md#the-enrolled-secret)). A registrar's error text is shown with the exchange id and the relay key, and those of an acceptor's other enrollment sent at the same time, replaced by a fixed marker only where one appears in one of five forms (as written, URL-encoded, JSON-escaped, and base64 with and without padding), each matched by letter case, so the same value in another encoding (upper-case hex, for one) or cut short is shown as the registrar wrote it.
- **Any https host.** The registrar an invitation names may be any https host, a loopback or private address on the accepting machine's network included; the run sends it the fixed request above, with no credential and following no redirect, after the operator saw the address on the acceptance review and accepted, and nothing checks the address.
- **What the run lists.** The invitation's TURN urls after its own relay's ([Which relay a run uses](#the-invitations-relay-locator)), whether or not it enrolled there or its enrollment confirmed, since the partner derives the same key and id and may have enrolled them. A `relay_registrar` of its own is registered as [above](#registering-the-rotated-relay-key) whatever the enrollment's outcome.
- **The cap on each client.** The registrar holds at most 70 rows enrolled without a token for each client address ([infra/relay/README.md](../../infra/relay/README.md#enrollment-without-a-token)), so a host running more exchanges at once than that can be refused. The refusal is a 429, reported as above.

## The web application's relay check

The web application checks the relays of an exchange an acceptor is reviewing, and of a saved exchange, in that exchange's Connection settings ([WEB_APP.md](../WEB_APP.md#checking-the-relays)). The browser side is `apps/web/src/psi/transport/exchangeRelayCheck.ts`.

- **What it contacts.** Before any contact it states the hosts a run of the exchange may contact (`runRelayHosts` in `apps/web/src/psi/transport/runRelayPlan.ts`): every TURN url and WebSocket relay url the run lists, less those the allowed relays leave out, and the default relay's registrar where the run enrolls there. It contacts none of them until the user starts it, and never the coordination server or a STUN server.
- **The enrollment.** It takes the run's own relay plan, `relayPlanForRun`, so it enrolls at the default relay's registrar exactly where a run of the exchange would, under the id and key derived from the exchange's current secret ([Enrolling at a default relay](#enrolling-at-a-default-relay)). A repeated check repeats that enrollment, which the registrar confirms as a same-key repeat. A default relay url the plan leaves out because its enrollment failed is reported as not enrolled, and is not contacted.
- **The TURN request.** For each TURN url the plan lists, two peer connections in the page, each held to relay candidates and given that url alone with the credential a run mints from the exchange's current secret (`turnIceServer` in `apps/web/src/psi/transport/turnIceServer.ts`). One opens a data channel and sends one message; the other returns it.
- **The WebSocket relay request.** For each WebSocket relay the plan lists under the current secret, one socket in each role through the run's relay client, under the exchange id and relay key a run uses there. Once the relay pairs the two, both send their start and one message passes from one to the other. Where one socket is paired and the other is refused as role taken (4006), another party of the exchange is waiting at the relay: both sockets close with no start sent, and the relay is reported as admitted.
- **The bound.** The requests run at once under one timer of 30 seconds (`RELAY_CHECK_BOUND_MS`), started once the enrollment has ended.
- **The outcomes.** A relay works when its message comes back. Otherwise it does not work, with one cause:
  - credential refused, where the browser reports a TURN error 401 or 441 for the url, or the WebSocket relay refuses the proof with 4004 or 4005;
  - not enrolled, where the default relay's enrollment failed, or the WebSocket relay holds no key for the exchange (4003);
  - no relayed path, where the relay gave both TURN connections a relay candidate, or paired both WebSocket sockets, and no message passed;
  - not reached, for anything else.
- **The words.** The web words each cause itself (`apps/web/src/exchange/exchangeRelayCheckModel.ts`), not with the words of `alcove doctor relay` ([CLI_DOCTOR.md](CLI_DOCTOR.md#the-relay-check)): a line states what the check saw and a step the user can take on the page or ask of the partner, and names no CLI command, registrar, exchange id, proof, or close code. A remedy goes by whose relay it is:
  - a default relay that did not enroll the exchange states the reason the web run's own notice gives, and says to check again, after the wait the answer stated where it stated one;
  - a WebSocket relay that holds another key for the exchange (4004), or holds none (4003) where a run does not enroll at the registrar the invitation names, takes a remedy by whose relay it is: for the user's own, Relay registration where the saved exchange's page shows it, for a WebSocket relay only where each run registers its new key there (`runsRegisterAtOwnRelay` in `apps/web/src/psi/managed/managedRelayRegistration.ts`), and otherwise removing the relay or, where that would add it, turning on the default relay; for one the invitation names, asking the partner to enroll, and for 4004 to replace the key the relay holds; for the default relay, checking again;
  - a 4003 where a run enrolls at the registrar the invitation names asks the partner whether the relay the invitation names is working;
  - a TURN relay of the user's own or of the invitation's that refuses the credential takes the same remedy, and the default relay's says to check again later;
  - a url that does not answer as a relay -- a request that threw, whose line says the check could not start, an answer no WebSocket relay sends, or a refusal of a message the check sent -- takes correcting the url for the user's own, asking the partner to check it for the invitation's, and checking again later for the default relay;
  - a relay that passed no message takes checking or removing it for the user's own, asking the partner to check it for the invitation's, and checking again later for the default relay;
  - a TURN credential the browser could not make is not reached on every TURN url, and its line says so and asks for a reload;
  - a relay not reached takes checking that this computer reaches it, and a WebSocket relay's other refusals take checking again, correcting this computer's clock, checking the network path, or asking whoever runs the relay, as the cause calls for.

  A url shown is escaped and bounded for display.
- **The stated limit.** A browser reports a TURN relay's refusal only through the peer connection's candidate errors, so a refusal it does not report is not reached.

**The inviter's check.** The inviter of an invitation this page creates checks on the share screen instead, from when its run reaches its relays until the partner connects, where the run dials a WebSocket relay. The run that **Try again** starts offers it again, not started. The browser side is `apps/web/src/exchange/inviterRelayCheckModel.ts`, reading the run's `RunRelayWatch` (`apps/web/src/psi/transport/runRelayWatch.ts`).

- **What it contacts.** Nothing. It reads the run's own enrollment at the default relay's registrar and the socket the run holds at each WebSocket relay, and opens no connection of its own.
- **The outcomes.** A WebSocket relay works where the run's socket there is paired. While the run's relay client there has not failed, it also works where its socket has stayed open for 2 seconds after its hello (`HELLO_ANSWER_WAIT_MS`, an arbitrary working value), since the relay sends nothing on accepting a hello, and where the last close the relay sent is role taken (4006), as the acceptor's check reads it, since the relay checks the proof before the role ([WEBSOCKET_RELAY.md](WEBSOCKET_RELAY.md#the-hello)). Otherwise the cause, with the words above, comes from the last close the relay sent where it is a refusal the acceptor's check ends on (`REFUSALS_ENDING_THE_CHECK`), from a proof refused as expired where the run's relay client then failed, from another failure of that client, or from a default relay url the run left out because its enrollment failed. A relay with no answer 30 seconds after the check starts (`RELAY_CHECK_BOUND_MS`) is not reached.
- **Its words.** The share screen keeps the summary and meaning above, with remedies and a verdict of its own. Create fixes the Connection settings, so a remedy that changes them names **Replace this invitation**. A remedy says to check again only where the run's relay client still dials the relay, as it does after a 4003 ([WEBSOCKET_RELAY.md](WEBSOCKET_RELAY.md#the-web-applications-client)). A relay that works is shown as waiting for the partner, and the verdict says only that the page is waiting for the partner where a relay works, and otherwise that no relay accepts the exchange from this page.
- **The stated limit.** Only this side is checked. A TURN relay is listed only where the default relay's enrollment failed, since the run first allocates on it when the partner connects.
