# File-sync modes and bilateral configuration

This document specifies the settings of the file-sync transport that the two parties choose and that a run must agree on or survive: the rendezvous and message-loop mode axes, the split inbound and outbound directories, the retain-mode declaration the invitation token carries, the reuse of a retain-mode directory, the per-run peer id, and the detection of a bilateral mismatch, with the version selection at the rendezvous, and the version-bump policy of the token members that carry file-sync settings.
It does not cover the file-sync state machine, its filenames, invariants and enforcement sites, nor its phases and error taxonomy (see [FILE_SYNC.md](FILE_SYNC.md)), the memory bounds of a round (see [FILE_SYNC_MEMORY.md](FILE_SYNC_MEMORY.md)), the invitation token's wire format (see [INVITATION_TOKEN.md](INVITATION_TOKEN.md)), or the user-facing configuration reference (see [EXCHANGE_REFERENCE.md](../EXCHANGE_REFERENCE.md)).
Intended readers are developers and designers.

## Two orthogonal mode axes

The transport has two independent binary modes. They are bilateral: both parties must choose the same value, and there is no negotiation (see [Bilateral configuration](#bilateral-configuration-detect-and-fail)).

- **Rendezvous mode** -- how the two parties meet:
  - *Lock* (default, `lockless_rendezvous: false`): atomic exclusive-create plus a `-lock.json` tiebreaker; the joiner deletes the peer hello and writes its own. Requires deletion visibility and exclusive-create.
  - *Lockless* (`lockless_rendezvous: true`): an ack-handshake barrier that uses neither exclusive-create nor delete; both hellos and both acks coexist. For sync-mediated transports where both sides "win" a local create or deletions do not propagate.
- **Message-loop mode** -- how send/consume is signaled:
  - *Delete-as-signal* (default): the receiver deletes the sender's message file; the sender waits for that deletion before sending the next.
  - *Retain* (`retain_files: true`): no exchange file is deleted; the receiver writes a zero-length `ack` marker the sender waits for instead. For transports that do not propagate deletions, and for audit transcripts.

Not all combinations are valid. Retain mode requires lockless rendezvous: lock rendezvous is delete-based (the joiner deletes the peer hello as a role-assignment signal) and cannot produce the whole-directory no-delete transcript retain mode guarantees. The three valid combinations are lock + delete-as-signal (default), lockless + delete-as-signal, and lockless + retain. Lock + retain is rejected by schema validation.

## Split inbound/outbound directories

By default one directory is both read and written. A *split* configuration names two: this party reads the peer's files from the **inbound** directory and writes its own to the **outbound** directory, with no single shared path. It is for deployments where inbound and outbound folders are separate -- a managed share, or an SFTP server with distinct drop and pickup directories -- bridged so one party's outbound is the other's inbound. Configured as `inbound_path`/`outbound_path` (filedrop top-level, or under `server` for sftp), the pair mutually exclusive with the single `path`/`server.path`; see [EXCHANGE_REFERENCE.md](../EXCHANGE_REFERENCE.md#connectioninbound_path--connectionoutbound_path).

**Routing rule.** Every *peer-file read* -- the hello, message, ack, and abort-marker listings and reads -- comes from the inbound directory; every *self-write* -- this party's hello, messages, ack markers, abort marker, and in-flight `temp-*.tmp` files -- goes to the outbound directory. The lockless barrier lists only the inbound directory. It prunes `responsibleFiles` against that listing in delete mode only, and delete mode is always shared mode (split requires retain), so there the inbound listing is also this party's own directory. A message's temp write and its atomic rename both occur within the outbound directory, so **no rename ever crosses the two directories** (cross-filesystem rename is not atomic). In shared mode inbound and outbound are the same directory, so this reduces to the single-directory behavior exactly. `this.path` is the inbound directory throughout the code; the outbound directory is resolved via `outboundPath` (which falls back to `this.path` in shared mode).

**Split mode requires retain mode** -- a deliberate constraint, not a mechanical necessity in every topology. On a shared store a delete-mode sender could poll its outbound (which is the peer's inbound) and observe the peer's delete; but that only holds when deletions propagate back, which fails across the one-way or delete-suppressing bridge that motivates separate folders. Retain mode signals with ack/abort markers that are always retained, and keeping the files directly serves the separate-folders goal of an auditable record of what flowed each way. Lock rendezvous is excluded for the same reason it is excluded from retain mode generally: its lock/tiebreaker file must exist in one shared location for the delete-based handshake. Because retain mode already implies lockless rendezvous and timestamped filenames, **only the lockless+retain code paths ever observe split directories** -- the lock and delete-mode paths are unreachable with an outbound directory configured (rejected at config validation), so they stay on `this.path` unchanged.

**Both directories are checked.** Retain mode's [directory precondition](FILE_SYNC.md#preconditions-for-a-correct-exchange) is enforced on the inbound *and* the outbound directory at `synchronize()` entry: peer files never land in outbound (the peer writes to its own outbound, which is this party's inbound), so a protocol-grammar file there is this party's own, from an earlier exchange or a crashed prior session. What an earlier exchange left there is ignored ([Reusing a retain-mode directory](#reusing-a-retain-mode-directory)), and anything else, an unanswered hello included, fails the clean-start guard exactly as on the inbound side. An orphaned `temp-*.tmp` is swept from both directories once entry is accepted, and left in both when it is refused; a foreign file in either is snapshotted and tolerated. The two directories must differ, checked by one shared textual-normalization rule (`pathsResolveToSameDir`) at both config validation and `open()`, so the schema and the live connection give the same verdict (the `open()` check additionally guards a caller that constructs a connection directly, bypassing the schema). On both channels it catches redundant separators, `.` segments, trailing slashes, and backslashes (the fold is unconditional, not filedrop-gated), so e.g. `/x` vs `/x/`, `/x//y` vs `/x/y`, and `/x/./y` vs `/x/y` are all caught. The normalization is textual only: `..` segments (which may cross a symlink), case (Windows is case-insensitive), and a relative-vs-absolute SFTP path under the unknown login home cannot be resolved client-side and remain the operator's responsibility, not a guaranteed reject.

**Invitation-borne role swap.** Split directories are a per-party choice the deployment bridges (one party's outbound is the other's inbound), so an invitation cannot hold a single shared path -- but it can hold the *role mapping*. The invitation connection-endpoint wire format therefore holds the split pair: the sftp and filedrop endpoint sub-schemas (`packages/core/src/config/invitation.ts`) have `inboundPath`/`outboundPath` beside the single `path`, under the same directory-mode rules the connection config uses (both halves together, mutually exclusive with `path`, the two halves distinct, and filedrop must name a directory in one form). Like every field of the token, these are **camelCase on the wire**: the encoder `JSON.stringify`s the validated token verbatim with no snake_case pass, and the sub-schemas are `z.strictObject`, so a token minted with `inbound_path`/`outbound_path` is rejected by the decoder rather than read. The snake_case spellings belong to the connection config on disk, not to the endpoint. They remain credential-free locators. Distinctness is enforced on the endpoint itself -- it survives the mirror swap (equal inviter halves yield equal acceptor halves), unlike the absolute-path rule, which is a per-party property the acceptor remaps and so stays deferred to the connection config's own validation. The token records the **inviter's own** pair verbatim; the cross-party swap happens at exactly one consumer, `connectionFromEndpoint` in apps/cli, which sets the acceptor's `inbound_path` from the inviter's `outbound_path` and its `outbound_path` from the inviter's `inbound_path`, so the two parties start as mirror images. Centralizing the swap at that single seeding site keeps the token a faithful record of the inviter's config rather than a pre-swapped acceptor view, and forecloses a double-swap -- the offline invite path calls the same function with no endpoint, so it never reaches a seeded branch. The seeded block also holds the retain-mode trio a split exchange requires (so it is runnable once credentials are filled in); the inviter's literal paths are a starting point the operator reconciles, since the swap fixes the *roles*, not the literal names -- in an asymmetric topology the paths, host, and even channel differ between parties. An SFTP login-home (unset) path has no concrete value to mirror, so such an endpoint conveys roles with no suggested path rather than erroring. Two accept paths consume that swap, both through this one function so the single-swap-site invariant holds across them: the **offline** accept seeds its whole connection block from `connectionFromEndpoint` directly, and the **online** accept (`applyEndpointSplitDirectories` in apps/cli) calls the same function only to lift out the swapped pair, then grafts that pair onto the connection it built from the acceptor's own URL. The online merge keeps the channel, host, port, and credentials from the URL (the endpoint is credential-free, and a bridged acceptor may reach the rendezvous over a different host or even channel). It takes the split `inboundPath`/`outboundPath` from the endpoint -- fully replacing the URL's single path, which cannot express a role mapping and whose inbound leg, if it won, would break the mirror. It also layers the retain-mode trio over any URL-derived options. An explicit `--outbound-path` (which instead routes through `applyConnectionOverrides`) is the override and wins, so the merge is skipped whenever it is set. The grafted split connection is re-validated through the connection schema before any network activity, so a degenerate endpoint (e.g. relative filedrop paths the endpoint schema defers) fails with the schema's own message rather than at connect time. The accept-time reconcile of a pre-existing config diffs against this merged connection, not a URL-only target, so a location disagreement still aborts before any acceptance is sent.

**A stated limit: on filedrop the pair names directories on the acceptor's machine.** On a filedrop endpoint the online accept takes the two directories the inviter named as local paths of the acceptor, so the run lists one and writes its exchange files into the other, in place of the folder the operator typed in the URL. The acceptor is shown the pair before it consents, with `--outbound-path` as the way to use its own ([CLI.md](../CLI.md#online-acceptance)), and a run given `--consent-to-terms` uses the pair without asking.

**No token-version bump.** Adding `inboundPath`/`outboundPath` to the `z.strictObject` endpoint sub-schemas is in principle an incompatible wire-format change -- an older decoder rejects the unknown keys rather than ignoring them, as it rejects any unknown member of the token. The invitation-token `version` was nonetheless left at `"1"`: the change landed while Alcove is pre-release with no decoder deployed in the field, so no reader can observe the incompatibility and a bump would only churn the version. Version 1 of the token holds the pair ([INVITATION_TOKEN.md](INVITATION_TOKEN.md#version-policy)); an endpoint member added after a release ships is entered in the token's version table, so a token using it is written at the version that adds it. What is newly disclosed on the wire is the inviter's own inbound/outbound directory paths -- public locators with no credential or server-identity material, exactly as the single `path` already did.

## Retain-mode declaration on the token

**The `inviterRetainsFiles` top-level field.** The invitation token has an optional top-level `inviterRetainsFiles: boolean` (camelCase on the wire, beside `connectionEndpoint`): the inviting party's statement that its own `retain_files` is on, so the exchange keeps every file it writes and the rendezvous location becomes a permanent transcript rather than being emptied as each message is consumed. It is the one disclosure of this transport that outlives the run, and the invitation is the only artifact that always reaches a partner, so it is stated where the partner decides.

**It is a declaration, and nothing applies it.** No accept path reads it into a connection: the accepting party sets its own half exactly as before, and a disagreement fast-fails at the hello with `BilateralModeMismatchError`, identically to an invitation with no declaration at all. The enforcement model is untouched -- see [Bilateral configuration](#bilateral-configuration-detect-and-fail), which records why disclosing a bilateral flag stays inside the detect-and-fail boundary.

**Three states, and absence is not the negative.** `true` is the declaration; `false` is a stated delete mode; an omitted field is *no declaration*. Alcove's mint paths write only `true`, and only from a configuration that has retain mode on -- the online `alcove invite` reads its post-override connection, the config-as-source invite reads `connection.options.retain_files` off the config the exchange will run, and the console reads the options block the run holds ORed with the endpoint's shape (below). That is a description of the three producers rather than a rule they are held to, with one exception the mint checks: where the endpoint holds the split pair, the declaration is not theirs to omit (below). Every other path omits it: an offline invite whose written connection block is still a placeholder scaffold has no settled mode to declare, a `webrtc` mint has no retain mode to declare, and a token minted before the field existed has nothing. Of the three, only `true` is stated: `false` and absent render nothing on the declaration's own account, because delete mode is not the mirror claim (a run killed outright, or one that fails after the handshake, leaves files behind in either mode) and a stated negative would promise a cleanup this transport does not make. The endpoint beside the field is the second ground on which the same line renders.

**The display's second ground: the endpoint's shape.** An acceptance surface states the retention where the token declares `true`, and also where its `connectionEndpoint` holds the split `inbound_path`/`outbound_path` pair -- a shape no connection can be built from without retain mode, since a separate outbound directory requires `retain_files: true` ([Split inbound/outbound directories](#split-inboundoutbound-directories)) and the accept paths seed exactly that trio. Both the seeding and the display read one predicate, `endpointRequiresRetainedFiles` in `packages/core/src/config/invitation.ts`, so the shape that puts a party into retain mode and the shape that is stated to it cannot drift apart. The case it covers is a token with a split endpoint and no declaration: Alcove's own mints cannot produce that pair, because the mint-only refusal below rejects it, but a foreign or older token can, and on the declaration alone the accepting party would be seeded into retain mode with the consent line silent. The rendered sentence is the same fixed first-party copy on either ground: a split rendezvous cannot be run in delete mode on either side, so the mode the copy states is the mode any run of it is in.

**One flag only.** `lockless_rendezvous` is equally bilateral and equally fast-failing and is not included: nothing about it changes what an acceptor consents to, and the token's declaration list is held to facts with consent weight. That limit is the recorded line against flag-advertisement drift; adding a second flag means revisiting it here rather than following the precedent.

**Refused on a webrtc endpoint.** A token pairing `inviterRetainsFiles: true` with a `webrtc` `connectionEndpoint` is rejected at both encode and decode by the token schema's own refine: retain mode is a file-sync setting the WebRTC transport does not have, so the pair would state a mode no run of that token could be in. This is the operative gate, not a mirror of one on the connection side. `ConnectionConfigSchema` has a corresponding defense-in-depth refine over a webrtc connection's `options.retainFiles`, but a webrtc connection's `options` parses through `SharedOptionsSchema`, which declares no `retainFiles` field and so strips it before that refine ever sees it. A hand-authored `alcove.yaml` pairing `channel: webrtc` with `options: {retain_files: true}` loads successfully and runs in delete mode, with the field silently dropped rather than refused. A token with no endpoint at all is unconstrained -- the offline file-sync invite holds the declaration with no locator beside it.

**Refused as a false declaration on a split endpoint.** The mirror refusal on the file-sync side, by a second refine on the same schema and likewise at both encode and decode: a token pairing `inviterRetainsFiles: false` with a `connectionEndpoint` holding the split `inbound_path`/`outbound_path` pair is rejected. That endpoint's shape seeds the acceptor into retain mode whatever the token says -- the refine reads `endpointRequiresRetainedFiles`, the same predicate the accept path's own seeding reads -- so the negative states a mode no run of that token could be in, exactly as a `true` on webrtc does. Scoped to the explicit negative: a token omitting the field on the same endpoint stays valid to decode, since absence is *no declaration* rather than a contradicted one, and it is the very pair the display's second ground above exists to cover. The refusal is keyed on the shape, not the channel: a single shared `path` runs in either mode, so a stated `false` beside one decodes. And it binds the field's declared spelling only: the token body folds case only for the keys inside `linkageTerms`, so an unrecognized spelling of the declaration -- `inviter_retains_files` among them -- is refused in decode as an unknown member.

**Refused at mint when a split endpoint leaves it undeclared, and only at mint.** The one rule that is not symmetric between encode and decode: `encodeInvitation` validates against a mint-only schema (`MintedInvitationTokenSchema` in `packages/core/src/config/invitation.ts`) that requires `inviterRetainsFiles: true` on any token with a split `inbound_path`/`outbound_path` endpoint. Emitting such an endpoint hands the partner a permanent transcript that only the locator's shape reveals, and any artifact composed from the declaration rather than from the shape -- an accept kit's file-handling disclosure among them -- would then state nothing about it. The rule lives at the single boundary every mint path reaches, the CLI's three and the web app's alike, rather than as a gate each producer restates.

Decoding is untouched: the same token still decodes, and the acceptance surfaces still state the retention on the endpoint's shape (the display's second ground above). Absence is *no declaration* on a decode path, every Alcove read path derives the retention from the shape rather than from the declaration, and the token is a public protocol surface -- so refusing it there would reject a foreign token Alcove already handles and displays correctly, buying nothing. The asymmetry is the point: Alcove holds itself to declaring what it hands over without demanding the same of an implementation it does not control.

The web mint (`generateInvitation` in `apps/web/src/psi/invitation.ts`) derives the declaration rather than leaving it to its caller: `invitationDeclaresRetainedFiles` ORs `endpointRequiresRetainedFiles` over the endpoint into the retain flag it was passed, and both partner-facing surfaces -- the token and the accept kit's file-handling disclosure -- read that one value, so a split endpoint minted with the flag omitted declares the retention instead of failing this check.

The CLI's mint paths need no such derivation, and a test holds each fact that keeps it unnecessary. The online invite's connection reaches `encodeInvitation` through `applyConnectionOverrides`, which refuses `--outbound-path` without retain mode by a flag-named message (`outboundPath without retain mode is rejected naming --retain-files`, `apps/cli/test/unit/config.test.ts`) and re-validates the merged connection through `ConnectionConfigSchema`, whose split-requires-retain refine is held by the two `a separate outbound directory without retain_files is rejected` cases in `packages/core/test/config/connection.test.ts`. The config-as-source invite emits no `connectionEndpoint` at all, so the shape it would be checked against is absent (`validateInvite: a file-sync config-as-source invite emits no connection endpoint`, `apps/cli/test/unit/commands/invite.test.ts`).

**No token-version bump.** The field is a member of version 1 of the token, added before any release ([INVITATION_TOKEN.md](INVITATION_TOKEN.md#version-policy)). What the field puts on the wire is a setting the inviter advertises in its hello a few seconds later regardless; what it moves is the point at which the partner sees it, from after the acceptance to before it.

The classification the two acceptance surfaces render it under -- enforced on the mode agreement, the inviter's word on what becomes of the transcript -- is the `retainedFiles` entry of `packages/core/src/consent/consentFacts.ts`, with the reasoning in [shared-consent-summary.md](../notes/shared-consent-summary.md).

## Reusing a retain-mode directory

In retain mode with no sweep flag, the entry scan (site 1) ignores the files an earlier exchange left instead of refusing them, and deletes none of them. Their names go into an in-memory set kept beside the foreign snapshot, and every later listing drops them before any check reads it: the rendezvous hello scans, the `poll()` scan (site 3), the ack wait, and `hasOutstandingMessage` (site 4). Delete mode keeps the refusal, with `--sweep-exchange-files` as the remedy.

**What is ignored.** The scan classifies by name (`classifyRetainLeftovers`, [fileSyncLeftovers.ts](../../packages/core/src/connection/fileSyncLeftovers.ts)) over the inbound listing and, in a [split configuration](#split-inboundoutbound-directories), the outbound one:

- every ack marker and every message under a non-empty id, its writer's: for a message, what precedes its timestamp, counter and byte count, read right-anchored; for an ack, what precedes a non-empty acknowledged name;
- every abort marker under a non-empty id;
- every answered hello under a non-empty id;
- a partner hello in the inbound directory that nobody answered, once it is older than `ignore_files_older_than_ms` (below).

Everything else reaches the guard as before: a lock, a `joining` sentinel, a bare name (a message, ack, abort marker or hello under an empty id), an unanswered hello under this party's own id or `peer_id`, an unanswered hello in the outbound directory, and an unanswered partner hello younger than `ignore_files_older_than_ms`, which is met as a live partner.

**Answered.** A hello `<X>-hello-<n>.json` is answered when the listing holds `<Y>-<X>-hello-<n>-ack.json` for a non-empty `<Y>`, the rendezvous ack its partner writes on reading it. An ack name that splits into a writer id and a hello stem at more than one dash is read at every split. This rule was measured on the SFTP harness ([retainFolderReuse.test.ts](../../apps/cli/test/integration/retainFolderReuse.test.ts)): after a completed lockless retain exchange, each party's hello has exactly one such ack, written by the other party.

**The age setting.** `ignore_files_older_than_ms` is the age at which the scan ignores an unanswered partner hello: a positive whole number of milliseconds up to `MAX_TIMEOUT_SECONDS` (seven days), or `infinite`, which never ignores one. Unset, it is this side's own peer timeout: when both parties set the same peer timeout, a partner run still waiting wrote its hello less than that long ago. The age is this host's clock minus the hello's listed `modifyTime`, which is the one use this model makes of `modifyTime` ([I1](FILE_SYNC.md#invariants)).

**The log line.** The scan logs one line: how many files it ignored, the directories, the age of the youngest, and how many of them were unanswered partner hellos older than `ignore_files_older_than_ms`.

**The peer-timeout message.** A run that ignored an unanswered partner hello and then reaches its peer timeout (exit 69) names that hello, its age and the `ignore_files_older_than_ms` it was older than, and says that raising `ignore_files_older_than_ms` or giving both sides the same peer timeout fixes it. Its failure cause holds the age and the setting as the `ignoredHello` fact ([CLI_EVENTS.md](CLI_EVENTS.md#the-failure-cause)), so the console's timeout screen states them with its own remedy; the hello's name is in the CLI's message only.

**A reused name is refused at the reusing side's start-up.** Ignoring by name holds only while each run writes new names. A run whose start-up listing holds an ack answering the hello name it would write refuses entry (exit 64), naming that ack and saying `peer_id` needs fields. It writes nothing, so its partner never sees a hello it could meet and waits out its peer timeout. An ignored name stays ignored for the whole run, whatever its listed time or size later shows, so a partner hello written again under it is never met.

A `peer_id` with no field writes the same hello name on every run, so a scheduled run into one retain folder sets a `peer_id` with fields, such as `site-%Y%m%d%H%M%S` ([Per-run peer id](#per-run-peer-id)), rather than a fixed id.

**Limit -- the age relies on the server's time stamp.** The listed `modifyTime` is whatever the server's file system holds. Measured on the SFTP harness with both backends: SFTP reports whole seconds, and the stamp on a file the other party wrote lay between that party's times before and after its write; a stamp set back on the server's file is listed set back. A server clock behind this host's, or a transfer or sync tool that keeps a source file's time, therefore makes a live partner's hello look older than it is, and the run may ignore it and wait out its peer timeout, whose message names the file. The harness shares one clock, so it cannot produce skew itself. No server-clock reference is taken. Raising `ignore_files_older_than_ms`, or setting it to `infinite`, is the remedy.

**Limit -- an ack moved out of the outbound directory.** In a split configuration a partner's ack counts only while it is listed. A transfer that moves files out of the outbound directory leaves this party's hello unanswered, so `ignore_files_older_than_ms` decides for it.

**Limit -- listings grow.** Ignored files are still listed on every poll, so each exchange added to a reused folder makes each listing longer.

**Limit -- a reused name the reusing side cannot see answered.** In a split configuration where a transfer moves files out of the outbound directory, the reusing party sees neither its earlier hello nor the ack, writes its hello under the ignored name again, and both runs reach their peer timeout. When its earlier hello is still listed, the guard for an unanswered hello under its own id refuses its start-up instead.

**Limit -- a running exchange looks like an earlier one.** Once a retain exchange's rendezvous completes, its hellos are answered and its files have writers, so a run started into the same folder while that exchange is still running ignores them, writes its hello and waits out its peer timeout instead of being refused at entry. A live party whose `unexpected_files` policy is `error` ends its exchange when that hello appears.

**Limit -- an ack from any writer.** A hello counts as answered when an ack of it under any non-empty id is listed, so a party that can write to the folder can make a waiting partner's hello read as answered at entry, and the run ignores it and waits out its peer timeout. Write access to the folder already lets a party stop an exchange by removing its files.

## Per-run peer id

A `peer_id` may hold fields filled in each time the connection opens, giving each run its own id for a transfer system that never passes a file name twice (operator reference: [EXCHANGE_REFERENCE.md](../EXCHANGE_REFERENCE.md#fields-in-peer_id)). The grammar and expansion are `packages/core/src/config/peerIdTemplate.ts`. A `peer_id` with no `%` is used as written, exactly as without this section.

**The effective id.** `open()` sets the party id to `peer_id` with its fields filled in, once per call; every name this party writes, the hello, joining sentinel, lock, messages, acks and abort marker, is built from that id, and the partner adopts it from the hello name as it does any id. The configured `peer_id` is kept beside it as written. Nothing else fills the fields in: a configuration read, validated, disclosed to the console's browser or written back holds the text as written. The text before the first field starts every name this party writes, the lock aside, which starts with whichever id sorts first.

**The fields.** Every field fills in a fixed number of ASCII characters, so a `peer_id` has one expanded length:

| Field | Fills in | Characters |
| --- | --- | --- |
| `%Y` | UTC year, zero-padded | 4 |
| `%m`, `%d`, `%H`, `%M`, `%S` | UTC month, day, hour, minute, second, zero-padded | 2 each |
| `%K` | lowercase hex of 8 bytes from the platform's cryptographic random source, fresh per field | 16 |
| `%%` | a literal `%` | 1 |

The clock is read once per expansion. A clock outside the years 0000-9999 refuses the expansion rather than write a five-digit `%Y` past the length the configuration was checked at. `%K` is a letter neither POSIX `strftime` nor GNU `date` defines (coreutils 9.1 prints `date +%K` as `%K`), so no `date` format string gives it another meaning.

**The random field's size.** 64 bits keeps the ids of one configuration distinct across a long schedule. One run a minute for ten years is n = 60 x 24 x 365.25 x 10 = 5,259,600 runs. By the birthday bound, the chance that any two of n uniformly random 64-bit values are equal is at most n(n - 1) / 2^65, about 7.5 x 10^-7 for that n: near one in a million, from `%K` alone, before the date and time fields separate runs further. A `peer_id` with only date and time fields gives two runs started within the same second the same id.

**The load-time refusals.** `FileSyncOptionsSchema` refuses, under the `peer_id` path, each with a message naming the problem and what to change:

- a `%` followed by anything but one of the fields above, and a single `%` at the end;
- an expansion over `MAX_PEER_ID_BYTES` (211) UTF-8 bytes, the cap that keeps the longest two-id name within the 255-byte limit beside a one-byte partner id ([site 5](FILE_SYNC.md#the-five-enforcement-sites));
- an expansion that is the reserved id `temp`, which only a `peer_id` with no field can be.

Core admits every character in `peer_id`, and the fields fill in digits and hex, so no expansion holds a character the id does not admit and core has no character refusal for them. The console's job-intent boundary holds a `peer_id` with fields to its own party-name shape at every expansion ([SERVER_JOB_API.md](SERVER_JOB_API.md#the-exchange-intent)).

**The leftover check.** The rendezvous classifies a hello or joining sentinel by whether its id is one this party writes: its current id, or any expansion of its `peer_id` (each literal exactly, each date or time field as digits of its width, `%K` as lowercase hex of its width; a linear, anchored match on a partner-written name). The entry scan therefore refuses an earlier run's hello as this party's own (exit 64, naming the file), as it does an exact self-hello; in retain mode an answered one is ignored first ([Reusing a retain-mode directory](#reusing-a-retain-mode-directory)), and the in-flight lock and lockless scans skip such a name as they skip this party's own hello. A joining sentinel at entry is refused whatever its id, and in split mode every unanswered hello in the outbound directory is refused whatever its id, so neither depends on the match.

**The partner-facing id checks.** `peerIdLengthRefusal` and `peerIdPrefixRefusal` run on the two effective ids, each read from the other's hello name, so both parties reach the same verdict: an effective id that is the partner's id followed by `-` and more text (`site-%Y%m%d` against a partner `site`) is refused by both.

**Limit -- a partner id in this party's own format.** A partner whose id matches this party's `peer_id` with its fields filled in (both parties configured with the same `peer_id`, say) is taken for this party's own earlier run. Present at entry, its hello is refused as a leftover; arriving later, it is skipped, and the run reaches the peer timeout with the shared-name fact on its failure cause ([CLI_EVENTS.md](CLI_EVENTS.md#the-failure-cause)). The party whose hello the partner refused at entry saw no such file, and its timeout holds no such fact. `--sweep-exchange-files` deletes such a hello as this party's own, without first reading it for the partner's retain setting as it does a partner's hello. The partner, which cannot see this party's `peer_id`, sees an ordinary hello and waits likewise. The prefix refusal does not catch it, since neither id is the other followed by `-`. The two parties' ids must not match each other in this way, as they must not be equal without fields.

**Limit -- an own leftover reads as a shared `peer_id` first.** The start-up refusal for a hello that fits this party's own `peer_id` names a shared `peer_id` as the likely cause before it names a leftover from an earlier run of this party. A genuine leftover from a killed run in a shared directory gets the same refusal, with its remedy second; nothing local tells the two apart.

## Bilateral configuration: detect and fail

`lockless_rendezvous` and `retain_files` are bilateral agreements with no negotiation step. The deliberate stance is **mismatch detection and clear failure, not capability negotiation**: a party advertises its own flags in its hello (`HelloEnvelope`, the two required fields) and fails fast with a both-sides-named error when the peer's differ. It never adapts to the peer's mode. This boundary is intentional and critical -- advertising flags is one step toward negotiation, and the design stops there for every bilateral setting.

The one item the hello negotiates is the version lists of a run with no key exchange ([Selecting the versions at the rendezvous](#selecting-the-versions-at-the-rendezvous)). The compatibility policy requires two builds of different releases to exchange at the highest version both hold ([RELEASES.md](../RELEASES.md#compatibility-policy)), and that run has no other step before its first message in which to select one. Every other bilateral setting stays detect-and-fail. Do not let mismatch detection of any other setting grow into capability negotiation without revisiting this decision.

**A declared flag on the invitation stays inside that boundary, and this is the decision revisited on the record.** The invitation states the inviter's `retain_files` as [`inviterRetainsFiles`](#retain-mode-declaration-on-the-token), which is a *third* home for a bilateral flag beside the connection config and the hello -- so the stance above has to answer for it rather than be quietly eroded. The boundary the stance draws is **adaptation**: what it forbids is a party changing its own mode to match the peer's, because that turns a misconfiguration the operator must fix into a silent behavior change neither operator chose. A declaration changes no mode. Nothing on the accept path reads the field into a connection, the accepting party still sets its own half from its own config, and a disagreement still reaches the hello and still fast-fails there with both sides named. Every mismatch that failed before this field fails after it, in the same place, with the same error. Disclosure is not negotiation.

What it buys is a consent fact, not a capability. Retain mode is the disclosure of this transport that outlives the run -- the rendezvous location becomes a permanent transcript -- and without the declaration a partner learns of it from a failed run, from an accept kit the inviter may not send, or from word of mouth: never before the point at which they consent. The declaration is therefore scoped to that justification and no further. It is not read, not applied, and not answered; the token holds `retain_files` alone and not `lockless_rendezvous`, which is equally bilateral and equally fast-failing but has no disclosure content of its own.

That scope is the line to hold. The next flag proposed for the invitation is admitted only if it discloses something an acceptor consents to, and the mechanism stays declaration-only: an accept path that *reads* a declared flag into its own configuration -- even to pre-fill it, even to warn -- has crossed from disclosure into adaptation and needs this section rewritten, not extended.

One derivation sits inside that line, which is why the sentence above says *declared* flag: a split-directory `connection_endpoint` seeds the acceptor's connection with the retain trio -- `retain_files`, `lockless_rendezvous`, `timestamp_in_filename` -- at `connectionFromEndpoint` and `applyEndpointSplitDirectories`. The function returns the adopted pair as its `endpointDirectories` result, and its caller in `apps/cli/src/commands/accept.ts` names both directories on the acceptance consent display. That trio is derived from the endpoint's shape, not from any flag the inviter declared: a separate outbound directory is unusable without it, since `ConnectionConfigSchema` refuses the pair unless retain mode is on, so what the acceptor is seeded with is entailed by the locator it was handed rather than adopted from a mode the peer announced. It is written into the acceptor's own connection block, where the operator reviews it -- on the online path, where that block is written only after the handshake, the operator reviews the adopted directories on the consent display before the run -- and the acceptance surfaces state it as a consent fact ([Retain-mode declaration on the token](#retain-mode-declaration-on-the-token)). A newly proposed flag is weighed against the sentence above, never against this derivation.

The same bilateral-vs-local split governs the CLI surface: `lockless_rendezvous`, `retain_files`, and `timestamp_in_filename` get command-line flags (`--lockless-rendezvous`, `--retain-files`, `--timestamp-in-filename`) because an operator must coordinate them with the peer at invocation, whereas a purely-local tuning preference such as `unexpected_files` -- which the two parties may set differently -- is configured in YAML only. CLI flags are otherwise reserved for bilateral settings that must match across parties; local tuning lives in the connection config.

`--outbound-path` is the deliberate exception to that rule: a local setting (each party chooses its own inbound and outbound directories, which the deployment bridges) that is nonetheless a CLI flag. The justification is that it is a *locator*, not a tuning preference -- the companion to the inbound directory, which is already a command-line argument (the server URL or positional path) -- so pairing it with that argument on the command line is the natural surface, where a per-party tuning flag would not be. The CLI maps the URL/positional path (or, for `alcove exchange`, the loaded config's directory) to `inbound_path` and `--outbound-path` to `outbound_path`, for both `sftp` and `filedrop`, in the single `applyConnectionOverrides` chokepoint every bootstrap command routes its connection through (so the four commands share one mapping). It then validates the assembled connection through the same `ConnectionConfigSchema` a hand-written `alcove.yaml` is parsed with, so the split-mode preconditions -- the pair set together, the two directories distinct ([`pathsResolveToSameDir`](#split-inboundoutbound-directories)), the filedrop-absolute rule, and the retain-mode requirement -- reject identically whether a split arrived from flags or from YAML. Only the retain-mode requirement is additionally fast-failed at the CLI, with a `--retain-files`-named message, before the schema runs; the rest surface with the schema's own messages. The invitation-borne role swap for a split exchange (one party's outbound seeding the other's inbound) is a separate mechanism from this local CLI surface: it rides the invitation connection-endpoint wire format and is applied once at accept-seed time through `connectionFromEndpoint`, not through `applyConnectionOverrides`. Both accept modes consume it -- offline seeds the whole block from it, online grafts only its swapped pair onto the URL-built connection -- and an explicit `--outbound-path` (which does route through `applyConnectionOverrides`) overrides it on the online path. See [Invitation-borne role swap](#split-inboundoutbound-directories) above. (The inviter-side complement -- emitting that endpoint from online `alcove invite` -- is `endpointFromConnection`, defined in `packages/core/src/config/endpointProducer.ts` and re-exported by the CLI, the producer inverse of `connectionFromEndpoint`: it derives the endpoint from the connection the invite is using and records the inviter's pair verbatim, with no pre-swap at emit, so the single accept-side swap runs end-to-end. The acceptor mirror-swap is in place regardless of which inviter produced the endpoint. The producer is typed to the file-sync channels only: a webrtc locator names a signaling server, authored from the browser location rather than derived from a connection config, so a webrtc connection cannot reach it.)

The entry-sweep flags (`--sweep-exchange-files`, `--force-retain-sweep`) are a third category that does not fit that split: they are **CLI-only, unilateral, and non-persistable**. CLI-only not because they are bilateral but because "always sweep" must never be a persisted state -- they thread to the connection's runtime options on a path separate from config construction, never as `FileSyncOptions`/`alcove.yaml` fields. Unilateral: one party sweeps its own view of the directory, no peer must pass them, and they have none of the bilateral-mismatch *stall* risk of `retain_files`/`lockless_rendezvous`. They do, however, interact destructively with the bilateral `retain_files` agreement: because the sweep runs before rendezvous, a *blind* sweep would delete the peer hello that the bilateral flag check reads to detect a `retain_files` mismatch -- destroying a retain peer's transcript and bypassing the fast-fail that would have caught the misconfiguration. The pre-sweep retain-signal inspection (site 1) is what closes this; it must not regress to a blind sweep.

**Detection is symmetric (two-sided), via durable hellos.** The flag check sits at *every* peer-hello read site, not just one, and a detecting party leaves its own advertised hello in the directory (writing it first if it had not yet done so) and does not delete the peer's hello. The two rendezvous protocols are not symmetric in *who reads whom* -- a `lockless_rendezvous` mismatch pairs a lockless ack-barrier against a delete-based lock rendezvous -- so a check at one site alone would fast-fail only the party that happens to read the peer hello, leaving the other to hit the peer timeout. Because the advertisement is durable on both sides, the peer (whatever protocol it runs) reaches a peer-hello read site, reads the flags, and fails the same way. This holds in both arrival orders and for both flags, including a `retain_files` mismatch where both parties run the lockless ack-barrier. Leaving an already-written hello so the peer can read it is **not** adaptation: the boundary the bilateral stance forbids is adaptation, not durability, so symmetric detection stays inside it.

**A mismatch leaves both hellos as the directory's terminal state.** The mismatch path does not sweep the hellos: a party that advertised a mode has its advertisement respected as the terminal state rather than silently swept, and the peer needs the file on disk to reach the same conclusion. In-memory session state is still reset (`resetSessionState()`) so the instance is not wedged; only the on-disk sweep is skipped. The cost is that a rerun against the same directory is rejected by the entry guard ([I0](FILE_SYNC.md#invariants)) -- a terminal usage error, not a silent stall. Which of I0's two refusals fires turns on the ids: with the default fresh id per run, both leftover hellos are *peer* hellos to the rerunning party, so it is the at-most-one-peer-hello check (several partner hello files are present) that rejects. That refusal names the way out: if no other session is using the path, one party reruns with `--sweep-exchange-files`, then the other starts. In retain mode it names `ignore_files_older_than_ms` instead, since the bare flag refuses a retain-mode folder: rerun once the hellos are older than it, and the run starts; with it set to `infinite`, which never ignores a hello, it says to set a duration first. A delete-mode party that follows the advice and reruns with a bare `--sweep-exchange-files` is refused in turn, because the leftover partner hello advertises retain mode, and that refusal names `--force-retain-sweep`. Only with a configured `peer_id` does this party's own leftover read as a self hello and take the unexpected-protocol-file refusal instead. Neither party acks the other's hello before refusing, so both hellos are unanswered. A rerun in retain mode therefore meets them as live partners while they are younger than its [`ignore_files_older_than_ms`](#reusing-a-retain-mode-directory) and is refused as above; once both are older, the rerun ignores them and proceeds, unless one is under the rerunning party's own `peer_id`, which stays refused. Measured on the mock transport (`fileSyncRetainLeftovers.test.ts`): a mismatch leaves no ack, an immediate rerun of both parties in retain mode takes the several-partner-hellos refusal, and the same rerun with both hellos an hour old, with `ignore_files_older_than_ms` at its default, the peer timeout, set to two seconds, completes. Otherwise the operator clears the directory and reruns with corrected flags. The mismatch is reported as a distinct typed error (`BilateralModeMismatchError`, a `UsageError` subclass) so the two cleanup sites -- the rendezvous outer catch and the joiner fast-path, which has no enclosing catch -- branch on it deterministically rather than by string-matching the message.

**The symmetric guarantee is best-effort, contingent on the advertising write landing.** Leaving a durable hello presumes the `put` that writes it succeeds. The joiner fast-path -- the one mismatch site that must write a new hello at detection time -- retries that write up to a bounded budget (`ADVERTISE_HELLO_RETRY_ATTEMPTS`, at the polling cadence), so a transient failure has more chances to land. The peer polls concurrently, so the advertisement need not arrive on the first try, only before the peer would otherwise time out, and the budget stays far under `peerTimeoutMs`. If the write still fails every attempt (a transport error sustained across that whole window), no write ordering can recover -- there is no durable file for the peer to read, so the peer falls back to the ordinary peer-timeout on that one side. The detecting party still fails locally and correctly: it swallows the write failure and throws the typed `BilateralModeMismatchError` (CLI exit 64) rather than letting a transport rejection mask the actionable cause as a generic error (exit 69). This degradation is the floor, never the target -- it is no worse than the pre-advertisement behavior (a silent stall until the peer timeout), and it only occurs when shared storage is failing writes, in which case the exchange could not have proceeded regardless.

### Selecting the versions at the rendezvous

A run with no key exchange -- the CLI's quick exchange, and the console's direct exchange, which runs it -- has no version hello ([KEY_EXCHANGE.md](KEY_EXCHANGE.md#p-256-authenticated-key-exchange), The version hello), so its rendezvous hello offers the versions instead:

```
{"locklessRendezvous":false,"retainFiles":false,"versions":{"protocol":[1],"envelope":[1,2]}}
```

- **The lists.** `versions.protocol` and `versions.envelope` follow the version hello's value rules: each is a list of 1 to 32 integers from 1 to 2^31-1, this build's taken from `OFFERED_PROTOCOL_VERSIONS` and `OFFERED_ENVELOPE_VERSIONS` (`packages/core/src/versionHello.ts`). A reader ignores a member it does not know, at the top level and inside `versions`, so a later build adds a member rather than changing one. A `versions` member that breaks the rules fails the hello read as a malformed hello. Order and repeats are not rules, as in the version hello: the selection takes the highest version in both lists, which neither changes. With both lists at their longest the hello stays inside the 1,024-byte control-file bound.
- **An absent member.** A hello with no `versions` member offers protocol 1 and envelope 1, which every build before the member existed speaks, so such a build and this one exchange at version 1.
- **The selection.** Each party reads the peer hello at whichever read site its rendezvous reaches and takes, in each layer, the highest version both hellos list, by the version hello's selection rule (`selectLayerVersion`). Both parties read both hellos, so both select the same versions before either sends a message. The terms exchange then states the selected protocol version ([PROTOCOL.md](PROTOCOL.md#protocol-version-reconcile-at-the-terms-exchange)), and every binary message frame after a party's first holds the selected envelope version in byte 0; the first frame and every JSON message stay at 1, as on every path ([File taxonomy](FILE_SYNC.md#file-taxonomy)).
- **No common version.** Where a layer has no version in both hellos, the party refuses at the read site, before any terms, record count or match data moves, with `the partner is running an Alcove version this one cannot exchange with: this party supports <layer> versions <list> and the partner supports <list>; the party on the older version must update`. The lists are the schema-checked integers of the two hellos; no release version is on the wire. The refusal follows the detection and terminal-state rules of a bilateral mismatch above: the refusing party leaves its hello in place, writing it first on the lock joiner's path, keeps the peer's, and writes no ack, so the peer reaches the same refusal from its own read. A rerun against the hellos it leaves is refused by the entry guard, whose refusal names the recovery: one party reruns with `--sweep-exchange-files`, then the other starts, or in retain mode both rerun once the hellos are older than `ignore_files_older_than_ms`. A peer from before the `versions` member reads no lists and so does not refuse; it fails on its own timeout instead, which can happen only once a build no longer offers version 1. The command-line application shows its partner-refusal next step beneath the refusal, as it does beneath the version hello's. It is a `PartnerProtocolRefusalError` (CLI exit 76) naming the older side where one list lies wholly below the other, not a `UsageError`.
- **Unauthenticated.** Nothing on this path is keyed, so nothing binds the lists, as nothing binds anything else a quick exchange sends (the CLI's quick-exchange trust notice says so). Whoever can write the shared directory can rewrite a hello to force the lowest version both builds still hold, or the refusal; the same party can already stand in for the partner outright. The keyed path selects from the version hello, which the handshake transcript binds.
- **Keyed runs.** A run with a key exchange writes no `versions` member and selects from the version hello alone. A peer's `versions` member is still read against the list rules above, so one that breaks them fails the hello read as on any run.
