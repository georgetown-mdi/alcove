- - -> The relay check
- - -> `doctor relay` runs only when it is named: `doctor probe` and `doctor mount` contact no relay and no registrar.
- - -> The check contacts exactly the relay hosts a run of the configuration contacts, and nothing else: the first TURN url the run lists, and the registrar `invitation_relay` names only where `runEnrollsAtInvitationRegistrar` is true for the configuration.
- - -> It discloses this machine's address, and the credential a run presents, to no host a run of the configuration would not disclose them to.
- - -> **Refusals.**
- - -> A configuration whose `connection.channel` is not `webrtc`, one that configures `ice_provision`, and one that lists no TURN url are each a usage error (exit 64), refused before anything is contacted.
- - -> **The host statement.**
- - -> Before its first request, the check prints the hosts it will contact:
- - -> the first TURN url, with the transport it names, whether it came from `connection.turn` or the invitation, and that it is the relay a run allocates on;
- - -> the registrar, where the run would enroll there, with the statement that the check enrolls this exchange's relay key there as a run does and that whoever runs it learns this machine's network address.
- - -> It then prints each host the configuration names that it will not contact, with the reason that a run of this configuration does not contact it: every TURN url after the first, which a run does not allocate on, and the registrar where `invitation_relay` names one the run would not enroll at.
- - -> Where `invitation_relay` names no registrar, the statement says the check contacts none and enrolls nothing; where the configuration has no `invitation_relay` block, it says nothing about one.
- - -> Each host is on a line of its own, with the explanation on the lines below it.
- - -> It prints them to the destination the human check lines use -- stderr, or the `--log-file` -- with or without `--json`, at every `--log-level`, `silent` included.
- - -> It contacts no other host: not `connection.relay_registrar`, no coordination server, and no STUN server.
- - -> **The enrollment.**
- - -> Where the run would enroll at the registrar `invitation_relay` names, the check enrolls the exchange's relay key there before it asks the relay, through the call a run makes before it dials (`enrollAtInvitationRelay`; [PROTOCOL.md](PROTOCOL.md#enrolling-at-a-default-relay)): one attempt without a token, under the run's wait.
- - -> Its outcome is the `enrollment` check: `ok` with the lapse the registrar states, or `warn` with the first sentence of the run's warning, holding the registrar's answer, as the summary.
- - -> The `warn` has a `meaning` saying a run makes the same enrollment, and an `action` to run the check again and, if the enrollment keeps failing, to ask the partner whether the registrar their invitation names is up; it adds that a run goes on without the enrollment, and that the invitation's relay refuses the run's credential until either party enrolls the exchange there.
- - -> The answer is the registrar's text, so it stays in the summary the JSON withholds.
- - -> A failed enrollment does not stop the check: the relay is still asked.
- - -> Where `invitation_relay` names a registrar the run would not enroll at, the `enrollment` check is `skipped`, with a `meaning` that a run of this configuration does not enroll there, because the relay it allocates on is not one the invitation names or is sent its `connection.turn` entry's own credential.
- - -> **The request.**
- - -> For the first url alone the check builds the werift peer connection a run builds, with `ice_transport_policy` `relay` and that url as its only ICE server, presenting what the run presents there: the entry's own `username` and `credential`, or the credential the run mints from the shared secret (`relayCredentialForRun`).
- - -> It creates a data channel and a local offer, and waits for gathering to complete.
- - -> No later url is contacted.
- - -> **The bound.**
- - -> The request runs under one timer of 30 seconds, an arbitrary working value, started once the enrollment has ended.
- - -> A gathering that has not completed when it expires is reported as not reached, and the peer connection is closed, ending the gather.
- - -> A gather that throws rather than ending ends the check with an error and no verdict.
- - -> **The outcomes.**
- - -> The first url is reached when a relay candidate is among this side's candidates (the same reading of the ICE statistics a run's failure diagnosis makes).
- - -> Its check, `turn_1`, is `ok` when it is reached, and `fail` otherwise, with `no relay candidate gathered` in the summary and the remedy a run's relay failure has in [CLI.md](../CLI.md#when-a-webrtc-exchange-does-not-connect) as the `action`.
- - -> werift reports no per-server error from the peer connection, so a relay that refused the allocation, one that never answered, and one whose certificate did not verify are one outcome, and the `meaning` says the reason is not reported.
- - -> A relay that has not enrolled the exchange's relay key refuses the minted credential, so where the enrollment failed and no run on either side has enrolled the key, the invitation's url is not reached on any network, and its check's `meaning` names the failed enrollment as the likely cause.
- - -> Every later url's check is `skipped`, with a `meaning` that a run of this configuration does not contact it, since a run allocates on the first url alone, and an `action` to list it first and run the check again if it should be the run's relay.
- - -> The human rendering prints that shared `meaning` and `action` once, under the last of them.
- - -> **Rollup.**
- - -> As [Overall verdict](#overall-verdict) states, a `fail` makes `overall` `fix_and_retry`, and a `warn` or `skipped` leaves it `ok`.
- - -> Only `turn_1` can fail, so it alone decides `overall`.
- - -> A failed enrollment is a `warn` and leaves `overall` `ok`: the enrollment serves the relay a run allocates on, and that relay's own check has the consequence.
- - -> The check reports no `fatal`.
- A usage error -- a missing or malformed input, or a bad flag -- is not in that set: it exits 64 (`EX_USAGE`) and prints no verdict on either stream, because the checks never ran. -> A usage error -- a missing or malformed input, a bad flag, or a configuration `doctor relay` refuses -- is not in that set: it exits 64 (`EX_USAGE`) and prints no verdict on either stream, because the checks never ran.
