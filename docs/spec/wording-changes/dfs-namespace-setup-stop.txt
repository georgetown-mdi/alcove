The captured output allows each entry line room for a full-length name, but a listing can still be cut short of the bound -- by lines longer than that allowance -- so a listing too long to capture whose counted entries are within the bound is a separate `warn`: the count is reported as a lower bound, the `meaning` states that the listing could not be captured in full, and the `action` asks the operator to confirm the folder is within the bound or use a dedicated one. A configured subdirectory that is a DFS link is a `fail` whose `action` points at the Windows guide's "Reading the real path from Windows", and the run stops there, before anything is written: either the server answers `NT_STATUS_PATH_NOT_COVERED`, or `smbclient`, which follows a referral on its own, reports through `showconnect` that it reached the folder on a server or share other than the configured one, compared case-insensitively. A `showconnect` answer naming no server and share decides nothing. With no subdirectory configured `showconnect` is not run, so a redirect at the share itself (a domain-based namespace root, or a Samba share set to `msdfs proxy`) is not detected; with one configured, such a redirect is reported as the folder being a DFS link.
