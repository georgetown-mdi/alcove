- - -> Per-run peer id
- - -> A `peer_id` may hold fields filled in each time the connection opens, giving each run its own id for a transfer system that never passes a file name twice (operator reference: [EXCHANGE_REFERENCE.md](../EXCHANGE_REFERENCE.md#fields-in-peer_id)).
- - -> The grammar and expansion are `packages/core/src/config/peerIdTemplate.ts`.
- - -> A `peer_id` with no `%` is used as written, exactly as without this section.
- - -> **The effective id.**
- - -> `open()` sets the party id to `peer_id` with its fields filled in, once per call; every name this party writes, the hello, joining sentinel, lock, messages, acks and abort marker, is built from that id, and the partner adopts it from the hello name as it does any id.
- - -> The configured `peer_id` is kept beside it as written.
- - -> Nothing else fills the fields in: a configuration read, validated, disclosed to the console's browser or written back holds the text as written.
- - -> The text before the first field starts every name this party writes, the lock aside, which starts with whichever id sorts first.
- - -> **The fields.**
- - -> Every field fills in a fixed number of ASCII characters, so a `peer_id` has one expanded length:
- - -> Field | Fills in | Characters
- - -> `%Y` | UTC year, zero-padded | 4
- - -> `%m`, `%d`, `%H`, `%M`, `%S` | UTC month, day, hour, minute, second, zero-padded | 2 each
- - -> `%K` | lowercase hex of 8 bytes from the platform's cryptographic random source, fresh per field | 16
- - -> `%%` | a literal `%` | 1
- - -> The clock is read once per expansion.
- - -> A clock outside the years 0000-9999 refuses the expansion rather than write a five-digit `%Y` past the length the configuration was checked at.
- - -> `%K` is a letter neither POSIX `strftime` nor GNU `date` defines (coreutils 9.1 prints `date +%K` as `%K`), so no `date` format string gives it another meaning.
- - -> **The random field's size.**
- - -> 64 bits keeps the ids of one configuration distinct across a long schedule.
- - -> One run a minute for ten years is n = 60 x 24 x 365.25 x 10 = 5,259,600 runs.
- - -> By the birthday bound, the chance that any two of n uniformly random 64-bit values are equal is at most n(n - 1) / 2^65, about 7.5 x 10^-7 for that n: near one in a million, from `%K` alone, before the date and time fields separate runs further.
- - -> A `peer_id` with only date and time fields gives two runs started within the same second the same id.
- - -> **The load-time refusals.**
- - -> `FileSyncOptionsSchema` refuses, under the `peer_id` path, each with a message naming the problem and what to change:
- - -> a `%` followed by anything but one of the fields above, and a single `%` at the end;
- - -> an expansion over `MAX_PEER_ID_BYTES` (211) UTF-8 bytes, the cap that keeps the longest two-id name within the 255-byte limit beside a one-byte partner id ([site 5](#the-five-enforcement-sites));
- - -> an expansion that is the reserved id `temp`, which only a `peer_id` with no field can be.
- - -> Core admits every character in `peer_id`, and the fields fill in digits and hex, so no expansion holds a character the id does not admit and core has no character refusal for them.
- - -> The console's job-intent boundary holds a `peer_id` with fields to its own party-name shape at every expansion ([SERVER_JOB_API.md](SERVER_JOB_API.md#the-exchange-intent)).
- - -> **The leftover check.**
- - -> The rendezvous classifies a hello or joining sentinel by whether its id is one this party writes: its current id, or any expansion of its `peer_id` (each literal exactly, each date or time field as digits of its width, `%K` as lowercase hex of its width; a linear, anchored match on a partner-written name).
- - -> The entry scan therefore refuses an earlier run's hello as this party's own (exit 64, naming the file), as it does an exact self-hello, and the in-flight lock and lockless scans skip such a name as they skip this party's own hello.
- - -> A joining sentinel at entry is refused whatever its id, and in split mode every protocol file in the outbound directory is refused whatever its id, so neither depends on the match.
- - -> **The partner-facing id checks.**
- - -> `peerIdLengthRefusal` and `peerIdPrefixRefusal` run on the two effective ids, each read from the other's hello name, so both parties reach the same verdict: an effective id that is the partner's id followed by `-` and more text (`site-%Y%m%d` against a partner `site`) is refused by both.
- - -> **Limit -- a partner id in this party's own format.**
- - -> A partner whose id matches this party's `peer_id` with its fields filled in (both parties configured with the same `peer_id`, say) is taken for this party's own earlier run.
- - -> Present at entry, its hello is refused as a leftover; arriving later, it is skipped, and the run reaches the ordinary peer timeout.
- - -> The partner, which cannot see this party's `peer_id`, sees an ordinary hello and waits likewise.
- - -> The prefix refusal does not catch it, since neither id is the other followed by `-`.
- - -> The two parties' ids must not match each other in this way, as they must not be equal without fields.
- - -> On the two exchange arms, `peerId` may instead hold core's per-run fields ([FILE_SYNC.md](FILE_SYNC.md#per-run-peer-id)): the console's name control takes none, so such a value reaches an intent only from a mounted configuration, and the composed run writes it back as written.
- - -> It is admitted only when it parses under core's grammar, holds at least one field, and every expansion is a label the rule above admits; the fields fill in digits and hex of fixed widths, so one expansion decides it.
- - -> A literal `%` (`%%`) therefore never passes.
- - -> The zero-setup arms admit only the plain label.
