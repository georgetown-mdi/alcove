# Units the change adds.
- - -> `outcome` | string | `relay` mode's WebSocket relay checks only | What the relay answered the proof a run presents: one of `admitted`, `not_admitted`, `not_reached`, `certificate_not_verified` or `unexpected_message` (see [The relay check](#the-relay-check)).
- - -> `close_code` | integer | `relay` mode's WebSocket relay checks, `not_admitted` only | The close code the relay refused the proof with: one of 1001, 1009, 1011, 4001, 4002, 4003, 4004, 4005, 4007 or 4008 ([WEBSOCKET_RELAY.md](WEBSOCKET_RELAY.md#close-codes)).
- - -> `websocket_1`, `websocket_2` | The WebSocket relay at the check's `url`, which a run dials, admitted the proof a run presents there. A run dials every WebSocket relay it lists, so each is contacted. The number is the relay's 1-based position in the run's list, and a run lists two at most. Present only where a run lists a WebSocket relay.
- - -> So is one that lists a WebSocket relay and sets no `role`, since the proof a WebSocket relay takes names this side's role.
- - -> each WebSocket relay a run dials, whether it came from `connection.websocket_relay` or the invitation, that the check opens two connections to it, presents on each the proof a run presents there, and closes both once the relay answers, and that whoever runs it learns this machine's network address;
- - -> **The WebSocket relay request.**
- - -> For each WebSocket relay a run dials, the check takes the run's own dial (`webSocketRelayDialsFor`), so the exchange id, the role, the relay key and the proof are derived as a run derives them, and parks two sockets on it in this side's role through the run's own relay client (`parkWebSocketRelay`; [WEBSOCKET_RELAY.md](WEBSOCKET_RELAY.md#the-command-line-client)).
- - -> Each socket sends the hello a run sends, and corrects an expired proof on the relay's clock as a run does.
- - -> The relay sends nothing to an admitted hello until a partner arrives, and it checks the role only once the proof has verified ([WEBSOCKET_RELAY.md](WEBSOCKET_RELAY.md#the-hello)), so the second socket it admits is refused as role taken (4006).
- - -> The check reads that refusal, or `paired` on either socket, as the admission.
- - -> It closes both sockets once it has an answer, with 1000, as a run closes a socket on which it has not sent its start.
- - -> Neither socket sends a start, so the check opens no relayed path and sends no exchange message.
- - -> **The stated limit of the WebSocket relay request.**
- - -> The check stops at admission.
- - -> It establishes that this host reached the relay and that the relay accepted the proof a run presents, and not that a relayed path between the two parties would carry the exchange: that needs the partner, which the check does not wait for.
- - -> A partner already waiting at the relay in the other role is paired with one of the check's sockets, and the check's close then reads to that partner as a partner leaving the pairing, on which its relay client dials again ([WEBSOCKET_RELAY.md](WEBSOCKET_RELAY.md#the-command-line-client)).
- - -> A WebSocket relay that has not answered when it expires is reported as not reached, and its sockets are closed.
- - -> The certificate check of a WebSocket relay runs under the same timer as well as its own budget, the signaling certificate check's ([WEBRTC_TRANSPORT.md](WEBRTC_TRANSPORT.md#budgets)), so the check takes no longer than the one bound.
- - -> **The WebSocket relay outcomes.**
- - -> Each WebSocket relay's check is `ok` with `outcome` `admitted` where the relay admitted the proof.
- - -> It is `fail` otherwise, with one of four outcomes, each with its own `meaning` and `action`:
- - -> `not_admitted`, where the relay refused the hello with a close code [WEBSOCKET_RELAY.md](WEBSOCKET_RELAY.md#close-codes) lists for a hello it refuses, held in `close_code`.
- - -> A first 4005 on a socket is not an answer, since the relay client makes the proof again at once on the relay's clock.
- - -> The `action` follows the code:
- - -> For 4003, run the check again and ask the partner whether the registrar their invitation names is up, where a run enrolls at that registrar on this relay's account (`webSocketRelayEnrollsAtInvitationRegistrar`, decided by the url as `runEnrollsAtInvitationRegistrar` is), and otherwise enroll the exchange's relay key with `alcove enroll-relay`.
- - -> Where the enrollment failed and a run enrolls there on this relay's account, the 4003 `meaning` names the failed enrollment as the likely cause.
- - -> For 4004, register the current key with `alcove enroll-relay --replace-relay-key`.
- - -> For a 4005 after the relay client made the proof again on the relay's clock, the `meaning` says this computer's clock is not the cause, and the `action` is to run the check again and, if the relay refuses the proof the same way, check the relay and the exchange's enrollment at its registrar, as the relay client's own failure says.
- - -> A 4005 whose reason is not a second the relay client reads is the answer at once, since no proof can be made on the relay's clock; for it the `action` is to correct this computer's clock first.
- - -> For 4007, check the network path to the relay, including any proxy.
- - -> `unexpected_message`, where the relay answered the proof with a message the run's relay client does not take at that point, so the url may not name an Alcove WebSocket relay.
- - -> The `action` is to check that the url names one.
- - -> `certificate_not_verified`, where a socket closed before it opened and the certificate check a run makes of a failed signaling socket ([WEBRTC_TRANSPORT.md](WEBRTC_TRANSPORT.md#connection-attempts)) found that the relay's TLS certificate did not verify on this host.
- - -> The `action` names the remedy where the network intercepts TLS: add its certificate authority to this machine's trust store, or name a file holding it in `NODE_EXTRA_CA_CERTS`.
- - -> `not_reached`, for anything else: a socket that closed before the relay answered the proof, a certificate that verified or could not be checked, or no answer within the bound.
- - -> Where Node's environment proxying is on, the certificate is not checked, and the `meaning` and `action` say so.
- - -> A close from the relay, and a message from it that the run's relay client does not take, are that relay's own outcome, and every other check is reported beside it.
- - -> Where a run also dials a WebSocket relay, that `action` adds that each WebSocket relay line below shows whether the exchange can still go that way.
- - -> When any relay the check asks is not reached, not admitted, or does not answer as an Alcove WebSocket relay, `overall` is `fix_and_retry`, even though a run may still succeed over another relay the configuration lists.
- - -> **A configuration with no role is offered the check.**
- - -> A configuration that lists a WebSocket relay and sets no `role` is offered the check, and starting it answers `refused`, as a run of that file is refused.
- - -> Neither rendering, nor the host statement, holds the credential or the proof a run presents, or anything else derived from the shared secret, such as the relay key or an exchange id the run derives.
- - -> At a WebSocket relay the check's sockets hold this side's role while it runs, so the run's own socket is refused as role taken and dials again, as its relay client does on that refusal ([WEBSOCKET_RELAY.md](WEBSOCKET_RELAY.md#the-command-line-client)).
