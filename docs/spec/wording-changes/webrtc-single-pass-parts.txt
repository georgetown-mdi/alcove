- - -> A forked-process run of the real linkage with the phase-boundary churn relief (above) active, at `D` ~= 2M distinct values (the worst-case `keyCount * rows`), put the *heavier* party, which at scale is the sender (it holds its own encrypted setup plus the re-encrypted request resident at once), at 2,620 MiB relieved, the receiver at 1,513 MiB, over a WebAssembly linear heap of 175 MiB on each side and a post-GC live heap of 114 MiB on the sender and 121 MiB on the receiver.
- - -> It is **transport-aware**: file-sync uses the derived cap, held to the AEAD's limit on one frame on an encrypted connection under envelope version 1; the WebRTC data channel keeps its fixed per-frame bound `MAX_WEBRTC_FRAME_BYTES` (256 MiB) at its reassembly read gate (see [TRANSPORT_BOUNDS.md](TRANSPORT_BOUNDS.md#webrtc-data-channel-inbound-bound)), and a message whose cap passes that bound is sent in parts, the cap counting them at the length of the one frame they replace ([Single-pass messages in parts](#single-pass-messages-in-parts)).
- - -> At a browser party's ceiling, 8,388,608 value slots a side at one key, the request cap is 293,601,282 bytes and the reply cap, its response term that request, 696,254,722 bytes (about 664 MiB), so both go in parts.
- - -> What limits a run is:
- - -> **One PSI set.**
- - -> Over WebRTC a party's own single-pass set is held to `MAX_PSI_DECODE_ELEMENTS`, above a browser party's ceiling.
- - -> A browser party's ceiling holds the partner to fewer rows than that, so only a run between two command-line parties reaches the refusal.
- - -> **Memory, at the terms exchange.**
- - -> **Between two command-line parties over WebRTC.**
- - -> Neither party states a receive ceiling under `MAX_PSI_DECODE_ELEMENTS`, so neither holds the other to a value-slot budget.
- - -> **The caps the counts derive, in parts.**
- - -> Each message is held to the cap the counts derive for it, and one whose cap passes the per-frame bound is sent in parts, each within that bound ([Single-pass messages in parts](#single-pass-messages-in-parts)).
- - -> A party's own set is held to `MAX_PSI_DECODE_ELEMENTS` and refused past it before any value is masked, its partner sent `PSI_SET_TOO_LARGE_ABORT_REASON`.
- - -> A receiver holds the partner's set to `MAX_PSI_DECODE_ELEMENTS` too.
- - -> A setup in parts is held at its first part to the [combined bound](#a-psi-set-is-sent-in-parts) and to what the reply cap leaves, and its element scan to the lesser of the sender's value slots and `MAX_PSI_DECODE_ELEMENTS`.
- - -> A request in parts is held at its first part to the request cap and to the combined bound, and once joined its element scan holds it to the receiver's value slots, as over file-sync.
- - -> Each party weighs the message it will read and the message it will send, each at the measured multiple of one part, and the hand-off to the PSI worker as over file-sync ([FILE_SYNC.md, Memory an inbound frame takes](FILE_SYNC.md#memory-an-inbound-frame-takes)).
- - -> A need over what is available is a `RoundCapacityError` that sends the partner `PARTNER_SET_OVER_CAPACITY_ABORT_REASON`, or with `--allow-memory-shortfall` a warning.
- - -> Both parties need a build with this rule, a browser party as much as a command-line one.
- - -> A build that reads messages 1 and 2 only as one frame refuses a part, and one that holds every WebRTC party to a fixed value-slot budget refuses an exchange the other admits; a party on each side of the rule is not a supported pair.
- - -> Below release `1.0.0` partners upgrade together ([RELEASES.md, Compatibility policy](../RELEASES.md#compatibility-policy)).
- - -> An exchange whose messages each fit one frame is byte-identical under either build.
- - -> A browser party's budget therefore buys width with rows, and what it admits depends on the whole template rather than on the widened key alone.
- - -> Over WebRTC a reply whose cap passes the 256 MiB `MAX_WEBRTC_FRAME_BYTES` bound is sent in parts ([Single-pass messages in parts](#single-pass-messages-in-parts)), so a legitimate reply is never rejected mid-exchange.
- - -> Over file-sync each message is one frame; over WebRTC one past the per-frame bound is sent in parts ([PROTOCOL.md, Single-pass messages in parts](PROTOCOL.md#single-pass-messages-in-parts)).
- - -> **Where a browser is a party the real ceiling is a memory budget, fixed and non-configurable.**
- - -> Its value and its derivation from the rounds measured in a browser tab are specified there, under the single-pass dataset ceiling.
- - -> **Between two command-line parties over WebRTC no value-slot budget applies.**
- - -> The limits are the derived caps, each message past the per-frame bound sent in parts, the set maximums, and the memory check each party makes at the terms exchange on the message it reads and the message it sends ([Memory a message in parts takes](#memory-a-message-in-parts-takes)), which `--allow-memory-shortfall` turns into a warning.
- - -> The receiver holds each part to the per-frame bound and the whole message to its derived cap, so a legitimate single-pass message is never rejected by the WebRTC bound.

- - -> **A frame after the reply.**

- - -> **The single-pass reply in parts.**
- - -> Single-pass message 2 in parts is its setup, response and tail sent back to back, with no receive between ([PROTOCOL.md, Single-pass messages in parts](PROTOCOL.md#single-pass-messages-in-parts)).
- - -> Between two command-line parties no value-slot ceiling bounds it, so it can be longer than the crossing; the reply cap the agreed counts derive bounds it instead.
- - -> While the receiver of the reply reads it, it holds the queue's byte bound to at least the frames that cap takes, and restores the bound the queue was built with once the reply is read (`holdInboundQueueBytes`, `packages/core/src/connection/messageConnection.ts`).
- - -> The frames are `floor((cap - 8) / part) + 3`, where `part` is the set bytes one part holds and the three sets together take at most three parts more than their bytes fill whole, and one frame more for the frame in hand, each at the stated per-frame bound (`singlePassReplyQueueBytes`, `packages/core/src/psi/link.ts`).
- - -> The bound is never lowered below the default.
- - -> It passes the default only when the reply's sets fill four parts or more, and there it is under twice the reply cap, which the terms-exchange memory check weighs at three times the cap ([Memory a message in parts takes](#memory-a-message-in-parts-takes)), so the raised bound admits nothing that check did not weigh.
- - -> For a browser party the value-slot ceiling of 8,388,608 holds the reply cap to 696,254,722 bytes, which takes five frames and the frame in hand, within the browser bound of six.
