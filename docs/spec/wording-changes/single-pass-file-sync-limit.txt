- - -> **The limits over file-sync.**
- - -> `sftp` and `filedrop` have no value-slot budget: neither `linkViaSinglePassPSI` nor `prepareForExchange` applies `MAX_SINGLE_PASS_CELLS` there.

- - -> What limits a run is:
- - -> **One message file.**
- - -> The request and the reply are each one frame, held to `MAX_FRAME_SIZE_BYTES` (536,870,888 bytes) as the file they are written in, unchanged by the derived cap, which only tightens it.
- - -> The counts bound a frame from above without deciding its size, so a frame's real size is what is weighed, once masking has built it: a frame too large for the file is refused before the write, with its size in the message, and the partner is sent `PSI_SET_TOO_LARGE_ABORT_REASON`.
- - -> A run that fits its file is not refused for what its counts could have reached.
- - -> At 25 keys and 70 effective keys, 150,000 records sending to 5,000 derive a cap of 491,000,256 bytes.
- - -> **One PSI set.**
- - -> `MAX_PSI_DECODE_ELEMENTS`, as for every set.
- - -> **Memory, at the terms exchange.**
- - -> Before either party masks anything, a receiver refuses a run when the sender's index table alone, `4 * keyCount * senderRows` bytes, cannot fit in `process.availableMemory()` at that moment.
- - -> No choice of values reduces that table, so the refusal blocks only a run that could not finish.
- - -> `senderRows` is the declared record count, or that count over the fan-out factor where the factor divides it.
- - -> The refusal sends `PARTNER_SET_OVER_CAPACITY_ABORT_REASON`, and `--allow-memory-shortfall` turns it into a warning.
- - -> Every other run proceeds, and the operator is told at the terms exchange the partner's declared value slots and the run's worst-case memory and time, at the rates measured below.
