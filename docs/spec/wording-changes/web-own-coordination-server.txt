# A browser's own coordination server, set in relay settings, is named by the
# invitations it creates; an inviter registers at the server its invitation
# or saved record names, so a change to the setting moves nothing sent or saved
# until the inviter re-invites, which names the browser's current server and
# stores it on the record.
- On the webrtc re-run path the document's `server` locator is what an acceptor's later run dials. -> On the webrtc re-run path the document's `server` locator is what both sides' later runs reach.
- - -> Each record saved the `host`, `port` and `path` of the invitation: the acceptor's from the invitation it accepted, the inviter's from the invitation it created or last re-invited with.
- The acceptor's record saved the `host`, `port` and `path` of the invitation it accepted, and every re-run dials that address and no other -- not the page's location, not its own deployment's setting -- so two parties on different deployments keep reaching each other. -> Every re-run reaches that address and no other -- not the page's location, not its own deployment's setting, not the browser's own coordination server setting -- so two parties on different deployments keep reaching each other, and a change to that setting alone moves no saved exchange.
- - -> The acceptor dials the address and the inviter registers there.
- The inviter registers at its own deployment's signaling address and does not read the locator. -> -
- - -> An inviter's re-invite does not read the saved address.
- - -> It names the coordination server a new invitation from that browser names: the browser's own setting where it is set and readable, the deployment's address otherwise (see [WEBRTC_TRANSPORT.md](WEBRTC_TRANSPORT.md#the-browser-partys-own-signaling-address)).
- - -> The write that stores the fresh secret replaces the document's `server` with that endpoint's `host`, `port` and `path`, so the inviter's later runs register where the partner's accept of the re-invite dials.
- - -> A re-invite is therefore how an inviter moves a saved exchange to another server, and it recovers an inviter's record whose saved address is refused.
- A browser party resolves one address for the signaling server its own deployment uses, and every place that needs it reads that one value: where an inviter registers, on a fresh invitation and on a saved exchange's later runs, and the endpoint its invitation names. -> A browser party resolves one address for the signaling server its own deployment uses.
- - -> A new invitation names this browser's own coordination server where the user set one on the relay settings page, and the deployment's address otherwise.
- - -> The browser setting is kept in the browser's storage for the page's origin, and is held to the rule the published file's reader applies (`publishedSignalingServerURL` in core) with the page's scheme, a port from 1 to 65535, and no character the URL parser stores percent-escaped, such as a space in the path; an address failing it is refused when entered, and a stored one failing it on a later read names no server.
- - -> Its address states the port, the scheme's default included.
- - -> A web app's `http:` or `https:` address is refused, since the hosted build's `_headers` gives its published file ([below](#the-published-coordination-server)) no `Access-Control-Allow-Origin` header for a page on another origin to read it under.
- - -> An inviter registers at the endpoint its invitation names.
- - -> A saved exchange's later runs register at the endpoint the inviter's record stored from that invitation, after the validation an acceptor's dial applies (below).
- - -> A re-invite from the record names the endpoint a new invitation names, from the browser setting or the deployment's address, and stores it on the record, where the inviter's later runs then register ([MANAGED_EXCHANGE_RECORD.md](MANAGED_EXCHANGE_RECORD.md#role-a-local-side-field-not-the-document)).
- - -> A change to the browser setting therefore moves no invitation already created, and moves a saved exchange only when its inviter re-invites from it.
- With the setting unset, the endpoint names the `port` only when the page's is not the scheme's default. -> With neither setting set, the endpoint names the `port` only when the page's is not the scheme's default.
- With the setting set, the endpoint always names the `port`, the scheme's default included, so the port an acceptor dials never depends on its own page. -> With the build setting or the browser setting set, the endpoint always names the `port`, the scheme's default included, so the port an acceptor dials never depends on its own page.
- The console build (`VITE_DEPLOYMENT_PROFILE=console`) resolves no signaling address, whatever the setting holds: its server serves no signaling and its origin is loopback. -> The console build (`VITE_DEPLOYMENT_PROFILE=console`) resolves no signaling address, whatever either setting holds, and offers no browser setting: its server serves no signaling and its origin is loopback.
- The setting's `ws:` or `wss:` URL, its path ending in `/`. -> The setting's `ws:` or `wss:` URL, its path ending in `/`, never a browser's own coordination server, so a CLI given the app's address dials the build's server whatever a browser on it set.
