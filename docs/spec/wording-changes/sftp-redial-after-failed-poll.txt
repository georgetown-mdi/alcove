# The SFTP pins state that a failed dial can reject before its connection
# closes, that the ssh2 Client's 'close' event rather than the socket's flags
# tells whether that close is still to come, and that the adapter waits that close
# out before reporting.
- - -> A failed dial of any kind can reject before its connection has closed.
- - -> Measured against the pinned stack, a dial whose key exchange the server refuses rejects before the `Client`'s `'close'` for its connection, and a dial issued on the same `Client` before that `'close'` lands fails as well, against a server that accepts it.
- - -> The socket cannot tell whether that `'close'` is still to come: Node sets a socket's `closed` and `destroyed` flags synchronously inside `destroy()`, before its `'close'` event fires, and a dial that fails on its handshake timeout or on a reset connection rejects over a socket already in that state.
- - -> So the adapter subscribes once to the `Client`'s `'close'` before each dial, removes that listener however the dial settles, and takes that event as the only reading of whether the dial's `'close'` has been delivered.
- - -> After a failed dial whose `'close'` it has not seen, it waits for that `'close'`, destroys the socket only if it does not come within the same bound as the closes above, and waits the destroy's `'close'` out on that bound too, all before it reports the failure.
- - -> A socket exposing no `destroy()` at that point is left to the operating system under a warning, once the wait for its own `'close'` has run.
- - -> A socket the dial did not open, such as the live session's that a refused `connect()` leaves in place, is left alone.
- - -> Each assumption is a check in `apps/cli/test/integration/sftpStackPremises.test.ts`: a dial issued before that `'close'` fails, a destroyed socket reads `closed` before the `Client`'s `'close'` fires, a dial that fails on its handshake timeout or on a reset connection rejects over a socket already `closed` with that `'close'` still to come, and a dial issued after that `'close'` connects.
- - -> `apps/cli/test/integration/sftpKexRedialPolicyFlip.test.ts` drives the adapter's cycle-start re-dial at once after a refused one and requires it to connect.
- - -> Two readings stay open: a `'close'` arriving late from an earlier connection, after that connection's own bounds have run out, is counted as the failed dial's own, so the new socket is left open and the next dial on it runs on its own deadline; and a destroyed socket whose `'close'` does not arrive within the bound is reported without a warning, as the release's forced close is.
