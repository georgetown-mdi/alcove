A `"too-large"` failure records a refusal to send a PSI set of this party's own over the most values its partner stated it can receive, or over the most any receiver admits ([PROTOCOL.md](PROTOCOL.md#the-receive-ceiling)): the first-round check, before connecting against the most any receiver admits and after the terms exchange against the partner's figure, which refuses before any set is sent, including a set whose size that check could not count; and a later round, which refuses its set before sending any of it. It is benign and outside the desync/attack framing. The entry holds no size, as no entry holds a count: the next visit and the between-visit notification state the remedy, and the bound where the entry names one, and only a live launch shows the refusal's own message, with the size where the check counted one. The set over the bound is this party's own, so both surfaces state one remedy: split your input into smaller exchanges. An entry an earlier build wrote may also hold `tooLargeSetOwner` (`"local"` \| `"partner"`); a reader drops it and states that same remedy. A `"too-large"` entry also holds `tooLargeBound` (`"partner-ceiling"` \| `"webrtc-message"`), which bound the refusal found the set over: the most values the partner stated it can receive, or, in an entry an earlier build wrote, the bytes one WebRTC message holds. Both surfaces name that bound, and its figure for the second; an entry without it names no bound. Where the first-round check could not count the set at all, the entry holds `setUncounted` instead, admitted only as `true` and omitted rather than written `false`: no bound was found crossed, so both surfaces say the set could not be counted and name no bound, and a reader states that even beside a `tooLargeBound`. Why the count failed is in the live launch's message only, as no entry holds free text. A `"partner-set-too-large"` failure records a run stopped over a partner's set for a linkage key with more values than `BROWSER_PSI_SET_MAX_ELEMENTS` ([PROTOCOL.md](PROTOCOL.md#the-receive-ceiling)), at one of two points, both after sets of this party's may have been sent -- its sets of earlier rounds, and a sender's setup for the same round: the partner's abort in place of its set, stating the fixed reason "a PSI set is too large to send", or this browser's refusal at the first part of the partner's set inside a round. An entry an earlier build wrote may record a refusal at the terms exchange, before any linkage key moved. Both current cases hold `refusedInRound`, admitted only as `true` and omitted rather than written `false`; the run history states that nothing was disclosed for an entry without it, and for an entry with it states that the run did not complete and that whether any data reached the partner is not recorded. It is benign and outside the desync/attack framing, and the entry holds no count: both surfaces state the cause and the remedy, the command-line application or a smaller input on the partner's side. A `"partner-refused-set"` failure records the partner's abort in place of its first set stating the fixed reason "a PSI set was refused before sending": the partner's run refused the set for a cause other than its size. It is met at the same point, after sets of this party's may have been sent, so it always holds `refusedInRound` and the run history states the uncertain line. It is benign and outside the desync/attack framing; the reason names no cause, so both surfaces say the partner's run refused and to ask the partner. A `"partner-storage"` failure records the partner's abort stating the fixed reason "the partner could not save the next shared secret" on a run that stored the next secret itself, which only the initiator does before it ([SHARED_SECRET_ROTATION.md](SHARED_SECRET_ROTATION.md#the-rotation-at-the-terms-exchange)), so the two parties now hold different secrets. It is met after the terms exchange, after sets of this party's may have been sent, so the run history states the uncertain line. The run's rotation write kept the secret the run used as `previousSharedSecret`, so the next run can still meet the partner. Both surfaces say that the partner could not save the new secret, that this device kept the secret the partner still holds, so the next run can still reach the partner, and that a re-invite is the step if runs keep missing the partner or stopping, and offer the re-invite. It raises a [standing condition](#the-standing-condition), which keeps that state past the runs after it until one succeeds. A `"partner-refused-terms"` failure records the partner's abort at the terms exchange naming linkage terms that differ from the partner's own (`termsDifferenceRefusedBy` reading `"partner"`, [PROTOCOL.md](PROTOCOL.md#a-terms-change-at-the-terms-exchange)), before any linkage key or data moved. It is benign and outside the desync/attack framing, and the run history states that nothing was disclosed. Both surfaces state the refusal and its remedy, terms agreed on with the partner through a [terms update](#a-terms-update) made or applied on the exchange's page, and only a live launch shows the terms that differ, as no entry holds free text. An entry an earlier build wrote for the same refusal holds `"transport"` and reads as the transport state. A `"partner-protocol-refusal"` failure records this party's refusal of what the partner sent as not following the exchange protocol (`isPartnerProtocolRefusal`, `packages/core/src/failureClass.ts`): a `PartnerProtocolRefusalError`, which only the sites refusing the partner's frames raise, such as a PSI setup out of ascending order, an unreadable response, a terms message missing a required field, or another protocol version ([PROTOCOL.md](PROTOCOL.md#the-single-pass-dataset-ceiling-receiver-memory-and-masking-compute)). The partner's own abort, a refusal over the linkage terms, and a refusal whose fault could be either party's are not among them. It can be met at any point from the version hello on, after sets of this party's may have been sent, so the run history states the uncertain line. A refusal of another protocol version is met before the key exchange authenticates anything, so whoever passes frames between the parties, the signaling server included, can make an attempt end in this kind, and can choose which side a live launch names as running the older version ([KEY_EXCHANGE.md](KEY_EXCHANGE.md#p-256-authenticated-key-exchange), The version hello, "A limit."). It is benign and outside the desync/attack framing. The entry does not hold whether the refusal was over a version mismatch, so both surfaces state that the partner's data did not follow the exchange protocol and that the two parties check which version each runs, the one running the older version updating; only a live launch shows what was refused, and for a version mismatch which party runs the older version where the partner's version is an integer, as no entry holds free text. An entry an earlier build wrote for the same refusal holds `"transport"` and reads as the transport state. A `"partner-stop-at-matching-start"` failure records this party's refusal of a partner whose first message of matching was its local-fault abort (`isPartnerStopAtMatchingStart`, `packages/core/src/failureClass.ts`), which a partner on an earlier build sends and a partner on this build sends when its run faults before its first still-working frame ([PROTOCOL.md](PROTOCOL.md#the-still-working-frame)). It is recorded apart from `"partner-protocol-refusal"`, and checked before it, because nothing shows which party runs the older version. It is met after sets of this party's may have been sent, so the run history states the uncertain line. It is benign and outside the desync/attack framing. Both surfaces state that the partner's run stopped, and that the two parties make sure each runs the current version, then run the exchange again. An entry an earlier build wrote for the same refusal holds `"partner-protocol-refusal"` and is treated as that state. A `"partner-stopped-responding"` failure records a run whose partner sent nothing for the partner-silence bound during matching ([WEBRTC_TRANSPORT.md](WEBRTC_TRANSPORT.md#the-wait-through-a-partners-psi-step)). It is met after sets of this party's may have been sent, so the run history states the uncertain line. It is retried as `"transport"` is, and the next visit says that the partner stopped responding and to ask the partner to check their run. An entry an earlier build wrote for the same failure holds `"transport"` and is treated as the transport state. A `"shard-stalled"` failure records a run whose split encryption stopped on a PSI worker that reported no progress for `BROWSER_PSI_SHARD_PROGRESS_TIMEOUT_MS` ([PROTOCOL.md](PROTOCOL.md#the-single-pass-dataset-ceiling-receiver-memory-and-masking-compute)), a fault on this device. It is met during matching, so the run history states the uncertain line. It is retried as `"transport"` is, and the next visit states the stall and to run the exchange again. An entry an earlier build wrote for the same failure holds `"transport"` and is treated as the transport state. An attended run refused for its saved signaling address is recorded as a `"transport"` failure, with no kind of its own; the refusal alert, which offers no retry, is shown only in the run that met it, and a later visit shows the generic transport alert. `"terms-shortfall"`, `"too-large"`, `"partner-set-too-large"`, `"partner-refused-set"`, `"partner-storage"`, `"partner-refused-terms"`, `"partner-protocol-refusal"`, `"partner-stop-at-matching-start"`, and `"custody-unreadable"` are the failure kinds a surface must **not** present as retryable: the same input falls the same way short of the same keys and builds the same too-large set, the same partner input is refused at the same ceiling, the partner's run refuses its set the same way, the partner's save must work before a run completes, which the next scheduled run tries under the secret this device kept, the partner refuses the same terms until the two parties agree on them, the partner's run sends the same nonconforming data, a partner on an earlier build stops at matching the same way until it updates, and a partner on this build whose run faulted shows its reason only on its own side, and a run reads the same unusable stored copy every time, so the remedy is the operator's, not another attempt's. A record written before a value was added to either enum still reads -- an entry with `"input"` for a shortfall loads and tiers as the generic input state; the converse is the reader-rejects-unknown rule's consequence, an artifact with an outcome or kind this reader does not know being refused whole rather than read with the value dropped. Widening either enum therefore leaves `schemaVersion` where it is: the version moves for a member an older build would read past and lose state by, not for a value it refuses, and not for `singleColumnInput`, `tooLargeBound`, or `setUncounted`, whose absence is the copy every build states (the agreed-keys copy, and a too-large set with no bound named): a build that does not know one gives worse advice rather than reading a state wrongly. `refusedInRound` is outside that reasoning: a build that does not know it reads past it and states that nothing was disclosed. A **re-invite clears `lastRun`** in the same rotation transaction that advances the fresh secret: the re-invite is the recovery for the failure the entry recorded, so leaving it would re-derive a consumed tier at the next visit -- and once the import marker is cleared alongside, a stale `"auth"` failure would re-derive as the attack tier rather than the benign import one. A `"succeeded"` entry holds `healedCutRotation`, admitted only as `true` and omitted rather than written `false`, where either side's key exchange used its [previous secret](SHARED_SECRET_ROTATION.md#the-previous-secret): the run healed one cut before the partner saved the rotated secret. The run states the heal note while it runs, and the run history states it beside the entry, the ahead side's copy on an acceptor and the behind side's on an inviter, so that a heal cannot hide a copy of the exchange running elsewhere. A build that does not know it reads past it and shows the run as an ordinary success. A `"storage"` entry holds `nextRunHeals`, admitted only as `true` and omitted rather than written `false`, where the partner saved the next secret first and completed the key exchange under its [previous secret](SHARED_SECRET_ROTATION.md#the-previous-secret), which shows that it keeps one: the next run can still reach the partner under the secret this run used. The standing condition and the saved-exchanges list read it at later visits and name the next run, with the re-invite for runs that keep failing, until a later entry records a failed-closed handshake, a failed save without it, or a success; without it they name the re-invite. A build that does not know it reads past it and names the re-invite, which is worse advice rather than a wrong reading, so `schemaVersion` does not move for it. A successful run instead advances `lastRun` to `"succeeded"`; two recoveries drop it: the re-invite, and an apply of a partner's terms change, which drops a `"terms-change"` entry for the same reason ([A refused terms change](#a-refused-terms-change)). Which of two runs' entries the store keeps is [Recording a run outcome](#recording-a-run-outcome).
