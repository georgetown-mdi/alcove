- - -> `shared-secret-unusable` | `problem` (one of `malformed`, `expired`), and for `expired`: `expires` (non-empty string) and `stage` (one of `before-handshake`, `before-next-saved`) | This party's shared secret cannot be used: it is not a base64url-encoded 32-byte value (`malformed`), or its expiry, `expires` as the key file states it, had passed before the handshake (`before-handshake`) or before the next secret was saved (`before-next-saved`, [SHARED_SECRET_ROTATION.md](SHARED_SECRET_ROTATION.md#expires-enforcement-and-the-expiring-soon-advisory)). An `expires` value holding a control byte reaches the console escaped twice, so its marker reads `\\x0a` rather than `\x0a`; a valid expiry holds none.
- - -> `partner-stopped-at-matching` | none | The partner's first message of matching was its local-fault abort: a partner on an earlier build, or one whose run stopped before matching started ([PROTOCOL.md](PROTOCOL.md#the-still-working-frame)).
- - -> `message-write-unconfirmed` | `failure` (one of `rename-unconfirmed`, `write-incomplete`, `sequence-spent`), and for `sequence-spent`: `seq` (non-negative integer) | On a file-sync connection, a message may or may not have reached the partner: renaming its file into place was cut off and could not be confirmed (`rename-unconfirmed`), or its direct write did not complete (`write-incomplete`). `sequence-spent` is the refusal of a later send, as sequence number `seq` was spent on such a write.
- - -> `shared-name-at-entry` | none | On a file-sync connection, the exchange directory held a hello file whose id fits this party's own `peer_id` at entry, which this run takes for its own leftover: the likely cause is that both parties set the same `peer_id`.
