# The browser's key reaches the pool's helper workers, never the page.
- The worker loads its own WASM engine (`@openmined/psi.js/psi_wasm_worker`, the worker-context sibling of the main thread's `psi_wasm_web`) and the exchange's secret key is generated inside it (by `servePsiWorker`'s `createWithNewKey`) and never leaves it; only bytes, value lists, index lists, the processed-element count a long operation reports part-way through, and a failure's message with whether the engine raised it cross the boundary, so the exchange result is byte-identical to the in-process path. -> The worker loads its own WASM engine (`@openmined/psi.js/psi_wasm_worker`, the worker-context sibling of the main thread's `psi_wasm_web`) and the exchange's secret key is generated inside it (by `createWithNewKey`) and never posted to the page, which only connects the workers of the pool below; only bytes, value lists, index lists, the processed-element count a long operation reports part-way through, and a failure's message with whether the engine raised it cross the boundary, so the exchange result is byte-identical to the in-process path.
# A pool worker that makes no progress ends the run on its own message.
- Every other failure ends the run on its own message: a refusal the engine names past the deserialization (the setup that holds no Raw data structure, and a request whose reveal flag disagrees with this party's mode, PSI-C, above), an engine precondition the calling party broke, a fault in the PSI worker the engine runs behind (a disposed engine, a caller breaking the worker's lockstep rule, a worker that crashed or exited under the call), and a step stopped because the connection to the partner ended, which ends the run on that connection's error. -> Every other failure ends the run on its own message: a refusal the engine names past the deserialization (the setup that holds no Raw data structure, and a request whose reveal flag disagrees with this party's mode, PSI-C, above), an engine precondition the calling party broke, a fault in the PSI worker the engine runs behind (a disposed engine, a caller breaking the worker's lockstep rule, a worker that crashed or exited under the call, a browser pool worker that made no progress for the pool's timeout), and a step stopped because the connection to the partner ended, which ends the run on that connection's error.
# The browser's PSI worker pool: what it splits, how many workers, the macOS
# bound, the key path, the merge in the primary, the failure rules, the
# progress timeout and its basis, and the single-threaded path measured
# against the pool, in time and in heap.
- - -> **The browser runs its masking across a pool of PSI workers.**
- - -> The web app creates its request, and answers its partner's request, across several PSI workers at once: each masks a contiguous part of the set under the round's one key, and the primary merges their outputs by the chunk rules above (`ShardedPsiEngine`, `packages/core/src/psi/shardedPsiEngine.ts`, run in the primary by `apps/web/src/psi/workers/psiCryptoWorkerProgram.ts`; the pool is `apps/web/src/psi/workers/psiWorkerPool.ts`).
- - -> Nothing on the wire changes, and the pool needs no cross-origin isolation headers and no `SharedArrayBuffer`: each worker has its own WASM instance and memory, and the workers exchange only structured-clone messages.
- - -> **Which operations.**
- - -> Creating the request and answering the partner's request are split.
- - -> Creating the setup and the match run on one worker, the primary, so a count-only match counts the whole response once: counts summed over parts would count a value the partner repeated once per part.
- - -> A set under 2,048 elements, two shards of `PSI_SHARD_MIN_ELEMENTS` (1,024), runs on the primary alone.
- - -> **The output is one engine's.**
- - -> The merged request and response are byte-identical to one engine's under the same key.
- - -> `packages/core/test/psi/shardedPsiEngine.test.ts` holds this at 1 to 5 engines in both modes on both backends, `apps/web/test/unit/psi/psiWorkerPool.test.ts` over the worker program against an engine built from the pool's key, and `apps/web/test/browser/psiCryptoWorker.test.ts` over real workers in Chromium, running a test-only worker entry whose keys are fixed, against an engine on the page built from the same key.
- - -> **How many workers.**
- - -> `browserPsiShardCount` (`apps/web/src/psi/workers/psiShardPolicy.ts`): the logical core count `navigator.hardwareConcurrency` reports, at most `BROWSER_PSI_SHARD_CAP`, 4, the count the measurements recommend ([wasm-parallel-evaluation.md](../notes/wasm-parallel-evaluation.md#recommendation)), and one where the count is missing or unusable.
- - -> **macOS runs one worker.**
- - -> A browser any of whose platform reports names a Mac runs the single-threaded path, one worker, because Chrome's renderer crashed in 3 of 123 sharded runs there ([wasm-parallel-evaluation.md](../notes/wasm-parallel-evaluation.md#decision-2026-10-18-the-macos-bound)).
- - -> `apps/web/test/unit/psi/psiShardPolicy.test.ts` tests the platform check, and `psiWorkerPool.test.ts` that the engine factory then starts one worker.
- - -> **The key goes from worker to worker.**
- - -> The primary generates the key.
- - -> For each helper the page creates a MessageChannel and transfers one end to the primary and the other to the helper, keeping neither; the primary posts each helper its own transferred copy of the key over that channel.
- - -> A primary takes only the first key-ports message it is given, before any request and with a port for each helper its seed names, and sends a refusal down the ports of any other, so the one-worker path's primary, seeded with no helpers, sends its key to no port.
- - -> A helper builds its engine only from the key that arrives on its one port, generates none, and takes its parts from the primary over that port alone, refusing every request the page sends it.
- - -> `psiWorkerPool.test.ts` checks over real channels that no message between the page and a worker contains the key.
- - -> **A helper that fails its setup leaves the run on the primary.**
- - -> A helper reports to the page once its engine is built from the key.
- - -> The first request the pool creates or answers waits for every helper's report, up to the progress timeout below.
- - -> If any helper failed or has not reported, every helper is terminated and the run goes on the primary alone, the single-threaded path.
- - -> A primary that fails to start sends each helper a refusal in place of the key, so the wait ends at once.
- - -> **The primary merges the parts.**
- - -> The page sends the primary the whole operation and receives only the merged message, as on the one-worker path.
- - -> Once every helper has set up, the page tells the primary so, and the primary splits the set, sends each helper its part over the channel its key took, masks its own part last, so that every helper has its part before the primary's thread is taken, and takes each helper's output back on the same channel.
- - -> `psiWorkerPool.test.ts` checks that the only result a split posts to the page is the merged message.
- - -> **A worker that stops fails the run.**
- - -> A fault in any worker during a split operation fails that operation, and so the run, at once, by the path a fault in one worker takes: a helper's failed reply, or its report of a part it could not read, reaches the primary, and a helper's error event the page.
- - -> No worker is retried or started again.
- - -> **The progress timeout.**
- - -> A worker of a split operation that reports neither a processed count nor its result for `BROWSER_PSI_SHARD_PROGRESS_TIMEOUT_MS`, 33 minutes, is treated as stopped, and the run fails with `Encrypting the data made no progress for 33 minutes.
- - -> Run the exchange again.`
- - -> This catches a worker that ends with no error event.
- - -> The primary times each helper, and the page times the primary, whose count rises with every part's.
- - -> The primary's own part holds its thread until it ends, so a part that ends restarts the timers of the parts still running, whose counts may have waited behind it.
- - -> The longest measured gap between one worker's consecutive progress events, below, was 0.58 ms per element of the chunk it was masking.
- - -> A split operation at `BROWSER_PSI_SET_MAX_ELEMENTS`, 8,388,608, gives each of at least two workers at most 4,194,304 elements in five chunks of at most 838,861, about 487 s at that rate.
- - -> The timeout is four times that, rounded up to whole minutes; masking is linear in the element count (above).
- - -> Measured 2026-10-20 in the development container (aarch64 Linux, 10 CPUs) in Playwright's Chrome for Testing 156.0.8078.4 run headless: the pool over the web app's own worker bundle, 100,000 values, identifier-revealing, the two parties in one page.
- - -> The harness was a local script, not kept in the tree.
- - -> Other work ran beside it, at a one-minute load average of 2.6 to 13:
- - -> Workers | Create the request | Answer the request | Longest gap between progress events
- - -> 1, the single-threaded path | 49.9 s, 47.7 s | 37.4 s, 37.5 s | 10.4 s over a chunk of 20,000
- - -> 2 | 24.9 s | 19.8 s | 5.3 s over 10,000
- - -> 4 | 12.3 s, 13.7 s | 9.8 s, 10.1 s | 4.8 s over 8,333
- - -> The heap each round grew, in the same harness with `--enable-precise-memory-info`, measured the same day at a one-minute load average of 1.1 to 3.3: the page's `usedJSHeapSize`, and each worker's used heap as the DevTools protocol reports it, sampled through the operation, as its peak less its start.
- - -> The table is the pool as built, the primary merging.
- - -> Where the page merged instead, decoding the partner's whole request and each worker's output itself, its heap grew by 37 to 38 MB creating the request and 57 MB answering it on four workers, in the same times.
- - -> Workers | Page, creating the request | Page, answering it | Primary, creating | Primary, answering | Each helper, creating and answering
- - -> 1, the single-threaded path | 4 MB | 4 MB | 33 MB | 56 MB | none

- - -> So a pooled round grows the page's heap about as the single-threaded path does, and the primary's about as that path's one worker's, the path measured to complete at `BROWSER_PSI_SET_MAX_ELEMENTS` (above); no pooled round that large has been measured.
