- - -> The count-only rounds
- - -> **Every agreed key, in order, every round full-size.**
- - -> No round's set is narrowed by an earlier round's matches, as a `psi` cascade round's is: neither party learns which of its own records matched, so there is nothing either could remove on the wire.
- - -> Every round includes every record of both parties, and the cascade's removal takes place inside the receiver's computation of the count ([Computing the count](#computing-the-count)).
- - -> **Roles.**
- - -> Below, `n_R` is the receiver's declared record count and `n_S` the sender's, both as the terms exchange states them.
- - -> **One element per record, in record order.**
- - -> In every round each party's set has exactly one element for each of its records, so its element count is its declared record count, the figure the [first-round count at the start](#the-memory-ceiling-and-the-csv-intake-cap) and the count against the partner's [receive ceiling](#the-receive-ceiling) weigh for a count-only round:
- - -> The receiver's request lists its records in its own record order, the same order in every round, so position `i` of every round's request is the receiver's record `i`.
- - -> The sender's setup has one element for each of the sender's records.
- - -> Otherwise the element is a dummy.
- - -> A dummy is 32 bytes from the platform's cryptographically secure random generator, written as 64 lowercase hexadecimal characters, drawn anew for each record in each round and never reused.
- - -> It contains no colon, so it never equals a round value, and two dummies coincide only with negligible probability.
- - -> On the wire it cannot be told from a real element.
- - -> **Round values are separated by round.**
- - -> Both parties apply it to every real element before encryption.
- - -> A party's PSI key may serve every round of the exchange, so without the prefix a value appearing under two keys would encrypt to the same element in both rounds, and the receiver, which knows which of its own records share a value across keys, could link those two rounds' slots to those records.
- - -> **The sender's permutation.**
- - -> Once the terms exchange has given it `n_R`, the sender draws one permutation `pi` of the positions `0` to `n_R - 1`, uniformly at random from the platform's cryptographically secure random generator.
- - -> In every round it processes the receiver's request in the library's revealing mode, then reorders the response under `pi` before it sends any part of it: slot `s` of the response as sent is the element at position `pi(s)` of the response the library returned.
- - -> The same `pi` serves every round of the exchange.
- - -> It MUST NOT be sent, written to disk, or logged, and MUST be discarded when the exchange ends, whether it completes or fails; each run of an exchange draws its own.
- - -> The library returns a revealing-mode response in request order, so slot `s` of every round answers the receiver's record `pi(s)`.
- - -> A slot is therefore a stable pseudonym of one receiver record for the whole exchange, and only the sender, which holds `pi`, can map it back.
- - -> **The sender's pseudonyms and the index table.**
- - -> The sender draws a second permutation, `sigma`, of its own records `0` to `n_S - 1`, under the same rules as `pi`; `sigma(j)` is the pseudonym of its record `j`.
- - -> The library sorts a setup by ciphertext, and reports the input index at each setup position (its sorting permutation).
- - -> So in each round, after building the setup, the sender sends that round's **index table**: `n_S` entries, entry `p` being `sigma` of the record whose element is at position `p` of the setup as sent.
- - -> The table is a binary frame of `n_S` little-endian `Int32` values, so `4 * n_S` bytes, and it is a permutation of `0` to `n_S - 1`.
- - -> A matched setup position therefore names a sender pseudonym that is the same in every round, without naming a sender record.
- - -> **The frames of one round.**
- - -> **sender -> receiver** -- the setup message over `n_S` elements, each encrypted once under the sender's key, as a `Raw` data structure, in parts ([A PSI set is sent in parts](#a-psi-set-is-sent-in-parts)).
- - -> **sender -> receiver** -- the round's index table, one binary frame.
- - -> **receiver -> sender** -- the request over `n_R` elements, each encrypted once under the receiver's key, in parts.
- - -> **sender -> receiver** -- the response: the request re-encrypted under the sender's key and reordered under `pi`, in parts.
- - -> Each round sends `35 * (n_S + 2 * n_R)` bytes of encrypted elements and `4 * n_S` bytes of index table, whatever the key's coverage.
- - -> After the last round comes the count-report leg where the entitlement calls for it ([Count reporting and entitlement](#count-reporting-and-entitlement)).
- - -> **Each frame's size is checked against the declared counts.**
- - -> The receiver MUST refuse a setup whose element count is not `n_S`, and an index table whose length is not `n_S` or which is not a permutation of `0` to `n_S - 1`.
- - -> The sender MUST refuse a request whose element count is not `n_R`.
- - -> Each refusal is a protocol error raised before the round goes on ([Partner-supplied index tables are checked against local state](#partner-supplied-index-tables-are-checked-against-local-state)), and a response is held to its request's element count as every response is.
- - -> These checks hold a conforming partner to the padded shape.
- - -> They do not stop a party choosing its own inputs ([Threat-model scope of the count-only claim](#threat-model-scope-of-the-count-only-claim)).
- - -> **Revealing mode, with Alcove applying the permutation.**
- - -> Both parties MUST construct their base-function objects with the library's reveal-intersection flag set, as a `psi` run does, and MUST NOT run the library's cardinality mode, the flag cleared, for a count-only round.
- - -> In that mode the library's server sorts each round's response by ciphertext and takes no permutation, so no order can be held across rounds, and its match returns only a size.
- - -> The revealing match returns, for each response element it matches, that element's position in the response as received and the setup position it equals; under `pi` the position is a slot.
- - -> Two properties the cardinality mode's flag would give are therefore provided elsewhere:
- - -> **The flag does not tell the algorithms apart.**
- - -> Both a `psi` and a `psi-c` round set it, so the library's own mode check does not refuse a partner running the other algorithm.
- - -> That agreement is the agreed terms': `algorithm` is a mandatory-consistency term, compared at the terms exchange and again at the agreed-terms run boundary before any round (`resolveCountOnlyRun`, `packages/core/src/exchange.ts`), so a `psi` party and a `psi-c` party never reach a round together.
- - -> **The receiver's engine, not the library, withholds the matches.**
- - -> The library hands the revealing match's pairs to whatever calls it; the receiver's engine keeps them (below).
- - -> **The receiver's engine returns only the count.**
- - -> A count-only receiver's engine takes each round's setup, index table and response, keeps every round's matched pairs inside the engine across the exchange's rounds, and returns one figure, the count, after the last round.
- - -> It MUST NOT return to its caller, report as progress, or log an association table, a slot, a pseudonym, a per-round or running match count, or any other per-record result; its progress reports count elements processed and nothing else.
- - -> Its identifier-revealing operations, and any operation returning a per-round result, are refused in count-only mode.
- - -> This holds on both backends, and whether the engine runs in process, in a worker, or across a pool of workers.
- - -> Nothing the engine keeps is beyond what the receiver's software could derive from the frames with its own key, but keeping all of it inside the engine is what makes "the operator sees only the count" a property of the software rather than of each of its callers.
- - -> The probabilistic structures the library also offers -- a Bloom filter and a Golomb-coded set -- admit false positives, which here would be spurious pairs in the count.
- - -> Computing the count
- - -> The count is the size of the one-to-one cascade's association table in the permuted space, computed by the receiver's engine:
- - -> **The round's pairs.**
- - -> In round `k`, for each response slot `s` whose decrypted element equals the setup element at position `p`, the engine forms the pair (`s`, `T_k[p]`), `T_k` being that round's index table.
- - -> Each party's elements in a round are distinct, so a slot or a pseudonym occurs in at most one of the round's pairs; a round whose pairs repeat either is refused as an internal fault.
- - -> **The replay.**
- - -> Two sets start empty: the accepted slots and the accepted pseudonyms.
- - -> A round's pairs are disjoint, so their order within the round does not change the result.
- - -> **The count** is the number of pairs accepted.
- - -> The replay is symmetric in the two parties, so the count does not depend on which party is the receiver, and it is at most the smaller of the two record counts.
- - -> **Comparability with `psi`.**
- - -> Where no key value is repeated within either party's dataset, the count equals the size of the association table a one-to-one `psi` run over the same terms and the same data produces, under either linkage strategy, since both produce the same table.
- - -> Where a value is repeated within one party's dataset for a key, the two can differ, and only through such values:
- - -> The `psi` cascade applies its within-round uniqueness rule to the records still unmatched at that key's round ([Matching Algorithms](#psi)).
- - -> A repeated value whose other holders an earlier key has matched is unique among the unmatched records, so it takes part in the `psi` round.
- - -> PSI-C gives every holder of a repeated value a dummy, so that value takes no part in the key's round.
- - -> A pair one run accepts and the other does not changes which records are still free for later keys, so the difference can propagate to later rounds and can go in either direction.
- - -> Applying the `psi` rule exactly would mean sending every holder of a repeated value and resolving the repetition in the replay, since neither party knows on the wire which of its own records have matched.
- - -> The receiver's software would then see a repeated value of its own as one setup position matched by several slots, and since the receiver knows which of its records share a value, those slots would be tied to those records.
