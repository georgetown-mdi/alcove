- - -> The chunked envelope, version 2
- - -> Envelope version 2 encrypts a frame as a run of AES-GCM chunks, so a frame is not held to the most one `crypto.subtle` call encrypts (2^31 - 18 bytes, [TRANSPORT_BOUNDS.md](TRANSPORT_BOUNDS.md#inbound-frame-size-bound), "The AEAD's limit on one frame"), and neither party copies the whole frame to encrypt or decrypt it.
- - -> The keys, the type tag and the sequence number are those of version 1; the layout and the nonce are these (`packages/core/src/connection/chunkedAead.ts`):
- - -> envelope = version || seq || chunk_0 || ... || chunk_(n-1)
- - -> version = 0x02 # 1 byte
- - -> seq = the frame's sequence number # 8 bytes, big-endian
- - -> plaintext = type_tag || payload # L bytes, L >= 1
- - -> C = AEAD_CHUNK_PLAINTEXT_BYTES = 16,777,216
- - -> n = ceil(L / C)
- - -> chunk_k = AES-256-GCM(key, IV_k, plaintext[k*C : min(L, (k+1)*C)], AAD_k) # ciphertext || 16-byte tag
- - -> IV_k = uint32_be(k) || uint64_be(seq) # 12 bytes
- - -> AAD_k = version || uint64_be(seq) || uint32_be(k) || final_k # 14 bytes
- - -> final_k = 0x01 where k = n - 1, else 0x00
- - -> **The chunk size.**
- - -> `C` is 2^24 bytes of plaintext, the fastest of the chunk sizes measured under Node ([the measurement](../notes/chunked-aead-envelope.md#the-chunk-size)).
- - -> Not measured: the browser's `crypto.subtle`, which a web party's frames, at most `MAX_WEBRTC_FRAME_BYTES`, go through.
- - -> **Every frame is chunked.**
- - -> Version 2 has one shape, since chunking measured no slower than one call ([the measurement](../notes/chunked-aead-envelope.md#every-frame-is-chunked)): a frame of at most `C` plaintext bytes is one chunk.
- - -> The cost is 16 bytes of tag for each chunk, so the envelope adds `10 + 16 * n` bytes to a frame, a figure that grows with the frame (`outboundFrameOverheadBytes`); a sender sizing a frame to a bound takes that figure at the bound, which is never below it at a smaller frame.
- - -> **The nonce.**
- - -> `IV_k` is the chunk index in its leading 32 bits and the frame's sequence number in its trailing 64.
- - -> Under one key, which is one direction of one session, the sequence number differs for every frame ([IV construction and SP 800-38D conformance](#iv-construction-and-sp-800-38d-conformance)) and the index differs for every chunk of a frame, so no IV repeats under a key across frames or chunks.
- - -> A frame is at most 2^53 - 1 bytes, the largest exact integer and Node's largest `Buffer`, so `n` is at most 2^29 and the index never reaches its 32-bit limit.
- - -> Chunk 0's IV equals the version-1 IV of the same sequence number, and the two never meet under one key: a session uses the one envelope version it negotiated.
- - -> **The additional data.**
- - -> `AAD_k` binds the version byte, the frame's sequence number, the chunk index and the final-chunk flag.
- - -> The sequence number and the index are in the IV as well, so a chunk decrypted at another position or in another frame than the one it was encrypted for fails its tag: a dropped, reordered or repeated chunk moves some chunk to another index, and a chunk spliced in from another frame of the session has another sequence number.
- - -> A chunk from another session or direction fails under the key.
- - -> The final-chunk flag is in the additional data alone, and it is what authenticates where the frame ends.
- - -> A receiver derives `n` from the envelope's length, so an envelope cut after a whole chunk makes a chunk encrypted as non-final the last, and one with a chunk's worth of bytes appended makes the final chunk not the last; either fails that chunk's tag under the flag the receiver expects.
- - -> Bytes cut from or appended to within the last chunk move its tag, which then fails.
- - -> **Reading the length.**
- - -> With `B` the envelope's length less its 9 header bytes, a receiver takes `n = ceil(B / (C + 16))`, the last chunk as `B - (n - 1) * (C + 16)` bytes, and the plaintext as `B - 16 * n` bytes.
- - -> An envelope shorter than 26 bytes, or whose last chunk is shorter than 17 bytes (one plaintext byte and the tag), is refused as a `security` failure before any chunk is decrypted, as is a version byte other than the negotiated one.
- - -> The sequence-number checks of version 1 (replay, order and gap, [Inbound integrity, replay, and ordering checks](#inbound-integrity-replay-and-ordering-checks)) run on `seq` before any chunk is decrypted.
- - -> **A frame that fails at chunk k.**
- - -> A receiver decrypts the chunks in order and writes each chunk's plaintext into the envelope's own bytes, ahead of the chunks not yet decrypted, so the frame is in memory once.
- - -> No plaintext is released before the final chunk's tag verifies: `receive()` returns the payload only then.
- - -> A tag that fails at chunk `k` fails the frame as a `security` failure and latches the connection, as any tag failure does, and the plaintext of chunks 0 to `k - 1` already written is overwritten with zeros before the failure is raised.
- - -> Those chunks each passed their tag, but the protocol above acts on whole frames, and the start of a frame is not a frame its sender sent.
- - -> **The negotiation.**
- - -> Version 2 is selected by the version hello where both parties offer it: this build offers envelope versions 1 and 2, and the hello selects the highest both list ([PROTOCOL.md](PROTOCOL.md#p-256-authenticated-key-exchange), The version hello).
- - -> A party on an earlier build offers 1 alone, so the two select 1 and the run uses the version-1 envelope, whose frame limit is the AEAD's limit on one call: a single-pass frame over it is refused before it is written, and the partner told, as between two earlier builds.
- - -> A downgrade cannot remove version 2 from two parties that both offer it, by the hello's own guarantee: the transcript binds both hellos as sent, so a hello rewritten in transit fails the key confirmation, and what a rewrite can do is stop the run (The version hello, "Bound as received" and "A limit").
- - -> Version 1 is not the weaker construction, in any case: what it limits is a frame's size, not what the AEAD protects.

- - -> `packages/core/test/vectors/aead-chunked-envelope-vectors.json` pins version 2 as the version-1 vectors pin version 1, from an independent oracle (`node:crypto` `createCipheriv`): one-chunk frames of each type in each direction, frames of several chunks at a small chunk size the test gives the decorator, and a frame of one chunk and one byte at the real chunk size, recorded by its SHA-256.
