- - -> `heldAppUpdate` | object | Whether the last scheduled window that made an attempt started it on the code its page loaded while a newer app version waited, because something held the update back (see [Applying a waiting app version between windows](#applying-a-waiting-app-version-between-windows)). Only the window's own bookkeeping write sets it, and only for a window that made an attempt: the held form where a hold kept a waiting update back before the first attempt, the none form otherwise. A window that made no attempt leaves it as it is. A takeover that did not land within the wait writes the none form, since nothing held the update back (see "The one exception to the holds" there), and so does a lock state the runner could not read where nothing in its own window holds the update, since it names no holder. It is this device's alone: an export does not include it, a new or imported record starts at the none form, and a replace keeps the stored one. The field is **required**, for the reason `standingCondition` is.

- - -> **Which holder each hold is.**
- - -> Each hold is one of four holders, by what releases it (`AppUpdateHolder`, `apps/web/src/utils/appUpdateHolder.ts`):
- - -> `"run"`: a record's single-writer lock, or a leave-page prompt armed by a live exchange.
- - -> `"file"`: a leave-page prompt armed by an invite or accept form with a file not yet sent, or a view holding an invitation, a loaded file, or an import waiting on the operator's answer.
- - -> `"results"`: a view showing a finished run's downloads or failure, or a minted re-invitation.
- - -> `"edits"`: a view holding an unsaved edit.
