- **Where it is read.** -> -
- The rule-set citation -> -
- Beside the matching basis, the governance block records the **named rule set the agreed terms cited** (`linkageRuleSet`), when they cited one: the name and content version of the field set and of the key set, copied from the terms. -> -
- Where the basis enumerates the fields the match keyed on, the citation is the artifact a data-sharing agreement or a governance review can name, so "which rules did this linkage match on" is answerable from the record without quoting the key list. -> -
- Its source is [`linkage_terms.linkage_rule_set`](../EXCHANGE_REFERENCE.md#linkage_termslinkage_rule_set). -> -
- Three limits on what it asserts: -> -
- **It is a citation, not the account of the run.** -> -
- A run matches on a subset of the cited set -- terms derived from an input file leave out any key that input cannot supply -- so the citation bounds what was tried above; the matching basis beside it is what the keys actually referenced. -> -
- **It is the authoring party's declaration**, recorded verbatim -- an acceptor adopts the inviter's citation into its own record unaltered. -> -
- Nothing on the exchange path resolves the name to a set. -> -
- What the exchange holds both parties to is the linkage fields and keys, which are cross-checked byte for byte; what the writing party could check about the name it recorded is the separate [verdict](#the-writing-partys-verdict) beside it. -> -
- **Its cross-party consistency is the terms' own.** -> -
- Two parties that both cite a set are required to cite the same one before any data moves, so their records hold the same names; where one cites none, its record omits the field while the other's holds its own citation. -> -
- The verdict beside it has no such guarantee, for the reason given below. -> -
- Omitted when the agreed terms cited no set (their rules were authored rather than drawn from one) -- absent by omission, never a null, which is why the record's format version moves with it. -> -
- The web disclosure-accounting screen and the CSV it exports present it beside the matching basis, each half named and versioned, so a governance reader answers "which rules did this linkage match on" from the accounting alone. -> -
- Both show a caveat with it, since a citation shown bare would be taken for a checked provenance. -> -
- The caveat states that the citation is the authoring party's own declaration recorded as written, sends the reader to the [verdict](#the-writing-partys-verdict) recorded beside it for what the writing party could establish about the names, and names the matching basis as what the exchange held both parties to. -> -
- A record whose terms cited no set is treated as that rather than as a blank. -> -
- The writing party's verdict -> -
- Beside the citation, and present exactly when it is, the record holds `linkageRuleSetVerdict`: **the writing party's own verdict** on whether the linkage fields and keys the agreed terms declare are drawn from the sets those terms cite them to. -> -
- It is per half -- `fieldSet` and `keySet` -- and each half takes one of three values: -> -
- `consistent` | The cited half names a rule set this build ships, and the declared rules for that half are drawn from it. -> -
- `contradicted` | The cited half names a rule set this build ships, and the declared rules are **not** drawn from it: the citation states a provenance the rules beside it do not have. -> -
- `unchecked` | The cited half names a set this build does not ship. Nothing resolved the name, so nothing was compared. -> -
- Three values rather than two, because the absence of `contradicted` must not read as verification: a build that could not resolve a name has checked nothing, which is a different statement from having checked and found the rules to match. -> -
- The halves are decided independently, for the same reason they are named and versioned separately -- a document can truthfully cite the shipped field set while its keys are not the shipped key set. -> -
- **Drawn from** means exactly what the implementation's own predicate means by it: every declared key byte-identical to a key the set declares, in the set's cascade order, and every declared field byte-identical to a distinct field it declares. -> -
- A narrowed emission passes -- what an input file cannot supply is left out -- while an added, edited, or repeated rule, or a reordered cascade, does not. -> -
- Four properties fix how the row is read. -> -
- **It is per party and build-relative.** -> -
- The verdict is written locally from the sets the writing build ships, not agreed between the parties and not folded into the agreed-terms hash. -> -
- Two parties running different builds may therefore write different verdicts for one run and neither is wrong: a set one of them ships is a set the other may not. -> -
- Nothing in the exchange compares the two, and a reader must not read one party's verdict as the other's. -> -
- **The set identity it was checked against is the citation beside it.** -> -
- A `consistent` or `contradicted` half is reached only where the cited name *and* content version resolve to a set the build ships, so that half's own recorded name and version identify what it was compared against. -> -
- An `unchecked` half resolved to nothing. -> -
- **The citation is annotated, never replaced.** -> -
- A record with a `contradicted` half still records the citation verbatim. -> -
- Dropping or rewriting a refuted citation would launder the declaring party's claim out of the artifact and leave the record silent about a claim that was made; annotating it keeps both the claim and the finding in the disclosure record an auditor reads. -> -
- **It changes nothing about the run.** -> -
- The verdict is written after the exchange, from terms both parties already agreed; which fields and keys a run matches on, and what it discloses, are settled entirely by the declared rules. -> -
- Both parties write it on the same rule -- the inviting party over its own citation, the accepting party over the inviter's citation as adopted -- so the row means the same thing in either record. -> -
- The record is the one place the verdict is kept: neither the pre-consent accept prompt (CLI) nor the consent review screen (web) shows the citation or the verdict ([`linkage_terms.linkage_rule_set`](../EXCHANGE_REFERENCE.md#linkage_termslinkage_rule_set)). -> -
- The disclosure accounting presents the citation under its caveat, whose pointer to the verdict beside it in the record is as far as it goes -- the value itself is not a row there. -> -
