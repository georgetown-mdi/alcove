- - -> **A deviating sender can time the receiver's frames.**
- - -> A sender that builds its next round's setup before it sends a response, and sends the two together, can time the gap to the receiver's next request, which then includes the receiver's match of the round.
- - -> At about 10^6 records a side no per-round count, and no difference between every record matching and none, showed within one exchange against the spread of the receiver's own masking.
- - -> A sender averaging recurring exchanges over unchanged data would need about 45 rounds in which every record matched to tell all from none, and about 700 to resolve steps of 25%.
- - -> Those figures were measured on a loaded host.
- - -> An honest sender's own setup hides the match entirely.
- - -> This is accepted under the honest-but-curious model.
- - -> **A stated limit: any key holder sets the row's lapse.**
- - -> For a row the relay-owner token enrolled, a rotation or renewal under a proof takes `maxAgeDays` from its body, `null` included.
- - -> So any holder of the exchange's current relay key, the partner included, can renew the row, or replace its key with one only it holds, with any lapse or none, and keep the row past the exchange's last run.
- - -> What it gains is use of the relay, not exchange data, and the registrar's journal records each such write with `authority=proof`.
- - -> The operator revokes an ended exchange with the token.
- - -> A row enrolled without a token keeps the lapse the registrar fixed at enrollment.
- - -> **A stated limit: the host-key types offered include `ssh-rsa`.**
- - -> The host-key types a connection offers are not configurable: `provider_options.algorithms` admits no `serverHostKey` (`SFTP_ALGORITHMS_ALLOWED_SUBKEYS`, `packages/core/src/connection/sftpConnect.ts`), and the offer includes `ssh-rsa`, whose signature uses SHA-1.
- - -> A server that offers only `ssh-rsa` is negotiated with, and a pin binds the server's key, not the signature algorithm ([FIPS_SFTP_PROFILE.md](../FIPS_SFTP_PROFILE.md#host-key-types-cannot-be-constrained)).
- - -> Every rename destination is self-prefixed, but a name is a convention, not proof of who wrote the file.
- - -> A file another writer of the directory planted there gives that writer nothing it could not do without the re-issue, as a server can answer a first rename with success without performing it.
- - -> **A stated limit: a payload's total is bounded only by its rows.**
- - -> A payload part has no bound but the per-frame bound, and the receiver keeps a copy of each part's values until the run ends, so the partner's payload can total its declared row count times the per-frame bound, the row count at most the pairs in this party's matched table: 1,000 rows over WebRTC admit up to 268,435,456,000 bytes.
- - -> A partner that sends that much ends the receiver's run on memory, and nothing is disclosed.
- - -> The payload is the partner's own disclosure, which the operator agreed to receive, and a legitimate payload of large values cannot be told from one sent to exhaust memory, so no total is enforced.
- - -> **A stated limit: a direct write follows a link a co-tenant planted.**
- - -> An account on the server that can write the exchange directory, and is not its admin, can plant a symlink at a final name there too.
- - -> A direct write to a final name ([FILE_SYNC.md, Writing without renaming](FILE_SYNC.md#writing-without-renaming)) is opened by the server, so on a server that follows a link when it opens a file for writing, the write lands in whatever file the link names that this party's server account can write.
- - -> Writing without renaming is opt-in.
- - -> **A stated limit: the partner's start is the relay's word.**
- - -> Nothing authenticates the start a relay passes on, so any relay the run lists can end the WebRTC wait by sending one, and one both parties dial can move onto itself an exchange whose WebRTC path would have opened ([WEBSOCKET_RELAY.md](WEBSOCKET_RELAY.md#pairing-and-the-start)).
- - -> **A stated limit: a refusal shows whether an id is enrolled.**
- - -> The relay refuses a hello under an exchange id with no key as not enrolled (4003) before it checks the proof, and one under an enrolled id whose proof fails as 4004 or 4005.
- - -> So anyone who can reach the relay learns from the close code whether an exchange id is enrolled there, as the registrar's answers show ([The registrar request proof](PROTOCOL.md#the-registrar-request-proof)).
- - -> An exchange id an operator chooses should reveal nothing about the parties.
- - -> **A stated limit: the start a party receives is the relay's.**
- - -> Nothing shows that the partner sent it, so a relay can send `paired` and `start` to a party whose partner never sent its start, and that ends the party's WebRTC wait ([WEBRTC_TRANSPORT.md](WEBRTC_TRANSPORT.md#falling-back-to-the-websocket-relay)).
- - -> Sent to both parties, it moves onto the relay an exchange whose WebRTC path would have opened; sent to one, it fails a run that would have completed.
- - -> The exchange's content stays under the application-layer encryption, and the relay sees the size and timing of each message it forwards.
- - -> **A stated limit: the confirmation is the relay's word.**
- - -> A party takes a 1000 close, or the partner's close sentinel, as the partner's close, and the relay can write either.
- - -> A relay that withholds a party's last message and sends one makes that party's close report the message delivered, while the partner, still waiting for it, fails at its own inactivity bound.
- - -> Only an authenticated end-of-stream acknowledgement would close this, and it is not built ([CHANNEL_SECURITY.md](CHANNEL_SECURITY.md#end-of-stream-and-truncated-tail-detection)).
