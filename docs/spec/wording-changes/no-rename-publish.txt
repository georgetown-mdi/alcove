- - -> Publishing without rename
- - -> `publish_without_rename` (`--publish-without-rename`) replaces every temp-then-rename publish in this model with a single `put` straight to the final name, for a party whose server refuses `rename`.
- - -> It is one party's local setting: neither the hello envelope nor the invitation states it, the directory holds the same final names either way, and a partner running without it completes the same exchange.
- - -> It applies to `sftp` and `filedrop` alike, since the switch is in the connection, not the transport.
- - -> **The assumption.**
- - -> A direct write is visible under its final name while it is still being written.
- - -> The operator who turns the option on vouches that the shared folder never delivers a file to the partner in that state; for a service-synced share, that the sync does not carry a file across mid-write.
- - -> Alcove cannot check this and does not police it; the run states it in a warning before it connects.
- - -> **What each reader relies on.**
- - -> Every reader already has a completeness signal that does not depend on the rename, so the mode adds none:
- - -> File | What its reader relies on under a direct write
- - -> message | its on-disk size reaching the byte count its name declares (site 3)
- - -> ack, rendezvous and message | nothing: it is zero-length, so its name appearing is completion
- - -> hello | the I5a read gate, which retries a short or unparseable read until its bounded deadline, then validates `HelloEnvelope`
- - -> joining sentinel | nothing: the peer matches it by name and never reads it
- - -> abort marker | its verification: a torn body fails it, reads as no marker, and the loop keeps polling, at worst falling back to the peer-silence hedge
- - -> lock | unchanged: it is already a direct write (`createExclusive`)
- - -> **The lock-path joiner.**
- - -> The joiner writes its `<id>-joining.json` sentinel, deletes the peer hello, writes its own hello, and only then deletes the sentinel.
- - -> The sentinel still spans the window in which the peer hello is gone and the joiner's is not yet written, so the peer's bounded recovery wait is unchanged.
- - -> The new window is the one after the hello is written and before the sentinel is deleted, in which the peer can list both.
- - -> The peer tolerates that during rendezvous because the sentinel's id matches the hello it completes against (Phase 1, lock path), and in its message loop because the peer's sentinel is in the recognized-for-the-loop set (site 3).
- - -> Both tolerances are the peer's own, whatever the peer's setting, which is what keeps the option per-party.
- - -> A sentinel delete that fails does not fail the rendezvous, since the hello is already visible and the peer may have read it: the joiner warns, tracks the sentinel again so `cleanup()` removes it at close in delete mode, and its own loop recognizes it by name meanwhile.
- - -> Requiring lockless rendezvous for the mode would have avoided the sentinel, but `lockless_rendezvous` is bilateral and advertised in the hello, so it would set the partner's configuration.
- - -> **Write tracking.**
- - -> In delete mode, a write the default publish tracks after its rename is tracked before its `put` instead, as the `lock` is ([I4a](#invariants)), because a `put` that throws can still leave the final name on disk.
- - -> That covers the hello, the joining sentinel (released once the peer hello is deleted, as before), the joiner's hello, the lockless rendezvous ack (whose path the [terminal rendezvous rollback](#phase-1----terminal-rendezvous-failure) also holds before the write), and the message.
- - -> The abort marker and the hello a refusing joiner advertises stay untracked, as they are by default, because both must persist for the peer to read.
- - -> A message whose direct write throws is an unsettled publish, as an undetermined rename is ([I8](#invariants)): the file may be on disk in full and already read, so `send()` rejects with `TransportPublishIndeterminateError` and the clean-directory remedy, the NNN is spent, and the next `send()` refuses.
- - -> Over SFTP, a `put` whose reply a dropped session lost is decided by what the re-dialed session finds under the final name: complete, the publish landed and the `put` resolves; short, the `put` is re-issued once; absent, longer, or unreadable, the publish is undetermined, as above ([SFTP_SESSION_RECOVERY.md](SFTP_SESSION_RECOVERY.md#re-issuing-an-operation)).
- - -> **Limits.**
- - -> A hard kill mid-`put` can leave a torn `<id>-hello.json`, the case the temp-then-rename hello publish exists to prevent.
- - -> The next run's I5a gate fails it within the rendezvous read bound, and `--sweep-exchange-files` clears it.
- - -> Whether a given sync service delays a direct-written file's size relative to its name more than a renamed file's is not measured; the byte-count gate and the I5a gate are what absorb it, and the I5a bound (six poll cycles under the wall-clock floor) has not been measured against such a write.
- - -> Policing the sync, and detecting a partial file beyond those gates, are out of scope.

- - -> A `put` to any other name is a direct publish, whose re-issue is below.
- - -> A party [publishing without rename](FILE_SYNC.md#publishing-without-rename) issues no `rename`, so neither arm above runs for it: each publish is a `put` to the final name, and a reply lost to a drop is resolved by probing that destination, never by re-issuing the `put` blind.
- - -> A destination present at the source's full byte length is the publish landed, and the `put` resolves without a re-issue.
- - -> A destination present but shorter is a `put` that stopped short, on which no reader has acted (a message reader waits for the byte count its name declares, the hello reader retries a short read, and an ack or sentinel is zero-length), so the truncate-overwrite `put` is re-issued once.
- - -> A destination absent, longer than the source, or that the probe could not read is rejected as `TransportPublishIndeterminateError`: in delete mode the partner may already have consumed it, and nothing the adapter can read separates that from a `put` that never landed.
- - -> A message whose `put` rejects spends its sequence number the same way.
- - -> A first attempt a server refuses with `SSH_FX_NO_SUCH_FILE`, which is how a server that does not allow renames answers, is not a re-issue: it propagates as itself, and core restates it naming that option.
