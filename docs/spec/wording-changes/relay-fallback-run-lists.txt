# The invitation's relay locator names the exchange id its WebSocket
# relay holds the key under, a registrar may stand beside a WebSocket
# relay url alone, and each run lists its WebSocket relays with the id
# each is proven under. A browser enrolls at the default relay where
# either of its urls is kept, and a CLI run enrolls at the invitation's
# registrar where it lists the invitation's WebSocket relay. An inviter
# names a registrar beside a WebSocket relay url only where that relay
# reads the keys the registrar enrolls, so the web app names none
# beside the browser's own WebSocket relay.
- A webrtc connection endpoint MAY hold `relay`, the inviting party's relay locator: an object with an optional `turn` list and an optional `stun` list of urls, an optional `websocket` url, an optional `registrar` url, and no other key. -> A webrtc connection endpoint MAY hold `relay`, the inviting party's relay locator: an object with an optional `turn` list and an optional `stun` list of urls, an optional `websocket` url, an optional `websocketExchangeId`, an optional `registrar` url, and no other key.
- A locator that names it names at least one `turn` url. -> A locator that names it names at least one `turn` url or a `websocket` url.
- - -> An inviter names it beside a `websocket` url only where the WebSocket relay at that url reads the keys the registrar enrolls, since a CLI run that lists that url enrolls there ([A command-line party](#enrolling-at-a-default-relay)).
- Where the locator names the default relay's TURN url, the web app also names that relay's registrar as `registrar`; the CLI names none. -> Where the locator names the default relay's TURN url or its WebSocket relay url, the web app also names that relay's registrar as `registrar`, unless the locator's `websocket` url is the browser's own rather than the default relay's (`invitationRelayWithDefault` in `apps/web/src/psi/transport/defaultRelay.ts`); the CLI names none.
- - -> **The WebSocket relay's exchange id.**
- - -> `websocketExchangeId` is the exchange id the `websocket` relay holds the exchange's relay key under, where the inviter enrolled the key there under an id of its own rather than the one [derived from the secret](#relay-credential-derivation); a party's hello to that relay names it ([The WebSocket relay proof](#the-websocket-relay-proof)).
- - -> It follows the grammar of [`relay_registrar`](../EXCHANGE_REFERENCE.md#connectionrelay_registrar)'s `exchange_id`: 1 to 128 of `[A-Za-z0-9._-]`, not starting with `-` or `alcove-verify-`, not one or two dots alone, and with no run of 64 hex characters.
- - -> A refusal does not repeat it.
- - -> A locator that names it names a `websocket` url.
- - -> The CLI names its `relay_registrar`'s `exchange_id` beside the `websocket_relay` it names (`endpointFromConnection`), and the web app names a saved exchange's registrar's exchange id (`relayRegistrar`) beside the browser's own WebSocket relay url on a re-invite (`composeManagedReinvite` in `apps/web/src/psi/managed/managedReinvite.ts`); neither names one otherwise.
- - -> It is not a credential: it names the key the relay checks a proof under.
- - -> `websocketExchangeId` was added the same way, beside `websocket` only, so a decoder predating it refuses an invitation that names it, and one predating `websocket` already refuses every invitation that could.
- - -> **The list.**
- - -> A CLI run lists its connection's `websocket_relay`, then the invitation's `websocket` url (`selectRunRelay`).
- - -> A browser run lists the browser's own relay setting's, then the invitation's, then a build's default WebSocket relay once its enrollment there confirmed (`relayPlanForRun`).
- - -> Either lists each url once, less every one its allowed relays leave out, and a browser run leaves out the default relay's url where its enrollment did not confirm, even where another source names it, as it does the default relay's TURN url.
- - -> **The exchange id of each.**
- - -> A run's proof to each relay it lists names an exchange id decided by the url ([The WebSocket relay proof](#the-websocket-relay-proof)).
- - -> The url the invitation names takes its `websocketExchangeId`, since the inviter proves to that relay under it.
- - -> A url of the party's own takes its own registrar's exchange id: the CLI connection's `relay_registrar`, or a saved exchange's `relayRegistrar` in the browser.
- - -> Any other url, and one with no exchange id named, takes the id [derived from the secret](#relay-credential-derivation), the one an enrollment without a token uses.
- A CLI run enrolls at the registrar the invitation's relay names only when the url it allocates on is one the invitation names and takes the run's derived credential ([A command-line party](#enrolling-at-a-default-relay)); a browser partner enrolls there for its own allocation, so an exchange on a hosted invitation is still enrolled by the party that uses that relay. -> A CLI run enrolls at the registrar the invitation's relay names only when the url it allocates on is one the invitation names and takes the run's derived credential, or when it lists the invitation's WebSocket relay url ([A command-line party](#enrolling-at-a-default-relay)); a browser partner enrolls there for its own allocation, so an exchange on a hosted invitation is still enrolled by the party that uses that relay.
- A browser run of a build that names a default relay also enrolls at that relay, one-shot and managed alike, and so does a CLI run that allocates on an invitation relay naming a registrar with the credential it derives ([Enrolling at a default relay](#enrolling-at-a-default-relay)). -> A browser run of a build that names a default relay also enrolls at that relay, one-shot and managed alike, and so does a CLI run that allocates on an invitation relay naming a registrar with the credential it derives, or lists that relay's WebSocket relay ([Enrolling at a default relay](#enrolling-at-a-default-relay)).
- - -> The build may also name that relay's WebSocket relay url (`VITE_DEFAULT_RELAY_WEBSOCKET_URL`), whose relay reads the keys the registrar enrolls.
- A CLI run accepting an invitation such a build made enrolls there too when it allocates on that relay with the credential it derives (**A command-line party**, below). -> A CLI run accepting an invitation such a build made enrolls there too when it allocates on that relay with the credential it derives, or lists its WebSocket relay (**A command-line party**, below).
- Where the allowed relays that apply (a saved exchange's own, otherwise those set on the review of the invitation accepted or created) leave out the default relay's TURN url, the browser neither enrolls there nor names that relay in an invitation it creates. -> Where the allowed relays that apply (a saved exchange's own, otherwise those set on the review of the invitation accepted or created) leave out both the default relay's TURN url and its WebSocket relay url, the browser neither enrolls there nor names that relay in an invitation it creates.
- - -> Where they keep either, it enrolls there, and an invitation it creates names the relay as [The invitation's relay locator](#the-invitations-relay-locator) states.
- - -> A confirmed enrollment also lists the default relay's WebSocket relay url, where the build names one and the allowed relays keep it, after the browser's own and the invitation's ([Which WebSocket relays the allowed relays keep](#the-invitations-relay-locator)), and an unconfirmed one leaves that url out too.
- - -> A CLI run whose `invitation_relay` names a `registrar` and a `websocket` url that the run lists ([Which WebSocket relays the allowed relays keep](#the-invitations-relay-locator)) enrolls there too, whatever its first TURN url (`runEnrollsAtInvitationRegistrar` in `packages/core/src/relayCredential.ts`).
- A CLI run whose first TURN url is one the invitation does not name, or is its own `turn` entry setting a `username` and `credential`, contacts no registrar the invitation names, and states on the log that it did not, naming the url it allocates on. -> A CLI run that lists no WebSocket relay url the invitation names, and whose first TURN url is one the invitation does not name, or is its own `turn` entry setting a `username` and `credential`, contacts no registrar the invitation names, and states on the log that it did not, naming the url it allocates on.
- One whose `allowed_relays` leaves out every TURN url the invitation names states that as the reason instead. -> One whose `allowed_relays` leaves out every TURN url and the WebSocket relay url the invitation names states that as the reason instead.
- - -> An invitation whose `websocket` url is the browser's own rather than the default relay's names no registrar ([The invitation's relay locator](#the-invitations-relay-locator)), so a CLI run accepting it enrolls nowhere, even where it allocates on the default relay's TURN url.
- `enrollment` | The registrar `invitation_relay` names enrolled the exchange's relay key, as it does for a run before it dials when the url the run allocates on is the invitation's and is sent the minted credential (`runEnrollsAtInvitationRegistrar`). Present, and first, only where `invitation_relay` names a `registrar`; `skipped`, with nothing contacted, where a run of the configuration does not enroll there. -> `enrollment` | The registrar `invitation_relay` names enrolled the exchange's relay key, as it does for a run before it dials when the url the run allocates on is the invitation's and is sent the minted credential, or when the run lists the invitation's WebSocket relay url (`runEnrollsAtInvitationRegistrar`). Present, and first, only where `invitation_relay` names a `registrar`; `skipped`, with nothing contacted, where a run of the configuration does not enroll there.
- `relay` is the inviting party's relay locator, TURN and STUN urls, a WebSocket relay url and a registrar url only (`relayLocatorSchema` in `packages/core/src/config/connection.ts`), with its grammar and bounds in [PROTOCOL.md](PROTOCOL.md#the-invitations-relay-locator). -> `relay` is the inviting party's relay locator, TURN and STUN urls, a WebSocket relay url with its exchange id, and a registrar url only (`relayLocatorSchema` in `packages/core/src/config/connection.ts`), with its grammar and bounds in [PROTOCOL.md](PROTOCOL.md#the-invitations-relay-locator).
- For the browser path the document's connection block is the `webrtc` channel restricted to its credential-free locator subset: `server` locator fields only (`host`/`port`/`path` -- no `server.username`, no PeerJS `key`), the `invitation_relay` the invitation named (TURN and STUN urls, a WebSocket relay url and a registrar url only, see [PROTOCOL.md](PROTOCOL.md#the-invitations-relay-locator)), and no `turn`, `ice_provision`, or `provider_options` entries (a TURN entry holds relay credentials, and the provider map is opaque and `@`-file-pathed). -> For the browser path the document's connection block is the `webrtc` channel restricted to its credential-free locator subset: `server` locator fields only (`host`/`port`/`path` -- no `server.username`, no PeerJS `key`), the `invitation_relay` the invitation named (TURN and STUN urls, a WebSocket relay url with its exchange id, and a registrar url only, see [PROTOCOL.md](PROTOCOL.md#the-invitations-relay-locator)), and no `turn`, `ice_provision`, or `provider_options` entries (a TURN entry holds relay credentials, and the provider map is opaque and `@`-file-pathed).
