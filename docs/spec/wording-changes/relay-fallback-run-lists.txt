# The invitation's relay locator names the exchange id its WebSocket
# relay holds the key under, a decoder admits a registrar beside a
# WebSocket relay url alone, and each run lists its WebSocket relays
# with the id each is proven under. No run enrolls at a registrar for a
# WebSocket relay, since no run dials one, so no build names a registrar
# beside a WebSocket relay url alone. A locator's registrar enrolls the
# key of its TURN relay; which registrar a WebSocket relay's key is
# enrolled at is decided when a run first dials one.
- A webrtc connection endpoint MAY hold `relay`, the inviting party's relay locator: an object with an optional `turn` list and an optional `stun` list of urls, an optional `websocket` url, an optional `registrar` url, and no other key. -> A webrtc connection endpoint MAY hold `relay`, the inviting party's relay locator: an object with an optional `turn` list and an optional `stun` list of urls, an optional `websocket` url, an optional `websocketExchangeId`, an optional `registrar` url, and no other key.
- A locator that names it names at least one `turn` url. -> A locator that names it names at least one `turn` url or a `websocket` url.
- - -> A locator's registrar enrolls the key of its TURN relay: a CLI run enrolls there only when the TURN url it allocates on is one the locator names ([A command-line party](#enrolling-at-a-default-relay)).
- - -> Which registrar a WebSocket relay's key is enrolled at is decided when a run first dials a WebSocket relay, and no run does yet ([No run dials one](#the-invitations-relay-locator)).
- - -> **The WebSocket relay's exchange id.**
- - -> `websocketExchangeId` is the exchange id the `websocket` relay holds the exchange's relay key under, where the inviter enrolled the key there under an id of its own rather than the one [derived from the secret](#relay-credential-derivation); a party's hello to that relay names it ([The WebSocket relay proof](#the-websocket-relay-proof)).
- - -> It follows the grammar of [`relay_registrar`](../EXCHANGE_REFERENCE.md#connectionrelay_registrar)'s `exchange_id`: 1 to 128 of `[A-Za-z0-9._-]`, not starting with `-` or `alcove-verify-`, not one or two dots alone, and with no run of 64 hex characters.
- - -> A refusal does not repeat it.
- - -> A locator that names it names a `websocket` url.
- - -> The CLI names its `relay_registrar`'s `exchange_id` beside the `websocket_relay` it names (`endpointFromConnection`), and the web app names a saved exchange's registrar's exchange id (`relayRegistrar`) beside the browser's own WebSocket relay url on a re-invite (`composeManagedReinvite` in `apps/web/src/psi/managed/managedReinvite.ts`); neither names one otherwise.
- - -> It is not a credential: it names the key the relay checks a proof under.
- - -> `websocketExchangeId` was added the same way, beside `websocket` only, so a decoder predating it refuses an invitation that names it, and one predating `websocket` already refuses every invitation that could.
- - -> A `registrar` beside a `websocket` url and no `turn` url was admitted without a `version` bump too, so a decoder predating that refuses such a locator.
- - -> No build mints one: no run enrolls at a registrar for a WebSocket relay until a run dials one ([No run dials one](#the-invitations-relay-locator)).
- - -> **The list.**
- - -> A CLI run lists its connection's `websocket_relay`, then the invitation's `websocket` url (`selectRunRelay`).
- - -> A browser run lists the browser's own relay setting's, then the invitation's, then a build's default WebSocket relay once its enrollment there confirmed (`relayPlanForRun`).
- - -> Either lists each url once, less every one its allowed relays leave out, and a browser run leaves out the default relay's url where its enrollment did not confirm, even where another source names it, as it does the default relay's TURN url.
- - -> **The exchange id of each.**
- - -> A run's proof to each relay it lists names an exchange id decided by the url ([The WebSocket relay proof](#the-websocket-relay-proof)).
- - -> The url the invitation names takes its `websocketExchangeId`, since the inviter proves to that relay under it.
- - -> A url of the party's own takes its own registrar's exchange id: the CLI connection's `relay_registrar`, or a saved exchange's `relayRegistrar` in the browser.
- - -> Any other url, and one with no exchange id named, takes the id [derived from the secret](#relay-credential-derivation), the one an enrollment without a token uses.
- - -> The build may also name that relay's WebSocket relay url (`VITE_DEFAULT_RELAY_WEBSOCKET_URL`), whose relay reads the keys the registrar enrolls.
- Where the allowed relays that apply (a saved exchange's own, otherwise those set on the review of the invitation accepted or created) leave out the default relay's TURN url, the browser neither enrolls there nor names that relay in an invitation it creates. -> Where the allowed relays that apply (a saved exchange's own, otherwise those set on the review of the invitation accepted or created) leave out the default relay's TURN url, the browser neither enrolls there nor names that TURN url or the registrar in an invitation it creates, even where they keep the relay's WebSocket relay url.
- - -> No run enrolls there for the WebSocket relay alone, since no run dials one ([No run dials one](#the-invitations-relay-locator)).
- - -> A confirmed enrollment also lists the default relay's WebSocket relay url, where the build names one and the allowed relays keep it, after the browser's own and the invitation's ([Which WebSocket relays the allowed relays keep](#the-invitations-relay-locator)), and an unconfirmed one leaves that url out too.
- - -> Listing the invitation's `websocket` url does not make a run enroll there, since no run dials a WebSocket relay yet (`runEnrollsAtInvitationRegistrar` in `packages/core/src/relayCredential.ts`).
- One whose `allowed_relays` leaves out every TURN url the invitation names states that as the reason instead. -> One whose `allowed_relays` leaves out every TURN url and the WebSocket relay url the invitation names states that as the reason instead.
- `relay` is the inviting party's relay locator, TURN and STUN urls, a WebSocket relay url and a registrar url only (`relayLocatorSchema` in `packages/core/src/config/connection.ts`), with its grammar and bounds in [PROTOCOL.md](PROTOCOL.md#the-invitations-relay-locator). -> `relay` is the inviting party's relay locator, TURN and STUN urls, a WebSocket relay url with its exchange id, and a registrar url only (`relayLocatorSchema` in `packages/core/src/config/connection.ts`), with its grammar and bounds in [PROTOCOL.md](PROTOCOL.md#the-invitations-relay-locator).
- For the browser path the document's connection block is the `webrtc` channel restricted to its credential-free locator subset: `server` locator fields only (`host`/`port`/`path` -- no `server.username`, no PeerJS `key`), the `invitation_relay` the invitation named (TURN and STUN urls, a WebSocket relay url and a registrar url only, see [PROTOCOL.md](PROTOCOL.md#the-invitations-relay-locator)), and no `turn`, `ice_provision`, or `provider_options` entries (a TURN entry holds relay credentials, and the provider map is opaque and `@`-file-pathed). -> For the browser path the document's connection block is the `webrtc` channel restricted to its credential-free locator subset: `server` locator fields only (`host`/`port`/`path` -- no `server.username`, no PeerJS `key`), the `invitation_relay` the invitation named (TURN and STUN urls, a WebSocket relay url with its exchange id, and a registrar url only, see [PROTOCOL.md](PROTOCOL.md#the-invitations-relay-locator)), and no `turn`, `ice_provision`, or `provider_options` entries (a TURN entry holds relay credentials, and the provider map is opaque and `@`-file-pathed).
