# A CLI run allocates a relay on the first TURN url it lists and queries the
# first STUN url; the limit is stated once in PROTOCOL.md, and the pins name
# the parser test and the gathering test that vouch for it.
- - -> **A CLI run gathers from one TURN url and one STUN url.**
- - -> The CLI's WebRTC library takes the first TURN url and the first STUN url of the list it is given, so a CLI run gathers relay candidates from the first TURN url it lists (its own first `turn` entry, else the invitation's first url) and server-reflexive candidates from the first STUN url it lists (its own first `stun` url, else the invitation's first).
- - -> A CLI run whose connection has its own `turn` entry allocates only on the first such entry, which is on the invitation's relay only when that entry names one of the invitation's urls; the exchange may still pass through the invitation's relay by way of the partner's relayed candidates.
- - -> A CLI run enrolls at the registrar the invitation's relay names only when the url it allocates on is one the invitation names and takes the run's derived credential ([A command-line party](#enrolling-at-a-default-relay)); a browser partner enrolls there for its own allocation, so an exchange on a hosted invitation is still enrolled by the party that uses that relay.
- - -> A url both the connection and the invitation name is the same relay to the run only when it is written identically; an own entry spelled differently is a different relay, allocated on without the invitation's enrollment.
- - -> A browser run uses every server it lists.
- What a run states about the relays it uses, its relay credential notice among them, names the invitation's relay beside the party's own, and a report that no relay candidate was gathered means none was gathered from any relay the run lists. -> What a run states about the relays it uses, its relay credential notice among them, names the invitation's relay beside the party's own, and a report that no relay candidate was gathered means none was gathered from any relay a browser run lists, or from the one TURN url a CLI run gathers from.
- - -> **werift keeps the first TURN url and the first STUN url of the `iceServers` list and drops the rest.**
- - -> Its `parseIceServers`, given a list of two STUN urls and two TURN urls, returns options holding the first STUN address and the first TURN address with its username and credential only.
- - -> A CLI run therefore gathers relay candidates from the first TURN url it lists and server-reflexive candidates from the first STUN url, as [PROTOCOL.md](PROTOCOL.md#the-invitations-relay-locator) states.
- - -> The parser test (`test/unit/connection/webrtcIceConfiguration.test.ts`) pins what `parseIceServers` keeps.
- - -> The integration test (`test/integration/webrtc/firstTurnUrl.test.ts`) shows what a real peer contacts: a peer given two STUN and two TURN loopback servers, each answering with an error at once, sends requests to the first of each kind only by the time its gathering completes.
- - -> Run `npm run test:integration:webrtc -w apps/cli -- test/integration/webrtc/firstTurnUrl.test.ts` and `npm run test:unit -w apps/cli -- test/unit/connection/webrtcIceConfiguration.test.ts` for the one-TURN-url, one-STUN-url assumption.
- - -> A bump that contacts a further url reddens in the integration test, and the stated limit in [PROTOCOL.md](PROTOCOL.md#the-invitations-relay-locator) is then updated with it; the other documents link to it.

- The export writes the record's `invitation_relay` as the invitation named it, its `registrar` included, so a command-line run lists that relay and enrolls at the registrar the invitation names, whichever build named it ([PROTOCOL.md](PROTOCOL.md#enrolling-at-a-default-relay)). -> The export writes the record's `invitation_relay` as the invitation named it, its `registrar` included, so a command-line run lists that relay and enrolls at the registrar the invitation names, whichever build named it, only when the relay it allocates on is one the invitation names and takes the run's derived credential ([PROTOCOL.md](PROTOCOL.md#enrolling-at-a-default-relay)).
- Where the invitation names a registrar, the export panel states that each command-line run registers there before it connects and that whoever runs it learns that machine's network address. -> Where the invitation names a registrar, the export panel states, from the connection the export writes, whether a command-line run registers there before it connects, and where it does, that whoever runs that registrar then learns that machine's network address.
# The run credential paragraph says a run configures each url with a credential, and that a CLI run presents one to its first TURN url alone.
- A run that lists the invitation's TURN urls presents one credential to each of them, minted when the run starts (`mintRunRelayCredential`) and, in a CLI run, minted again for each connection attempt after the first while it waits for the partner ([WEBRTC_TRANSPORT.md](WEBRTC_TRANSPORT.md#connection-attempts)): the relay key derived from the shared secret the run holds, `ttl` = 3600, and `label` = `alcove`. -> A run that lists the invitation's TURN urls configures each of them with one credential, minted when the run starts (`mintRunRelayCredential`) and, in a CLI run, minted again for each connection attempt after the first while it waits for the partner ([WEBRTC_TRANSPORT.md](WEBRTC_TRANSPORT.md#connection-attempts)): the relay key derived from the shared secret the run holds, `ttl` = 3600, and `label` = `alcove`.
- A CLI run presents the same minted credential to each of its own `turn` entries that sets no `username` or `credential`, and an entry's own static pair to every other, whether or not it also lists the invitation's urls; a run holding no shared secret refuses such an entry by its url before anything is dialed. -> A CLI run configures each of its own `turn` entries that sets no `username` or `credential` with the same minted credential, and every other entry with its own static pair, whether or not it also lists the invitation's urls; a run holding no shared secret refuses such an entry by its url before anything is dialed.
- - -> Its WebRTC library contacts only the first TURN url it lists, so a CLI run presents a credential to that url alone ([the stated limit](#the-invitations-relay-locator)).
