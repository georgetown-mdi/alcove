- - -> **JSON messages on an encrypted channel.**
- - -> Once the application-layer encryption takes over the connection (`EncryptedMessageConnection.create` calls `requireBinaryFrames` before its first await), the encryption layer refuses any frame that is not `type 1`.
- - -> So the reader refuses a `type 0` message there before its payload is parsed, as a terminal `security` failure -- the class the encryption layer gives a frame that is not binary.
- - -> It consumes the refused file as it does any message it receives: deleted in delete mode, acknowledged and kept in retain mode.
- - -> If that delete or acknowledgement fails, the run ends with that failure instead.
- - -> The one `type 0` message a partner sends there is the cleartext key-exchange abort after a failed message 3 ([PROTOCOL.md](PROTOCOL.md#p-256-authenticated-key-exchange), "A failure of message 3"), and consuming it lets that partner's `close()` finish without waiting out the terminal-frame drain.
- - -> A new session on the same connection (`resetSessionState`) lifts the requirement.
- - -> A `type 0` message once the encryption layer requires binary frames is terminal too, as a `security` `ConnectionError` ([Message body format](#file-taxonomy), "JSON messages on an encrypted channel").
- - -> In both modes the receiver defers reading a complete message while it would hold more unreceived than the inbound cap ([TRANSPORT_BOUNDS.md](TRANSPORT_BOUNDS.md#inbound-frame-size-bound), "Read-ahead"), leaving it unconsumed and unacked, so the sender's wait for the delete or the ack also bounds the receiver's read-ahead.
- The post-handshake `TYPE_JSON` frame is decoded through it after AEAD decryption (the *counterparty*'s reach); but the file-sync transport's own reads - the peer-hello control file and every message body - are JSON-parsed off the raw inbound file *before* decryption, so they are shaped by the hostile *server admin*, and the invitation token is parsed from attacker-influenced bytes a victim opens. -> The post-handshake `TYPE_JSON` frame is decoded through it after AEAD decryption (the *counterparty*'s reach); but the file-sync transport's own reads - the peer-hello control file and every message body before the encryption layer takes over the connection - are JSON-parsed off the raw inbound file *before* decryption, so they are shaped by the hostile *server admin*, and the invitation token is parsed from attacker-influenced bytes a victim opens.
- - -> Once the encryption layer takes over, the transport parses no message body: it refuses a JSON message unread ([FILE_SYNC.md, File taxonomy](FILE_SYNC.md#file-taxonomy), "JSON messages on an encrypted channel").
- - -> **Read-ahead.**
- - -> The cap bounds one message file; the poll loop also bounds what it reads ahead of the consumer.
- - -> It reads the next message file only while that file and the message files it has read that the consumer has not yet received (the `QueuedMessageConnection` queue, whose count the loop reads through `setInboundQueueReader`) come to no more than the cap in force.
- - -> With none unreceived it reads the file, so no file within the cap is held back for good.
- - -> A file left unread is neither consumed nor acknowledged, so the partner's next send waits on it, within that send's own inactivity budget, until the consumer receives what is queued: frames a partner sends back to back, such as the parts of a PSI set, wait on disk rather than in memory, and none is refused.
- - -> A partner that stops sending is still caught by the receive deadline, since a receive waits only on an empty queue, and an empty queue holds no file back.
- The queue is **a count bound** rather than a byte one: the lockstep protocol drains one frame before sending the next, so the queue sits at depth ~1 in practice, and a peer that floods frames out of turn trips the count capacity (a `protocol` failure) rather than accumulating. -> The queue is **a count bound** rather than a byte one: a peer that floods frames out of turn trips the count capacity (a `protocol` failure) rather than accumulating without end.
- So the theoretical per-frame x depth aggregate requires both proportional wire bytes per frame *and* the consumer to stall, and is the count capacity's concern rather than this control's. -> -
- A byte-aware queue bound (or a smaller web-transport capacity) would close the theoretical multiplier but buys little against a practical depth of ~1. -> The file-sync poll loop holds what it reads ahead of the consumer to its inbound cap ([Inbound frame-size bound](#inbound-frame-size-bound), "Read-ahead"), but a data channel pushes its frames, so on this transport the frames a sender sends back to back, such as the parts of a PSI set, queue while the consumer is busy, up to that count.
- Unlike the per-frame scan, whose constants are WebRTC-specific, it would land on `QueuedMessageConnection`, which every transport shares, so it is a decision about all of them rather than this one, better made when a transport actually needs it. -> -
- - -> **Per-message byte caps.**
- - -> The structural ceilings bound a body's shape, not the memory its parse holds, which grows with the body's length.
- - -> So each message the table below lists is held to a byte cap sized to the largest legitimate message of its type, and a longer one is refused before it reaches `parseBoundedJson`.
- - -> These caps sit at the parse sites rather than in the chokepoint, because only the site knows which message it reads.
- - -> Each cap's worst case is static: the last column is the most a body at the cap was measured to hold once parsed, on Node 26.13.0 under `--expose-gc`, across the object, array, string and number shapes the structural ceilings admit.
- - -> Message | Cap, checked before the parse | Basis | Most held at the cap
- - -> File-sync rendezvous hello and control file (`fileSyncRendezvous.ts`) | 1,024 bytes (`HELLO_MAX_BYTES`), on the listed size and on the read | The envelope is under 100 bytes | 41 KB
- - -> File-sync abort marker (`abortMarker.ts`) | 1,024 bytes (`ABORT_MARKER_MAX_BYTES`), on the listed size and on the read | The envelope is about 80 bytes | 41 KB
- - -> JSON message on a file-sync run with a key exchange (`fileSyncMessageLoop.ts`, set by `apps/cli/src/run/prepare.ts`) | 4,096 bytes of payload (`KEX_MESSAGE_MAX_BYTES`) | The run's only JSON messages are the key exchange's; the largest, message 2 carrying a hello at the hello's limit, is 1,683 bytes, and the rest is room for further key shares in message 1 | 163 KB
- - -> Version hello within a key-exchange message (`versionHello.ts`) | 1,368 characters, 1,024 decoded bytes | The prologue length-prefixes a hello in two bytes; a hello this build writes is under 100 bytes | 41 KB
