# An invitation accepted on the console sets its own allowed relays on its
# review: the job request holds them, the console writes them into the run's
# alcove.yaml, and an opened alcove.yaml discloses its own.

The create refuses it unless it is the authored server's `host`, `port` and `path` and, for an acceptor's run, its `invitationRelay`, or, for an inviter's run, the `turn` urls of its `ownRelay` (see [The coordination server](#the-coordination-server)). It reaches no composed config key and no CLI argument: the connection is still drawn from the authored server alone. - - -> `allowedRelays` | optional array of strings, on the webrtc arm only, each graded and normalized by core's `connection.allowed_relays` entry rule (`AllowedRelaySchema`); an empty array admitted; refused beside `mountedConfigurationOpened: true` | The relays the run may use, as the console's accept review commits them. Each entry is a host with an optional port from 1 to 65535, with no scheme, path, query, user information or whitespace, written lowercase with no trailing dot. It is composed as the connection's `allowed_relays` and nothing else, never a path, credential or argv fragment, and it only narrows the TURN urls the run lists: no host it names is contacted for being named. A run of the opened configuration states its own `connection.allowed_relays`, so a create naming both fails validation. The array has no count or length cap of its own, as on the command line; the body cap and core's node budget for the composed document bound it.
- - -> The intent's `allowedRelays`, where it states them, are composed as `allowed_relays`, an empty list included.
- - -> Where the file states `connection.allowed_relays`, it holds that list as `allowedRelays`, an empty list included, which the browser shows on the review step and does not edit.
