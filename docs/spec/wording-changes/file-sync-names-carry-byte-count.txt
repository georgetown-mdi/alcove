- - -> This is why the `poll()` scan (site 3) must rely on the grammar discriminant: the party's own `<id>-hello-<bytes>.json` and ack share its message prefix and would be false positives under a bare `<id>-*` glob.
- - -> A rendezvous that fails terminally rolls back **this party's own rendezvous artifacts and nothing else**: its `<id>-hello-<bytes>.json`, the `<myId>-<peerId>-hello-<bytes>-ack.json` it wrote if it had already seen a peer hello, and its lock file on the lock path.
- - -> At `synchronize()` start (enforcement site 1), with no sweep flag, the directory must be empty except for at most one *peer* hello (a `-hello-<bytes>.json` whose recovered id is non-empty and not this party's own; a bare `-hello-<bytes>.json` parses to an empty id and is an unexpected protocol file, not a peer hello -- see site 5) and any foreign files.
- - -> The abort marker is the one kind whose disposition here is mode-dependent: in delete mode a well-formed `<id>-abort-<bytes>.json` under any id is swept by site 1(d) before this guard runs and so never reaches the rejection, while in retain mode it is rejected exactly like the kinds above.
- - -> A bare `-abort-<bytes>.json` recovers no id, is swept in neither mode, and is rejected in both.
- - -> A partner hello in an earlier version's shape, with no byte count, is refused ahead of this guard with a `UsageError` naming the earlier version ([Names an earlier version wrote](#file-taxonomy)).
- - -> Under lockless rendezvous a live peer the operator wrongly believed dead may have written its hello and its `-hello-<bytes>-ack.json` and a first message/ack; the sweep deletes every peer-prefixed protocol file, not only a second hello.
- - -> A file is routed as a message iff its terminal `.json` segment is all digits and the segment before it is not `hello`, `joining` or `abort`.
- - -> Control files (`hello`, `ack`, `joining`, `lock`, `abort`) are never routed.
- - -> A party's **own** files fall out of the same rule -- its hello has a type word before its byte count and its ack a non-numeric terminal, so site 3 never routes them as self-messages, which matters because under lockless rendezvous they persist into Phase 2.
- - -> Site 3 holds that with the discriminant itself (`isMessageName`), never a bare `<id>-*` glob or a per-type suffix list.
- - -> A **temp-then-rename** write (`hello` in the rendezvous write, the lock joiner's `joining` sentinel, `message` in `send()`, `ack` in `writeAck()`, and the lock joiner's rename of its sentinel into `<id>-hello-<bytes>.json`) is tracked *immediately after* the rename, because the final name only appears at that atomic step and the `add` follows it with no throwable statement between.
- - -> The joiner's `<id>-joining-<bytes>.json` sentinel, which holds the hello envelope, is written through the same `temp-hello-<uuidv4()>.tmp` stage as the hello.
- - -> No party reads the sentinel (the peer matches it by name existence -- see the `joining` taxonomy row), and it is the staged body the joiner renames into `<id>-hello-<bytes>.json`, so that hello appears atomically like any other.
- - -> Under [`write_without_renaming`](#writing-without-renaming) every temp-then-rename write above is a direct write instead and is pre-tracked like the `lock`; a body another party reads is then complete under its final name only by the operator's stated assumption, and what absorbs one read early is the reader's own byte-count gate (I5a for the hello, site 3 for a message).
- - -> Every payload-bearing file self-describes its full size in its filename, and a reader waits until the size reaches it.
- - -> For the message that is site 3.
- - -> The hello's reader is a read gate (`readControlFileWithGate` in `fileSyncRendezvous.ts`) that retries a read shorter than its name's byte count until its deadline, then validates `HelloEnvelope` on a read of exactly that size.
- - -> A hello listed or read larger than its name's count, or one of exactly that count that fails to parse, is a terminal `MalformedHelloError` ([I5b](#invariants)).
- - -> The gate first refuses a hello whose listed size or declared count exceeds `HELLO_MAX_BYTES` (1 KiB) with a terminal `FrameSizeExceededError`, and caps every read it makes at that size (see [TRANSPORT_BOUNDS.md](TRANSPORT_BOUNDS.md#inbound-frame-size-bound)).
- - -> The `joining` sentinel holds a hello envelope but is matched by name and never read, and the abort marker is read under its own `ABORT_MARKER_MAX_BYTES` cap, a pre-`get()` listed-size refusal, and a listed size and body that must equal its name's byte count or leave it unverified, rather than through this gate (see the [file taxonomy](#file-taxonomy) for both).
- - -> Every atomic write this model specifies ends in a `rename` to the final name: the hello write's `temp-hello-<uuidv4()>.tmp` -> `<id>-hello-<bytes>.json`, the joiner's `temp-hello-<uuidv4()>.tmp` -> `<id>-joining-<bytes>.json`, and its `<id>-joining-<bytes>.json` -> `<id>-hello-<bytes>.json` in Phase 1, a message's `temp-<uuidv4()>.tmp` -> its numeric-terminal name and an ack's temp -> `<writerId>-<originalName>-ack.json` in Phase 2.
- - -> hello | its size reaching the byte count its name declares, through the I5a read gate, which retries a short read until its bounded deadline, then validates `HelloEnvelope`
- - -> abort marker | its size equalling the byte count its name declares, then its verification: a torn body fails either, reads as no marker, and the loop keeps polling, at worst falling back to the peer-silence hedge
- - -> The joiner writes its `<id>-joining-<bytes>.json` sentinel, deletes the peer hello, writes its own hello, and only then deletes the sentinel.
- - -> A hard kill mid-`put` can leave a torn `<id>-hello-<bytes>.json`, the case the temp-then-rename hello write exists to prevent.
- - -> For the modes where the directory is still writable (a transport-op fault, a terminal parse error, a graceful crash) the authenticated `<writerId>-abort-<bytes>.json` marker covers it, letting the waiting party fail fast with a definitive `PeerAbortError` (CLI exit 76) rather than waiting out the full timeout.
- - -> It is additive to the filename grammar: the `abort` type word before its byte count routes it as a control file (the `isMessageName` discriminant), never mis-consumed as a message (see [the filename grammar](#the-single-critical-invariant-the-filename-grammar)).
- - -> It still exceeds the order-of-ten files a legitimate exchange produces (the two `-hello-<bytes>.json` files, at most one `-lock.json` or the `-ack.json` markers, transient `-joining-<bytes>.json` sentinels and `temp-*.tmp` writes, and the bounded set of PSI message frames) by roughly three orders of magnitude.
- - -> The lock joiner's `<id>-joining-<bytes>.json` sentinel is written temp-then-rename, the same as the hello (see [FILE_SYNC.md](FILE_SYNC.md)).
