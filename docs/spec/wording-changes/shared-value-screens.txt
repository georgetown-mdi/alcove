- - -> Shared-value screens
- - -> A shared-value screen drops a cleaned value held by more people in the party's own file than the field allows.
- - -> It is stated as a transformation's `max_people_per_value`, a whole number of at least 1, rather than as a step, because it reads the whole file and a step reads one value.
- - -> What the screen does
- - -> The screen runs after the field's pipeline has cleaned every record, and before any key is built.
- - -> It counts the distinct people in the file who hold each cleaned value of the field.
- - -> A value held by more than `max_people_per_value` people is dropped from every record holding it, as a step producing `null` drops it: the records keep their other fields, and every key that references the field leaves them out.
- - -> The defaults state these limits:
- - -> Field type | `max_people_per_value`
- - -> `ssn` | `1`
- - -> `phone_number` | `5`
- - -> `email_address` | `5`
- - -> No other default transformation states one.
- - -> Counting distinct people
- - -> A person is a record's cleaned `first_name`, `last_name` and `date_of_birth` values.
- - -> Each is read from the party's own column of that type, the first `role: linkage` column of the type in its metadata, declared or inferred, whether or not the terms declare a field of the type.
- - -> A type with no such column takes no part in the count.
- - -> The column is cleaned by the party's own transformation for a linkage field of that type where its standardization has one reading that column, and otherwise by the default pipeline for the type, a date's format inferred from the column (see [Date-format inference](#date-format-inference)).
- - -> The terms cannot remove a column from the count.
- - -> Records holding the same three values are one person, so a person's own duplicate records count once.
- - -> A record missing one or more of the values, because its cell was empty or its pipeline dropped the value, is the same person as a record that holds the same value of the field, agrees with it on every value it has, and has a value it lacks.
- - -> A record no other record completes this way is a person of its own.
- - -> When the file has none of the three columns, every record holding a value is one person, and the screen drops nothing.
- - -> The count has two limits:
- - -> A record with neither a name nor a date of birth agrees with every holder of its value, so it never counts as another person.
- - -> A person's own duplicate record whose cleaned name differs, such as a spelling variant, counts as another person, so a value can be dropped from one person's records.
- - -> For example, two records sharing an SSN, one holding `MARIA`, `LOPEZ`, `19800101` and the other no name and `19900505`, are two people, so the SSN is dropped from both.
- - -> Had the second record held `19800101`, the two would be one person and the SSN would be kept.
- - -> A record holding `MARIA`, `LOPES`, `19800101` beside the first is another person: the count compares cleaned values and corrects no spelling.
- - -> Under one-to-one matching the cascade accepts a pair only on a key value one record on each side holds (see [PSI](PROTOCOL.md#psi)), so a key value two of a party's records share already matches neither of them.
- - -> When one of two records sharing an SSN lacks the name or date a key needs, only the other builds that key and its value is unique, so the SSN screen is what drops it.
- - -> Why five people for a phone or email
- - -> A household shares a phone number or an email address, and an organization -- a shelter, a clinic, a case manager -- records its own number on many of its clients.
- - -> A shared number causes a false match only when two different people on it share a first name, which a key on first name and phone number cannot separate.
- - -> Household sizes in the US Census run 1 person 28%, 2 at 35%, 3 at 15%, 4 at 13%, 5 at 6%, 6 at 2%, and 7 or more about 1.5%, so a limit of five keeps about 96% of households.
- - -> The expected number of same-first-name pairs among h people is about h(h-1)/2 times the first-name collision rate, about 1% in general and 3% among concentrated names: 0.1 to 0.3 pairs among five people, and 12 to 37 among fifty.
- - -> The cost that remains is a household of six or more, which loses its phone and email values, and a household where two members share a first name, which only a date of birth separates.
- - -> Per-party limits
- - -> Each party may change a limit or remove it in its own standardization.
- - -> The cost of the count grows with the square of the limit, so a very large limit slows the first read of that field.
- - -> A limit decides only which values are dropped, never the form of a value kept, so it cannot make two different values equal.
- - -> Each party applies the screens to its own file only: the partner's records take no part in the count, and nothing about the screens is sent beyond the values that remain.
- - -> An authored standardization replaces the defaults entirely, so a transformation it writes without `max_people_per_value` has no screen.
- - -> A coverage count taken record by record before the run does not apply the screen.
- - -> No screen drops a date of birth for being frequent in the file.
- - -> The date-of-birth screens are the per-value ones its pipeline lists.
