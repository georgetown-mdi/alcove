# A browser run with the default relay switched off whose own relay setting
# names the relay's TURN url enrolls for it, as it does for an invitation's.
- Switched off, a run uses each of the relay's urls only where the invitation it accepted names that url: the TURN url, and the enrollment below, only where the invitation names the TURN url, and the WebSocket relay url only where the invitation names the WebSocket relay url (`defaultRelayForRun` in `apps/web/src/psi/transport/defaultRelay.ts`). -> Switched off, a run reads the relay's urls from one source, the invitation it accepted where that names the relay's TURN url and otherwise the browser's own relay setting, and uses each of them only where that source names it: the TURN url, and the enrollment below, only where the source names the TURN url, and the WebSocket relay url only where the source names the WebSocket relay url (`defaultRelayForRun` in `apps/web/src/psi/transport/defaultRelay.ts`).
- An unconfirmed one leaves it out, even where the invitation names it: the run says once, as the enrollment fails, that the relay could not be set up, and connects with its other relays. -> An unconfirmed one leaves it out, even where the invitation or the browser's own relay setting names it: the run says once, as the enrollment fails, that the relay could not be set up, and connects with its other relays.
- A run with the relay switched off whose invitation names the WebSocket relay url and not the TURN url enrolls nowhere, and lists that url as the invitation's. -> A run with the relay switched off where neither the invitation nor the browser's own relay setting names the TURN url enrolls nowhere, and lists the WebSocket relay url, where either names it, as that source's.
# An invitation created with the relay switched off names the relay's urls
# where the browser's own relay setting names them, never its registrar, so a
# command-line acceptor does not enroll.
- Where the locator names the default relay's TURN url, the web app also names that relay's registrar as `registrar`; the CLI names none. -> Where the default relay is in use and the locator names its TURN url, the web app also names that relay's registrar as `registrar`; the CLI names none.
- - -> With the relay switched off, the web app names no registrar, even where the browser's own relay setting names the default relay's TURN url and the locator names that url as one of the setting's (`invitationRelayWithDefault` in `apps/web/src/psi/transport/defaultRelay.ts`), so a CLI party accepting that invitation enrolls nowhere ([A command-line party](#enrolling-at-a-default-relay)).
- One created with the relay switched off names neither it nor its registrar. -> One created with the relay switched off names no registrar, and names the relay's TURN url or WebSocket relay url only where the browser's own relay setting names that url, as one of the setting's.
- A CLI party learns the registrar from the invitation: an invitation such a build makes names it as its relay locator's `registrar` ([The invitation's relay locator](#the-invitations-relay-locator)), and the accepting party keeps it in `invitation_relay`. -> A CLI party learns the registrar from the invitation: an invitation such a build makes with the relay in use names it as its relay locator's `registrar` ([The invitation's relay locator](#the-invitations-relay-locator)), and the accepting party keeps it in `invitation_relay`.
- `registrar` was added to the strict locator without a `version` bump too: a decoder predating it, an earlier web app or CLI build among them, refuses every invitation that names it, as every invitation a build with a default relay makes does. -> `registrar` was added to the strict locator without a `version` bump too: a decoder predating it, an earlier web app or CLI build among them, refuses every invitation that names it, as an invitation a build makes with its default relay in use does.
- - -> An invitation a browser created with the default relay switched off names no `registrar`, even where it names that relay's TURN url because the browser's own relay setting names it ([Composition](#the-invitations-relay-locator)), so a CLI run accepting it that allocates on that url enrolls nowhere and states nothing about it.
- - -> The relay then takes that allocation only where the browser inviter's own run enrolled the key there, which it does before it contacts the coordination server, and refuses it where that enrollment failed.
