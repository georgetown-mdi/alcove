- - -> The CLI holds a remote candidate that arrives before the remote description, within the cap in [Budgets](#budgets), and hands every held candidate to the ICE agent once the description is applied, without waiting for any of them to be applied first, and an inviter sends its answer without waiting for them either.
- - -> A candidate arriving after the description is handed over as it arrives, independently of the others.
- - -> werift takes 10 s to give up on a browser's `.local` host candidate that no host answers for ([DEPENDENCY_PINS.md](DEPENDENCY_PINS.md#the-behavioural-assumptions)), so waiting on each in turn would delay every candidate behind it, and the answer, by that much.
- - -> **A remote host candidate named `<uuid>.local`, the form a browser gives its host candidates by default, is resolved by an mDNS query, and one no host answers costs 10 s.**
- - -> werift 0.25.0's `addIceCandidate` does not settle until the query is answered or 10 s pass; an unanswered candidate is then dropped without an error and never reaches the ICE agent or `getStats`, and a candidate handed over after it is kept.
- - -> So the transport hands held candidates over without waiting on each ([WEBRTC_TRANSPORT.md](WEBRTC_TRANSPORT.md#negotiation-envelope)).
- - -> Driven with two werift peers through the broker, the partner's description followed by two unresolvable `.local` candidates and then the one usable `srflx` candidate, the channel opened about 20 s after the description when each held candidate waited on the one before it, and about 0.2 s after it without (`test/integration/webrtc/heldRemoteCandidates.test.ts`).
- - -> A lookup still pending when its peer connection closes keeps its timer, which holds the Node event loop until the 10 s are up: measured on a bare peer connection, the loop drained about 9.8 s after the close.
- - -> Run `npm run test:integration:webrtc -w apps/cli -- test/integration/webrtc/heldRemoteCandidates.test.ts` for the `.local` assumption.
- - -> It holds that a channel whose only working path follows two unresolvable `.local` candidates opens within 5 s of the description, in both roles; it does not time the lookup itself, so re-time one `addIceCandidate` of an unresolvable `.local` candidate by hand, and a bump that changed the 10 s goes back into the bullet above with its new value.
