# WEBRTC_TRANSPORT.md specifies the CLI's fallback from WebRTC to the
# WebSocket relay in a section beside Connection attempts, and its Budgets
# row states that the channel-open budget also sends the relay's start.
- - -> Falling back to the WebSocket relay
- - -> A CLI run that lists WebSocket relays races the connection attempts above against them, on the relay client of [WEBSOCKET_RELAY.md](WEBSOCKET_RELAY.md#the-command-line-client).
- - -> No run lists one yet ([No run dials one](PROTOCOL.md#the-invitations-relay-locator)): a run with an empty list dials no relay socket and opens WebRTC alone.
- - -> **Parked as the rendezvous starts.**
- - -> The run dials every relay it lists, in parallel, as its first registration starts, and holds its start on each.
- - -> **What sends the start.**
- - -> This side sends its start on the first of these: the channel-open budget expiring on any attempt, the last or not; the peer connection reporting `failed`; a registration with the coordination server failing with no refusal from it, or the registered socket dropping once the partner has sent its description; and the partner's start arriving on any relay.
- - -> A certificate that did not verify on this host is not one of them, and fails the run as above whatever the relays are doing.
- - -> Any other failure of the wait before one of these fails the run and closes every relay socket.
- - -> **Where the start goes.**
- - -> The inviter sends its start on one paired relay: the first the partner's start arrived on, else the first paired in the run's list order, else the first to pair.
- - -> If that relay fails, it sends its start on the next by the same rule.
- - -> The acceptor sends its start on every relay that is paired or pairs later, and keeps the one the inviter's start arrives on.
- - -> Only one inviter start exists, so both parties end on one relay.
- - -> **WebRTC after the start.**
- - -> Sending the start does not stop the WebRTC wait: its attempts go on until the partner's start arrives, which abandons it at once.
- - -> A WebRTC wait that fails once this side has sent its start leaves the exchange to the relays.
- - -> **The first path to open.**
- - -> A data channel that opens first closes every relay socket, with 1000 where this side's start was not sent on it and with 4000 where it was, as the relay client closes an unused socket.
- - -> A relay that opens first, both starts having crossed it, closes every other relay socket and abandons WebRTC, and a data channel that opens after that is closed unused.
- - -> **When both fail.**
- - -> The run fails once the WebRTC wait has ended and every relay has failed.
- - -> It fails with the WebRTC failure, or, where the partner's start abandoned WebRTC, with the failure of the first relay this side started on.
- - -> Every other relay's refusal is logged as a warning before it.
- - -> **What the operator sees.**
- - -> The run logs at info level when it sends its start, and which path carries the exchange: the WebRTC connection, or the WebSocket relay at its url.
- - -> **A stated limit.**
- - -> The two parties can take different paths when a data channel opens on one side as the partner's start abandons WebRTC on the other.
- - -> Each then fails on its own path, the WebRTC side when the partner's peer connection closes and the relay side when the partner closes its relay socket, and running the exchange again recovers.
