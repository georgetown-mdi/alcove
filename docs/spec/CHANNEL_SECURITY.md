# Channel security construction

This document specifies the construction and implementation of Alcove's
channel-security controls, the section headings below indexing the individual
controls. It is
the implementation-level complement to the **Channel security** overview in
[SECURITY_DESIGN.md](../SECURITY_DESIGN.md#channel-security), which covers what
each control protects against and why the design is sufficient; this document
covers the wire formats, the derived constant values and their justification, the
enforcement points, and the dependency assumptions each control rests on. It does
not cover the threat model or authentication design (see
[SECURITY_DESIGN.md](../SECURITY_DESIGN.md)), the PSI and key-exchange wire
protocol (see [PROTOCOL.md](PROTOCOL.md)), or the network channels and transport
contract (see [COMMUNICATION.md](../COMMUNICATION.md)). Intended readers are
security auditors and implementors.

Every net-new control specified here is subject to the explicit pre-release
security review required by
[CONTRIBUTING](../../CONTRIBUTING.md#dependency-policy); the per-section notes
below repeat this only where a control has an extra scope nuance (an
internet-facing surface, a new security-relevant dependency, or a modification
layered on an existing control).

# Application-layer AEAD

Both parties use the HMAC-based Extract-and-Expand Key Derivation Function (HKDF) to derive AES-GCM keys from the 32-byte key-exchange session key - two directional keys, one per direction (HKDF info strings `alcove-aead-v2:initiator-to-responder` and `...responder-to-initiator`) rather than a single common key - so that every key has a single sender, and messages are encrypted using Authenticated Encryption with Associated Data (AEAD). Each message holds a per-direction sequence number as its nonce, preventing replay and reordering. The separate per-direction keys are what keep that nonce construction safe: both directions number their messages from zero, so a single common key would encrypt two different messages under the same key and nonce - a reuse that is catastrophic for AES-GCM - whereas one key per sender keeps every key-nonce pair unique. The server admin sees only opaque ciphertext files, and tampering with a file causes the authentication tag to fail and the exchange to abort. The AEAD context is restricted to this fixed pair of per-direction labels (a closed union, guarded at runtime), not an open string. Both parties must derive identical per-direction keys from identical labels; a variable, non-ASCII, or non-NFC label would make the two sides derive different keys and fail the AEAD with an opaque error rather than a clear authentication failure, so the label set is closed by construction.

The concrete envelope the `EncryptedMessageConnection` decorator emits is a binary frame `version || IV || ciphertext || 16-byte GCM tag`, encoded as raw bytes (no base64url, no JSON wrapper). `version` is a single leading format/version marker (`AEAD_ENVELOPE_VERSION`, currently `1`); the 12-byte IV is four leading zero bytes (authenticated, but not separately validated) followed by the 8-byte big-endian sequence number; and the encrypted plaintext is a one-byte type tag (`0` for a JSON object, `1` for a `Uint8Array`) ahead of the payload. The type tag stays inside the authenticated ciphertext and is never promoted to a cleartext envelope field, so a transport admin cannot flip JSON/binary routing without failing the GCM tag. The version marker turns a format mismatch -- an envelope from an incompatible build, or an inbound that is not the binary shape at all (the clean break from the prior base64url-in-JSON `{ enc }` format) -- into a clean `security` rejection rather than a silent misparse. This wire format is pinned byte-for-byte by a checked-in known-answer vector at [`packages/core/test/vectors/aead-envelope-vectors.json`](../../packages/core/test/vectors/aead-envelope-vectors.json), following the cross-implementation vector precedent of `canonical-vectors.json` and `exchange-record-vectors.json`: each vector fixes a session key, role, sequence number, and plaintext and records the exact `envelopeHex`. An independent implementation can therefore reproduce it from those inputs, and any change to the version marker, nonce construction, byte order, envelope shape, or tagging is caught. The vectors are regenerated by `generate-aead-envelope-vectors.mjs` in that directory and asserted against the decorator in `packages/core/test/connection/encryptedMessageConnection.test.ts`, which separately pins the per-direction HKDF key derivation (`deriveAeadKey`).

Because the type tag is encrypted, the file-sync transport beneath the AEAD layer cannot read it to route a frame, so it has its own outer, cleartext discriminator. Every data-plane message file is a binary envelope `version || type || seq || payload` (serialized and parsed in `fileSyncFraming.ts`, which `send()`/`poll()` in `fileSyncMessageLoop.ts` call), where `type` selects a JSON control payload (UTF-8 JSON, parsed through the `parseBoundedJson` chokepoint) or a raw binary frame (delivered as-is). This too holds the frame as raw bytes -- no base64url and no whole-frame string conversion -- so the read path never calls `Buffer.prototype.toString()` and a frame larger than Node's maximum string length can be read.

## Which channels request it

The wrap is applied when the key exchange's transcript-bound decision says so, and that decision is the OR of the two parties' requests: either party asking for it turns it on for both. What each party asks for is fixed by the channel, not configurable.

| Channel | Requests the wrap | Why |
| ------- | ----------------- | --- |
| `sftp`, `filedrop` | yes | The exchange sits in a server's or a share's filesystem. Its administrator can read and alter every frame, so the confidentiality and integrity have to come from a layer above the transport. |
| `webrtc` | no | A data channel is end-to-end confidential and integrity-protected under DTLS between the two parties. The signaling server introduces them and sees no exchange content, and a TURN relay forwards ciphertext. The wrap would protect nothing the transport has not already protected. |

The `webrtc` posture is also a compatibility requirement rather than only a judgement: the web implementation declines the wrap and refuses a partner that requests it (`apps/web/src/psi/authenticateExchange.ts`), so a CLI peer that asked would abort the exchange rather than upgrade it.

The one case that would change this is a transport leg an intermediary terminates -- concretely, a WebSocket-to-TCP proxy relaying a party's traffic, which would put a third party inside the confidential channel. No such transport exists. If one lands, the request bit is how the party behind it asks for the wrap, and the web side's hard refusal of a true request is what would be revisited then. No negotiation mechanism is built for that case in advance.

The limit that leaves is the browser path's, and it is a stated one: a web exchange has no application-layer encryption of its own, so every frame's confidentiality is the data channel's DTLS and nothing above it. Both connection shapes the web app can form keep that DTLS end to end -- a direct path, and a TURN-relayed one, which forwards without terminating -- so the limit binds only against an intermediary-terminated leg of the kind above, which no shipped configuration can put in the path.

## IV construction and SP 800-38D conformance

The 96-bit IV is the deterministic construction of [SP 800-38D](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-38d.pdf) (November 2007) section 8.2.1, laid out as that section suggests for the default 96-bit IV length: the leading 32 bits hold the fixed field and the trailing 64 bits hold the invocation field. Read against section 8.2.1's own stated requirements, the construction **satisfies** them, with one qualification -- stated at the end of this section -- on what the all-zero fixed field rests on.

- **The IV is a fixed field concatenated with an invocation field.** `seqToIv` writes the 8-byte big-endian counter at `IV_SEQ_OFFSET` = 4 into a zeroed 12-byte buffer, giving a 32-bit fixed field followed by a 64-bit invocation field. Section 8.2.1 suggests, but does not require, exactly those lengths and positions for a 96-bit IV.
- **The fixed field identifies the context.** The fixed field is 32 zero bits and identifies nothing by itself, which section 8.2.1 permits where "the entire fixed field may consist of arbitrary bits when there is only one context to identify, such as when a fresh key is limited to a single session of a communications protocol". Each AEAD key here is limited to one direction of one session. It is derived by HKDF from the per-session key-exchange session key, which is transcript-bound and mixes each run's fresh ephemeral scalars, and it is imported non-extractable with a single usage (`encrypt` for the send key, `decrypt` for the receive key) held only by the decorator, so exactly one sender ever invokes the authenticated encryption function under it. One context, so the arbitrary-bit case applies.
- **No two distinct sets of inputs share an invocation field.** `sendSeq` starts at 0 and is consumed by a synchronous post-increment, one value per `send()`, ahead of the encrypt and transport awaits, so two concurrent sends cannot take the same value. A value consumed by a send that then fails is never re-issued: the failure latches the wrapper terminal, so nothing is sent under it or after it. A counter past `Number.MAX_SAFE_INTEGER` is refused with a `security` failure rather than wrapped.
- **The lengths and positions are fixed for the life of the key.** `IV_SEQ_OFFSET` is a module constant and 96 bits is the only IV length this layer supports, so the split is fixed across every key rather than only within one. The known-answer vectors above assert the two fields separately at three sequence numbers across both roles -- that the fixed field is the four bytes `00000000` and that the invocation field decodes big-endian to the vector's sequence number -- so a change to either field's length or position fails the suite.
- **Exactly one construction is used per key (section 8.2).** `seqToIv` is the sole producer of IVs under an AEAD key. The two keys are imported non-extractable with a single usage each -- the receive key cannot invoke the authenticated encryption function at all, which WebCrypto enforces -- and the send key is held in the decorator's private field rather than returned to a caller, so no second instance encrypts under it and no RBG-based IV is produced for it.
- **The invocation constraints hold with margin (section 8.3).** Section 8.3's 2^32 global invocation cap does not reach this construction -- it excludes an implementation that only uses 96-bit IVs generated by the deterministic construction, which is this one. The two constraints section 8.3 does apply at every IV length are both met: the 64-bit invocation field bounds invocations under one key and fixed field at 2^64, against the counter's own ceiling of `Number.MAX_SAFE_INTEGER` (2^53 - 1); and the 32-bit fixed field bounds distinct contexts under one key at 2^32, against the single context each key has.

**The qualification.** Section 8.2.1 attaches a condition to the arbitrary-bit fixed field: "if different participants in the session share a common fixed field, then the protocol shall ensure that the invocation fields are distinct for distinct data inputs". Both participants do use the same all-zero fixed field and both number their messages from zero, so their invocation fields are not distinct. What keeps the construction off that condition is that section 8.2.1's requirements are scoped *for any given key*, and the per-direction key split means the two participants never share one -- each key has exactly one sender, so there are no two participants under it whose invocation fields could collide. The satisfied outcome therefore rests on the key split, not on the IV alone: collapsing the two directional keys into one shared key turns it into a violation of section 8.2.1, which is the conformance statement of the key-nonce reuse the AEAD description above calls catastrophic.

Section 8.2.1 constrains how an implementation generates IVs for the authenticated encryption function, not what it accepts, so the receiver's not separately validating that an inbound IV's leading four bytes are zero is outside the section. Those bytes are covered by the GCM tag either way, so an IV that is not the sender's own fails authentication.

Conformance to section 8.2.1 is a statement about the construction and not about a module certificate's approved services. The FIPS 140-3 certificate this project targets makes AES-GCM with an externally supplied IV a non-approved service whatever construction produced the IV, and a `crypto.subtle` AES-GCM call supplies one by construction; see [COMPLIANCE.md](../COMPLIANCE.md#fips-140) for the scoped claim that follows from that.

## Associated data is not bound

The envelope binds no Associated Data (AAD), and this is a deliberate, recorded decision rather than an omission. AAD would matter only to stop a frame authenticated under one context (role/direction, session, or transcript) from being spliced or replayed into a different context that shares the same key. Here every such context is already separated below the AAD layer by a distinct key. Direction is bound by the key: each direction uses its own AES-GCM key, derived with a distinct HKDF info string (`alcove-aead-v2:initiator-to-responder` versus `...responder-to-initiator`), so a frame presented to the opposite direction decrypts under the wrong key and the tag fails. Session is bound by the key: both keys derive from the per-session key-exchange session key, which is transcript-bound and mixes in each run's random ephemeral scalars, so it is distinct even across two runs of the same shared secret - a frame from one session decrypts under the wrong key in another. Ordering within a single direction of a single session is bound by the sequence-number nonce and the strict-increasing replay guard. The only set of frames that share one AEAD key is those one sender emits in one direction of one session, and the decorator holds exactly one logical stream there - it does not multiplex sub-channels or protocol phases, and the one-byte payload type tag that distinguishes binary from JSON lives inside the authenticated plaintext. There is therefore no second logical context under a shared key for AAD to separate, so binding the direction (or a session id) as AAD would only restate what the key already enforces. The sequence number is the GCM nonce, not a substitute for AAD: the reason AAD is unnecessary is the absence of a second context under one key, not that the nonce stands in for AAD. Practically, the decorator holds only its inner connection and its two directional keys - no session or transcript id is in scope to bind without new plumbing from the caller that constructs it.

Revisit this decision if a future change multiplexes more than one logical stream or protocol phase over a single direction's key, or collapses the per-direction key split into one shared key. In either case a context or sub-stream id bound as AAD would stop being redundant: it would still block cross-direction splicing, though not the key-nonce reuse that collapsing the key split would itself make catastrophic (AAD does not protect against nonce reuse). Until then, the per-direction key plus the sequence nonce are sufficient and no AAD is bound.

## Inbound integrity, replay, and ordering checks

This layer's AEAD/MAC and sequence-number (replay and ordering) checks run at the protocol layer, on the output of a `receive()` call: the decorator validates and decrypts each inbound envelope inside `receive()` and rejects with a `security` `ConnectionError` on any integrity, replay, or ordering failure. These checks are not latched into the inner connection as a transport control (the `fail`/`finish` teardown signals) behind a buffered inbound frame. The message queue drains an already-received frame to the consumer ahead of any terminal error, whether the close was clean or abnormal (see [Message delivery and teardown](../COMMUNICATION.md#message-delivery-and-teardown)), so a check wired as a transport-level latch could hand a suspect frame to the consumer before the integrity alarm fires. The decorator honors this - it raises the failure from `receive()` itself, and the inner transports latch no integrity check behind a frame (the `security` error an inner transport can raise, such as an SFTP host-key refusal, fires while connecting, before any frame) - so the constraint holds and remains one to preserve.

Mid-stream gap detection is strict: the decorator rejects any inbound sequence number that is not exactly the last accepted plus one, so a frame dropped or withheld between two delivered frames is caught here as a `security` failure on the output of `receive()` - the same protocol-layer reporting as the replay and tag checks, never a transport-level latch. It raises no false alarm against the send path's synchronous `sendSeq++` ahead of the encrypt (which is what keeps two concurrent sends from peeking the same counter and reusing an AES-GCM nonce). A send that consumes a counter value but then fails to transmit (an encrypt fault or an inner transport failure) latches the wrapper terminal, so no later frame is ever sent, and a consumed-but-unsent value can only truncate the tail, never leave a gap between two delivered frames.

## End-of-stream and truncated-tail detection

End-of-stream / truncated-tail detection is a deliberate accepted deferral, not a coverage gap to be closed with a marker. A truncated tail - a stream that simply stops, including a dropped final frame - is indistinguishable at the AEAD layer from a clean end, and no AEAD tag can authenticate the *absence* of a frame: an omitted frame can be detected only by expecting one and not receiving it. The PSI protocol is self-driven lockstep (see [PROTOCOL.md](PROTOCOL.md)): each party drives a deterministic script of matched send/receive calls, so the receiver always knows from its own script whether another frame is due. In the symmetric case a truncated tail therefore is reported - as a stalled `receive()` that hits the inactivity timeout - and an explicit, integrity-protected end-of-stream marker could only reclassify that timeout from `transport` to `security`, not detect the omission any sooner. Reclassification alone does not justify net-new, security-reviewed cryptographic surface, so the marker is not built. The lockstep is unconditional in every implemented cardinality: the matching loop runs `identifyIntersection` for every agreed key on both parties -- the key set is fixed by the linkage terms, and the PSI library returns an empty intersection without error for an empty input set, so a locally-empty round is a correct no-op that both sides still perform. A per-party-data-gated skip (`if (data_j.length === 0) continue;`) would break this: `data_j` is built from a party's own still-unmatched records, so one side can empty a later key while its partner does not, and skipping there drops a send/receive the partner still performs and desyncs the exchange. Any future cardinality loop must therefore not reintroduce such a skip. This is a protocol-loop invariant, not an absent-frame one: no AEAD-layer marker could detect or repair a lockstep desync, so the end-of-stream marker's deferral is independent of it.

## Authenticated abort marker

A distinct channel control is the **authenticated cross-party abort marker**, the one mechanism here that is not a bound on a hostile operation but an authenticated signal between the two honest parties. On the file-sync transports a failed exchange gives the waiting peer no in-band notice that its partner has given up, leaving it to wait out the full peer-inactivity budget (default one hour) and then print a generic peer-silence hedge. The marker closes that gap: when a party fails terminally with its directory still writable, it writes a best-effort `<id>-abort.json` holding a 32-byte token `HKDF(sessionKey, "alcove-abort-token-v2:<role>")`; a waiting peer that reads a `<peerId>-abort.json` whose token verifies against its own locally-derived peer token fails fast with a definitive `PeerAbortError` (exit 76) instead. The token is the authentication: a hostile filedrop/SFTP admin can write or rename any file in the rendezvous directory, but cannot produce a token that verifies without the per-session session key, so cannot forge an abort against a live peer. The label is domain-separated from the other session-key derivations - exact-distinct and prefix-free from the AEAD `alcove-aead-v2:<context>` and the `alcove-shared-secret-rotation-v2` labels - so an abort token can never collide with or substitute for an AEAD key or the rotation secret. The comparison is constant-time and length-safe, and the read fails closed on every absent, oversized, malformed, wrong-version, or non-matching input. The per-direction (role) binding makes a captured marker renamed to the other party's name verify under the wrong token and fail; the per-session ephemeral key makes a marker captured from one exchange inert in another.

The marker is best-effort and has no cause, both deliberate. Its absence is strictly uninformative: a deleted, withheld, or forged marker simply degrades to the peer-silence timeout and hedge - it is never treated as success - so a hostile admin can at most *suppress* the fast-fail, never forge an abort or turn a failure into an apparent success. It has no cause because the cause is not actionable to the waiting party - which holds no local error and must contact its partner regardless - and a plaintext cause on the untrusted channel would only widen disclosure; the token itself is a one-way HKDF output that reveals nothing about the session key or any other derived key. Because the marker is re-read every poll cycle, it is capped small - a pre-`get()` listed-size refusal and a bounded `get()`, both at 1 KiB rather than the ~512 MiB frame maximum - so an admin-plantable file cannot become an availability vector. A marker that fails to parse or verify is ignored and re-read next cycle, but a read the transport refuses as stalled or over its cap ends the run on that typed error, as the same refusal does on every other read of the cycle, rather than degrading to the peer-silence timeout. The write is short-budgeted on both its `put` and `rename` (a few seconds each) so a sick directory cannot hang teardown. The mechanism is file-sync only: the connectionless file transport is the only one with a parked-waiter problem, since a WebRTC peer's death drops the DTLS data channel and is reported promptly; a future cross-transport abort would instead state a protocol-layer error kind rather than an on-disk marker.

# Display bounds

## Display sanitization escape format

The display sanitizer escapes a string for operator-facing output by replacing every byte or code point that is not printable ASCII - C0 and C1 control characters, DEL, and any non-ASCII code point - with a hex escape: `\xHH` for a code point <= 0xFF, `\uHHHH` for a code point <= 0xFFFF, and `\u{HHHHH}` or `\u{HHHHHH}` (unpadded) for an astral code point above 0xFFFF. A literal backslash is doubled (`\\`), and printable ASCII (0x20 to 0x7E) is otherwise left unchanged. The output is truncated to a bounded maximum length with a visible truncation marker. It is a one-way display transform: the escaped form is never parsed back and never used to build a filesystem path. Matching and routing decisions use the original bytes, with one deliberate exception: the console's relay of CLI events (`apps/web/src/jobs/cliDriver.ts`) escapes an event's keys, compares the escaped key against the name of the field the relay itself owns (so a source key that would land as that name is dropped), and uses escaped keys as the keys of the relayed object. That use is fail-safe, since escaping can only make a key differ from the source's.

The transform is applied once per fragment, at the sink that shows it, to the fragments the operator did not choose - the boundary the next paragraph draws - on every route the assignment below governs; the routes that do not yet meet it are enumerated at the end of this section rather than left implicit. Every escape doubles a literal backslash, so a value escaped at two altitudes reaches the operator with a backslash count that no longer matches the bytes it names - one backslash in a partner filename shown as four, in a message telling the operator to go and delete that file. The two altitudes are therefore assigned rather than left to each call site: a fragment interpolated into an `Error` message or `cause` is composed raw and escaped once by `sanitizeErrorForDisplay` where the error is rendered (which also caps each cause-chain link and strips PEM/OpenSSH private-key blocks). A value that reaches a log, a console, or a UI element without ever becoming an `Error` is escaped by `sanitizeForDisplay` at that call site, which is its sink. A fragment bound for a log or prompt sink takes both halves in one call, `redactAndSanitizeForDisplay`, which redacts and then escapes -- the same single escape, not a second altitude.

**The escape applies to the side of the fragment boundary the operator did not choose.** Doubling a literal backslash is what keeps the `\xHH` tokens unambiguous over bytes somebody else chose, and it is wrong over a path the operator typed: `C:\data\in.csv` reaches them as `C:\\data\\in.csv`, a path they cannot copy back into a command. So the two altitudes above assign a treatment per FRAGMENT rather than per value. A fragment nobody marked is escaped, which is the default and the reason a partner-chosen value keeps its escape by doing nothing. A fragment the composition site marks as the operator's own -- `operatorSuppliedText` (`packages/core/src/utils/operatorSuppliedText.ts`) -- is rendered as they typed it by `renderOperatorSuppliedText` (`packages/core/src/utils/sanitizeForDisplay.ts`), which replaces the control class with the same printable `<HH>` marker the control replacement emits, replaces the U+2028 and U+2029 line separators and any lone surrogate with a `<HHHH>` marker of that same shape, and leaves every other code point standing. A message assembled from both sides therefore escapes the part of itself the operator did not choose. What the render gives up against the escape, over bytes the operator chose, is the bidi and confusable neutralization. What it keeps out is the class that drives a terminal -- an ESC opening an ANSI sequence, a break spoofing a log line -- along with the two line separators `\p{Cc}` does not hold and a reader still breaks a line on, and a lone surrogate, which would leave what the sink is handed non-well-formed. It keeps them out because a path can be copied into a configuration out of an invitation the partner wrote, and each renders to a marker with no backslash for the sink to escape.

The mark reaches each sink on the route that sink is on. On the ERROR route the composition site builds its message through `messageWithOperatorText` and marks the error with `keepOperatorSuppliedText`, which records the message's spans and their origins; `sanitizeErrorForDisplay` then renders that link span by span, redacting each span, escaping the ones nobody marked, and spending one per-link budget (`COMPOSED_MESSAGE_MAX_DISPLAY_LENGTH`) across all of them, so a partitioned link is bounded exactly where an unpartitioned one is. Redacting per span narrows the fail-closed dangling rule the way a composition site does: a `BEGIN` marker in the path costs the path and not the instruction composed behind it. On the LOG, console and prompt route the call site takes `redactAndRenderOperatorSuppliedText`, the operator-origin sibling of `redactAndSanitizeForDisplay`; the log prefixer's own per-argument strip is unchanged and runs over both renderings alike. Both entry points take the MARK rather than a string, so on either route the claim "the operator chose these bytes" is a value the composition site builds and a plain string or a `PartnerOriginText` is a compile error at the sink; a value that reaches one unmarked regardless is escaped rather than rendered as given. Two limits are measured rather than assumed. The mark is a registered symbol property, so no value a partner sends can ask for the treatment -- no parse produces a symbol key -- and it is read only where its spans join back to the link's own message, so a mark describing other text costs a doubled backslash rather than a wrong rendering; a link that also kept its own line breaks renders through that form instead, which escapes every span. And a boundary holding a chain as rendered TEXT has no mark to read: `sanitizeErrorChainLinks` escapes each link whole, so an operator's path relayed to the console arrives there with its separators doubled. `packages/core/test/utils/operatorSuppliedText.test.ts` pins the rendered output of a message carrying an operator path beside a partner-chosen fragment, and `packages/core/test/utils/logger.test.ts` pins the two on one log line.

Which sites are on the mark is held by a check over the names it can recognize rather than by a roster. An ESLint ban over `apps/cli/src` (`eslint.config.mjs`) reports a name composed into an `Error` message, a cause, or a log, console or prompt call without the mark, since the name is the only origin evidence text alone holds -- the config runs no TypeScript program. The names it matches are exactly three shapes: a name ENDING in `Path`, `File`, `Dir`, `Directory` or `Folder`, with or without a trailing `s` and with or without a trailing `Arg` or `Args`, or one of those words alone (`configPath`, `keyFile`, `inputDir`, `identityFileArg`, `path`); a name OPENING with `path`, `file`, `dir`, `directory` or `folder`, followed by `s`, `name` or `names` or nothing, and then a capital or the end of the name (`pathValue`, `fileName`, `filename`, `dirPath`); and the bare words `target` and `input`, with or without a trailing `s` and with or without a trailing `Arg` or `Args`, which a positional or flag argument takes its name from (`targets`, `inputArg`). A name outside those three shapes is NOT held -- `output`, `destination` and `source` compose unnoticed -- so a sink written under such a name is marked or left raw in silence rather than being reported, and what the check holds is the shape it can recognize by name and not every operator path; a sink named outside the shapes is held by its case in `apps/cli/test/unit/commands/operatorPathMarks.test.ts` rather than by the ban. A value a partner or a server named is a match the ban is wrong about and takes a one-line `eslint-disable`, the same opt-out as its two siblings above. `scripts/eslint-unmarked-operator-path-ban.test.mjs` holds the ban's own coverage -- both the names it reports and a name outside the pattern it lets through -- because a selector that stops matching keeps reporting zero problems.

Every CLI source is linted by the ban, new files included -- held for the names the three shapes above reach and for no others -- and the sensitive-file re-export shim takes a config block of its own, so the raw-parse exemption it needs does not spare it this one. No source is exempt. What stays unmarked is a path whose bytes a partner or a server chooses in part -- the operator's configured rendezvous directory joined to a peer-chosen name, or that directory seeded from the invitation on an offline accept -- and such a path keeps the escape whole, so the operator's own directory renders there with its separators doubled; over-escaping is the safe direction. Each site takes the one-line `eslint-disable`, stating why where it sits -- the inbound file of the frame-size refusal, the rendezvous directory of the listing refusals (seeded from a partner's invitation endpoint on an offline accept), the stalled operation's path, and the publish destination an indeterminate publish names (`apps/cli/src/connection/frameSizeGuard.ts`, `listingGuard.ts`, `sftpLivenessGuard.ts`, `sftpAdapterWarnings.ts`). What the ban cannot see is a path under a name none of the three shapes reaches -- `output` or `destination` above -- so a sink written under such a name is held by a case of its own or not at all. The private-key strip has a second, separate assignment, because it is not escaping and does not double. A whole `BEGIN`..`END` block is replaced where it sits; a truncated block -- a `BEGIN` with no `END`, which is what a key sliced into an error looks like -- is replaced from the marker to the end of the unit the pass runs over: a cause-chain link at the error renderer, one log argument at the log sink. That reach is fail-closed: a key that reaches an error has whatever structure the thing that held it left behind, and the separators are not predictable -- real line breaks from a file read, single spaces from a folded or plain multi-line YAML scalar, backslash escapes from a JSON scalar, or no separator at all. So a rule that consumes only armor organised into lines leaks the entire body of every other delivery. The reach stops at that unit's boundary: each cause-chain link, and each log argument, is redacted independently, so a marker in one cannot reach the next. The cost of failing closed is that the replacement also consumes first-party text composed after the marker in the same link. That cost is paid off at the composition site rather than by narrowing the reach: a partner- or server-controlled fragment is passed through `redactPrivateKeyMaterial` where it is interpolated, so a planted marker is replaced inside its own fragment and no longer exists when the link is rendered. The function is idempotent and never lengthens its input, so the later per-link pass is a no-op on an already-redacted fragment and a display budget fitted over raw fragments still holds. Redacting per fragment narrows the reach in one measured case, recorded here rather than left implicit: where two adversary-controlled fragments are adjacent in one link, a `BEGIN` marker ending the first and the key body opening the second are no longer one string when the rule runs, so that body survives where the per-link pass alone would have consumed it. Adjacent fragments under different parties do occur - a partner-derived peer id beside this party's own configured id, a partner-seedable inbound path beside the operator's outbound path. So what bounds the loss is not common provenance but what the surviving bytes are: in every composition reachable today they are that party's own or the operator's own path or id, never an Alcove secret. Adjacency under ONE party is the other shape, and a joined list is where it occurs: the sorted received column list of `assertNoPayloadReceived` and the joined key-name enumerations of the satisfiability refusal. Per-fragment redaction confines a marker to the fragment holding it there too, so a body the same chooser placed in a neighbouring column name or key name survives as ordinary text. Those bytes are that chooser's own, so what the strip lets through is text they already held rather than an Alcove secret. The safety check exists for an unanticipated sink, and a key split across two fragments of one link is where its reach stops. Applying it at a composition site is redaction, not a second escaping altitude: the fragment is still interpolated raw and still escaped exactly once, at the sink. Outside the reach of the branded type below, the assignment is a convention over composition sites rather than a mechanism that enforces itself -- the renderer cannot tell a first-party span from a partner one -- so there it is stated here rather than checked. How much of it a test can hold varies by site, and at the two refusals of the CLI first-use host-key flow (`establishHostKeyTrust` in `apps/cli/src/hostKeyTrust.ts`) it is not pinnable at all. A site with no marker test of its own, whose fragment is composed ahead of first-party text, reddens nothing when its composition-site call is dropped; that is the cost of the assignment being a convention, and it is why the sweep is uniform rather than fitted to where text happens to follow today.

**A branded type closes one chokepoint of that convention, measured rather than assumed.** A string whose bytes the partner chose leaves the wire decode as `PartnerOriginText` (`packages/core/src/utils/partnerOriginText.ts`), a type not assignable to `string`: concatenation, template interpolation, assignment to a string field, and a `join` over its list form are compile errors, so no site composes one into first-party copy. Those four forms are what a composition uses, and they are the whole of what a type refuses here: TypeScript special-cases `String(value)` and `value.toString()`, which compile on any type and hand back the partner's bytes as a plain string, and no type blocks them without a lint rule Alcove does not run. An explicit conversion at a composition site is therefore the tell a review looks for rather than a build failure, and `packages/core/test/utils/partnerOriginText.test.ts` records both forms compiling, so the bound stated here cannot drift from what the compiler does. Its single elimination builds the `Error` itself -- first-party text as the message, and each partner value redacted, control-replaced, fitted to the per-value budget and labelled -- so "a labelled place per chooser" is the type's obligation rather than the composition site's. The claim it holds is scoped to that: a chooser's fragment reaches a message only behind a first-party label, never inside `Error.message`, which stays a plain string so classification and message-equality consumers are unchanged. The values are packed three to a cause link rather than taking a link each, and the ceiling that follows is measured against the renderer: it walks at most eight links (`MAX_ERROR_CAUSE_DEPTH`), so a link per value would show seven and mark the rest elided, while three labelled values to a link -- 962 rendered characters at the label and per-value budgets, inside the per-link cap of 1024, so the renderer never clips a link this builds -- show eighteen, which is every reason site a terms refusal states itself from: seventeen in `validateCompatibility` and the responder's parse refusal. So a diagnosis of several lines is read over several lines on either, and the marker standing at the head of each line it opens is what tells such a line from a link boundary, which opens on the separator's own `caused by: ` text. **On the abort route that layout meets the packed list, and each value keeps a line of its own.** The values of a `PartnerOriginTextList` are packed several to a cause link, separated by one line break this composition places. The seat opens a line only in front of the `<0a>` marker, which a partner can also spell literally with those four printable characters, so a marker-led line may be partner-authored. The label-led lines cannot be forged, since no value can open a line in front of a label; that is the property that matters. `apps/web/test/unit/exchange/abortReasonLayout.test.ts` measures the lines a packed abort reads as, including a reason that holds no break of its own and so reads as one line.

**A window redacts its stream, not its contents.** A sink that keeps a rolling WINDOW of what a run wrote clips before anything renders it, so a key wider than the window lands in that window as body alone -- the `BEGIN` marker already evicted, the `END` not yet written -- and neither the block rule nor the truncated-block rule above sees that shape. Alcove owns one such sink, the console's retained CLI stderr tail (`attachStderrTail` in `apps/web/src/jobs/cliDriver.ts`), and it redacts the STREAM in front of the window rather than the window's contents. `createPrivateKeyStreamRedactor` (beside the marker patterns in `packages/core/src/utils/sanitizeErrorForDisplay.ts`) holds "inside a block" across deliveries: it replaces once on a `BEGIN` marker, emits nothing further until an `END` marker is consumed, holds back a marker's worth of each delivery so a marker split across two is scanned whole, and leaves a block still open at close redacted to the end. The reach is forward only there as at the render boundary, so an `END` with no `BEGIN` of its own is ordinary text and no delivery deletes what an earlier one already emitted. The console's other spawn boundary drains its child's stderr and discards it, which makes "no other reader of the raw stream" a checkable claim rather than a stated one: `apps/web/test/unit/jobs/stderrTailRedaction.test.ts` holds it alongside the window's own content, and the chunk-split, split-marker, lone-`BEGIN`, lone-`END` and long-body properties are held over the redactor itself in `packages/core/test/utils/sanitizeErrorForDisplay.test.ts`. What the streaming form gives up against the whole-text one is a marker whose label runs past 64 characters AND falls across a delivery boundary, a shape no PEM or OpenSSH label takes. A second gap is measured too: when a second `BEGIN` marker arrives before the first block's `END`, the whole-text pass refuses to match across it, and its truncated-block rule redacts from the first `BEGIN` to the end of the unit -- while the stream closes its suppressed region at the first `END` it meets and passes the text after it through. No key byte reaches the tail either way; the difference is only how much of the ordinary text after the nested block the operator still sees, and the stream's reading keeps more of the run's own words. An unterminated `BEGIN` costs more at a stream than at a link. The truncated-block reach stops at the end of the unit the pass runs over, and here that unit is the rest of the run: a `BEGIN` the child never closes suppresses every later byte through the close, so the retained tail ends at the replacement and the operator reads nothing the run wrote after it, with no second copy of it where the run was given no `--log-file`. Redacting to the end is the fail-closed direction, and the property is pinned as `a BEGIN marker with no END stays redacted through the close`.

**Two limits stand behind the strip in either form**, recorded here rather than left to be discovered. A key body that arrives with NEITHER marker on it, from outside any window Alcove owns -- spliced by a library, truncated upstream -- is redacted by nothing and cannot be: scrubbing by secret SHAPE is refused on purpose, because a host-key fingerprint and a shared secret share that shape and fingerprints are shown to the operator by design. And `[redacted private key]` is printable, unauthenticated text that any chooser can spell, so its presence in a rendered string is not evidence that a redaction ran; only its absence is meaningful, and reading it as a guarantee that the bytes it replaced were a key is reading more than the strip states.

Uniformity costs something of its own at two operator surfaces that run no sink pass, and so had nothing needing containment: the interactive host-key trust prompt (`apps/cli/src/hostKeyTrust.ts`, through `promptConfirm` in `apps/cli/src/util/prompt.ts`, written by readline rather than through a prefixed logger), and the browser consent screen the web app renders from `invitationSummary.ts`. A partner-seeded host, a partner-declared identity or column name, or one of this party's own header columns, shaped like armor displays as `[redacted private key]` at the very surface where the operator decides whether to trust a host key or accept the terms, where the escape alone would show it whole. Each composition also takes a log route, which is what the redaction is there for; showing the operator one string on both routes is the trade. The cost is display fidelity at a decision point, recorded here rather than left to be discovered at the prompt. Rendering a raw error at a sink is banned by an ESLint rule over `packages/core/src` and `apps/cli/src` (excepting the three parse chokepoints those blocks already ignore, which have no display sink). The sinks it reads are the `console` methods, a prefixed logger's levels, and the CLI's terminal prompts (`writePromptLine`, `promptConfirm`, `promptFreeText`), which write what they are handed. The CLI integration console sentinel fails on any captured line with a byte outside printable ASCII once the `\ncaused by: ` framing the cause-chain renderer emits between links is removed - the framing is removed before the test rather than exempted from it, so a forged log line of printable ASCII plus a bare newline still fails. Both halves are bounded. The rule matches the raw error where it sits directly in a sink argument and does not follow it through an intermediate local, a method call on the message, or a container the sink unpacks, since that would need taint analysis TypeScript cannot run. The sentinel observes only `console` calls, so a direct `process.stderr.write` is outside it, as is a dependency that writes the file descriptor itself. The sentinel's framing strip is also a literal one with no notion of who emitted the sequence, so a line whose unescaped payload itself contains `\ncaused by: ` passes the byte test. Neither is a claim about every byte that lands on the terminal. The composition side of the assignment is banned by a second rule, over `packages/` and `apps/cli/` and their test sources: a call returning `Displayable` -- the brand below -- or a `displayText` template may not sit in an argument, a template interpolation, a concatenation, a ternary branch, an arrow body, an array element, or the `cause` property of a `...Error` construction or of the two cause-chain composers (`chainDetailCauses`, `fittedCauseLink`), since an `Error` is not a sink and that fragment is escaped again where the chain is rendered. It is syntactic in the same way: a value reaching an `Error` through an intermediate -- a local, a property, a function returning `string` -- is outside it. And it has no runtime half, the sentinel failing on a byte outside printable ASCII while a fragment escaped twice is printable ASCII throughout, so what stands behind it is a check over the governed sources instead (`scripts/eslint-displayable-error-argument-ban.test.mjs`), holding the producing calls the rule names to every exported function that declares a `Displayable` return type.

The strip therefore has three sinks, and the unit it runs over differs at each. At the error renderer it runs per cause-chain link (`sanitizeErrorForDisplay`). At the diagnostic log it runs per argument, in core's log prefixer (`setLogPrefixer` in `packages/core/src/utils/logger.ts`) rather than in a consumer's diagnostic sink. The prefixer sits upstream of both CLI routings (stderr and `--log-file`) and of the browser console the web app keeps, and it also covers a line logged before a consumer installs its sink, which a sink-side pass would miss entirely. The prefixer is handed raw `unknown[]` and the sink owns its own formatting, so the pass rewrites only the members that are already strings and passes every other member through by reference - an object argument prints exactly as it would without the pass. The CLI's fd-3 warning event is the third (`buildWarningEvent` in `apps/cli/src/eventStream.ts`), because that stream is a persisted machine sink whose terminal error event is already redacted through `sanitizeErrorForDisplay`; leaving its one other free-text field unredacted would make the stream the exception. That event's display cap is sized for a composition rather than for one value: the host-key divergence warning is the whole reason a supervisor that discards stderr reads the stream, and the per-value default cuts that warning mid-explanation, taking its re-pin instruction with it.

Each unit boundary is also a reach limit, stated rather than closed. Key material split across two cause-chain links is not seen by the per-link pass, and key material split across two arguments of one `log.warn(a, b)` call is not seen by the per-argument one. Joining first would close either, at the cost this whole assignment exists to avoid: a dangling marker in the first unit would then consume every unit behind it, which is how the party a warning is about deletes the warning about itself. The composition-site rule is what makes that trade the right one - a fragment redacted where it is interpolated holds no marker by the time either pass runs, so the wider reach of a sink pass costs nothing that the composition sites have not already paid. The third limit is which sinks have a pass at all: the three above are the error renderer, the diagnostic logger, and the fd-3 warning event, so an operator-facing sink that does not route through the prefixed logger runs none of them. The receipt-verification report (`apps/cli/src/commands/verifyReceipt.ts`) and the argument-parser rejection (`apps/cli/src/cliParser.ts`) write `console.log` and `console.error` themselves, and are escaped at composition without being redacted. None of them can suppress first-party text, because no pass runs there to fail closed; what they lack is the safety check, and closing that means moving them onto a logger or giving each its own pass. The CLI's plain-line sink (`LogSink.writePlain` in `apps/cli/src/util/logging.ts`) belongs to that class for a different reason and is the one that reaches a persisted destination: it feeds the same writer the prefixed lines go through, so a `--log-file` captures it, but it bypasses the prefixer and therefore the per-argument strip. Its only caller is the `doctor` verdict rendering (`apps/cli/src/commands/doctor.ts`), which includes an NT_STATUS token and `smbclient`'s own output. For that sink the composition is the only place a pass can run, and the rendering runs three of them, with the unit differing between them as it differs across the three sinks above. The first runs on the whole tool output before the rendering splits it into lines (`clampDetail` in `apps/cli/src/doctor/verdict.ts`): a tool hands a key block over in its canonical multi-line form, so a pass over the lines that come out matches its `BEGIN` line alone and renders every body line verbatim. The second runs on the whole of a check's meaning or action text before the rendering re-flows it under its label (`wrapLabelled`, below). The third runs per rendered line, where the rendering escapes (`emit`), and the first two are what make it a no-op over the tool output and the wrapped blocks. That third pass is not free: a summary line composes an operator-supplied value -- the SMB server name, or the mounted directory -- ahead of its own predicate, so an operator who names one with a `BEGIN` marker reads `OK: [redacted private key]` and loses the predicate to the fail-closed rule. The marker filename is composed the same way but cannot reach it: `MARKER_PATTERN` admits no space, and every redaction pattern requires one, so a marker-shaped `SMB_MARKER` is refused as a usage error before any check runs. Those bytes are the operator's own and no partner reaches them, which is why the cost is recorded here rather than closed by redacting each fragment before composition; all three passes are pinned by marker tests rather than resting on the convention.

The wrap is why the second of those passes exists, and it is the one shape in this assignment where the strip could fail OPEN rather than closed. `wrapLabelled` re-flows a check's meaning and action text on whitespace at 76 columns, and every marker the rule matches contains spaces, so a `BEGIN` straddling a wrap would reach the per-rendered-line pass as two lines, neither matching a pattern that requires the whole marker, leaving the material behind it to render verbatim. Redacting the whitespace-normalized text ahead of the re-flow closes that, exactly as `clampDetail` closes the same shape ahead of its split -- and normalizing before redacting is critical: the re-flow collapses every whitespace class to ASCII spaces, so a marker whose internal separators are non-ASCII whitespace would otherwise be re-formed by the normalization after a raw-text redaction had run. The unit is one labelled block -- meaning and action are wrapped separately -- and the label is composed outside the redacted text, so a dangling marker takes the rest of its own block and reaches neither the label nor the sibling block. What the wrap holds is the operator's own `SMB_SERVER`, `SMB_SHARE`, and `SMB_PATH`, the `SMB_MARKER` filename `MARKER_PATTERN` already confines to a space-free charset, and smbclient's own NT_STATUS token, whose `NT_STATUS_[A-Z_]+` shape admits no space either; the server-controlled `detail` is redacted whole before the split and its lines are never wrapped. The replacement is prose to the wrap like any other phrase and can itself be broken across two rendered lines, a legibility cost of the ordering rather than a disclosure one. The property is pinned at the rendered boundary by a marker planted so the wrap splits it, alongside a marker-shaped control string rendered at the same offset, which is what establishes that the wrap falls inside such a run rather than leaving it whole.

The per-link cap is a second bound on the same output, independent of redaction, and it falls wherever it lands: on a link that mixes first-party text with a fragment somebody else chose, the chooser spends the budget and the operator loses the instruction.

That per-link budget is **not** the per-value default. A cause-chain link is a composition -- first-party explanation and recovery text with fragments interpolated raw into it, by the single-altitude assignment above -- where `DEFAULT_MAX_DISPLAY_LENGTH` (**256**) is sized for one value. So charging a whole link to it cuts the composition's own instruction with no fragment involved at all: the connection-endpoint locator rejection in `packages/core/src/config/invitation.ts` is 394 characters of fixed guidance before its prefix and its list of rejected keys. `sanitizeErrorForDisplay` therefore caps each link at `COMPOSED_MESSAGE_MAX_DISPLAY_LENGTH` (**1024**, `packages/core/src/utils/sanitizeForDisplay.ts`), sized to admit the longest fixed guidance Alcove composes into one message together with the bounded values that message names, and left well under the **4096** of `WARNING_MESSAGE_MAX_DISPLAY_LENGTH`, whose four re-escaped fragments crossing three boundaries are a larger shape. The whole rendered chain stays bounded without a separate total-length cap: at most `MAX_ERROR_CAUSE_DEPTH` (**8**) links at that budget each. The budget bounds what any single link can spend; whose bytes spend it is decided by the partition below, which is why a wider link is not a wider flood allowance. The two SFTP host-key refusals (`installEnforcingVerifier` in `packages/core/src/connection/sftpSession.ts`) are therefore composed as a partition by provenance - one link per party that chose the bytes on it - rather than as one string, the same remedy `entryGuardRefusal` applies in `packages/core/src/connection/fileSyncRendezvous.ts`. The refusal itself, the presented fingerprint (base64, of fixed length), and the operator's pin or re-pin instruction ride the error's own message plus, where they exceed one budget, further first-party cause links. Each fragment somebody else chose then takes a labelled cause link of its own - the configured host and the presented key type on the no-pin refusal, the pinned set and the presented key type on the pinned-mismatch one. `FileSyncConnection.open` folds those links in ahead of the transport error the connect rejected with, so the cause-depth bound can never drop a detail in favour of ssh2's opaque `Host denied`.

Splitting by chooser rather than into refusal-plus-detail is what keeps the fix from reproducing the defect one level down. The host and the key type are chosen by different parties: on the acceptor route the host is the partner's, copied verbatim out of the invitation endpoint into the written config (`connectionFromEndpoint` in `apps/cli/src/onlineBootstrap.ts`), and `SFTPServerSchema` bounds `connection.server.host` neither in length nor in format, while the key type is decoded from the server's blob under no bound at all. So a shared trailing link would let either delete the other's disclosure. The pinned set is the operator's own rather than an adversary's, but `SFTPServerSchema` bounds each pin's format and not the array's length, so a many-pin config would eat the re-pin instruction from a shared link; its own link is the right place for it. The property this buys is that the cap can only ever consume a chooser's own bytes, and it is pinned by test at the rendered boundary. Each refusal renders its fingerprint in full and its instruction whole under a benign key type, an over-length one, one holding a PEM `BEGIN` marker, a configured host at the full 256 characters the invitation schema admits (which the link budget delivers whole), and one past that budget, where the cut falls on the host's own link and no other. Reachability differs between the two refusals and the partition does not rest on it: the pinned-mismatch form is reachable from any CLI run, while the no-pin form is core's fail-closed safety check for a direct library caller, ahead of which the CLI's own first-use trust flow normally pins. Nothing enforces that ordering, so the no-pin refusal is composed to the same standard as its sibling rather than treated as unreachable.

The cap is not removed, only kept off first-party text: a fragment that overruns still truncates on its own link, and the whole rendered chain stays within the cause-depth bound times the per-link budget plus the separator the renderer emits between links - also pinned by test, with each branch's live fragments flooded at once. Enforcement is untouched throughout: the connection is refused and a changed key is never auto-accepted. One residual bound remains: each first-party link fits its budget by measurement, not by construction, so growing the fixed copy past the cap would put the cap back on the operator's text. That residual is held by a check rather than by this paragraph - rendered with every variable fragment at its ordinary size, no link of either refusal truncates at all, so any growth past a budget fails there.

The receipt verification notes reach the operator on neither of those routes: no error, no chain, and no sink pass of their own. A note is a composition of the same shape as a cause link -- Alcove's own sentence, with any column name drawn from the files the operator re-supplied escaped where it is interpolated (`reconstructCommittedData` and `reproductionMismatchCauses`, `packages/core/src/records/recordVerification.ts`) -- so charging the whole note to the per-value default cuts the sentence rather than the fragment: the reproduction-limitation note is 403 characters, of which the operator loses the half stating what a mismatch can and cannot mean. Each note is therefore composed as a `Displayable` where it is written (`firstPartyNote`, `packages/core/src/utils/sanitizeForDisplay.ts`) with the column name escaped and capped at `DEFAULT_MAX_DISPLAY_LENGTH` where it is interpolated, and the two sinks that render one -- `alcove verify-receipt` and the browser verify page -- show what they are handed instead of escaping and capping it again. The slot is what holds the arrangement: both note lists are declared `Displayable[]`, so neither sink can be reached by a raw `string`. What `firstPartyNote` accepts is checked rather than taken -- a note holding any code point outside printable ASCII is escaped and capped as an ordinary value instead, that being the class first-party copy and an already-escaped fragment both sit inside -- so the exemption is from the length cap alone, and a fragment rendered with non-ASCII kept as the operator typed it (`renderOperatorSuppliedText`) is not composable into a note. What the mark claims about provenance is checked where the note is written, since the runtime guard reads the note's characters rather than who chose them: `scripts/first-party-note-argument-shape.test.mjs` refuses a `firstPartyNote` call under `packages/core/src` whose argument is not literal text with every interpolation wrapped in a direct `sanitizeForDisplay(...)` call, and refuses any such call in another shipped source tree, where a consumer is handed a note already composed. It reads `.ts` and `.tsx` files and the direct import name only, so an aliased or namespace import, a second argument that raises the cap, and an `.mts` source are outside it and are review's to catch (the script's header lists the alias and namespace limits).

The cause-depth bound is the same kind of bound one level up -- over links rather than characters -- and it discloses its cut the same way. A walk that stops at `MAX_ERROR_CAUSE_DEPTH` with the chain still running appends `CAUSE_DEPTH_ELISION_MARKER` (`...[further causes elided]`) to the last link it renders, so a chain the bound cut displays as cut rather than as the whole failure; a chain that ends on its own, or that the cycle guard stops on a link already rendered, holds no marker. Neither marker is authenticated, and neither can be: both are plain printable ASCII the escape passes through unchanged. So a link whose own message ends with the marker's text renders byte-identically to one the bound really cut -- the same shape the transport-refusal checks work around for `DISPLAY_TRUNCATION_MARKER` by expressing "this link truncated" as a length comparison against the cap rather than as a marker search. The cost is one-directional and bounded: a copy of the marker claims a loss that did not happen, and cannot conceal one that did, because the renderer appends its own after the escape whatever the link held. So what an operator can rely on is the marker's absence, its presence saying detail MAY be missing rather than that it is. Both directions are pinned by test at the rendered boundary, a partner message holding the marker's text driven alone, at the depth cut, and against a genuinely cut chain it renders identically to. The marker has no count, because counting the remainder means walking the rest of the chain -- the walk this bound exists to refuse, and unbounded in exactly the adversarial case it is defensive against. A composition site whose link count is driven by a list length therefore states its own overflow, where the count is free: `checkLinkageSatisfiability` (`apps/cli/src/commands/linkagePreflight.ts`) gives each dead key, unsatisfiable key, and unsatisfied field a labelled link, and `LinkageTermsSchema` bounds `linkageFields` and `linkageKeys` only at `MAX_LINKAGE_ENTRIES` (**256**). So it fits the enumeration to the links the renderer reaches -- the summary and the remedy chained ahead of the names take one each -- and spends the last of them on `and N more details of the terms this CSV cannot satisfy (M in total)` rather than on one more name. What puts a site in that class is the count of links it asks for, not the length of any one of them: a many-valued fragment on one link (the pinned-fingerprint set a [host-key mismatch](SFTP_CONNECTION.md#sftp-host-key-verification) names) spends that link's character budget and truncates where an operator sees it, while a list given a link per element runs off the end of the walk. Both are pinned by test at the rendered boundary, the enumeration at more names than the walk admits and at the widest count that needs no overflow link at all.

The accept-time reconcile refusal (`reconcileConflictMessage` in `apps/cli/src/config/reconcileDiffs.ts`) takes the same partition on one link rather than on a chain, because what a cut deletes there is a single recovery sentence rather than a step several links down. That budget's residuals are two, recorded rather than closed. The invitation consent summary has a static half of its own, over the display structs rather than over sink call sites. The guarantee runs in that direction only: the brand rejects a plain `string` assigned into a field already declared as the brand, and nothing forces a newly added field to be declared that way, so a new field declared `string` and filled from a partner value still compiles. The runtime half covers what the type half cannot: a test builds the summary from linkage terms whose every partner-controlled string holds a control, bidi, or non-ASCII byte, walks the whole returned value recursively, and fails on any string outside printable ASCII - the raw key name is its single exempted position. The same walk, run over the mounted consent screen and over the CLI prompt's emitted lines, catches a value that reaches an operator past the display structs entirely. What the brand adds over that is the compile-time half: an existing field cannot silently lose its escape. The brand is one-directional: a `Displayable` is still a `string`, so renderers, logs, and JSX text consume it with no cast, and it exists only in the type system - the sanitized bytes are identical with and without it. Fixed first-party copy (a semantic-type label) and composed entries (a compact label plus its breadth marker) enter through `displayText`, a tagged template whose literal spans are necessarily the call site's own text and whose interpolations must themselves be branded or numeric. What it bounds is the accidental omission: a deliberate `as Displayable` assertion, or a hand-built `TemplateStringsArray` passed to `displayText` as an ordinary argument, bypasses it. One value on the CLI prompt is outside the brand's reach because it never enters the summary: the acceptor's own outbound-send column names, read from its operator's input file rather than from the partner's token, are escaped inline where the prompt's renderer emits them, which is their sink. On the confirmation path, that emit reaches the prompt's own stream as well as the log.

That walk sees only the summary positions a fixture populates, so an optional field no fixture reaches holds nothing to inspect and passes it vacuously. What closes that, without reintroducing a per-field list, is a companion check that reads the optional property paths off the `InvitationSummary` declaration and the summary structs nested under it - with the TypeScript compiler API, at test time, array and tuple indices collapsed so a path reads `linkageKeys[].elements[].transforms[].effect`. The check collects the paths the fixtures populate, and fails naming any declared optional position none of them reaches. An optional field added to a summary struct therefore fails the check until a fixture reaches it, with nothing to add to a list. The reverse direction is asserted alongside it: a populated position the type walk never named fails as a derivation that stopped short of where values go. A summary position one terms document cannot hold alongside the others is reached by a hostile-terms variant of its own rather than left uncovered, and each variant is both summarized by the object walk and rendered by the render walks (the mounted web screen and the CLI prompt), so every half covers the same fixtures. A position no valid decoded token can populate is listed as an individually named exemption in that check with its reason recorded here, never as a blanket allowance that would swallow a newly unreached field; there is no such position - every optional position the summary declares is reached by a fixture.

The decode description is split per consumer, which is what the assignment asks of a value that feeds both a display sink and an `Error`. Both partner-chosen fragments are also FITTED where the description is composed, rather than left to the cap at the sink. This is the partition by chooser above, applied to a composition whose fragments sit inside one link rather than on links of their own: the path LEADS the description, so one unfitted segment -- a rejected record key, which Zod's `invalid_key` holds verbatim and no schema bounds in length -- spends the whole `COMPOSED_MESSAGE_MAX_DISPLAY_LENGTH` link and cuts the refusal reason behind it, leaving the operator a screenful of the inviting party's own bytes and no diagnosis. The fit is pinned at the rendered boundary in both positions, with a key past every budget: `packages/core/test/config/invitation.test.ts` for the web alert and the CLI composition, and `apps/cli/test/unit/invitationDecodeBudget.test.ts` through the real decode wrapper.

Each fragment is CUT to a raw length before either treatment, at two UTF-16 code units per character of the budget it is fitted to (`boundRawFragmentForFit`, `packages/core/src/utils/sanitizeForDisplay.ts`). The clip measures a fragment by materializing its escaped form, so measuring an uncut one costs time and memory linear in what the party that chose it sent -- and on the wire linkage-terms route the path segment is a `transform.params` key bounded by `MAX_FRAME_SIZE_BYTES` alone. A key of 5,000,000 code units measured at 755 ms and 271 MB of transient heap to describe, against 1.2 ms and no measurable growth once cut. Two code units per budget character rather than one: no code unit escapes to fewer than one output character, but a fragment cut to exactly the budget in printable ASCII renders at exactly the budget, which the clip returns whole and unmarked where the fragment it came from would have been clipped and marked. At twice the budget a cut fragment renders past the budget for a private key alone, text ahead of a private key, and plain text of any length, so for those shapes what the operator reads is what the uncut fragment would have rendered. The cut runs before the redaction, so a cut through a private-key block leaves a `BEGIN` marker whose `END` is gone and the fail-closed dangling rule takes it along with everything after it, while a cut landing inside the marker keeps no key body at all -- and a complete private-key block followed by more text falls outside the shapes above: redaction can shrink that cut fragment below the budget, and the fit then shows less of the trailing text than the uncut fragment would, with no truncation marker to say text was dropped. No key material survives either way. ## Compatibility diagnostic value delimiting

The escape above governs which bytes an operator can be shown. A second, orthogonal control governs which clauses: the cross-party compatibility diagnostics (`validateCompatibility`, `packages/core/src/linkageTermsNegotiation.ts`) are first-party prose whose structure an operator treats as Alcove's own -- `legal agreement reference mismatch: yours is X, your partner's is Y` -- around values a mutually-distrusting partner chooses. Both sides of that sentence can be the partner's, since `deriveAcceptedLinkageTerms` adopts the inviter's `legalAgreement` and `linkageRuleSet` verbatim into the acceptor's terms ("yours" names provenance in the exchange, not trust in the bytes). The escape does not reach this class: it rewrites what is not printable ASCII, and a reference of `A", your partner's is "B`, a rule-set name of `hmis-keys 9.9.9 over baseline-pii`, or a payload column named `a,b` is printable ASCII throughout. What answers it is delimiting, applied once at composition.

Every value one of these diagnostics names passes through one module (`packages/core/src/config/compatibilityMessage.ts`) in one of two forms. `quoteTermsValue` wraps the value in `"` and doubles every `"` inside it: reading from the opening delimiter, a doubled delimiter is one literal character and a single one closes the run, so the encoding is injective and no value can terminate its own run early or spell a clause of its own. `bareTermsValue` renders undelimited the values the terms schema constrains to a shape no clause boundary is made of -- a semver string or an ISO date -- and RE-CHECKS that shape on the value in hand: the charset `BARE_TERMS_VALUE_PATTERN` matches letters, digits, `.`, `_`, and `-`, at least one of them a digit. Since that pattern bounds no length, a `MAX_BARE_TERMS_VALUE_LENGTH` of **64** characters `bareTermsValue` checks beside it. It falls back to the quoted form for anything else. The re-check is what makes it a second safe constructor rather than an override: `validateCompatibility` takes two `LinkageTerms` objects and nothing in its signature makes them schema-parsed, so the assumption is executed rather than asserted. The shape excludes the delimiter and the `,`/`[`/`]` the payload list is built from; the digit is what stops a bare value spelling a connective. Excluding the space makes a bare value exactly one whitespace-delimited token, which on its own does not keep it out of a connective position, because the template supplies the spaces around a bare slot -- the rule-set clause renders `<name> <version> over <name> <version>`, so a letters-only version would stand in that sentence as undelimited as the `over` beside it. Every value these diagnostics render bare has a digit and no connective or label their templates are built from does, which leaves the two vocabularies in disjoint shapes; the digit-free half of that is executed rather than asserted, `packages/core/test/config/compatibilityMessage.test.ts` reading the templates out of their own module and failing if any token of first-party copy meets the bare shape. A value with no digit -- an algorithm or strategy enum member, say -- takes the quoted form instead, which costs the reading nothing. A payload column list quotes per element (`quoteTermsValueList`), so the rendered `["a","b"]` shows the same partition the byte-exact element-wise comparison used to decide the mismatch, rather than the `[a,b]` a single column named `a,b` would also print.

Doubling rather than a backslash escape is what keeps the control orthogonal to the escape at the sink: the module adds only printable ASCII, which `sanitizeForDisplay` passes through unchanged, so a run's boundaries survive the display boundary byte for byte and neither transform doubles the other's work. On the `warnings` route, which escapes at composition, the escape runs before the delimiting, so that transform's truncation can never take the closing delimiter off a run.

Beside the delimiting, `quoteTermsValue` replaces every control character in the value (Unicode `Cc`, so U+0000-U+001F and U+007F-U+009F) with a printable marker naming its code point in two lowercase hex digits inside angle brackets -- `<0a>` for a line break, the same four characters wide the escape's own `\x0a` is. So a budget measured over a treated fragment is the budget the untreated one asked for (`replaceControlCharactersForDisplay`, `packages/core/src/utils/sanitizeForDisplay.ts`). Delimiting bounds what a value can do in the message's printable structure; this bounds what it can do in the bytes a composition builds structure out of one level up. A message whose own structure is a control character -- a block separating its lines with `\n` -- states those lines to the display boundary through `keepFirstPartyLineBreaks` (`packages/core/src/utils/sanitizeErrorForDisplay.ts`), which escapes each line and joins them with the break, so the operator reads the block as a block. This treatment is what keeps a value's own line break out of that reading: inside a line it is the `<0a>` marker, not a break and not the escape's `\x0a` either. The marker has no backslash and nothing outside printable ASCII, so the sink's single pass finds nothing to rewrite: this is a composition-site treatment, the same shape as the private-key redaction above, not a second escaping altitude. On the `warnings` route the escape again runs ahead of the module, so nothing is left there for the treatment to act on and a value's control character instead arrives one backslash wider than a composition's own would -- the observable doubling that route already has, standing as the same distinction. Being printable, the marker is not authenticated and cannot be: a value that spells it renders as one that held the character it names, the same open class `DISPLAY_TRUNCATION_MARKER` has; what an operator relies on is the converse, that a control character Alcove itself composed renders as the escape's `\xHH` -- or, for the line breaks a composition states as its own, as a line break -- and no value can produce either. `packages/core/test/utils/sanitizeForDisplay.test.ts` drives the whole control class through the marker and fails if any of it renders as a token the escape writes for a control character, or if a marker costs the display more than the character it replaced; `packages/core/test/config/compatibilityMessage.test.ts` and `apps/cli/test/unit/config.test.ts` assert the property where each renderer shows it.

A kept break is also the one byte a first-party composition puts in front of the cause chain's own framing, so `keepFirstPartyLineBreaks` refuses a line that would stand behind it as a link boundary. A line opening on the separator's `caused by: ` text is prefixed with a backslash, which the escape doubles: the operator reads `\\caused by: `, and the split `sanitizeErrorChainLinks` performs reads no boundary there. It is enforced at the mark, over every line the caller hands over, rather than asked of the caller -- the parameter is a plain string array, so a later composition could put a value somebody else chose at the start of a line. The renderer applies it again to the lines it splits out of the marked text, since the mark holds that text rather than the lines it was stated as: code in the process that writes the registered symbol itself forges no boundary either (`packages/core/test/utils/sanitizeErrorForDisplay.test.ts`).

The enumeration is held by type rather than by a list. `validateCompatibility` accumulates `CompatibilityMessageFragment` -- a `string` intersected with a phantom property keyed by a `unique symbol` private to that module, the same brand construction the invitation consent summary uses for `Displayable` -- and the only ways to obtain one are the two constructors above and the `compatibilityMessage` tagged template, whose fixed spans only the compiler produces. A terms value interpolated into a diagnostic without passing the module does not compile, for a message edited later as much as for a mismatch check added later. `packages/core/test/config/compatibilityMessage.test.ts` is the runtime half: it drives every value slot of every diagnostic that names one -- both sides of a two-slot comparison, and each of the four the rule-set clause renders -- twice, once with a value it legitimately holds and once with an adversarial shape built around that same value. These are: one with the delimiter, one with every clause connective these messages are built from, one reading as the `<name> <version>` pair the rule-set clause renders, and two the bare charset admits, a connective spelled outright and a digit-carrying value that stays bare.
