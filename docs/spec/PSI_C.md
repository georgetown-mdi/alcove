# PSI-C

This document specifies PSI-C, the count-only algorithm that reports the size of a one-to-one linkage and nothing else: the rounds a count-only exchange runs, how the receiver's engine computes the count, the candidate sets a key may declare, the refusals, how the count is reported, what each party learns, and the threat-model scope of the claim.
It does not cover the PSI base function and the linkage rounds PSI-C reuses (see [PROTOCOL.md](PROTOCOL.md)), the exchange-agreement field that selects the algorithm (see [EXCHANGE_REFERENCE.md](../EXCHANGE_REFERENCE.md#linkage_termsalgorithm)), the exchange record a count-only run writes (see [EXCHANGE_RECORD.md](EXCHANGE_RECORD.md#count-only-psi-c-records)), the threat model and authentication design (see [SECURITY_DESIGN.md](../SECURITY_DESIGN.md)), or the design and the options weighed (see [psi-c-count-only.md](../notes/psi-c-count-only.md)).
Intended readers are security auditors, external implementors, and developers.

PSI-C ([`linkage_terms.algorithm: psi-c`](../EXCHANGE_REFERENCE.md#linkage_termsalgorithm)) reports the size of a one-to-one linkage over the agreed keys and nothing else: no identifier, no matched pairing, no payload, no per-record result. It is a feasibility instrument -- the exchange two parties run to find out whether a linkage is worth negotiating at all. The PPRL using PSI is intended for operational use, while PSI-C is intended only for research.

It runs at the point in a partnership where the least trust has been established, which is what fixes the scope of the claim it makes ([Threat-model scope of the count-only claim](#threat-model-scope-of-the-count-only-claim)). Why the construction has this shape: [psi-c-count-only.md](../notes/psi-c-count-only.md).

## The count-only rounds

**Every agreed key, in order, every round full-size.** A count-only exchange runs one [PSI base function](PROTOCOL.md#psi-base-function) round for each round the agreed keys run as, in the agreed key order: one for each entry of `linkage_keys`, and two adjacent rounds for a key with a [missing-field condition](PROTOCOL.md#keys-with-a-missing-field-condition) (`linkageRounds`, `packages/core/src/linkageKeyCondition.ts`). These are the rounds of [`linkage_strategy: cascade`](PROTOCOL.md#linkage-strategies-cascade-and-single-pass), and terms declaring `single-pass` run them too ([A declared `single-pass` runs the same rounds](#a-declared-single-pass-runs-the-same-rounds)). No round's set is narrowed by an earlier round's matches, as a `psi` cascade round's is: neither party learns which of its own records matched, so there is nothing either could remove on the wire. Every round includes every record of both parties, and the cascade's removal takes place inside the receiver's computation of the count ([Computing the count](#computing-the-count)).

**Roles.** The sender is the base function's server and the receiver its client, assigned by the ordinary rule ([Role resolution and work minimization](PROTOCOL.md#role-resolution-and-work-minimization)): when exactly one party expects output that party is the receiver, and when both do the smaller declared count is. Below, `n_R` is the receiver's declared record count and `n_S` the sender's, both as the terms exchange states them.

**One element per record.** In every round whose key declares no candidate set, each party's set has exactly one element for each of its records, so its element count is its declared record count, the figure the [first-round count at the start](PROTOCOL.md#the-memory-ceiling-and-the-csv-intake-cap) and the count against the partner's [receive ceiling](PROTOCOL.md#the-receive-ceiling) weigh for a count-only round:

- The receiver's request lists its records in a request order it draws once for the exchange, a uniformly random permutation of its records from the platform's cryptographically secure random generator, so position `i` of every round's request holds the same receiver record in every round, and only the receiver knows which. The request order MUST NOT be sent, written to disk, or logged, and MUST be discarded when the exchange ends, whether it completes or fails; each run of an exchange draws its own.
- The sender's setup has one element for each of the sender's records.
- A record's element is its round value (below) when the party builds the round for the record, the record has a value for the key ([Key input data](PROTOCOL.md#key-input-data)), and no other record the party builds the round for has that value for the key. Otherwise the element is a dummy.
- A party builds a round for every one of its records, except in a round a missing-field condition filters on its side (below), where it builds the round only for its records with no valid value for the field.
- A dummy is 32 bytes from the platform's cryptographically secure random generator, written as 64 lowercase hexadecimal characters, drawn anew for each element in each round and never reused. It contains no colon, so it never equals a round value, and two dummies coincide only with negligible probability. On the wire it cannot be told from a real element.

**Uniqueness over every record the round is built for.** A key value two or more of those records have is a dummy for every one of them. The test reads every record the party builds the round for, never only the records still unmatched, which is where the count can differ from a `psi` run's ([Comparability with `psi`](#computing-the-count)). That is the party's whole dataset, except in a round a missing-field condition filters on its side, where it is the party's records with no valid value for the field: a value one of those records shares only with records that have the field is real for it.

**A key with a missing-field condition.** Its two rounds are each full-size. In each, the party whose PSI role the round filters ([Keys with a missing-field condition](PROTOCOL.md#keys-with-a-missing-field-condition)) builds the key only for its records with no valid value for the field, and every other record of that party has a dummy, so its set still has one element per record and the round's element count does not tell the partner how many of its records the condition excludes. The partner builds the key for every record. The round filtering the receiver's side comes first, so a pair whose two records both lack the field is accepted there, as under `psi`.

**Round values are separated by round.** A record's round value in round `k`, `k` being the round's 0-based position in the exchange's round order, is the decimal `k`, a colon, and the key value: `0:` followed by the value in the first round. Both parties apply it to every real element before encryption. A party's PSI key may serve every round of the exchange, so without the prefix a value appearing under two keys would encrypt to the same element in both rounds, and the receiver, which knows which of its own records share a value across keys, could link those two rounds' slots to those records.

**The sender's permutation.** Once the terms exchange has given it `n_R`, the sender draws one permutation `pi` of the positions `0` to `n_R - 1`, uniformly at random from the platform's cryptographically secure random generator. In every round it processes the receiver's request in the library's revealing mode, then reorders the response under `pi` before it sends any part of it: slot `s` of the response as sent is the element at position `pi(s)` of the response the library returned. The same `pi` serves every round of the exchange. It MUST NOT be sent, written to disk, or logged, and MUST be discarded when the exchange ends, whether it completes or fails; each run of an exchange draws its own.

The library returns a revealing-mode response in request order, so slot `s` of every round answers the receiver's request position `pi(s)`, which holds the same receiver record in every round. A slot is therefore a stable pseudonym of one receiver record for the whole exchange. Only the sender, which holds `pi`, can map a slot to a request position, and only the receiver, which holds its request order, can map a request position to a record.

**The sender's pseudonyms and the index table.** The sender draws a second permutation, `sigma`, of its own records `0` to `n_S - 1`, under the same rules as `pi`; `sigma(j)` is the pseudonym of its record `j`. The library sorts a setup by ciphertext, and reports the input index at each setup position (its sorting permutation). So in each round, after building the setup, the sender sends that round's **index table**: `n_S` entries, entry `p` being `sigma` of the record whose element is at position `p` of the setup as sent. The table is a binary frame of `n_S` little-endian `Int32` values, so `4 * n_S` bytes, and it is a permutation of `0` to `n_S - 1`. A matched setup position therefore names a sender pseudonym that is the same in every round, without naming a sender record.

**The index table fits one frame.** The table is sent as one frame, not in parts. It has one entry for each element of the round's setup: `n_S` entries, or `n_S * w_S` in a round whose key declares a candidate set ([Candidate sets under count-only](#candidate-sets-under-count-only)). The sender sends it only after holding its setup to the per-set maximum and to the partner's receive ceiling, and the receiver reads it only after a setup of the element count it expects, within its own ceiling. So no table a party sends has more than `MAX_PSI_DECODE_ELEMENTS` entries, and none is longer than 67,108,864 bytes. A receiver reads the table frame under the channel's per-frame bound and refuses one whose length is not four bytes for each setup element once it has read it, so a partner that ignores the checks can make it read up to that bound first, as at any other frame. With its envelope, that is within the per-frame bound on either channel: `MAX_WEBRTC_FRAME_BYTES`, 268,435,456 bytes, on WebRTC, and `MAX_FRAME_SIZE_BYTES`, 536,870,888 bytes, for a message file (held by `packages/core/test/psi/countOnlyIndexTableBound.test.ts`).

**The frames of one round.** In the round order, each round is four frames:

Below, `w_S` and `w_R` are the round's widths, each 1 in a round whose key declares no candidate set ([Candidate sets under count-only](#candidate-sets-under-count-only)).

1. **sender -> receiver** -- the setup message over `n_S * w_S` elements, each encrypted once under the sender's key, as a `Raw` data structure, in parts ([A PSI set is sent in parts](PROTOCOL.md#a-psi-set-is-sent-in-parts)).
2. **sender -> receiver** -- the round's index table, one binary frame.
3. **receiver -> sender** -- the request over `n_R * w_R` elements, each encrypted once under the receiver's key, in parts.
4. **sender -> receiver** -- the response: the request re-encrypted under the sender's key and reordered under `pi`, in parts.

Each round sends `35 * (n_S * w_S + 2 * n_R * w_R)` bytes of encrypted elements and `4 * n_S * w_S` bytes of index table, whatever the key's coverage. After the last round comes the count-report leg where the entitlement calls for it ([Count reporting and entitlement](#count-reporting-and-entitlement)).

**Each frame's size is checked against the declared counts.** The receiver MUST refuse a setup whose element count is not `n_S * w_S`, and an index table whose length is not `n_S * w_S` or in which a pseudonym from `0` to `n_S - 1` does not occur exactly `w_S` times, a permutation of `0` to `n_S - 1` where `w_S` is 1. The sender MUST refuse a request whose element count is not `n_R * w_R`. Each refusal is a protocol error raised before the round goes on ([Partner-supplied index tables are checked against local state](PROTOCOL.md#partner-supplied-index-tables-are-checked-against-local-state)), and a response is held to its request's element count as every response is. These checks hold a conforming partner to the padded shape. They do not stop a party choosing its own inputs ([Threat-model scope of the count-only claim](#threat-model-scope-of-the-count-only-claim)).

**Revealing mode, with Alcove applying the permutation.** Both parties MUST construct their base-function objects with the library's reveal-intersection flag set, as a `psi` run does, and MUST NOT run the library's cardinality mode, the flag cleared, for a count-only round. In that mode the library's server sorts each round's response by ciphertext and takes no permutation, so no order can be held across rounds, and its match returns only a size. The revealing match returns, for each response element it matches, that element's position in the response as received and the setup position it equals; under `pi` the position is a slot. Two properties the cardinality mode's flag would give are therefore provided elsewhere:

- **The flag does not tell the algorithms apart.** Both a `psi` and a `psi-c` round set it, so the library's own mode check does not refuse a partner running the other algorithm. That agreement is the agreed terms': `algorithm` is a mandatory-consistency term, compared at the terms exchange and again at the agreed-terms run boundary before any round (`resolveCountOnlyRun`, `packages/core/src/exchange.ts`), so a `psi` party and a `psi-c` party never reach a round together.
- **The receiver's engine, not the library, withholds the matches.** The library hands the revealing match's pairs to whatever calls it; the receiver's engine keeps them (below).

**The receiver's engine returns only the count.** A count-only receiver's engine takes each round's setup, index table and response, keeps every round's matched pairs inside the engine across the exchange's rounds, and returns one figure, the count, after the last round. It MUST NOT return to its caller, report as progress, or log an association table, a slot, a pseudonym, a per-round or running match count, or any other per-record result; its progress reports count elements processed and nothing else. Its identifier-revealing operations, and any operation returning a per-round result, are refused in count-only mode. This holds on both backends, and whether the engine runs in process, in a worker, or across a pool of workers. Nothing the engine keeps is beyond what the receiver's software could derive from the frames with its own key, but keeping all of it inside the engine is what makes "the operator sees only the count" a property of the software rather than of each of its callers.

**`Raw` is required.** The setup message MUST use the `Raw` data structure, as every round of this protocol already does (a received setup that is not `Raw` is refused as a protocol error). It is what makes the count exact. The probabilistic structures the library also offers -- a Bloom filter and a Golomb-coded set -- admit false positives, which here would be spurious pairs in the count. Under `psi` such a false positive would be reported as a spurious pair an operator could notice; a count-only run reports no identifiers at all, so neither party can detect an inflated count, let alone correct it. The exactness requirement is therefore stricter for psi-c than for psi, not weaker.

## Computing the count

The count is the size of the one-to-one cascade's association table in the permuted space, computed by the receiver's engine:

1. **The round's pairs.** Before any element of a round's response is matched, the receiver's engine refuses, as a protocol error, a response that holds the same element twice or holds an element that is not 33 bytes in the protobuf framing. A conforming response never does: the receiver's elements are distinct, and the sender's processing maps distinct elements to distinct elements. The refusal does not depend on whether any element would have matched. That check reads only the framing, so a 33-byte element that is not a valid point, such as one whose x-coordinate is not reduced below the field prime or a point off the curve, passes it. The library refuses such an element during the match, as a library failure rather than a protocol error, after the elements before it have been fed to the match and progress has been reported. The round then ends with no count: the engine refuses the count and every later round call (held on both backends, for an x-coordinate not reduced, by `packages/core/test/psi/psiEngineCountOnlyPermuted.test.ts`). Where that refusal falls depends only on the element's position in the response, not on whether any element matched. In round `k`, for each response slot `s` whose decrypted element equals the setup element at position `p`, the engine forms the pair (`s`, `T_k[p]`), `T_k` being that round's index table. Each party's elements in a round are distinct, so in a round whose key declares no candidate set a slot or a pseudonym occurs in at most one of the round's pairs, and the engine refuses such a round whose pairs repeat as an internal fault. A round whose key declares a candidate set forms its pairs over blocks ([Candidate sets under count-only](#candidate-sets-under-count-only)), where one slot or pseudonym can occur in several.
2. **The replay.** Two sets start empty: the accepted slots and the accepted pseudonyms. Round by round, in the round order, every pair whose slot and pseudonym are both not yet accepted is accepted, and its slot and pseudonym join the two sets. A round's pairs are disjoint, so their order within the round does not change the result.
3. **The count** is the number of pairs accepted.

A round whose key declares a candidate set can give a slot or a pseudonym several pairs, and the replay then takes the general form [Candidate sets under count-only](#candidate-sets-under-count-only) specifies, of which steps 2 and 3 are the case where every round's pairs are disjoint.

The replay is symmetric in the two parties, and the count is at most the smaller of the two record counts. Where no key declares a candidate set the count therefore does not depend on which party is the receiver; a candidate set can make it depend on that, as it can the `psi` table ([Candidate sets under count-only](#candidate-sets-under-count-only)).

**Comparability with `psi`.** Where no key value is repeated within either party's dataset, the count equals the size of the association table a one-to-one `psi` run over the same terms and the same data produces, under either linkage strategy, since both produce the same table. Where a value is repeated within one party's dataset for a key, the two can differ, and only through such values:

- The `psi` cascade applies its within-round uniqueness rule to the records still unmatched at that key's round ([Matching Algorithms](PROTOCOL.md#psi)). A repeated value whose other holders an earlier key has matched is unique among the unmatched records, so it takes part in the `psi` round.
- PSI-C gives every holder of a repeated value a dummy, so that value takes no part in the key's round.
- A pair one run accepts and the other does not changes which records are still free for later keys, so the difference can propagate to later rounds and can go in either direction.

A round a missing-field condition filters keeps that difference and adds none. On the filtered side both tests read the records with no valid value for the field, `psi` only those of them still unmatched. A test over the party's whole dataset there would add a second difference, one no earlier match causes: a value that a record lacking the field shares only with records that have it would be a dummy under PSI-C and take part in the `psi` round.

A round whose key declares a candidate set adds no difference of its own: it counts the pairs the `psi` resolution accepts on the same round, in the same role assignment ([Candidate sets under count-only](#candidate-sets-under-count-only)). A value repeated within a party's dataset is there a value two or more of its records hold among their candidates for the key.

Applying the `psi` rule exactly would mean sending every holder of a repeated value and resolving the repetition in the replay, since neither party knows on the wire which of its own records have matched. The receiver's software would then see a repeated value of its own as one setup position matched by several slots, and since the receiver knows which of its records share a value, those slots would be tied to those records. Testing over every record the round is built for keeps every element of a round distinct, at the cost of the difference above.

## A declared `single-pass` runs the same rounds

Count-only terms declaring [`linkage_strategy: single-pass`](../EXCHANGE_REFERENCE.md#linkage_termslinkage_strategy) are accepted, and the exchange runs the rounds above, the cascade realization. The result is identical to what a batched realization would give:

- Every count-only round is full-size, and no round's set depends on an earlier round's matches, since the cascade's removal takes place inside the receiver's replay.
- Batching the rounds into one exchange would therefore change no element, slot, pseudonym, or pair. The count is the same, and so is what each party learns; the two would differ only in how many round trips the frames take.
- So no second wire format is specified for count-only. The `psi` single-pass reply is not one: it pools each party's distinct values across keys under one row-keyed index table, so a round's slots would not line up and no set would have the declared record count.

The bounds a count-only run is held to are those of these rounds, never [the single-pass dataset ceiling](PROTOCOL.md#the-single-pass-dataset-ceiling-receiver-memory-and-masking-compute), which bounds that reply.

**The declared strategy is stated as written.** `linkage_strategy` stays the value the terms declare. The terms exchange compares it as it compares every mandatory-consistency term, the agreed-terms hash and the agreed-terms file beside the record cover it as written ([EXCHANGE_RECORD.md](EXCHANGE_RECORD.md#count-only-psi-c-records)), and both parties' terms review and consent surfaces state it as written. What those surfaces state a count-only run discloses is this section's, never a `psi` single-pass run's: a count-only run sends no single-pass index table and has no association table to withhold.

## Candidate sets under count-only

**Which candidate sets.** A key element whose `transform` declares a fan-out function or `generate_fuzzy_comparisons` runs under count-only by the rules below. A key declaring `swap` adds no candidate set, since both parties sort its pair ([Where the expansion runs](PROTOCOL.md#where-the-expansion-runs-after-the-element-transform-into-the-cross-product)). A fan-out a party authors in its own data standardization stays refused ([Refusals under count-only](#refusals-under-count-only)).

**Each round has a width for each role.** In round `k`, the receiver's width `w_R` is the width the agreed terms declare for the round's key ([The width bound](PROTOCOL.md#the-width-bound-a-per-key-candidate-cap-the-terms-declare)). The sender's width `w_S` is the same product with the factor of each expansion only the receiver executes taken as 1: the full-variant `generate_fuzzy_comparisons` kinds ([Which party expands](PROTOCOL.md#which-party-expands-full-variant-and-deletion-neighbourhood-expansions)). On a key with a fan-out, `w_S` is `w_R` instead. A fan-out's factor does not bound how many values one element realizes, since the width bound holds only the whole key, so on such a key a sender record can realize more candidates than that product and up to `w_R`, as a `psi` sender's can. A key with no candidate set has width 1 in both roles. Both widths are functions of the agreed terms and the resolved roles, so each party derives both and neither is sent.

**One block per record.** In round `k` a party's set has `w` elements for each of its records, `w` being its own width for the round: `n_R * w_R` elements in the receiver's request and `n_S * w_S` in the sender's setup. A record's elements form one block, and the receiver's blocks follow its request order:

- A record's candidates for the key are the values step 5 of [Where the expansion runs](PROTOCOL.md#where-the-expansion-runs-after-the-element-transform-into-the-cross-product) yields for it, each written as its round value (above).
- A candidate is real when no other record the party builds the round for has it among its candidates, and a dummy otherwise. The record's other candidates stay real: this is the uniqueness rule above applied value by value, as [Value-level round participation](PROTOCOL.md#value-level-round-participation) applies it under `psi`.
- Both parties apply that one rule, each to the candidates it contributes, as both do under `psi`: the receiver after a one-sided expansion and the sender without it. The test reads every record the round is built for, never only the records still unmatched, as above.
- The block holds the record's real candidates and a fresh dummy for each element left over.
- The receiver orders each of its blocks under a permutation of `0` to `w_R - 1` drawn for that block in each round, under the rules its request order is drawn under. No place in a request block therefore says which candidate an element is, or whether it is a dummy, to a sender that answers chosen positions of the request ([Threat-model scope](#threat-model-scope-of-the-count-only-claim)). The sender's setup needs no such rule: the library sorts it by ciphertext.
- A record with more candidates than its width takes the fate [the width bound](PROTOCOL.md#the-width-bound-a-per-key-candidate-cap-the-terms-declare) gives it: a fan-out's drop leaves a block of dummies, and a fuzzy exceedance refuses the exchange, before the connection (below). A record holding more candidates than its width that the width bound does not reach, through an expansion no declared factor accounts for, is refused the same way.

**Every refusal over a party's own rows comes before the connection.** A party MUST build every round's candidates for its own records, and raise every refusal building them can raise, before it opens the exchange's connection. Those refusals include a fuzzy exceedance ([The width bound](PROTOCOL.md#the-width-bound-a-per-key-candidate-cap-the-terms-declare)) and a date value that is not eight digits ([Which party expands](PROTOCOL.md#which-party-expands-full-variant-and-deletion-neighbourhood-expansions)). Its role is not known until the terms exchange, so it builds them as the party that executes every one-sided expansion, and refuses on a row that would refuse in either role. Such a refusal is then a failure in front of its own operator, before any frame is sent, never an abort the partner sees after the rounds begin, whose round and timing would tell the partner that some row of this party's holds such a value. The cost is stated: a party that would resolve as the sender refuses on a row it would have sent as its exact value, so `psi-c` refuses some data `psi` runs on in that role assignment.

**The sender permutes blocks.** `pi` is a permutation of the receiver's `n_R` blocks: slot `s` of the response is the `w_R` elements answering block `pi(s)` of the request. Within each slot the sender orders the block's elements under a further permutation of `0` to `w_R - 1`, drawn for each slot in each round under the rules `pi` is drawn under. A matched response position `q` therefore names slot `floor(q / w_R)`, and its place within the slot does not say which element of the receiver's block it answers. With `w_R = 1` this is the response above.

**The index table names a pseudonym for each element.** The round's index table has `n_S * w_S` entries, entry `p` being `sigma` of the record whose block holds the element at position `p` of the setup as sent, so each pseudonym occurs exactly `w_S` times. It is the binary frame above, `4 * n_S * w_S` bytes long.

**The frame checks read the widths.** The receiver MUST refuse a setup whose element count is not `n_S * w_S`, and an index table whose length is not `n_S * w_S` or in which a pseudonym from `0` to `n_S - 1` does not occur exactly `w_S` times; with `w_S = 1` that is the permutation check above. The sender MUST refuse a request whose element count is not `n_R * w_R`. The counts at the start and against the partner's receive ceiling weigh each round's element count, the party's declared record count times its width for the round. A round sends `35 * (n_S * w_S + 2 * n_R * w_R)` bytes of encrypted elements and `4 * n_S * w_S` bytes of index table.

**The count over candidate sets.** The receiver's engine forms round `k`'s pairs as step 1 of [Computing the count](#computing-the-count) does, the pair for a response position `q` matching setup position `p` being (`floor(q / w_R)`, `T_k[p]`). A slot or a pseudonym can occur in several of a round's pairs, and two pairs naming the same slot and pseudonym are one candidate pair, as [the attribution rule](PROTOCOL.md#matching-multiplicity-the-record-value-incidence) collapses them. The replay then takes this form, of which steps 2 and 3 of that section are the case where every round's pairs are disjoint:

1. Two sets start empty: the slots and the pseudonyms that have left candidacy.
2. Round by round, in the round order, the round's graph is its candidate pairs whose slot and pseudonym are both still in candidacy. The round adds to the count the size of a maximum matching of that graph: the largest number of its pairs no two of which share a slot or a pseudonym.
3. Every slot and every pseudonym in a pair of the round's graph then leaves candidacy, whether or not a maximum matching includes the pair, as every record in a candidate pair does under `psi` ([Removal on a potential match](PROTOCOL.md#removal-on-a-potential-match)).
4. The count is the sum of what the rounds add.

Only the size of a maximum matching enters the count, never which pairs it holds, and that size is a function of the graph alone. The count therefore does not depend on the order of a record's candidates, the order the pairs are met in, `pi`, or `sigma`, and it is the same in every run on the same data in the same role assignment. Where every round's pairs are disjoint the graph is itself a matching, every pair counts, and the count is the one above.

**The replay's work is bounded by each round's pairs.** The receiver's engine finds a round's maximum matching with the searches [the `psi` resolution](PROTOCOL.md#record-level-resolution-canonical-order-and-tiebreak) runs (`maximumMatchingSize`, `packages/core/src/psi/roundResolution.ts`): one pass accepting each distinct pair whose slot and pseudonym are both still unmatched, then one augmenting-path search from each pseudonym the pass leaves unmatched, each search crossing each of the round's distinct pairs at most once. With `P` a round's distinct pairs in its graph, the round's work is at most proportional to `P` squared. A response element matches at most one setup element, so `P` is at most the round's matched response positions, `n_R * w_R`.

**Limit: a sender choosing its setup can reach the quadratic case.** The sender's setup shapes the round's graph, as a partner's grouping shapes a `psi` round's ([Limit: a partner who can shape the round's candidate pairs can reach the quadratic case](PROTOCOL.md#record-level-resolution-canonical-order-and-tiebreak)), and the searches are the same, so the replay's time grows as that section measures for the same number of pairs. The searches do not yield inside the engine, so a receiver running the engine on its own event loop is unresponsive while one round's replay runs.

**Each round adds what the `psi` round accepts.** The `psi` resolution accepts a largest pairing of each round's candidate pairs ([Record-level resolution](PROTOCOL.md#record-level-resolution-canonical-order-and-tiebreak)), so it accepts as many pairs as a maximum matching of them holds, and both remove every record in any of the round's candidate pairs. A round's graph over slots and pseudonyms is the `psi` round's candidate pairs under the two permutations wherever the two rounds hold the same participating values, so each such round adds the number of pairs the `psi` round accepts. The two can part in one way, able to carry into later rounds: a value repeated within a party's dataset, by the difference [Comparability with `psi`](#computing-the-count) states. A sender's block holds every candidate a `psi` sender sends, since the width bound holds a `psi` party's rows to the declared width `w_R` in either role, and a sender's block on a key with a fan-out holds `w_R` (above).

Where no such value occurs, the count is the size of the `psi` table on the same terms, the same data and the same role assignment.

**The two normative cases.** In [the normative double-match case](PROTOCOL.md#the-normative-double-match-case) the round's candidate pairs are `(S0, R0)`, `(S0, R1)` and `(S1, R1)`, held as slots and pseudonyms; a maximum matching has two pairs, so the round adds 2, the size of the table both `psi` parties produce. In the case beside it the pairs are `(S0, R0)`, `(S0, R1)` and `(S1, R0)`, and the round again adds 2, the two pairs both `psi` parties accept. Neither figure depends on which pair a sweep meets first, which nothing in the slots and pseudonyms fixes.

**The role assignment.** The count can depend on which party is the receiver as the `psi` table can, and in the same way. A one-sided expansion widens the receiver's candidates and not the sender's, so the uniqueness rule can drop a variant in one role assignment that the other keeps ([Which party expands](PROTOCOL.md#which-party-expands-full-variant-and-deletion-neighbourhood-expansions)). Where no candidate a one-sided expansion adds is held by two or more of the expanding party's records, in either role assignment, the round's graph is the same in both, and so is what it adds.

## Refusals under count-only

A psi-c terms document declaring any of the following MUST be refused:

- [`deduplicate: true`](../EXCHANGE_REFERENCE.md#linkage_termsdeduplicate) on either party;
- payload in either direction -- a non-empty [`payload.send`](../EXCHANGE_REFERENCE.md#linkage_termspayload) or `payload.receive`, or [input metadata](../EXCHANGE_REFERENCE.md#input-metadata) that would transmit a column (`is_payload: true` on a column whose `role` is not `ignored`);
- a fan-out a party authors in its own [data standardization](../EXCHANGE_REFERENCE.md#data-standardizing-transformations). A candidate set the agreed terms declare -- an element `transform` declaring a fan-out function or `generate_fuzzy_comparisons` -- runs by [Candidate sets under count-only](#candidate-sets-under-count-only). The standardization half is per-party and local, so no invitation holds it and a partner cannot derive it; it MUST be refused at the prepare step, as [the fan-out rule's local half](PROTOCOL.md#fan-out-runs-under-both-linkage-strategies) is.

Every rule above that a terms document alone decides MUST be refused at each parse of that document, the invitation-token decode included: the parse is the first point the rule's inputs are knowable, and it precedes any consent surface the terms reach. Two rules a parse cannot decide are the input metadata that would transmit a column and the standardization fan-out, each of them per-party and local.

Each MUST be refused at three further points, so that no combination of authoring path and partner reaches a run: when the terms are authored or an invitation over them is minted; at the local prepare step, before any credential, terms, or data are sent; and at the agreed-terms run boundary once the terms exchange has completed, which is the first point at which both parties' values are known. The run-boundary check is a symmetric function of the agreed pair, computed identically on both parties, so the lockstep round cannot begin on one side and be refused on the other.

The refusal is fail-closed at all three: an over-broad psi-c term is never silently narrowed to the specified shape, never derived and then discarded, and never downgraded to a `psi` run. Narrowing would deliver a disclosure the operator did not agree to; downgrading would reveal matched identifiers under terms that asked for a count -- the exact substitution the count-only algorithm exists to prevent.

**Why each is refused.** Each reason is psi-c's own:

- **`deduplicate`.** The count is the size of a one-to-one table. What a count means under a many-to-X cardinality is not specified here.
- **Payload.** A count-only exchange discloses no column, which is what its record states ([EXCHANGE_RECORD.md](EXCHANGE_RECORD.md#count-only-psi-c-records)).
- **A fan-out in a party's own data standardization.** Such a party declares its record count times the fan-out factor and declares no width ([The width bound](PROTOCOL.md#the-width-bound-a-per-key-candidate-cap-the-terms-declare)), so its records' blocks would be 20 times the width the terms declare, over a twentieth of the records it declares.
  - No frame of a round states the factor. A sender ordering a fanning receiver's request by blocks of `w_R` would split each of the receiver's records across 20 slots, and one record could then be counted against up to 20 of the sender's.
  - The refusal holds under both linkage strategies, so the cascade realizing candidate sets does not lift it ([The combinations that stay unsupported](PROTOCOL.md#the-combinations-that-stay-unsupported)).
  - The same split declared in a key element's `transform` runs, since the terms then declare its width.

## Count reporting and entitlement

The receiver alone computes the count. Whether it travels back is decided by the agreed terms' [`output`](../EXCHANGE_REFERENCE.md#linkage_termsoutput) entitlement, derived identically on both parties before the rounds run:

- **Both parties entitled** (`expects_output` true on both). After the last round the receiver sends a single **count-report** frame holding its tally to the sender over the authenticated channel. Only the receiver sends; the sender receives it and sends nothing back.
- **Exactly one party entitled.** By the role rule the entitled party is the receiver, so it already holds the count and there is no count-report frame at all. The non-receiving sender receives nothing -- not the count, not an empty frame. Suppressing the frame entirely, rather than sending a placeholder, is the same discipline the single-pass table withholding follows: a frame that is present but empty would still mark, by its presence, that a count existed to report.

Both parties derive that decision from the same agreed terms, so the receiver never sends a frame the sender will not read and the sender never blocks awaiting one the receiver will not send. The reference implementations are `linkViaCountOnlyPSI` (`packages/core/src/psi/link.ts`), which runs the rounds and this leg, and `reportsCountToSender` (`packages/core/src/protocolSetup.ts`), the entitlement predicate both parties evaluate.

**An exchange that ends before its last round has no count.** Whether it ends between two rounds or within one, on an abort, a refusal or a lost connection, the receiver takes no count, so neither party holds one and no count-report frame is sent. The receiver's software asks its engine for the count only once every round has been matched (`PSIParticipant.finishPermutedCount`, `packages/core/src/psi/participant.ts`; held by `packages/core/test/psi/countOnlyEveryKeyRun.test.ts`).

The count-report frame's `intersectionCount` is bounded like every other partner-supplied integer: a non-negative safe integer no greater than [`MAX_RECORD_COUNT`](PROTOCOL.md#the-single-pass-dataset-ceiling-receiver-memory-and-masking-compute) and no greater than the smaller of the two record counts the terms exchange stated, since a one-to-one table cannot exceed either party's dataset. The bound rejects an absurd figure at decode; it does not make the number checkable, which is the trust-contingency stated below rather than a gap in the bound.

## What each party learns, and on what basis

Stated in the vocabulary the consent surfaces use -- `enforced` is a claim about the run (either it holds or the exchange aborts), `trust-contingent` is a claim about the partner, whom Alcove does not stop (`CONSENT_BASIS_MARKERS`, `packages/core/src/consent/consentFacts.ts`):

- **A party's own count-only outcome is enforced.** Its own software shows its operator the count and nothing finer: the receiver's engine returns only the count, and the sender computes no match at all. Neither the partner's cooperation nor its honesty is required for this.
- **The sender learns nothing about the receiver's records but their number.** It sees `n_R` encrypted elements a round, or `n_R * w_R` under a candidate set, in the receiver's request order, and computes no match. Where only the receiver is entitled to the count, this is enforced for a receiver running this protocol against a sender deviating on the wire: no frame the receiver sends it contains more, and the sender receives no count. Where both parties are entitled to the count, a sender that substitutes points in its response learns whether the receiver's records at request positions it chose matched, but not which of the receiver's records those are ([Threat-model scope](#threat-model-scope-of-the-count-only-claim)). It is not enforced against a sender that chooses its input when both parties are entitled to the count. A sender whose input is one live candidate padded with values the receiver cannot hold reads that candidate's membership from the reported count, and two runs whose sets differ in one record give that record's. These are the crafted set and the differencing the [threat-model scope](#threat-model-scope-of-the-count-only-claim) states against the sender, turned on the receiver.
- **Each party learns when the other's crypto operations ran, and that is accepted.** On a WebRTC data channel or a WebSocket relay, each party's still-working frames state its progress through its current crypto operation about every 30 s ([The still-working frame](PROTOCOL.md#the-still-working-frame)), so a sender running this protocol learns when the receiver's match step started and ended, and how far it had got at each frame, to within about one frame interval. The figure carries no data value and no number of matches. The [threat-model scope](#threat-model-scope-of-the-count-only-claim) states what timing the match revealed when measured together with the receiver's masking, under the deviating sender's timing; the match step's duration on its own is not measured. A file-sync exchange sends no still-working frame.
- **That the receiver cannot attribute a match to a record rests on the sender's own software.** Only the sender draws `pi` and `sigma`, so a sender running this protocol protects its own records, and the receiver cannot tell whether a sender applied them. A receiver following the protocol cannot undo `pi` or `sigma` from its own side; what its own inputs and key coverage let it learn, and what a receiver that deviates from the protocol can recover, is stated in the next bullet and under the threat-model scope below.
- **The receiver's software learns more than the count, from genuine inputs, and that is accepted.** Its engine keeps every round's pairs, so the receiver's software can derive, beyond the count: the number of matches on each key; the overlap between keys, how many slots matched on each combination of keys; and the pseudonymous pair table of slots against sender pseudonyms. And from its own records' key coverage: a slot that matched on a set of keys belongs to one of the receiver's records with a real value for every one of those keys, so where few of its records have that coverage the match narrows the slot to those records, or names one. None of this needs a deviation from the protocol, and none of it is shown to the operator. How often coverage singles out a record on real data is not measured.
- **A key with a missing-field condition adds two facts of the same kind, and they are accepted too.** For each matched sender pseudonym the receiver's software learns which of the key's two rounds it matched in, and a match in the round filtering the sender's side tells it that the sender record behind the pseudonym has no valid value for the field, as a match on any key tells it that the record has a value for that key. A match in the round filtering the receiver's side narrows the slot to the receiver's own records with no valid value for the field, as its own coverage narrows any slot. Both are per-key results and coverage-based narrowing, the class the item above accepts, and neither is shown to the operator.
- **A key with a candidate set adds its round's graph and how many candidates each pair shares.** For each round of such a key ([Candidate sets under count-only](#candidate-sets-under-count-only)) the receiver's software learns, beyond what the items above state:
  - the round's candidate pairs over slots and pseudonyms: how many sender pseudonyms each slot matched and how many slots each pseudonym matched, so which matches were contradicted. A `psi` cascade states the same of its matched records to both parties, in its per-round grouping ([The disclosure delta fan-out pays](PROTOCOL.md#the-disclosure-delta-fan-out-pays));
  - each pair's multiplicity: how many of the slot's elements matched one of the pseudonym's. A value matches at most one element on each side, so this is how many candidates the two records share, and summed over a slot, or over a pseudonym, it is how many of that record's candidates matched, which a `psi` cascade's grouping states of each matched record;
  - what the multiplicity says about the match. Under `edit_distances` an exact match shares the value and every one of its deletions, where a match one edit apart shares few, so the number tells the two apart. Under a fan-out it is how many of a record's parts matched;
  - from its own records, that a slot whose elements matched `m` times in a round belongs to one of its records with at least `m` real candidates for the key, as its own coverage narrows any slot.

  The two orders within a block, the receiver's and the sender's within each slot, keep from it which of a record's candidates matched, except where the number settles it: a record with one real candidate, or a slot whose matched elements number its record's real candidates, every one of which then matched. None of this is shown to the operator.
- **A refusal over a party's own rows reaches the partner as an exchange that did not start.** Under a candidate set, every refusal building a round can raise comes before the party opens the connection ([Candidate sets under count-only](#candidate-sets-under-count-only)), so no such refusal ends a run the partner has joined, and its round and timing reach the partner as nothing.
- **The sender's knowledge of the count is trust-contingent.** In the both-entitled case the number the sender holds is the receiver's report; a receiver that reports a different one is not stopped by Alcove. This is the same posture as the `psi` association-table return leg, where the sender's half of the pairing likewise arrives as the receiver's word. A sender that needs the figure to be independently checkable does not get that from psi-c.

**What the rounds disclose.** Each party's set in every round has exactly its declared record count times its width for the round, which the terms exchange and the agreed terms already state, so a frame's element count tells the partner nothing more, and in particular not how well a key covers the party's dataset, nor, in a round a missing-field condition filters, how many of the party's records lack the field. Without `sigma`, an index table is a uniformly random arrangement of the pseudonyms, each occurring once, or `w_S` times under a candidate set, so beyond the matches it names it says only which setup positions belong to one sender record, each record having the same number of them. Neither party's frames state the count.

## Threat-model scope of the count-only claim

The count-only claim holds in the semi-honest (honest-but-curious) model this project adopts; see [SECURITY_DESIGN.md](../SECURITY_DESIGN.md#threat-model). It protects the sender against a receiver that contributes a genuine dataset, up to the disclosure from genuine inputs stated above. It does not protect the sender against a receiver that chooses its input set, and the choice is enough on its own:

- **A crafted pattern across the keys.** A receiver gives each of its records its own pattern of keys with a real value and keys with a dummy, for instance by leaving a field blank in its own input so that a conforming party sends a dummy. A slot can only match in rounds where its record has a real value, so with patterns chosen so that none contains another, a slot that matched on every key where its record had a real value names the record. About `log2(n_R)` keys or more give enough such patterns for every record, and one run then yields the membership of most matched records. It needs no modified software and only one run. It is the same mechanism as the cross-key count, so no padding or permutation removes it. A key with a candidate set adds a finer pattern: a slot's matched elements on the key narrow it to the receiver's records with at least that many real candidates, so a receiver varying its records' candidate counts as well can need fewer keys.
- **A crafted set.** A receiver whose input is one live candidate padded with values it knows the sender cannot hold reads that candidate's membership straight off a count of 0 or 1. A key with a candidate set lets such a receiver put up to `w_R` values in one record's block: a count of 1 then says that one of them matched, and its software reads how many of them matched, though not which. Nothing distinguishes a crafted set from a genuine one on the wire: both are opaque encrypted elements, and only their number is visible.
- **Differencing across runs.** Two count-only runs whose input sets differ in one record name that record's membership by the difference of their counts. This is the differencing attack SECURITY_DESIGN.md already names for linkage keys, applied to the count.

All three tamper with an input rather than merely observing one, so all three sit a step beyond honest-but-curious -- the same category as the record-count manipulation SECURITY_DESIGN.md records for role assignment -- and all three are accepted rather than prevented. The crafted pattern is the cheapest by far: one run, no modified software, and up to every matched record, where a crafted set or a differencing pair yields about one record a run. Preventing them would require binding a party's contributed set to a dataset it cannot choose per run, which nothing in this protocol does.

None of the three is a wire deviation. A wire deviation by a party running modified software is also a step beyond honest-but-curious. A sender that copies a response element into a second slot learns nothing from it: the receiver refuses a response that repeats an element before any of it is matched ([Computing the count](#computing-the-count), step 1). Three wire deviations are accepted rather than prevented:

- **A deviating receiver can recover `pi`.** The sender answers every round under one key and one `pi`, so a receiver that sends crafted requests across the rounds, the same elements shifted by one position or with one element replaced, rebuilds `pi` from which response elements are equal byte for byte. That yields per-record matches, the same result the crafted pattern across the keys gives with unmodified software in one run. The crafted rounds take the place of genuine key rounds, so the deviating receiver's own count is wrong, and the sender cannot detect it. A receiver can instead mask each of its records under a key of its own, and so name every matched record, and the sender's pseudonym for it, from one round of genuine data with its count intact. The sender sees valid points in the declared number and cannot detect that either.
- **A deviating sender can substitute points in its response.** The sender answers the request positions it chooses as the protocol does, and fills every other slot with distinct valid points that match no setup element. Such a response passes every check the receiver's engine makes. Request positions follow the receiver's request order, which the receiver draws at random for the exchange, so where both parties are entitled to the count, the reported count tells the sender whether the receiver's records at the chosen positions matched, but not which of the receiver's records those are. Under a candidate set the receiver orders each block at random each round ([Candidate sets under count-only](#candidate-sets-under-count-only)), so a position chosen within a block names no particular candidate of the record, such as its exact value. Where only the receiver is entitled, the sender receives no count. The count includes matches only at the positions the sender answered, so the count it receives omits every other match. The receiver's own count is wrong in the same way, and the receiver's engine accepts the response without an error, so the receiver is not told.
- **A deviating sender can time the receiver's frames.** A sender that builds its next round's setup before it sends a response, and sends the two together, can time the gap to the receiver's next request, which then includes the receiver's match of the round. At about 10^6 records a side no per-round count, and no difference between every record matching and none, showed within one exchange against the spread of the receiver's own masking. A sender averaging recurring exchanges over unchanged data would need about 45 rounds in which every record matched to tell all from none, and about 700 to resolve steps of 25%. Those figures were measured on a loaded host. On a file-sync channel an honest sender's own setup hides the match entirely. On a WebRTC data channel or a WebSocket relay the receiver's still-working frames tell any sender, honest or not, when the match step started and ended, and how far it had got at each frame, to within about one frame interval ([What each party learns, and on what basis](#what-each-party-learns-and-on-what-basis)). This is accepted under the honest-but-curious model.

The sender can also give up the count-only property on the wire, by returning a response it did not reorder, or reordered under a permutation the receiver can predict. That reduces only the sender's own protection, and the receiver cannot detect it.

Two consequences follow, rather than being left to be derived. First, the count-only property is a property of the algorithm, not of the partner: it says the protocol hands the receiver's operator only a number, not that the receiver cannot arrange for its software to learn which records matched. Second, psi-c has this scope where it bites hardest. It is the algorithm run to decide whether a data-sharing agreement is worth having -- which is exactly when the signed agreement the honest-but-curious assumption leans on does not yet exist. A count-only run is a disclosure to be weighed on its own terms, not a free look before the real decision.
