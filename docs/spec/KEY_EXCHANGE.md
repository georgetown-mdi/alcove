# P-256 authenticated key exchange

This document specifies the wire-level P-256 authenticated key exchange that authenticates every recurring exchange and yields its session key: the construction, the key-agreement derivation and key schedule, the version hello, the message flow, which secret a handshake uses, the failure handling, and the test vectors. It also specifies how the WebRTC rendezvous peer ids are derived from the shared secret.
It does not cover the rotation that the handshake's outputs feed and the previous secret (see [SHARED_SECRET_ROTATION.md](SHARED_SECRET_ROTATION.md)), the relay credentials derived from the same secret (see [RELAY_CREDENTIALS.md](RELAY_CREDENTIALS.md)), the application-layer AEAD the session key keys (see [CHANNEL_SECURITY.md](CHANNEL_SECURITY.md)), the key-agreement decision and the threat model (see [SECURITY_DESIGN.md](../SECURITY_DESIGN.md#key-agreement-design)), or the WebRTC channel's wire (see [WEBRTC_TRANSPORT.md](WEBRTC_TRANSPORT.md)).
Intended readers are security auditors, external implementors, and developers.

Alcove authenticates every recurring exchange with a P-256 authenticated key exchange: the key-agreement primitive that produces the exchange session key (see [SECURITY_DESIGN.md](../SECURITY_DESIGN.md#key-agreement-design) for the decision and its rationale). It performs an ephemeral P-256 ECDH keyed together with the pre-shared secret, plus an explicit, role-asymmetric mutual key confirmation, and yields a 32-byte session key with forward secrecy and mutual authentication. The handshake also includes a per-party request-encryption flag and returns a transcript-bound `applyEncryption` decision (`own request OR peer request`) that tells the caller whether to wrap the connection in the application-layer AEAD; see the **Request-encryption flag** discussion below. `authenticateConnection` (in `auth.ts`) runs it immediately after the connection opens and uses the resulting session key to key the application-layer AEAD and the wraps of the shared-secret rotation. It is implemented as `runKex` in `packages/core/src/kex.ts` and exported from `@alcove/core`. This section specifies the primitive and its wire format.

**Primitive selection.** The governing rule is to prefer a well-respected, ideally audited, dual-platform primitive and to hand-roll only the minimal glue. No production-ready, audited Noise Protocol Framework library with dual Node.js/browser support exists in the JavaScript ecosystem, so none qualifies. Every cryptographic operation in the handshake is therefore a platform `crypto.subtle` call: the ephemeral key generation (`generateKey`), the Diffie-Hellman (`deriveKey` from ECDH to a non-extractable HKDF key), the key-agreement derivation, the Noise chaining HKDF and the application HKDF (`deriveBits` over HKDF), SHA-256, HMAC-SHA-256, and the rotation's draw of the initiator's value (`generateKey`), its wrapping key (`deriveKey` over HKDF) and its AES-KW wrap (`wrapKey` and `unwrapKey`). The value that stands in for an absent previous secret is drawn the same way (`generateKey`). No key-establishment path calls a third-party curve library, and no dependency is added. The only hand-written layer is the minimal NNpsk0 glue: the Noise key-schedule mixing, the confirmation tags and their trial verification, and the history proofs and behind notices. The full Noise framework is not implemented. The Diffie-Hellman is a platform call, never hand-rolled curve math.

**Construction.** The handshake is pinned to the Noise NNpsk0 pattern over P-256 -- no static keys, the pre-shared secret mixed in at position 0, and ephemeral-ephemeral Diffie-Hellman -- followed by an explicit key-confirmation round whose construction is modelled on the bilateral key confirmation of [NIST SP 800-56A Rev. 3](https://doi.org/10.6028/NIST.SP.800-56Ar3) section 5.9.2 -- role-distinct MAC tags over the handshake transcript. The resemblance is to that construction and not to the scheme it is specified for: section 5.9.2 offers the feature for "any key-agreement scheme in which each party is required to own a static key-establishment key pair", and this handshake has no static keys at all, taking its authentication from the pre-shared secret instead. No other section of that publication reaches the round either -- section 6.1.2.3 records that "key confirmation is not incorporated for the C(2e, 0s) key-agreement schemes", the ephemeral-only category the Diffie-Hellman here belongs to -- so the citation names a construction the round is modelled on, never one it conforms to. Keying material comes from one SP 800-56C two-step key-derivation call over the shared secret, **The key-agreement derivation** below: [SP 800-56C Rev. 2](https://doi.org/10.6028/NIST.SP.800-56Cr2) section 2 (Scope and Purpose) scopes that document's derivation methods to a shared secret produced by an SP 800-56A or SP 800-56B key-establishment scheme, and its section 5 specifies the two-step method. The ephemeral Diffie-Hellman with that derivation as its key-derivation method is the (Cofactor) Ephemeral Unified Model of SP 800-56A Rev. 3 section 6.1.2.2, C(2e, 0s, ECC CDH); what is claimed from that is in [COMPLIANCE.md](../COMPLIANCE.md#nist-sp-800-53) (SC-12). The Noise chaining key schedule takes the derivation's first block as its `ee` input, never the shared secret itself, and each of its steps is a single [RFC 5869](https://www.rfc-editor.org/rfc/rfc5869) extract-and-expand (see **Key schedule** below).

Every Noise citation in this section is to [the Noise Protocol Framework](https://noiseprotocol.org/noise.html), revision 34 of 2018-07-11. That document specifies the pattern and the processing rules this handshake follows; it does not offer P-256 as an instantiation. Its section 12 defines DH functions for 25519 and 448 and no others, and the `DHLEN` of its section 4.1 is a single constant for both the public-key encoding and the DH output, which a 65-byte uncompressed point and a 32-byte shared secret cannot both be. So the framework is what the construction is built from and not a specification it conforms to; the divergences from a stock NNpsk0 session are enumerated under **Test vectors and interoperability** below.

**Curve and point encoding.** The curve is P-256 (`secp256r1` / `prime256v1`), whose domain parameters -- the field prime, the coefficients, the base point `G`, the order `n`, and the cofactor `h = 1` -- are published in [SP 800-186](https://doi.org/10.6028/NIST.SP.800-186) section 3.2.1.3. [FIPS 186-5](https://doi.org/10.6028/NIST.FIPS.186-5) states no curve parameters of its own: it specifies ECDSA and refers the recommended curves to SP 800-186. An ephemeral public key is encoded on the wire as the **uncompressed** point `0x04 || X || Y` of [SEC 1](https://www.secg.org/sec1-v2.pdf) Ver. 2.0 section 2.3.3: 65 bytes, `X` and `Y` each a 32-byte big-endian field element. That encoding is pinned, not merely preferred. A share of any other length, or of length 65 with any prefix other than `0x04`, is rejected without being decoded -- the compressed (`0x02` / `0x03 || X`, 33 bytes) and hybrid (`0x06` / `0x07 || X || Y`, 65 bytes) encodings of the very same point included. Only the compressed form is SEC 1's alongside the uncompressed one: for a point other than the identity, section 2.3.3 emits those two and no third, and section 2.3.4 admits a leading octet of `0x00`, `0x02`, `0x03` or `0x04` and rejects every other. The hybrid form belongs to IEEE Std 1363-2000 (informative Annex E.2.3.2, which admits `0x06` and `0x07` beside them) and to ANSI X9.62; it is named here because platforms decode it, not because SEC 1 defines it. Two reasons, either sufficient. The transcript binds the wire bytes rather than the decoded point, so a second admissible encoding of one point would let an in-path attacker re-encode a share and desynchronize the two sides' transcripts. And `crypto.subtle.importKey` does not answer the encoding question consistently across platforms (Node decodes compressed and parity-correct hybrid, Chromium decodes compressed and refuses hybrid), so a share's acceptance would otherwise depend on which peer received it. The shared secret is the 32-byte `X` coordinate of the shared point -- the `Z` that SP 800-56A Rev. 3 section 5.7.1.2 outputs from the ECC CDH primitive, which for a cofactor-1 curve is plain ECDH.

**Module boundary.** The key schedule is composed in application JavaScript above primitive calls, and sits outside any validated cryptographic module boundary. Where a validated module is configured, it performs every cryptographic operation the handshake makes, all of which reach it through `crypto.subtle` -- the shared-secret computation as `KAS-ECC-SSC` per SP 800-56A Rev. 3 over P-256, and each extract-and-expand as the module's approved HKDF key-derivation function -- `KDA HKDF Sp800-56Cr1`, CAVP certificate A7440, on certificate 5438, the module the FIPS variant image holds ([CONTAINER_IMAGES.md](CONTAINER_IMAGES.md#what-certificate-5438-attests) states both rows and points at the conditions that certificate attaches to them). The shared secret reaches the key-agreement derivation through a `deriveKey` from ECDH to a non-extractable HKDF key, so no value application code can read holds it, and the ephemeral private key's only usage, `deriveKey`, makes the platform refuse a `deriveBits` that would. It still crosses the module boundary between the two services, whose shared-secret parameters certificate 5438's security policy lists as API input and output parameters (Table 20). It does not perform the mixing order, the domain-separation labels, the transcript binding, or the confirmation round, none of which any module certificate attests. In the browser there is no module beneath the platform at all. A composition of this shape yields validated primitives and never a validated protocol -- what a scoped claim may and may not say is in [COMPLIANCE.md](../COMPLIANCE.md#fips-140), and the decision behind the boundary is recorded in [key-establishment-fips-boundary.md](../notes/key-establishment-fips-boundary.md).

**Protocol-version tag.** The Noise "protocol name" is the version tag and is the initial handshake hash, binding every derived key and confirmation tag to it:

```
protocol_name = "alcove-kex-v3:NNpsk0_P256_SHA256"
```

**A mismatched tag fails the handshake closed, and does so by construction.** The tag is the entire input to `h0`, and `ck0 = h0` (see **Key schedule** below), so two peers on different tags diverge at the first step of both the hash chain and the chaining-key chain. Every later value -- the handshake hash, the chaining key, the session key, and both confirmation tags -- differs, so the confirming peer's tag does not verify and the handshake aborts before any non-handshake frame is sent. There is no path on which two peers on different tags agree on a session key. The earlier tags, both under the product's former name ([rename-to-alcove.md](../notes/rename-to-alcove.md)), were its `kex-v1` tag for `NNpsk0_25519_SHA256`, which ran the exchange over X25519, and its `kex-v2` tag for `NNpsk0_P256_SHA256`, the same P-256 suite; a peer on either and a peer on the current tag therefore fail closed on this mechanism rather than negotiating, which is the intended and only outcome -- wire compatibility with either earlier tag is not offered.

A future authenticated mode (for example a certificate-chain variant) is an additive new suite, offered and selected through the version hello below, so the door stays open without any pluggable-auth framework today. The version tag is reserved for a genuine cryptographic-suite change and is not bumped for an additive transcript payload such as the request-encryption flag described below. That flag is a required field on the wire schemas, so a flag-aware and a flag-unaware peer already fail closed at parse -- the flag-aware side rejects a message that omits the required field, and the strict (`.strict()`) schema rejects a message that includes the unrecognized field -- before any transcript is computed.

The five `alcove-kex-v2:` domain-separation labels below keep their own namespace version, which does not track the suite tag (both earlier tags used the former name's `kex-v1:*` labels): the tag already separates one suite's transcript from another's totally, so re-versioning the labels would change derived bytes without separating anything the tag has not.

**The version hello.** Each party sends one hello listing, per layer, the integer versions it supports: `kex`, the key-exchange suites; `protocol`, the protocol version the terms exchange states ([Protocol-version reconcile at the terms exchange](PROTOCOL.md#protocol-version-reconcile-at-the-terms-exchange)); and `envelope`, the encrypted-channel envelope version ([CHANNEL_SECURITY.md](CHANNEL_SECURITY.md#application-layer-aead)), which on file-sync also sets the version byte of every binary frame after each party's first ([FILE_SYNC.md](FILE_SYNC.md#file-taxonomy)). The initiator's hello rides message 1 and the responder's message 2, each the base64url encoding of a UTF-8 JSON object. This build's hello is the one below: suite 3, the suite the tag above names, protocol version 1, and envelope versions 1 and 2 (`supportedVersions` in `packages/core/src/kex.ts`).

```
{"kex":[3],"protocol":[1],"envelope":[1,2]}
```

- **The frozen outer shape.** A hello is a JSON object of at most 1024 bytes whose three layer members are each a list of 1 to 32 integers from 1 to 2^31-1. A reader accepts a member it does not know and ignores it; a hello that is not such an object, or lacks a layer, fails the handshake with the generic failure. That shape is frozen: a later build adds a member rather than changing one, and a hello version field is introduced only for a change an existing reader cannot read.
- **Bound as received.** Neither party re-serializes a hello. The prologue is `len(hello_I) || hello_I || len(hello_R) || hello_R`, each length a 2-byte big-endian count of the hello's bytes as sent or received, and it is the first `MixHash` of the key schedule below. A hello removed in transit fails the parse, and one altered or given a member in transit, a member the reader ignores included, gives the two sides different transcripts so the confirmation fails; both end with the generic failure, unless the alteration leaves the two hellos no common version, which ends in the refusal instead (**A limit**, below).
- **One share per offered suite.** Message 1's `e` is an object keyed by suite id in decimal, holding one share for each suite the initiator's hello lists and no other key; a responder that finds the keys differing from the listed suites fails with the generic failure. The responder answers with one share, for the selected suite, and the initiator keeps only its ephemeral for that suite.
- **The selection rule.** Each side takes, in each layer, the highest version both hellos list. Both hold both hellos before either derives a key, so both select the same versions. `authenticateConnection` returns them as `AuthResult.negotiated`; the encrypted channel is keyed from that result at the negotiated envelope version, and the terms exchange reads the negotiated protocol version from the rotation inputs the result holds, so a caller passes neither on its own.
- **The FIPS variant.** Where the OpenSSL configuration sets `fips=yes` as the default property, as the FIPS variant image's does ([CONTAINER_IMAGES.md](CONTAINER_IMAGES.md#the-fips-variant-images-pins)), the CLI's hello lists only the suites marked approved. Suite 3 is approved, so both variants send the same hello today.
- **No common version.** Where some layer has no version both hellos list, the run ends before the key exchange completes, with the fixed refusal `the partner is running an Alcove version this one cannot exchange with; the party on the older version must update`, which holds nothing the partner authored. The responder decides first and sends `{ kexMsg: "abort", hello: hello_R }` in place of message 2, so the initiator reaches the same refusal from the responder's hello; neither side derives a key or sends a tag. The refusal is a `PartnerProtocolRefusalError` naming the older side where one side's versions all lie below the other's.
- **A limit.** The hellos are read before anything authenticates them, so an in-path attacker can rewrite one to force the refusal above. That costs the run and nothing more, as dropping its frames would. It cannot make the parties complete on a selection their own hellos do not give, because the transcript binds both hellos as sent. The side the refusal names as older is read from those same hellos, so such a rewrite also chooses which party is told to update.

**The key-agreement derivation.** The shared secret `Z` (the 32-byte X coordinate of the ECDH point, SP 800-56A Rev. 3 section 5.7.1.2) enters exactly one derivation, per side per handshake, and nothing else. It is the two-step key-derivation method of [SP 800-56C Rev. 2](https://doi.org/10.6028/NIST.SP.800-56Cr2) section 5 in its HKDF form, issued as one `crypto.subtle` HKDF `deriveBits` call whose base key is the non-extractable HKDF key `deriveKey` produced from the ECDH pair:

```
OKM        = HKDF-SHA-256(IKM = Z, salt = 64 zero bytes, info = FixedInfo, L = 2048 bits)
FixedInfo  = uPartyInfo || vPartyInfo                                   # 266 bytes
uPartyInfo = "alcove-kex-v2:key-agreement" || protocol_name || "initiator" || e_initiator_public
vPartyInfo = "alcove-kex-v2:key-agreement" || protocol_name || "responder" || e_responder_public
k_ee  = OKM[0:32]     # the Noise ee input (Key schedule, below)
ka    = OKM[32:64]    # the rotation input (SHARED_SECRET_ROTATION.md)
k_his = OKM[64:96]    # the history input (SHARED_SECRET_ROTATION.md, The rotation history)
```

The layout, byte by byte:

| Offset | Length | Field | Content |
| --- | --- | --- | --- |
| 0 | 27 | U label | `alcove-kex-v2:key-agreement`, ASCII |
| 27 | 32 | U protocol name | `protocol_name`, ASCII |
| 59 | 9 | U role | `initiator`, ASCII |
| 68 | 65 | U share | the initiator's ephemeral public key, as sent |
| 133 | 27 | V label | `alcove-kex-v2:key-agreement`, ASCII |
| 160 | 32 | V protocol name | `protocol_name`, ASCII |
| 192 | 9 | V role | `responder`, ASCII |
| 201 | 65 | V share | the responder's ephemeral public key, as sent |

- **The party-info fields.** U is the initiator and V the responder on both sides, so both bind the same bytes. Each `PartyInfo` is that party's identifier -- the label, the protocol name and the role, three items -- followed by its ephemeral public key, the information SP 800-56A section 5.8.2.1 names for `PartyUInfo` and `PartyVInfo`. Every item is fixed-length, which is how section 5.8.2 lets an item be represented unambiguously, so the concatenation parses one way and no item takes a length prefix.
- **Why this shape.** It is the fixed-info pattern (`uPartyInfo||vPartyInfo`), the concatenation encoding and the derived-key length (2048 bits) CAVP certificate A7440 records as tested for the module's `KDA HKDF Sp800-56Cr1` service. SP 800-56A section 5.8.2.2 lets a two-step derivation combine or omit the label, context and `[L]2` fields, and this layout carries the label and the context in the party-info fields and omits `[L]2`.
- **The output.** The three 32-byte blocks are taken from the front of the 2048-bit output and the rest is discarded. HKDF's expansion makes each block independent of `L`, so a 768-bit request gives the same three blocks.
- **The salt.** It is the SP 800-56C default, a byte string of zeros as long as the SHA-256 block, 64 bytes. The pre-shared secret is not an input, so the derivation is the same whichever secret a side tries: the pre-shared secret enters the key schedule at `MixKeyAndHash(psk)`.
- **What it does not change.** Every handshake message keeps its fields and lengths; the values that derive from the blocks change with them.
- **A local fault.** A fault the platform raises inside the derivation, rather than a refusal of the peer's share, ends the handshake with that error and sends no abort, so the partner stops at its own handshake timeout. That is a stated limit.

`packages/core/test/keyAgreement.test.ts` checks the layout at each offset, that the derivation is deterministic in both roles, that a changed byte in any field or the two parties in the other order changes every block, that `Z` reaches only this call through `deriveKey` with no ECDH `deriveBits` in a handshake, and that each block reaches only its consumer.

**Key schedule** (a minimal subset of the Noise `SymmetricState`: a chaining key `ck` and a handshake hash `h`). `protocol_name` is exactly 32 bytes, the hash output length, so the Noise `InitializeSymmetric` sets `h0 = protocol_name` (a name shorter than 32 bytes would be padded with zero bytes, a longer one hashed), and `ck0 = h0`. The NNpsk0 tokens (`-> psk, e` then `<- e, ee`, with both hellos as the prologue) are then processed in order:

```
MixHash(prologue)                 # both hellos, as received (The version hello, above)
MixKeyAndHash(psk)                # psk token at position 0
MixHash(e_initiator_public)       # initiator's e: MixHash ...
MixKey(e_initiator_public)        #                ... and MixKey (PSK mode)
MixHash(initiator_flag_byte)      # msg1 payload: initiator's request-encryption flag
MixHash(e_responder_public)       # responder's e: MixHash ...
MixKey(e_responder_public)        #                ... and MixKey (PSK mode)
MixHash(responder_flag_byte)      # msg2 payload: responder's request-encryption flag
MixKey(k_ee)                      # ee: the key-agreement derivation's first block, never Z
```

Each `e_*_public` enters the schedule as its 65-byte wire encoding. Noise states its HKDF's input keying material as zero, 32, or `DHLEN` bytes (section 4.3), an enumeration a 65-byte share sits outside; what makes the schedule well defined anyway is that the RFC 5869 extract beneath it takes an input of any length. The `ee` input is 32 bytes, so every derived length below is unchanged from a 32-byte-share construction.

Each `*_flag_byte` is a single byte, `0x01` if that party requests the additional application-encryption layer and `0x00` otherwise, MixHash'd as that message's handshake payload right after the party's `e` token. Noise handles a payload differently, in two ways: its `WriteMessage` (section 5.3) takes the payload after every token of the message pattern, which in message 2 is after `ee` rather than after `e`, and it passes the payload through `EncryptAndHash` (section 5.2), which encrypts under the key the `psk` token has already established and MixHashes the ciphertext. The position difference does not change a derived byte, because `MixHash` and `MixKey` touch disjoint state (below); the plaintext-for-ciphertext difference does, and is one of the divergences listed under **Test vectors and interoperability**. It is MixHash only -- the flag need not be confidential and enters `h` alone, so the chaining key (and the confirmation key derived from it) stays flag-independent while `h`, the session key, and both confirmation tags depend on both flags. See the **Request-encryption flag** discussion below.

In a PSK handshake, Noise (rev 34 section 9.2) processes each `e` token with `MixKey(e.public)` in addition to `MixHash(e.public)`, folding the ephemeral public keys into the chaining key as well as the hash; this implementation does both, so the mix chain is faithful NNpsk0. (`MixHash` touches only `h` and `MixKey` only `ck`, so their order within an `e` token does not affect the result, and the flag MixHashes likewise commute with the surrounding MixKey calls; the chaining-key order `psk -> e_initiator -> e_responder -> ee` and the hash order `e_initiator -> initiator_flag -> e_responder -> responder_flag` are what matter, and are preserved.) Here `MixHash(x)` sets `h = SHA-256(h || x)`; `MixKey(ikm)` sets `ck = HKDF-Noise(ck, ikm, 2)[0]`; and `MixKeyAndHash(ikm)` sets `(ck, temp_h) = HKDF-Noise(ck, ikm, 3)[0..1]` then `MixHash(temp_h)`. `HKDF-Noise(ck, ikm, n)` is the Noise chaining HKDF (Noise rev 34 section 4.3): `temp_key = HMAC(ck, ikm)`, then `output_i = HMAC(temp_key, output_{i-1} || byte(i))` for `i` in `1..n` (with `output_0` empty). This equals RFC 5869 HKDF with `salt = ck` and an empty info string, and is issued as exactly that: one `crypto.subtle` HKDF `deriveBits` call for `n * 32` bytes, split into the `n` blocks. The equality is what makes the two forms interchangeable, and the vector generator writes out the HMAC chain while the implementation issues the single call, so the two are checked against each other on every run.

After the tokens, the session key and a distinct confirmation key are derived, and the two confirmation tags computed, using the application HKDF (`hkdfDerive`: HKDF-SHA-256, 32-byte zero salt, named info):

```
session_key       = HKDF(ck || h, "alcove-kex-v2:session", 32)
confirm_key        = HKDF(ck,      "alcove-kex-v2:confirm", 32)
initiator_confirm  = HMAC(confirm_key, "alcove-kex-v2:initiator-confirm" || h || used_previous_byte || wrapped_N_I)
responder_confirm  = HMAC(confirm_key, "alcove-kex-v2:responder-confirm" || h || schedule_byte)
```

`wrapped_N_I` is the initiator's 40-byte wrapped rotation value ([Shared-secret rotation](SHARED_SECRET_ROTATION.md)), so a changed byte of it fails the initiator's tag. It is bound as the tag's MAC input only and is not mixed into `h`: its wrapping key derives from `session_key`, which derives from `h`. `used_previous_byte` is `0x01` if the initiator completed under its previous secret and `0x00` otherwise (**Which secret a handshake uses**, below), so a changed flag fails the initiator's tag too. The responder computes the expected initiator tag once it has read message 3. `schedule_byte` names the message 2 field a responder tag is sent in: `0x00` for `confirm`, the tag under the responder's current secret, and `0x01` for `previousConfirm`, the tag under its second schedule. So a tag moved to the other field does not verify.

Deriving `session_key` over both `ck` (which holds the pre-shared secret, both ephemeral public keys, and the key-agreement derivation's `k_ee`) and `h` (which holds the protocol-version tag, the prologue holding both hellos, the value `temp_h` that `MixKeyAndHash(psk)` derives from the pre-shared secret, both ephemeral public keys in role order each followed by its request-encryption flag) is the critical invariant. The session key depends on the ephemeral DH output, so it is neither the pre-shared secret alone -- which would have no forward secrecy -- nor the raw ECDH output alone, which would not be transcript-bound. The confirmation key is independent (distinct input keying material and a distinct label), and the two confirmation tags are role-asymmetric (distinct labels) and each binds the full transcript hash `h`. All labels here are namespaced `alcove-kex-v2:`. **The domain-separation label space.** The system's derivation labels form one disjoint space, enumerated here and cited from the sections that use each family: `alcove-kex-v2:*` (the key-agreement, session and confirmation derivations above), `alcove-aead-v2:*` (the application-layer AEAD), `alcove-shared-secret-wrap-v2`, `alcove-shared-secret-wrap-responder-v2` and `alcove-shared-secret-next-v2` (the rotation, in [SHARED_SECRET_ROTATION.md](SHARED_SECRET_ROTATION.md)), `alcove-rotation-history-v2:*` (the history verifier, proofs and behind notices, in [SHARED_SECRET_ROTATION.md](SHARED_SECRET_ROTATION.md#the-rotation-history)), `alcove-abort-token-v2:*` (the file-sync abort marker), `alcove-webrtc-peerid-v2:*` (the rendezvous peer ids below), `alcove-relay-key-v2` (the relay key, in [RELAY_CREDENTIALS.md](RELAY_CREDENTIALS.md#relay-credential-derivation)), `alcove-relay-exchange-id-v2` (the exchange id a relay key is enrolled under without a token, in [RELAY_CREDENTIALS.md](RELAY_CREDENTIALS.md#relay-credential-derivation)), `alcove-relay-registrar-v2:*` (the registrar request proof, in [RELAY_CREDENTIALS.md](RELAY_CREDENTIALS.md#the-registrar-request-proof), derived from the relay key), `alcove-relay-websocket-v2:*` (the WebSocket relay proof, in [RELAY_CREDENTIALS.md](RELAY_CREDENTIALS.md#the-websocket-relay-proof), derived from the relay key), the `alcove-signing-cert-*` domains (the certificate signature and fingerprint, in [PROTOCOL.md](PROTOCOL.md#signing-identity-and-certificate-pinning)), the `alcove-signed-receipt-*` labels (the receipt-content domain, and the receipt payload-MAC and binder derivations, which take the same session key as their input keying material, in [PROTOCOL.md](PROTOCOL.md#the-signed-receipt-step)), and `alcove-terms-update-v2:*` (the terms update's partnership identifier and MAC key, derived from the shared secret; see [EXCHANGE_FILE.md](EXCHANGE_FILE.md#terms-update)). No derivation under one family can collide with one under another.

Disjointness here means exact-string-distinct **and prefix-free** for every label consumed as an HKDF `info` string, because that string is not length-prefixed: a label that is a prefix of another is not separated from it by the derivation. One member, `alcove-kex-v2:key-agreement`, heads the key-agreement derivation's FixedInfo rather than being the whole `info` string; a FixedInfo that starts with a prefix-free member is prefix-free against every other member the same way. Three members travel instead as a field of a canonicalized JSON object, where the structure separates them: the certificate signature and fingerprint domains and the receipt-content domain. Each is a single fixed string and prefix-free among the rest all the same. No single label or family prefix -- a suffix-taking family's name through its `:` separator -- is a prefix of another (`alcove-relay-key-v2`, `alcove-relay-exchange-id-v2`, `alcove-relay-registrar-v2:` and `alcove-relay-websocket-v2:` share `alcove-relay-` and diverge after it; `alcove-shared-secret-wrap-v2`, `alcove-shared-secret-wrap-responder-v2` and `alcove-shared-secret-next-v2` share `alcove-shared-secret-` and diverge after it, the two wrap labels after `alcove-shared-secret-wrap-`), and a family that takes a suffix (`alcove-aead-v2:<context>`, `alcove-abort-token-v2:<role>`, `alcove-webrtc-peerid-v2:<role>`, `alcove-relay-registrar-v2:<use>` for `proof-key` and `request`, `alcove-relay-websocket-v2:<use>` for `proof-key` and `hello`, `alcove-rotation-history-v2:<use>` for `verifier`, `proof-initiator`, `proof-responder`, `notice-initiator` and `notice-responder`, `alcove-signed-receipt-payload-v2:<direction>`, `alcove-signed-receipt-binder-v2:<role>`, `alcove-terms-update-v2:<use>`) draws it from a fixed, non-empty, colon-free and prefix-free set behind that separator, so no member of one family is a prefix of a member of another or of its own family. `packages/core/test/labelSpace.test.ts` checks both properties, and that every `alcove-` string in core's source is an enumerated member or listed outside the space. Adding a label, or widening one of those suffix sets, is a change made against these properties.

**Message flow** (initiator sends first; all messages are JSON objects; `hello` is a base64url-encoded hello (**The version hello**, above); `e` is a base64url-encoded 65-byte uncompressed P-256 point, 87 base64url characters unpadded, keyed in message 1 by suite id; `confirm` is a base64url-encoded 32-byte HMAC-SHA-256 tag, 43 characters; `reqEnc` is the party's request-encryption boolean; `initiatorValue` is the base64url-encoded 40-byte `wrapped_N_I`, 54 characters; `previousConfirm`, `historyProof` and a behind notice's `tag` are base64url-encoded 32-byte HMAC-SHA-256 values, 43 characters; and `usedPrevious` is a boolean):

1. Initiator -> Responder: `{ kexMsg: "1", hello: hello_I, e: { "3": e_I }, reqEnc: req_I }`
2. Responder -> Initiator: `{ kexMsg: "2", hello: hello_R, e: e_R, confirm: responder_confirm, previousConfirm: responder_confirm', historyProof: proof_R, reqEnc: req_R }`, or `{ kexMsg: "abort", hello: hello_R }` where the hellos share no version
3. Initiator -> Responder: `{ kexMsg: "3", confirm: initiator_confirm, initiatorValue: wrapped_N_I, usedPrevious: used_previous }` or `{ kexMsg: "abort", historyProof?: proof_I, behindNotice?: { count, tag } }`

`responder_confirm'` is the responder's tag under its second schedule, and `proof_R` and `proof_I` are history proofs ([The rotation history](SHARED_SECRET_ROTATION.md#the-rotation-history)). The responder confirms first (in msg2); the initiator verifies `responder_confirm` before sending its own confirmation in msg3, and the responder verifies `initiator_confirm` on msg3, then unwraps `wrapped_N_I`. The initiator draws and wraps its rotation value only once `responder_confirm` has verified, so it sends no keying material before key confirmation; the abort form has no `initiatorValue`. A mismatched pre-shared secret therefore fails closed on both sides before any non-handshake frame is sent. Each side sends the tag for its own role and verifies the tag for the opposite role, so a reflected or echoed confirmation does not verify.

**Which secret a handshake uses.** A party holds its current secret and, after a run cut before its partner stored the next secret, a previous one ([The previous secret](SHARED_SECRET_ROTATION.md#the-previous-secret)). Each side runs the key schedule twice on every handshake: under its current secret, and under its previous secret or, when it holds none, under a 32-byte value drawn for that handshake and then discarded. So the work and message 2's shape do not depend on whether a previous secret is held.

- **The responder** sends both schedules' responder tags in message 2, current first, as `confirm` and `previousConfirm`.
- **The initiator** compares each of its schedules' expected responder tags against both received tags, the tag expected at each field made with that field's `schedule_byte`, all four comparisons made in constant time whatever matches. It completes under the first match in the order: its current secret against `confirm`, then against `previousConfirm`, then its previous secret against `confirm`, then against `previousConfirm`. Its drawn stand-in value is never chosen. It sends `used_previous` true when it completed under its previous secret, bound under its tag.
- **The responder** computes the expected initiator tag under both of its schedules with message 3's flag and wrapped value, and compares both whatever matches. It completes under its current schedule where that tag verifies, and otherwise under its previous one, only where it holds a previous secret. It unwraps `wrapped_N_I` under the session key of the schedule it completed under, and wraps `N_R` under the same one.

Each side so learns which secret each side used: the initiator from which of its schedules matched and in which field, which `schedule_byte` binds under the responder's tag, the responder from its own matching schedule and the flag. A message 2 whose two tags are swapped in transit matches in neither field and fails with the generic error. `authenticateConnection` returns both (`AuthResult.secretUsed`). A tag under a secret the other side does not hold verifies nothing, so a party with neither secret learns nothing from either tag. A previous secret whose `expires` has passed, or that equals the current secret, is not offered: that side runs the drawn value in its place.

**When no secret matches.** Where no tag verifies on the initiator, it sends an abort holding its history proof, and a behind notice where the responder's proof matched its history. A responder answers every abort holding a proof with an abort of its own, holding a behind notice where the initiator's proof matched its history; it does not answer an abort with no proof. Each side then fails:

- A side whose history matched the peer's proof at position `k` fails with `PartnerCopyBehindError` (`packages/core/src/errors.ts`), which states that the other side connected with a copy no more than `k` rotations behind and gives the confirm-with-your-partner and compromise steps. The initiator sends its abort and fails at once.
- Otherwise, a side that reads a behind notice that verifies under its own current secret's verifier fails with `LocalCopyBehindError`, which states that this copy is older than the other side's and does not repeat the count. The initiator waits for the responder's reply within the per-message bound below; a reply that is missing, malformed or holds no notice that verifies leaves the generic failure.
- Any other case is the generic failure.

Both errors are `AuthenticationError`s, so every consumer that classifies a failed key exchange classifies these the same way.

**Request-encryption flag.** Each party declares, on its own handshake message (`req_I` on msg1, `req_R` on msg2), whether it wants an additional application-encryption layer over the post-handshake connection. The flag is a required field on the strict message schemas. Both parties therefore hold both flags before the key schedule runs, so both compute the same negotiated decision `apply_encryption = req_I OR req_R` and bind both flags into the transcript hash `h` (as the per-message handshake payload, above) with no extra message or round-trip. Because `h` feeds both confirmation tags, a flag flipped on the wire makes the two sides derive different transcripts and the confirmation fails closed: the handshake cannot be downgraded to an encryption decision the parties did not agree on. The negotiation is a single fixed-meaning boolean, not an extensible options block -- open-ended in-handshake negotiation is the historical home of downgrade bugs. `runKex` returns `apply_encryption` as `KexResult.applyEncryption`; the caller applies the AEAD layer (see [SECURITY_DESIGN.md](../SECURITY_DESIGN.md#channel-security)) when it is true and a session key is in hand. Every channel requests it unconditionally: the file-sync transports (SFTP, file-drop) and WebRTC alike ([CHANNEL_SECURITY.md](CHANNEL_SECURITY.md#which-channels-request-it)).

**Peer-share validation.** A peer's `e` is validated in two layers before it reaches the Diffie-Hellman, and the split between them is deliberate:

1. **Encoding, in application code.** The decoded share must be exactly 65 bytes with the `0x04` prefix (see **Curve and point encoding** above). Anything else is rejected without being decoded.
2. **Point validity, by the platform.** The share is then imported through `crypto.subtle.importKey`, which rejects a point that is not on the curve, a coordinate at or above the field prime, and both byte strings a peer might send for the identity element. Those two strings are SEC 1's single `0x00` octet, which is the only encoding it gives the point at infinity (section 2.3.3 step 1), and the all-zero uncompressed string `0x04 || 0^32 || 0^32`, which SEC 1 section 2.3.4 reads not as the identity but as the point `(0, 0)`, off the curve. Driving the real API is what establishes this, on each platform, rather than assuming it; `packages/core/test/kex.test.ts` and the browser suite each make the measurement on their own platform.

P-256 has cofactor 1, so there is no small-order subgroup for a share to land in and the point at infinity is the whole of the degenerate case -- the contributory-check rationale behind the X25519 construction does not transfer. [RFC 7748](https://www.rfc-editor.org/rfc/rfc7748) section 7 states that rationale for the curves that document defines and rests it on their cofactors of 8 and 4, which let an input point of small order eliminate the other party's contribution. The all-zero check it points at (Section 6, whose detection prose sits in 6.1 with 6.2 cross-referencing it) is the detection for exactly that case, and neither the cofactor assumption nor the check it motivates applies to a cofactor-1 curve. An all-zeros shared secret is nonetheless still rejected, as a stated safety check rather than as the validation: the platform's rejection of the identity is a measured behavior rather than one this project controls, and a platform that admitted such a share would otherwise yield a shared secret an attacker knows, costing the handshake its forward secrecy silently. The shared secret is never read as bytes, so the check runs on the key-agreement derivation's output: the three blocks are compared, in constant time, against the same derivation over a 32-byte zero `Z` with the same FixedInfo, and a match fails the handshake with the generic failure and an abort before either side sends a tag.

**Failure handling.** All wire schemas use strict (`.strict()`) Zod parsing, so an unexpected field fails the parse; the hello a message carries is the one place an unknown member is accepted, and ignored (**The version hello**, above). Tag comparison is constant-time. Every authentication failure throws a single generic, non-oracular error (`"key exchange authentication failed"`) that does not reveal which check failed -- a malformed share, a rejected point, and a confirmation mismatch are indistinguishable to the peer -- while the error's `security` kind, not its message, carries the trust-boundary classification a consumer branches on. The two exceptions are the older-copy failures (**When no secret matches**, above), each shown only on a proof or notice that only a holder of this partnership's secrets can make. The no-common-version refusal is not an authentication failure: it is decided from the hellos alone, before the key schedule runs. A silent peer reports the distinct `"key exchange handshake timed out"` after a per-message bound of 30 s plus two of the transport's inbound poll intervals; any other failure of a handshake receive -- a transport refusal, a dropped link -- is reported as itself, its own class and message, so it is never mistaken for the peer going silent. The poll intervals apply only to a transport that polls for inbound frames (file-sync, through `MessageConnection.inboundPollIntervalMs`): a reply there reaches the waiting party up to one interval after each of the two writes in the round trip. WebRTC pushes frames, so its bound is 30 s. The connection's own inactivity budget (`inactivity_timeout_ms`) still caps each wait. Every receive-side failure before the final message sends a best-effort `{ kexMsg: "abort" }` so the peer stops waiting immediately rather than blocking until the timeout; the initiator's abort when no responder tag verifies also holds its history proof. The one exception is the no-common-version refusal an initiator reads from the responder's abort: that responder has already stopped, so the initiator sends nothing back.

**A failure of message 3.** A message 3 that fails the parse, whose tag does not verify, or whose `wrapped_N_I` fails its AES-KW integrity check fails the responder with the same generic error, and the responder sends the abort; a message 3 that is itself an abort with no history proof is not answered, and one holding a proof is answered as **When no secret matches** above states. The unwrap is a consistency check rather than a second defense: the tag already covers the wrapped bytes, so only a holder of the pre-shared secret that wrapped under another key reaches it. By then the initiator has completed, wrapped the connection in the application-layer AEAD, and sent terms message 1, and it waits for terms message 2 under the connection's inactivity budget rather than the per-message bound. The cleartext abort is not an AEAD envelope, so the initiator fails at once with a `security` failure. On `sftp` and `filedrop` the file-sync transport refuses the abort before parsing it and consumes it ([FILE_SYNC.md](FILE_SYNC.md#file-taxonomy), "JSON messages on an encrypted channel"); on other transports the AEAD layer refuses it ([CHANNEL_SECURITY.md](CHANNEL_SECURITY.md#application-layer-aead)).

Non-oracular covers the absence of a secret-dependent branch as well as the message: the only comparisons against secret-derived material are the constant-time tag and history checks, every one made whatever matches, and the key schedule runs identically whatever the pre-shared secret's value. Both schedules run on every handshake, the responder computes its history proof on every handshake, and each side checks a peer's proof against every history entry it checks, so the work does not depend on whether a previous secret is held or which entry matched. The history check's work does grow with the number of entries checked, at most 64, which a peer can time; that count is at most the partnership's number of rotations, which the shared folder's operator or the coordination server can already observe from the run cadence. What a peer can still distinguish by wall-clock timing is a failure before the key schedule (a bad parse or a rejected share) from one after it (a tag mismatch). That split is a function of the peer's own input, which on the adversarial path the adversary authored, and not of any secret, so it discloses nothing the peer did not already know.

**What a transport operator reads.** On `sftp` and `filedrop` the server's or shared folder's operator reads the handshake frames in the clear: message 3's `usedPrevious`, and whether an abort holds a behind notice and its count. So the operator sees when a run healed a cut rotation, or when a copy a few rotations old connected, metadata of the kind the run cadence it already sees gives.

**Test vectors and interoperability.** The chaining-key chain above -- `psk`, then each `e`, then `ee` -- is Noise NNpsk0 apart from the `ee` input, but the overall handshake is pinned by Alcove's own checked-in known-answer vector (`packages/core/test/vectors/kex-vectors.json`) rather than being wire-compatible with generic Noise. Six things diverge from a stock Noise NNpsk0 session. The Diffie-Hellman is over P-256, which the framework's section 12 does not specify. The prologue holds the responder's hello, which reaches the initiator only in message 2, where Noise fixes the prologue before the first message; that is sound here because neither side derives a key or a tag before it holds message 2. The `ee` token mixes the first block of the key-agreement derivation, not the Diffie-Hellman output. The protocol name differs, so the initial `h` differs. Each message's payload is a flag byte MixHash'd in the clear where Noise would `EncryptAndHash` it. And instead of Noise `Split()` the session key uses a custom KDF over `ck || h` with an added explicit confirmation round. So no end-to-end Noise vector corresponds. What does correspond is the underlying machinery, cross-checked against published references in `packages/core/test/kex.test.ts`: the Noise chaining HKDF against [RFC 5869](https://www.rfc-editor.org/rfc/rfc5869) test case 3, and the P-256 scalar multiplication and ECDH against the key pair published in [RFC 6979](https://www.rfc-editor.org/rfc/rfc6979) section A.2.5 over the base point [SP 800-186](https://doi.org/10.6028/NIST.SP.800-186) publishes. There `ECDH(d, G)` and `ECDH(1, U)` must both produce the published `U` X coordinate, so a wrong curve, a wrong base point, or a wrong shared-secret convention breaks the anchor. The vectors fix the pre-shared secret, both ephemeral private keys and both hellos, the responder's holding a member this build does not know, and record the prologue they make and, for all four `(initiator, responder)` request-encryption flag combinations, the handshake hash, session key, and both confirmation tags (the chaining key and confirmation key are flag-independent and recorded once). They also fix both parties' rotation values and record, per combination, each wrapped value, and once the next secret derived from them and the vector's `ka` ([Shared-secret rotation](SHARED_SECRET_ROTATION.md)). They fix a previous secret and record, per combination, the schedule under it, the responder's tag with `schedule_byte` set and the initiator's tag with `used_previous_byte` set, and once both secrets' history verifiers, each role's history proof under the current secret's verifier, and each role's behind notice under the previous secret's verifier ([The rotation history](SHARED_SECRET_ROTATION.md#the-rotation-history)). They record the key-agreement derivation's FixedInfo and its three blocks beside `Z`, which the generator computes with `node:crypto`'s `hkdfSync` over `Z` as bytes and the module reproduces from the recorded private keys through `deriveKey`. They are reproduced by the independent generator at `packages/core/test/vectors/generate-kex-vectors.mjs`, which composes the schedule from Node's OpenSSL-backed `crypto` rather than from WebCrypto, computing each wrap with OpenSSL's `id-aes256-wrap`, checked against [RFC 3394](https://www.rfc-editor.org/rfc/rfc3394) section 4.6, and the next secret with `node:crypto`'s HKDF. The same file is run against the browser build in real Chromium by `apps/web/test/browser/kex.test.ts`, so a CLI peer and a web peer are shown to derive an identical session from an identical transcript.

## WebRTC rendezvous peer-id derivation

The WebRTC transport meets its peer with no coordination backend: both parties derive their PeerJS rendezvous peer ids deterministically from the invitation's 32-byte shared secret, so each side computes the other's id locally and they rendezvous on the PeerJS signaling broker without exchanging an id out of band. This precedes and is independent of the P-256 handshake above -- it places the two parties on the same WebRTC connection, over which the handshake then runs.

The derivation is HKDF-SHA-256 over the decoded 32-byte shared secret as input keying material, with a 32-byte zero salt (matching the application `hkdfDerive` above) and a role-separated info string:

```
inviter_info  = "alcove-webrtc-peerid-v2:inviter"
acceptor_info = "alcove-webrtc-peerid-v2:acceptor"
peer_id       = hex(HKDF-SHA-256(ikm = secret, salt = 0x00 * 32, info = role_info, 32)[0..15])
```

The peer id is the first 16 bytes of the HKDF output, encoded as lowercase hex. Hex (not base64url) is used because the PeerJS client rejects an id with a leading, trailing, or doubled `-` or `_`, which base64url output can contain. The inviter listens on its derived id (`inviter_info`) and the acceptor dials it.

The ids change only when the shared secret does. The terms exchange that follows a successful handshake rotates the secret once the terms are agreed on (see [Shared-secret rotation](SHARED_SECRET_ROTATION.md)) and so moves both ids, while a scheduled window the partner does not meet leaves them unchanged, and every later attempt registers the same ids at the coordination server until a run rotates the secret or the exchange is re-invited. The server can read the partnership's liveness and cadence from that repetition, never its content. The derivation takes no window or clock input, so two parties holding the same secret derive the same ids without agreeing on anything else; the operator's account of a missed window is in [A missed window is neither desync nor attack](../MANAGED_EXCHANGE.md#a-missed-window-is-neither-desync-nor-attack).

**While the acceptor holds a previous secret.** A run cut between the two saves of a rotation leaves the acceptor, the initiator over WebRTC ([WEBRTC_TRANSPORT.md](WEBRTC_TRANSPORT.md#roles)), on the next secret with the one before it kept as its previous secret, and the inviter on the one before it, so the two derive different ids. A CLI acceptor whose key file, or a browser acceptor whose saved record, holds a previous secret that has not expired waits under both secrets at once (`openWebRtcPeerSession` in `apps/cli/src/connection/webrtc/weriftPeer.ts`, `beginManagedRendezvous` in `apps/web/src/psi/managed/managedRendezvous.ts`):

- **Two registrations.** Each attempt registers under the acceptor id of each secret and offers to the inviter id of the same secret, since an inviter takes an offer only from the acceptor id its own secret derives. The first data channel to open carries the run, and the other registration and its peer connection are closed. A wait that meets no partner under one secret ends when the other's does; any other failure ends both.
- **Only then.** An acceptor holding no previous secret, one whose previous secret has expired or equals its current one, and every inviter register under the current secret's ids alone. Every acceptor run registers, enrolls and dials under the previous secret while its key file or record holds one it would offer, until a run stores the next secret or the confirmation write drops it ([The previous secret](SHARED_SECRET_ROTATION.md#the-previous-secret)). A run that never meets its partner writes nothing, and a failed confirmation write leaves the previous secret in place ([EXCHANGE_FILE.md](EXCHANGE_FILE.md#the-previous-secret-and-the-rotation-history), [MANAGED_EXCHANGE_RECORD.md](MANAGED_EXCHANGE_RECORD.md#persisted-across-runs)). The previous secret's `expires`, where its key file or record holds one, bounds how long that lasts. Stated limit: a previous secret with no `expires` has no time bound, so an acceptor whose partner never returns registers, enrolls and dials under it on every run until the exchange is re-invited.
- **Expiry during the wait.** Stated limit: the run decides before its first attempt whether the previous secret has expired, by the rule the handshake offers it by (`offerablePrevious` in `packages/core/src/auth.ts`), and the handshake decides again, so a previous secret that expires while the run waits still meets an inviter left on it, and that run fails authentication rather than reporting a partner who never arrived.
- **The relays.** The same run enrolls the key and derived exchange id of both secrets at the registrar its invitation names, a browser run at the build's default relay where it uses that relay's WebSocket relay url, and dials each WebSocket relay it lists under the derived id under the id and key of both secrets. A relay under an id the connection or the invitation names is dialed under the current key alone ([Enrolling at a default relay](RELAY_CREDENTIALS.md#enrolling-at-a-default-relay)). Both dials of a browser run mint the TURN credential from the current secret, so the browser lists the default relay's TURN url only where the current secret's enrollment confirmed, and its WebSocket relay url under each secret whose enrollment confirmed. Each enrollment's failure detail is redacted of the exchange ids and relay keys of both of the run's requests ([A command-line party](RELAY_CREDENTIALS.md#enrolling-at-a-default-relay)), so a value a registrar received in the other request, such as the other secret's relay key, is replaced by its marker in the warning the run logs, as the request's own values are.
- **Who can link the two rotations.** Three parties see one host use both secrets at once, whether that host runs the command line or the browser. The coordination server sees one party registering under two acceptor ids and offering to two inviter ids in the same attempts. The registrar the invitation names, or the browser's default relay, receives both secrets' exchange ids and relay keys in two enrollments sent at the same time. Each WebSocket relay dialed under the derived id receives two hellos from one host under two exchange ids. Each of them can link two rotations of the partnership, on every run that registers under both secrets.

The one-off browser exchange keeps no previous secret, so it registers under one pair of ids. A CLI inviter cannot tell an acceptor that keeps a previous secret from one that keeps none, so where its own save fails after its acceptor saved, it exits 77 and names a new invitation, unless the acceptor completed that key exchange under its previous secret, which shows that it keeps one ([CLI_EVENTS.md](CLI_EVENTS.md#the-security-marker)). A browser inviter whose own save fails after its acceptor saved decides the same way: it names the next run as the step only where the acceptor completed that key exchange under its previous secret, and a fresh invitation otherwise (`classifyManagedRunFailure` in `apps/web/src/recurring/managedRunLaunchModel.ts`).

This is a cross-implementation contract: both implementations compute the same ids from the same shared secret, which is what lets a CLI party and a browser party rendezvous with each other (see [`cli-webrtc-stack.md`](../notes/cli-webrtc-stack.md)). On the CLI the role half of the derivation comes from the connection's `role` field, stamped by `alcove invite` and `alcove accept`; the browser takes it from which rendezvous function runs. The `alcove-webrtc-peerid-v2:` labels sit in the disjoint [domain-separation label space](#p-256-authenticated-key-exchange) above.

**Conformance vectors.** The contract is pinned by a checked-in known-answer vector at [`packages/core/test/vectors/webrtc-interop-vectors.json`](../../packages/core/test/vectors/webrtc-interop-vectors.json), on the precedent of `kex-vectors.json` above. It fixes one shared secret and records both derived ids, the encoded invitation a browser inviter mints from it (the whole base64url string, plus the canonical JSON body the checksum covers), and the signaling locator that invitation holds. It also records the locators a CLI inviter mints from a `ws:`/`wss:` URL together with the broker location both applications must resolve each of them to, and each side's pairing of rendezvous role to key-exchange handshake role and request-encryption flag. Both mint directions are recorded because each application resolves an absent locator field to a default of its own (see [WEBRTC_TRANSPORT.md](WEBRTC_TRANSPORT.md#broker-socket)), so a locator is a contract only where what it omits is pinned as well as what it states. `generate-webrtc-interop-vectors.mjs` beside it reproduces the derivations from Node's OpenSSL-backed `crypto` rather than from WebCrypto, and restates the invitation body's key order literally rather than reading it off the schema. The divergence this guards against lives in each application's own call sites rather than in the shared library. So every application asserts its own construction against the file from its own suite -- the ids it registers and addresses, the token it consumes, the role and flag it hands the handshake -- rather than one test computing both sides through a single path. Each flow that reads the side-to-role table is driven through its own entry point rather than through the table. The derivations that run on `crypto.subtle` -- the peer ids and the invitation checksum -- are additionally run against the browser build in real Chromium by `apps/web/test/browser/webrtcInterop.test.ts`, as `kex-vectors.json` is, since which bytes a platform produces is a property of that platform.
