# Upgrading the SFTP Stack (ssh2 / ssh2-sftp-client)

This document records the internal assumptions the CLI's SFTP adapter makes about `ssh2` and `ssh2-sftp-client`, the dependency source files to re-read, and the checks that re-verify them, so a version bump of either package is verified before it merges.
It does not cover how the other pinned stacks and the install-time policies are upgraded (see [DEPENDENCY_PINS.md](DEPENDENCY_PINS.md)), the controls the adapter implements on top of these assumptions (see [CHANNEL_SECURITY.md](CHANNEL_SECURITY.md), [TRANSPORT_BOUNDS.md](TRANSPORT_BOUNDS.md), [TRANSPORT_LIVENESS.md](TRANSPORT_LIVENESS.md), [SFTP_CONNECTION.md](SFTP_CONNECTION.md) and [SFTP_SESSION_RECOVERY.md](SFTP_SESSION_RECOVERY.md)), or the dependency-review requirement (see [CONTRIBUTING.md](../../CONTRIBUTING.md#dependency-policy)).
Intended readers are maintainers upgrading a pinned dependency, security auditors, and developers.

The channel-security bounds those documents specify reach past the public `ssh2-sftp-client` API and drive ssh2 internals directly (`apps/cli/src/connection/ssh2SftpAdapter.ts`), so they rest on assumptions about ssh2's internal behavior that an upgrade can silently break. Re-verify the following on any `ssh2` or `ssh2-sftp-client` version bump, before the bump merges.

**Which of these assumptions a check holds, and which stay prose.** An assumption
earns a check when a run can assert it at the layer it is stated and the failure
names the assumption that moved; otherwise it stays re-verify-on-upgrade prose,
which at least fires at the one moment it matters. Importance does not decide it
-- everything in this document is critical or it would not be here -- and
neither does cost alone. What decides it is whether the assumption is separable from
the adapter behavior built on it: a break that an adapter-level test can only
report as an opaque timeout leaves a bumper reading this document anyway, so
pinning it where it is stated is what the check buys.
`apps/cli/test/integration/sftpStackPremises.test.ts` is where an assumption that
separates that way is driven -- the raw `ssh2-sftp-client`, not the adapter,
against the in-process test server -- and each assumption it holds is named where
that assumption is stated below, the way the dial-deferral assumption already names its
own check. Three classes stay prose:

- An assumption about where in a dependency's source something happens rather than
  what it does -- an assignment's guard, a listener's bracketing, a constant's
  provenance. A run observes the behavior, not the shape of the code producing
  it; those are re-read from the source-file list below.
- A shape the in-process backend cannot produce: everything that would need a
  native `sshd`, and the one late-answer shape recorded with the captured wrapper
  below.
- An assumption whose only observable is an adapter behavior a suite already drives
  end to end, where a raw-layer check restates a covered outcome rather than
  separating a cause.

Which class an assumption falls in is decided at the assumption, not here: a bullet that
names its check, or gives its reason for having none, has been through this;
where a bullet does neither, this document's re-verify instruction is what stands.

## The internal assumptions the adapter relies on

### Wrapper listeners and numeric constants

- ssh2's `Client.sftp()` strips its own setup-time `'error'` listener (and the `'exit'`/`'close'` ones) from the `SFTPWrapper` before handing it back, so after a real connect the wrapper has zero `'error'` listeners until the adapter attaches its own. The whole crash fix is sound only while this holds; if ssh2 retains its listener the adapter's "no one else guards the wrapper" reasoning is false.
- ssh2 reports end-of-directory from the handle-based `readdir` as an `Error` whose `code` equals `STATUS_CODE.EOF` (numeric `1`), not as an empty success batch -- the EOF contract `list()`'s batch loop terminates on. Each call answers one server batch, and a call that errs passes no list; all three are driven in `apps/cli/test/integration/sftpStackPremises.test.ts`.
- `STATUS_CODE.EOF === 1` and `OPEN_MODE.WRITE | CREAT | EXCL === 0x2A`, the numeric SFTP constants the adapter hard-codes (it does not import them: ssh2 exposes their runtime values only from the internal `lib/protocol/SFTP.js`, not from its package entry point, and `@types/ssh2` types them only as a compile-time `sftp` namespace). These are fixed SFTPv3 wire-protocol values, so they are extremely unlikely to renumber, but confirm them against `STATUS_CODE`/`OPEN_MODE` in the source below if the surrounding code moves.
- `STATUS_CODE.FAILURE === 4` (`SSH_FX_FAILURE`), the third numeric SFTP constant the adapter hard-codes: `rename()` retries a transient server failure only on this status (the source still exists, so a re-issue is safe) and treats every other status as terminal, and `createExclusive` maps it to an `exists()`-disambiguated `EEXIST`. The assumption is that ssh2-sftp-client reports a server `FAILURE` on its high-level `rename` as numeric `err.code === 4` -- it passes ssh2's raw status through `fmtError` onto `err.code`, the same `4` `createExclusive` reads from the raw `open` callback. If a future version remaps `rename`'s `err.code` to a non-numeric string (e.g. `ERR_GENERIC_CLIENT`) or renumbers `FAILURE`, the retry silently stops firing -- the transient-rename flake returns, with no correctness break; the `ssh2SftpAdapter` unit tests pin the numeric-`4` behavior.

### Session release and close

- ssh2-sftp-client stores the raw wrapper on `this.sftp`, assigned in its `'ready'` handler on each `connect()` and otherwise only cleared -- the library performs no auto-reconnect of its own. Two adapter behaviors rest on this. (1) The captured-wrapper reads in `list()`/`createExclusive()` (`const { sftp } = ...` at method entry) assume nothing swaps `this.sftp` under an in-flight operation, and issuance order is not what holds that up -- the adapter issues operations concurrently (see [SFTP_SESSION_RECOVERY.md](SFTP_SESSION_RECOVERY.md#operations-concurrent-with-a-re-dial-or-a-release)). The library's assignment discipline is: `this.sftp` is assigned only from a `connect()` whose "already connected" guard passed, so every assignment is preceded by a clear, and only events implying the old transport has ended clear it. Driven against a real ssh2 server, no run reassigned the property while a `list()`/`createExclusive()` capture was live, identically with `ephemeralSessions` true and false. On the mid-exchange recovery path against a partner withholding its connection close, the forced close fails the captured wrapper's outstanding requests 210-221 ms before the fresh wrapper is assigned, across six samples, all the same sign, and the re-issue then captures the fresh wrapper. A capture that did go stale would be inert rather than misrouted: a request issued on a superseded `SFTPWrapper` neither transmits nor calls back (`staleWrapper.realpath(".", cb)` produces no callback at 1500 ms, while the fresh wrapper answers the identical call in single-digit milliseconds). And the fresh session is a different ssh2 channel on a different socket, so it cannot answer that request either. The holding operation would ride its own per-operation deadline rather than read another session's reply. That inertness is the security-bearing half of this bullet -- it is what makes a stale capture a deadline rather than a cross-session misroute -- so it is a check rather than prose: `apps/cli/test/integration/sftpStackPremises.test.ts` captures a wrapper, drops the session server-side, re-dials, and holds the superseded wrapper silent while the fresh one answers. The assignment discipline itself stays prose and is re-read from the source on a bump -- it is a claim about which guard an assignment sits behind, not about an observable outcome, and a version that reassigned the property under a live transport would put a stale capture under a live operation with nothing to see until it did. One shape is left unmeasured by design, rather than pending: `listOnce`'s late-`opendir` branch issues `sftp.close(openedHandle)` on the capture after the listing has settled, the one place a superseded wrapper could still be issued against, and reaching it needs a backend that answers a request late where this one can only withhold a response forever. What that branch stands to lose is bounded by the inertness above -- the listing has already settled, so the close is best-effort cleanup and its worst case is a handle held until session teardown -- which is why the boundary is not built for it. Nor was any of this driven against a native `sshd`. (2) Recovery re-dials by calling `connect()` again and does not call the library's `end()` first. That rests on ssh2-sftp-client clearing `this.sftp` on a clean drop, on the forced close below clearing it where a drop did not (so `connect()`'s "already connected" guard cannot fire either way), and on `end()` latching a permanent `endCalled` flag that disables the global `'close'` listener's `this.sftp` clear. That is why calling it would break detection of a later idle drop. If a future version stopped clearing `this.sftp` on a clean close/end, or reset `endCalled` on `connect()`, re-verify the recovery re-dial path.
- The connection-per-poll (ephemeral-session) mode's idle-boundary release (`releaseForIdle`, gated on the internal `ephemeralSessions` option; see [SFTP_SESSION_RECOVERY.md](SFTP_SESSION_RECOVERY.md)) is a new caller that closes the session, leaving the adapter in the same cleared-session state a server drop produces; what tells a deliberate release apart from a drop, and what each records, counts and warns, is specified in [SFTP_SESSION_RECOVERY.md](SFTP_SESSION_RECOVERY.md#what-the-accounting-counts). It drives the underlying ssh2 `Client`'s own `end()` (reached via `this.client`, the same boundary `setNoDelay` uses -- not ssh2-sftp-client's `end()`, which would latch `endCalled` and permanently disable the global `'close'` listener the mode depends on) and then awaits the `Client`'s `'close'` event to know the teardown finished before the poll loop idles. The critical assumption is that `Client.end()` emits `'close'`, not merely `'end'`: `releaseForIdle` awaits exactly `'close'` (via `Client.once('close', ...)`, bounded by a local `CLIENT_CLOSE_TIMEOUT_MS` safety check so a withheld close cannot hang the loop). It is that `'close'` -- not `'end'` -- that fires ssh2-sftp-client's constructor `globalListener` to clear `this.sftp`, leaving the adapter in the exact cleared-session state a server drop produces, ready for the next cycle's `ensureConnected` to re-dial. A session still set after that wait is reachable on the pinned version with no dependency change at all: `Client.end()` is `_sock.end()` and the `Client` emits `'close'` only from the socket's own `'close'`. A partner that accepts the disconnect and never closes the connection leaves it in half-close, and the local safety check settles the release first (measured against a real ssh2 server: the release spends its full bound, `this.sftp` is still set, `_sock.writableEnded` is true and `readableEnded` false). That state is not a surviving session -- the transport is already ended, so it can hold nothing and an operation issued on it does not settle -- and the release does not hand it to the next cycle: it forces the socket closed (next bullet). The boundary is not assumed: in this mode `connect()` verifies that the `Client` still exposes `end`, `once`, and `removeListener`, and fails the dial with one error naming the boundary and this document if any of them has moved.
- The forced close reaches one further internal: `net.Socket`'s own `destroy()` on the socket the bullet above names (`this.client._sock.destroy`), which `connect()` verifies in this mode alongside the boundaries above. On the branch where the release's own `end()` ended the transport but no `'close'` arrived within the bound, the release destroys that socket and awaits the `Client`'s `'close'` under a second, shorter bound (`FORCED_CLOSE_TIMEOUT_MS`), then checks that `this.sftp` actually cleared. That is the one assumption here `connect()` cannot verify, because nothing at connect time destroys the socket, so it is read back at that point and raised there instead. Measured against a real ssh2 server: the clear is not synchronous with `destroy()` (it still reads set in the same tick), the `Client`'s `'close'` follows in single-digit milliseconds, `this.sftp` is then cleared, the next `ensureConnected` dials, and the re-dial is charged to neither reconnect counter. The alternative shape -- leave the socket alone and clear the session property instead -- was measured and rejected: `connect()` refuses outright while the property is set (`connect: An existing SFTP connection is already defined`), and the abandoned half-open socket stays alive. So when the partner eventually does close it, the global `'close'` listener clears the fresh session's property and the next operation fails as an unexpected end -- a spurious counted drop, plus a leaked descriptor per cycle. The forced close's bound is the one liveness timer in this adapter left ref'd: the socket it waits on has just been destroyed, so nothing else holds the loop open and an unref'd timer would let the process exit (code 0, mid-exchange) instead of reaching that check -- measured both ways. Re-verify on an ssh2 bump that `_sock` is still a `net.Socket` exposing `destroy()` and that destroying it still drives the `Client`'s `'close'`.
- The connection's terminal close (`SSH2SFTPClientAdapter.end`) reaches one of the same boundaries in both session modes -- nothing on that path is gated on `ephemeralSessions`. The control itself, its two bounds, and what each degraded branch warns are specified in [SFTP_SESSION_RECOVERY.md](SFTP_SESSION_RECOVERY.md#the-connections-terminal-close); four library assumptions support it, each measured against a real ssh2 server. (1) ssh2-sftp-client's `end()` drives the ssh2 `Client`'s `end()` (a socket half-close) and resolves only from its own `'close'` handler, so a partner that accepts the disconnect and never closes the connection leaves that promise pending indefinitely. Measured with the close withheld, it was still pending at 20 s with `ephemeralSessions` false and at 20 s with it true, against 3 ms with a server that closes. (2) Destroying the socket beneath a pending `end()` resolves that promise rather than rejecting it (measured: resolved 2 ms after `destroy()`, with `_sock.destroyed` already `true` synchronously in the same tick), which is what makes the forced path a settlement of the call it raced rather than an abandonment of it. (3) An `end()` that rejects closed nothing: ssh2-sftp-client raises that rejection from the temporary `'error'` listener it installs for the call, whose `endListener`/`closeListener` are gated off by `endCalled`, so the socket is left exactly as a withheld close leaves it -- which is why a rejection is treated as the same open connection and not as a completed close. (4) An abandoned half-open socket is a ref'd libuv handle, and the CLI's success path exits by event-loop drain, so bounding the wait without destroying returns the caller over a process that never exits (measured in a child process against a withholding server: `close()` had neither returned nor let the process exit 60 s later). Re-verify all four on a bump, along with `_sock.destroyed` as the read-back -- the one assumption `connect()` cannot check, because nothing at connect time destroys the socket, so it is read at the boundary instead.
- The default held-session mode verifies the destroy boundary at dial time as the connection-per-poll mode does: `connect()` resolves `client._sock.destroy`, with `Client.once`/`removeListener`, in both session modes, because the subsystem-open bound closes an abandoned dial through them (see the bullets below), and refuses the dial where one has moved. What the default mode is not held to at dial time is the rest of the idle release's set -- `end` and `_sock.writableEnded` -- which it never drives. The terminal close still resolves `_sock.destroy` again where it uses it and, where it has moved since the dial, warns (naming the boundary and this checklist) and returns bounded rather than throwing. The close requires only what it drives -- `_sock.destroy`, and not the `end`/`once`/`removeListener`/`writableEnded` the idle release needs -- so a bump that relocated one of the wider set cannot disable a forced destroy that would still have worked. Consequence for an upgrade: in either mode a relocated `_sock.destroy`, `Client.once`, or `Client.removeListener` fails the dial with the library-incompatibility refusal rather than surfacing later as a teardown warning.
- The mid-exchange session recovery widens that reach further, in both session modes and beyond the destroy: a partner that drops the SFTP session and then withholds its connection close leaves the same half-open transport the release's bullets describe, with no release involved. Measured against a real ssh2 server made to drop an active session with its close withheld: the operation on the wire is never answered and ends on the adapter's own per-operation deadline, the socket beneath the `Client` reads `writableEnded: true, readableEnded: false, destroyed: false`, and `this.sftp` is still set -- identical with `ephemeralSessions` true and false. The control: the same drop against a partner that does close clears the property and recovers on one re-dial, in 228 ms. What the adapter does with that reading is specified in [SFTP_SESSION_RECOVERY.md](SFTP_SESSION_RECOVERY.md#what-is-re-dialed-and-what-stays-terminal); what it reaches here is the release's forced close -- `Client.once`/`removeListener` for the `'close'`, `_sock.destroy`, and Node's `_sock.writableEnded`/`readableEnded` as the ended-transport reading -- ahead of the re-dial, so the dial runs over a destroyed socket and ssh2-sftp-client's "already connected" guard cannot fire. Those boundaries are resolved at use, in both modes, for the reason the previous bullet gives: the severity here is a warning plus the operation's own terminal failure, never a failed dial, so a bump that relocated one costs an exchange nothing it had not already lost. `Client.once`/`removeListener` and `_sock.destroy` are also verified at dial time in both modes, for the subsystem-open bound's sake (next bullet), so a relocation of one of those three is refused there instead. Re-verify on a bump that a server-side session drop with the close withheld still leaves `this.sftp` set over an ended `_sock`, and that destroying that socket still drives the `Client`'s `'close'` and the property clear; `apps/cli/test/integration/heldSessionWithheldClose.test.ts` drives it end to end and `dialDeferral.test.ts` censuses the socket the re-dial is issued over. Only the in-process backend can be made to withhold a close, so none of this is verified against a native `sshd`.
- That recovery reaches one assumption further, into the order in which the pinned stack delivers a drop, because ssh2-sftp-client's per-operation listeners settle the operation -- and clear `this.sftp` -- from the ssh2 `Client`'s `'end'` as well as its `'close'`. Measured against a real ssh2 server made to drop an active session cleanly under an in-flight operation, at each of the first three opcodes of the operation. Every high-level call rejects between the `Client`'s `'end'` and its `'close'` -- `get`, `put`, `delete`, `rename`, `exists` and the library's own `list`, each with an `Unexpected end event` message -- with `this.sftp` already cleared at that `'end'`. The raw `readdir` the adapter's `list`/`createExclusive` drive instead rejects with `No response from server` after the `'close'`, cleared by it. So the side of the `'close'` a tear lands on follows the route, not the operation's name, and a route can settle later than its own listener fires -- the adapter's chunked `put` settles through its bounded source, a hop past the library's rejection. The socket does not separate the two -- at the high-level rejection it reads `writable: false, writableEnded: true, readableEnded: true, destroyed: true`, which is what it reads once the whole sequence has run as well. So the still-owed reading is taken from the `Client`'s own `'end'`/`'close'` pair, one persistent listener pair per adapter on the same `Client.on` boundary the keyboard-interactive answer handler uses. It is needed because a dial issued while that `'close'` is owed is failed by ssh2-sftp-client's connect-time listeners (`getConnection: Unexpected end event`) while the handshake it started runs on unowned at the server, so the recovery drives the previous bullet's forced close whether or not the session property is still set, and waits the `'close'` out before dialing. A `Client` exposing no `on()` leaves no reading to take, and the flag's unwritten default is the same value a delivered sequence leaves, so the retirement separates the two by whether the watch attached and treats an unwatched `Client` as *cannot tell* rather than as *nothing owed*. It warns once per adapter, naming the boundary and this checklist, and takes the conservative branch: the forced close, then the dial. Driven against a mocked `Client` in `apps/cli/test/unit/connection/ssh2SftpAdapter.test.ts` on the two shapes the relocation can take. With `on()` gone and `once()` still in place, a `get`/`put`/`exists` torn in flight still recovers on one dial (`this.sftp` cleared, `_sock.destroy` driving the `'close'`), so the boundary costs the reading and a wait, not the recovery. The wait is that on a transport whose `'close'` had already landed, the forced close spends the full `FORCED_CLOSE_TIMEOUT_MS`, since a `'close'` listener armed after the event never resolves early. With the whole `EventEmitter` surface gone -- Node's `once()` is itself implemented in terms of `on()`, so a `Client` that has actually lost the surface loses both -- the forced close has no boundary either, and the dial is refused under a second warning. That leaves the operation the `ERR_NOT_CONNECTED` it already had rather than a connect error and a spent budget: the same severity choice the previous bullet makes. Neither shape is reached on the pinned versions: `new (require('ssh2').Client)()` reads `instanceof EventEmitter` true on `ssh2@1.17.0`, with `on`, `once`, and `removeListener` all functions. Re-verify on a bump that a clean server-side drop under a high-level operation still settles it from the `Client`'s `'end'`, ahead of the `'close'` and with `this.sftp` already cleared, that destroying the socket still drives that `'close'`, and that the `Client` still exposes the `on()` the reading is taken through. `apps/cli/test/integration/inflightDropRecovery.test.ts` drives the operation classes and a sweep of cut positions inside one transfer. `inflightDropExchange.test.ts` holds a two-party exchange cut mid-message to a two-sided contract -- delivering the message or rejecting the sender's `send()`, and where the cut tears the reply to a write the partner then consumes, rejecting it as an undetermined outcome rather than as a determined non-delivery. `concurrentOpDropRecovery.test.ts` holds a cut that tears several operations at once to settling every one of them on the tear, and `dialDeferral.test.ts` censuses the socket the re-dial is issued over. Only the in-process backend can be made to cut a session this way, so none of this is verified against a native `sshd`, and the measured shapes are `ssh2.Connection.end()` at a counted opcode and the same `end()` from inside the RENAME handler, on either side of that request's `fs.rename` -- not the whole class of clean drops.

### Dial bounds and session-transition serialization

- ssh2's `Client.connect()` issued on a socket that is still writable defers the attempt behind `once('close', ...)` and arms no `readyTimeout` for the deferred attempt, so Alcove's `serverConnectTimeoutMs`-derived bound silently does not apply to it. Measured on the pinned versions, a second `connect()` on a live socket (`writable === true`, `readyTimeout: 5000`) was still unsettled at 45016 ms with no `'ready'` and no `'error'`, and the same at the ssh2-sftp-client layer (44998 ms) with its session property force-cleared. The precondition is narrower than "an open connection": `writable === true` -- a transport not yet ended -- together with a cleared session. Neither an ended transport (`writableEnded: true, destroyed: false`) nor a destroyed one defers; a dial on either settles in dial-scale time (~220 ms measured). No adapter path reaches the deferring state, and that is a check rather than a note: `apps/cli/test/integration/dialDeferral.test.ts` drives each dial path against the real stack -- against a partner that withholds its close, and against one that cuts cleanly under an in-flight high-level operation. It records the state of the socket beneath every dial the adapter issues, and fails if any is `writable`, if any dial does not settle, or if the live-session gate stops firing. The library mechanism itself still exists, so the unreachability is a property of Alcove's dial gates (`ensureConnected`'s `if (sftp) return true`, and `shouldRecoverFromSessionLoss`, which refuses a set session unless its transport has ended) plus the three forced closes above, which leave an ended transport destroyed rather than writable. The recovery's own forced close runs before its own re-dial, so that dial too is issued over a destroyed socket. That is exactly what the check pins. See [connection-per-poll-sftp.md](../notes/connection-per-poll-sftp.md) for the driven measurement behind it, the two barriers, and the caveats on its scope.
- ssh2's `readyTimeout` covers a dial only as far as authentication: ssh2 clears it in its `USERAUTH_SUCCESS` handling, and the `subsystem sftp` request ssh2-sftp-client issues next has no deadline of its own, in either package. So the phase after authentication is bounded by Alcove, not by the library: the adapter subscribes to the ssh2 `Client`'s `'ready'` -- the same event ssh2-sftp-client waits for before requesting the subsystem, and the one it exposes as `this.client` from its constructor, so the subscription is in place before the dial -- and arms the same `serverConnectTimeoutMs` window over what follows (see [TRANSPORT_LIVENESS.md](TRANSPORT_LIVENESS.md#connect-probe-bound)). Both halves are checks rather than prose, in `apps/cli/test/integration/sftpStackPremises.test.ts`: that `'ready'` precedes the subsystem request, and that a dial whose subsystem reply is withheld is still unsettled several times past its own `readyTimeout`, its socket undestroyed and writable, and holding its process open with nothing else on the event loop, which is why the bound's own timer is unref'd. An expiry closes the socket beneath the abandoned dial and waits the `Client`'s `'close'` for it out before reporting, on the same bound the two forced closes above take: measured against the pinned stack, a dial issued while that `'close'` is still owed is failed by ssh2-sftp-client's connect-time listeners (`getConnection: Unexpected close event`) without ever reaching the server, four such dials back to back leave the client dialing nowhere at all, and the wait itself costs 0-6 ms where the `'close'` lands. `apps/cli/test/integration/subsystemOpenBound.test.ts` holds both shapes -- a re-dial chained onto a bounded failure bounded again at the server, and four back-to-back failures leaving the connection able to dial a server that answers. A version that grew a deadline for this phase makes Alcove's redundant rather than wrong; one that requested the subsystem before `'ready'` would arm it over a phase that had not begun, and fails that check. The bound is not optional: a dial on a `Client` that no longer exposes `once` or `removeListener` is refused before it dials, and a first dial that succeeds on one whose socket no longer exposes `destroy` is refused there, both as a usage error (CLI exit 64), because without them the bound cannot be armed or a later dial would defer behind an abandoned one with no deadline. A first dial that expires before the socket could be checked leaves the expiry nothing to close it with, so it warns that the connection is left to the operating system and fails with its own expiry.
- A failed dial of any kind can reject before its connection has closed. Measured against the pinned stack, a dial whose key exchange the server refuses rejects before the `Client`'s `'close'` for its connection, and a dial issued on the same `Client` before that `'close'` lands fails as well, against a server that accepts it. The socket cannot tell whether that `'close'` is still to come: Node sets a socket's `closed` and `destroyed` flags synchronously inside `destroy()`, before its `'close'` event fires, and a dial that fails on its handshake timeout or on a reset connection rejects over a socket already in that state. So the adapter subscribes once to the `Client`'s `'close'` before each dial, removes that listener however the dial settles, and takes that event as the only reading of whether the dial's `'close'` has been delivered. After a failed dial whose `'close'` it has not seen, it waits for that `'close'`, destroys the socket only if it does not come within the same bound as the closes above, and waits the destroy's `'close'` out on that bound too, all before it reports the failure. A socket exposing no `destroy()` at that point is left to the operating system under a warning, once the wait for its own `'close'` has run. A socket the dial did not open, such as the live session's that a refused `connect()` leaves in place, is left alone. Each assumption is a check in `apps/cli/test/integration/sftpStackPremises.test.ts`: a dial issued before that `'close'` fails, a destroyed socket reads `closed` before the `Client`'s `'close'` fires, a dial that fails on its handshake timeout or on a reset connection rejects over a socket already `closed` with that `'close'` still to come, and a dial issued after that `'close'` connects. `apps/cli/test/integration/sftpKexRedialPolicyFlip.test.ts` drives the adapter's cycle-start re-dial at once after a refused one and requires it to connect. Two readings stay open: a `'close'` arriving late from an earlier connection, after that connection's own bounds have run out, is counted as the failed dial's own, so the new socket is left open and the next dial on it runs on its own deadline; and a destroyed socket whose `'close'` does not arrive within the bound is reported without a warning, as the release's forced close is.
- That release also reads Node's own half-close flags on the socket the bullets above reach (`this.client._sock.readableEnded` / `.writableEnded`) to tell who ended the transport, because the session property alone does not say. `readableEnded` marks a teardown the peer began: ssh2 emits `'end'` on the peer's FIN and `'close'` only after it, and ssh2-sftp-client's global `'end'` listener leaves `this.sftp` set, so without that flag a release landing in the window between the two would drive a no-op `end()`, see the `'close'` promptly, and read a server-side drop as a release of its own. `writableEnded` is read at two points and answers a different question at each. Before the release drives its own `end()`, a `writableEnded` transport is one something other than this release ended -- ssh2 answering a partner's `SSH_MSG_DISCONNECT` is the shape it is read for, alongside the withheld-close drop the recovery bullet above measures. After that `end()`, the same flag is the transport-is-ended assumption above, kept as a runtime check rather than a claim: `true` is the partner withholding its close, over a transport this side had already ended, so the release draws no `'close'`, spends its bound and forces the socket shut. `false` is an `end()` that did not end the socket, so the session may still be live. What each of those readings then records, counts and warns is specified in [SFTP_SESSION_RECOVERY.md](SFTP_SESSION_RECOVERY.md#what-the-accounting-counts). Measured against the in-process server driven to drop a session with its close withheld and the wire empty: the release forces the close and emits its operator line once, `reconnects` and the mid-exchange sub-count both stay 0, and the next operation's pre-establish gate dials exactly once -- `apps/cli/test/integration/ephemeralSessionExchange.test.ts` drives it. Both flags are plain `net.Socket` properties rather than ssh2 internals, so only the `_sock` boundary itself is at risk on a bump, and `connect()` verifies in this mode that `_sock` reports `writableEnded` -- a socket that does not is a failed dial rather than a reading that silently stops meaning anything.
- The adapter's session-transition serialization (`end()` takes the same FIFO lock every dial and release takes; see [SFTP_SESSION_RECOVERY.md](SFTP_SESSION_RECOVERY.md#the-session-transition-lock)) can put two `end()` callers on the adapter at once, and its memoized terminal close is what holds them to one client `end()`. ssh2's own idempotence sits behind that memo as a safety check rather than as the guarantee: it guards `Client.end()`'s body with `isWritable(this._sock)`, so a second call is a no-op that raises nothing, and ssh2-sftp-client's `end()` is likewise idempotent via its `endCalled` latch. Confirm both on a bump -- a version that dropped the `isWritable` guard or made a second `Client.end()` throw is a behavior change to note -- though the re-entrant teardown does not rest on either.
- That serialization's acquire is bounded (`TRANSITION_ACQUIRE_TIMEOUT_MS`, 10 s), and the one waiter whose expiry still closes something is teardown: it gives up ssh2-sftp-client's `end()` and destroys `this.client._sock` while the transition it was waiting on -- typically a dial mid-handshake -- still holds the client. Three assumptions about the pinned stack support that branch, each a check in `apps/cli/test/integration/sftpStackPremises.test.ts` driven at the `ssh2-sftp-client` layer -- not through the adapter, where every one of them displays as the same opaque timeout. They run against a real ssh2 server made to answer the SSH identification string and then write nothing further, so the client's dial hangs established but never ready. First, ssh2-sftp-client's `end()` driven mid-handshake closes nothing: it short-circuits on the session the handshake has not restored and resolved in 1 ms with the socket untouched (`destroyed: false, writable: true`) and the dial still pending. That is why this branch reaches the destroy and never `end()`, and why it cannot reuse the terminal close's forced branch (that one waits out the `end()` it captured; this teardown has none and must not create one). "Must not" is measured rather than preferred, and has a case of its own in that file: an `end()` driven mid-handshake ahead of the destroy also disables it, leaving the parked `connect()` unsettled 3 s later where the destroy on its own settles it inside that same 1-5 ms. Second, destroying the socket beneath a mid-handshake attempt settles that attempt rather than leaving it pending: `_sock.destroyed` reads `true` synchronously on return from `destroy()`. The parked `connect()` rejects 1-5 ms later across five samples, and with no retry budget left the `TCPSocketWrap` handle is gone one tick after and a child process that does nothing further exits code 0 about 50 ms later. Third, that rejection is a plain `Error` with `code: "ERR_GENERIC_CLIENT"` and message `getConnection: Unexpected close event`, and its machine-readable half is the one a peer close gives: the same class and the same code the server's own close of the same stalled connection produces, so nothing branching on class or code can attribute this destroy to the partner. The messages differ, and only in the transport event each names -- the peer's close arrives as `getConnection: Unexpected end event` -- so the message reads which event the transport delivered and not who caused it, and a matcher on either fragment reads a cause that is not in it. Both are pinned. The consequence that is Alcove's own code rather than the library's: with retry budget left, `connect()`'s loop re-dials on a fresh socket about a second after the destroy and the process stays alive for the remainder of the dial budget (measured), so that loop reads the teardown latch between attempts. A version that left the attempt pending after the destroy, that resolved `end()` by actually closing the transport mid-handshake, or that gave the destroy path an error code of its own changes what an expired teardown wait does, and fails that file rather than needing a hand-run re-verification. The bound itself rests on none of them -- it is a fixed ceiling on the wait, not on the transition being waited on -- so it does not inherit the per-attempt `readyTimeout` assumption a dial-side ceiling would have. See [connection-per-poll-sftp.md](../notes/connection-per-poll-sftp.md) for the driven measurement behind the figures above and its limits. The checks inherit one of them: the stall is imposed as the connection is accepted, which is after ssh2 has answered the identification string, so a server that stalls once the key exchange is under way is a different and unmeasured shape.

### Keepalive, concurrent operations and the put stream

- ssh2-sftp-client exposes the underlying ssh2 `Client` as `this.client`, and ssh2's `Client.setNoDelay(true)` toggles `TCP_NODELAY` on the live socket. `connect()` calls it once after the connection is established to disable Nagle's algorithm -- a per-round-trip latency optimization for the chatty rendezvous protocol. Unlike every other assumption here this one has no correctness weight: the call is guarded and non-fatal, so a future version that relocates the `Client` or drops `setNoDelay` makes the adapter log a warning and continue with Nagle enabled (slower, still correct) rather than fail.
- The ssh2 `Client` exposes its underlying `net.Socket` on `this.client._sock`, and ssh2 exposes `setNoDelay` but *not* `setKeepAlive`, so `connect()` reaches the socket directly to enable kernel TCP keepalive (`_sock.setKeepAlive(true, SFTP_TCP_KEEPALIVE_DELAY_MS)`) -- the transport-layer safety check beneath the application heartbeat (see [TRANSPORT_LIVENESS.md](TRANSPORT_LIVENESS.md#sftp-session-heartbeat-and-tcp-keepalive)). Like `setNoDelay` this has no correctness weight: the call is guarded and non-fatal, so a version that renames or relocates `_sock`, or one where `_sock` is not a `net.Socket` exposing `setKeepAlive`, makes the adapter log a warning and continue without kernel keepalive (the application heartbeat still defeats the server idle timeout) rather than fail.
- The application heartbeat issues its no-op keepalive through ssh2-sftp-client's *public* `realPath(".")`, so it adds no internal-API coupling of its own, and the ssh2-sftp-client concurrency assumption governing it is much narrower than "two operations must not be in flight on one client at once". Overlap on a healthy session is safe: driven against a real ssh2 server, 16 distinct pairs issued in the same event-loop turn, 5 rounds each (80 pair executions), covering `get` against `get`/`put`/`delete`/`rename`/`exists`, `list` against `get`/`list`/`createExclusive`, `createExclusive`+`exists`, `put`+`delete`, `rename`+`exists`, `safeDelete`+`get`, and the heartbeat's own `realPath(".")` beat against `get`, `list`, `createExclusive` and another beat. Every operation returned the correct result for the server state at the time -- including the later rounds' application-level answers to state an earlier round had changed, a `code: 2` on re-deleting and an `EEXIST` on re-creating an existing lock -- with no hang, no cross-talk and no mis-routed error. A non-fatal failure of one member does not disturb the other either (6 arms: a failing `get` (ENOENT), `createExclusive` (EEXIST) or `delete` (ENOENT) alongside a `list` parked on the wire, each of the three driven once on a healthy session and once with a drop following the failure; each failure got its own correct error and the survivor was unaffected). That holds because `removeTempListeners` removes by identity, so the survivor's own listeners stay installed. What overlapping operations do cross is the session-loss rejection: `addTempListeners` prepends its per-operation listeners, so the most recently issued high-level operation's listener runs first and consumes the ssh2 `Client`'s `'end'`, and the earlier operation's listener is then suppressed by the library's `eventHandled` bookkeeping and never rejects it. Issuance order therefore decides which of two concurrent operations takes which path out of a session loss, and the two paths do not have the same outcome. Measured on a clean partner-side drop, reversing the order within a pair reversed which member the rejection landed on -- between `exists` and `get`, where it reversed which of the two failed, and between the beat and a `get` alike. The beat is not special with respect to that crossing (it behaves as any other high-level operation, its being a beat mattering only in that its own outcome is swallowed). The adapter issues concurrent operations of its own with no suppression of any kind, so the beat suppression covers the beat and nothing else -- what it is still worth is in [TRANSPORT_LIVENESS.md](TRANSPORT_LIVENESS.md#sftp-session-heartbeat-and-tcp-keepalive). Re-verify on a bump that `addTempListeners` still prepends and its `_resetEventFlags`/`eventHandled` bookkeeping still suppresses the earlier listener once a later one has consumed the event (the ordering the crossing rests on), and that `removeTempListeners` still removes by identity (what leaves a survivor its own listeners). A version that serialized operations internally, or gave each operation its own connection-level listeners, retires the crossing rather than changing it.
- Whether the members that do not take the rejection settle at all is a separate question from which one takes it, and is measured separately, because the recovery re-dial that the taker enters is what the others are outstanding across. Driven against a real ssh2 server made to cut a session cleanly with several operations on the wire: a raw-wrapper `list` (batched one name per READDIR, so it spans hundreds of opcodes) alongside a high-level `get` of 8 MiB, in both issue orders and at five cut positions inside the pair, 50 runs. Also driven: forty-way `Promise.allSettled` `delete` and `Promise.all` `safeDelete` fan-outs, 18 runs each. Every member settled on the tear rather than on its own per-operation deadline, and every one inside the recovery chokepoint was re-issued and returned its own correct result -- the pair in 278-495 ms and the `delete` fan-out's forty members in 224-260 ms, against a 3000 ms deadline set for the runs. The tear order follows the operation kind and not issue order: the high-level `get` is settled from the `Client`'s `'end'` and enters recovery first in both orders, and the raw `list` from the `'close'` the retirement waits out, 0.13-0.47 ms after it. The beat as the outstanding member was driven under both partner classes -- parked on the wire by a withheld REALPATH response at a clean cut, and issued into the transport a withheld connection close leaves half-open (outstanding 2.0-2.8 s, settled 1.4-2.5 ms after the forced close's `'close'`, never at its own 3000 ms deadline). It rejected in both cases with `realPath: Unexpected close event`, never a stall. A beat is parked on the wire through the in-process server's `REALPATH` withhold, the same `inject.withholdOn` hook its other served opcodes use. `apps/cli/test/integration/concurrentOpDropRecovery.test.ts` holds each of these shapes against that server -- the pair in both issue orders, both fan-outs, and the beat under both partner classes -- at one cut position and one execution apiece. The cut-position sweeps and repeats behind the counts and ranges above were driven ad hoc and are not in the tree, so a bump re-drives the shapes rather than reproducing those samples. Re-verify on a bump that a member not taking the loss rejection still settles from the transport's own lifecycle rather than being left outstanding, since that is what keeps the stall exclusion above from swallowing a genuine loss. The runs' limits: nothing was driven in any state for the `rename()` re-issue's existence probe against anything; and at a session death specifically, nothing was driven for `get` against `put`/`delete`/`rename`, for `list`+`list`, `put`+`delete` or `rename`+`exists`, or for `keepalive` against `createExclusive` or another `keepalive`. Core's own concurrency -- a `send()` running alongside the free-running poll loop -- put two operations on the wire at the tear in 12 of the 20 runs driven across ten cut points, and none of those runs reached the window above at all (every message was delivered and every `send()` resolved). So the shapes above measure the adapter under such concurrency rather than showing the poll loop producing it at a drop. Nothing was driven against a native `sshd`, and the withheld-close class cannot be.
- What the same per-operation listeners cost is measured on the same assumption, because concurrency on one `Client` is what makes them stack. `addTempListeners` attaches exactly one `'end'`, one `'close'` and one `'error'` listener per in-flight operation, and `removeTempListeners` takes all three off when it settles. So a fan of width `w` peaks at `w + 2` on `'end'` and `'close'` and `w + 1` on `'error'` above the persistent 2/2/1 a connected client holds (ssh2-sftp-client's three constructor `globalListener`s, plus the adapter's own `'end'`/`'close'` transport-lifecycle watch). Node's default ceiling is 10 (`events.defaultMaxListeners`, which `client.getMaxListeners()` reads back), so a concurrent fan of 8 is silent, 9 emits two `MaxListenersExceededWarning`s (`'end'`, `'close'`) and 10 or more emits three -- identical in the default held-session mode and under `connection_per_poll`. Node raises that warning through `process.emitWarning` and never through `console`, so in a real child process it lands on stderr only (0 occurrences on stdout, where the CLI's own `[INFO]` operator lines go) and neither the integration suite's console sentinel nor `withCapturedLogs` can observe it; an in-process `process.on('warning', ...)` can, and is the hook the checks use. Its verbatim first line is `(node:NNNNN) MaxListenersExceededWarning: Possible EventEmitter memory leak detected. 11 end listeners added to [Client]. MaxListeners is 10. Use emitter.setMaxListeners() to increase limit`.
- The stacking is bounded rather than a leak: every shape driven came back to the exact persistent baseline on every event name once its fan settled, including a 512-wide fan whose peak was 1,541 concurrent listeners. So the adapter raises the ceiling on that one `Client` at construction to `SHARED_SSH2_CLIENT_MAX_EVENT_LISTENERS`, derived in code from the bounds that admit a fan onto the emitter rather than picked, and summed rather than maxed so that nothing rests on two fans being unable to overlap. That sum is `2 * MAX_DIRECTORY_ENTRIES` (16384) for core's rendezvous entry sweep, plus `MAX_DEFERRED_CLEANUP_DELETES` (64) for the `connection_per_poll` cleanup drain's concurrent re-issue, plus 3 for what runs beside a fan, plus the persistent 2 -- which is 16453. The entry sweep's term is twice the listing bound because that sweep is scoped to a party's directories rather than to one listing: `sweepProtocolFiles` merges the inbound listing's peer hellos and unexpected protocol files with the outbound listing's own leftovers into one array and fans a delete per element of it in a single `Promise.allSettled`. Under a split inbound/outbound scope those are two listings, each refused separately at `MAX_DIRECTORY_ENTRIES`, so one fan holds their union; under a shared scope the two collapse to one listing and the term is slack. That same term covers the three narrower delete fans core's entry scan (`scanEntryDirectory`) issues ahead of the sweep -- the orphaned-temp sweep and the leftover-abort-marker sweep over the inbound listing, and the split-mode outbound-orphan sweep over the outbound one -- each a `Promise.all` of `safeDelete` over a subset of one guarded listing and so at most `MAX_DIRECTORY_ENTRIES`, half the term. Each is awaited to completion before the next is issued and before `sweepProtocolFiles`, so none of them stacks on another or on the sweep, and the widest fan the entry scan puts on the client at any instant is the sweep's own. The drain's term is added to it rather than maxed against it because the entry sweep's deletes reach the same recovery chokepoint that sets the drain running. The ceiling is seated at that peak rather than one above it, because Node warns only strictly above a ceiling: an emitter whose maximum is `n` is silent at `n` listeners and warns on the `n + 1`th. That is driven both at a toy value (max 3: silent at 3, warns at 4) and at the adapter's own (max 16453: silent at 16453, warns at 16454), of which only the second is a committed check. Every enumerated fan, all of them at their bounds at once, is therefore silent, and the first listener past the enumeration is what warns. The `3` is measured rather than summed: a best-effort safety check held to evidence rather than an exhaustive count of what core can put on one connection, so the concurrency it is meant to cover is not a list of addends that totals it. An ordinary two-party exchange and its `connection_per_poll` variant are driven with the listener probe on each party's client, and the widest headroom either party spends above its idle baseline is asserted to stay within it. Both shapes spend 2 of the 3, on `'close'` and at teardown -- the pair ssh2-sftp-client's `end()` parks while it waits the close out, its own close handler plus the per-operation `'close'` bracket the `end()` call itself takes. What the term is meant to cover is that teardown pair together with the heartbeat's `realPath(".")` beat, the poll loop's own operation, and a `send()` resuming from the protocol continuation; which of those can be in flight together is core's business rather than the adapter's, which is why the term rests on the driven shapes instead of on that list. Crossing the ceiling costs a spurious warning and nothing else. That is what lets the one fan with no cap of its own -- the connection cleanup's `Promise.all` over this party's unconsumed `responsibleFiles` -- rest on the entry sweep's term as an assumption (those writes are entries of a directory this party's own poll listing enumerates) rather than on an enforced cap. It would only need revisiting if a fan appeared that no term governs; a bump that changed the trio's size or stopped removing it on settle invalidates the derivation and the boundedness respectively, which is why both are on the checklist below.
- Raising the ceiling gives up nothing that detected a real leak, because the ceiling never did. It fires at most once per emitter and event name (Node re-arms it when a listener array is rebuilt, so a later fan on the same client may warn again or not at all, and a fresh adapter always warns), and says nothing about whether the listeners came off. `apps/cli/test/integration/sharedClientListenerCeiling.test.ts` pins the accounting itself instead -- exact peak and exact return to baseline on every event name -- and holds no warning reaching the hook. Its runs reach fans of 9, 40 and 512: a fan of 9 issued after a `connection_per_poll` release and re-dial (which is also what pins that the emitter each operation attaches to is the one the constructor raised and that a re-dial does not replace it). They also reach the deferred-cleanup drain driven to its full 64 record cap (70 attempted, 64 admitted, 6 refused). Also driven: a shape that leaks by design, attaching one listener per operation and removing none, which the accounting reports and the raised ceiling does not, the strictly-above boundary at the derived value itself, and the two whole-exchange shapes the `3` rests on. The runs' limits: no fan at or near the derived 16453 was driven, nor one at the 8192 listing bound itself, nor a split-scope entry sweep at any width -- the doubled term is derived from the sweep's own construction and the per-listing refusal, not measured at scale. The concurrency term is checked only over the two exchange shapes named above, so a core-side concurrency neither reaches is unmeasured and would cost the spurious warning back. The uncapped `responsibleFiles` cleanup fan was driven only ad hoc, at 20 unconsumed sends, and is not in the tree, so a bump re-drives it rather than reproducing that sample. The strictly-above boundary's toy-value arm (max 3) was driven ad hoc as well and is not in the tree, the committed check holding that boundary only at the derived value itself. The stdout/stderr split was likewise measured ad hoc, through a child process, and no committed check holds it. And nothing here was driven against a native `sshd`.
- A malformed reply to the in-flight request itself is bounded by the adapter's wall-clock deadline, not by `cleanupRequests`, because ssh2 has already deleted the request from `_requests` by the time `doFatalSFTPError` runs. The `NAME` and `DATA` response handlers delete it unconditionally before the parse/check that calls `doFatalSFTPError`, and the `HANDLE` handler deletes it inside its malformed branch (on a defined request id) immediately before that call. All three leave nothing for `cleanupRequests` to fail. If a future ssh2 instead deleted after the fatal path (or stopped deleting in the `HANDLE` malformed branch), `cleanupRequests` would begin failing in-flight requests too - which would change the mechanism but not break it (the deadline still bounds the operation). The deadline must stay regardless; the `liveness` fault-injection unit test below proves the current ordering. That test is `apps/cli/test/unit/connection/sftpFatalInflight.test.ts`, which drives all three handlers by answering a `READDIR` with a malformed `NAME`, an `OPEN` with a malformed `HANDLE` and a `READ` with a malformed `DATA`, and asserts the in-flight call is not settled by `cleanupRequests`.
- ssh2-sftp-client's `put(src, dest)` pipes a non-Buffer `src` into the write stream (`_put`'s else-branch, `rdr.pipe(wtr)`), and that write stream consumes under ack-driven backpressure -- ssh2's `WriteStream._write` calls its stream callback (releasing the next pull) only after the server acknowledges the write. The `put` liveness idle window rests on both: the adapter hands `put` a Readable that streams the payload in `SFTP_PUT_PROGRESS_CHUNK_BYTES` (64 KiB) chunks and resets the window each time a chunk is pulled, so a withheld write ack stalls the pull and trips the window while a slow-but-progressing upload keeps resetting it. It rests further on ssh2's `SFTP.write` chaining a buffer larger than `_maxWriteLen` into multiple WRITE packets and firing the stream callback only after the *last* ack -- which is precisely *why* the source is chunked rather than handed over whole. A single whole-buffer write reports no progress until completion, making a large legitimate upload indistinguishable from a stall for its full duration. If a future version buffers a provided stream eagerly instead of piping it under backpressure, the window's progress signal would no longer track the server and the bound would need rework; if it merely acks per-sub-write incrementally, the chunking becomes redundant but harmless. This uses only the public stream interface (it does not drive the raw `SFTPWrapper`), so it adds no new internal coupling beyond these behavioral assumptions. The `ssh2SftpAdapter` unit tests pin the stall-fires and slow-but-progressing-does-not behaviors and byte-exact upload through the chunked source; the integration suite uploads real payloads through it. The last-ack callback is driven in `apps/cli/test/integration/sftpStackPremises.test.ts`, alongside two assumptions the chunked source's own teardown rests on: a failed `put` leaves the caller's source undestroyed, whether the server refused it or the session was lost, so every terminal path destroys it; and the client closes the server-side handle, and rejects the `put`, only on the source's `'error'`, so the stall destroys the source with an error rather than bare.

### Host key, diagnostics and authentication

- A host-key verification rejection (`hostVerifier` calling `verify(false)`, from either `open()` verifier in core's `fileSyncConnection` -- the pinned-key enforce path on a mismatch, or the no-pin fail-closed default) is reported as an `Error` whose message contains the fragment `Host denied`, with no machine-readable `code` set. Two adapter consumers match that fragment. (1) `connect()`'s retry predicate treats the rejection as terminal -- a non-matching (or absent) pin never becomes a matching one, so retrying only re-runs the key exchange against the same untrusted host. (2) In connection-per-poll mode, `ensureConnected`'s `isFatalDialError` matches the same fragment to classify a cycle-start re-dial's host-key rejection as fatal (terminate the exchange loud and fast) rather than a transient dial failure to skip-and-retry next tick. If a future version renames the fatal-handshake message (it originates in ssh2's `kex.js` as `Host denied (verification failed)`), both consumers stop firing. `connect()` retries a host-key failure `maxReconnectAttempts` times before failing with the same outcome (slower and noisier, no security regression, since core's `fileSyncConnection` re-wraps the same rejection into its `SFTP host-key verification failed:` message regardless). And `isFatalDialError` misclassifies a re-dial host-key mismatch as transient and rides it to the peer-inactivity ceiling instead of aborting at once -- a worse failure mode for a possible MITM, though still fail-closed (the exchange terminates, just late and with a generic peer-silence error). Confirm the fragment still appears on the rejection error if either package is bumped.
- The first-use host-key probe (`fileSyncConnection`'s `probeHostKeyFingerprint`) and the `settleVerify` guard around every verifier verdict rest on four ssh2 internal behaviors, all security-relevant. (1) ssh2 invokes the `hostVerifier` at host-key verification and reaches userauth -- credential transmission -- only after `verify(true)`, so `verify(false)` aborts the handshake before any password/private key is sent; this is what lets the probe connect with credentials present in its options yet never present them to an unverified host. (2) Returning `undefined` from the verifier (our `void` async callback) parks the handshake pending the async verdict. (3) ssh2's `readyTimeout` stays armed across that park, so the probe's use of the raw (unbounded) transport is still time-bounded. (4) A late `verify()`, delivered after the handshake has torn down, returns without throwing, whether a `readyTimeout`, a destroyed socket or an earlier `verify(false)` tore it down; `settleVerify` swallows any throw a later version makes there, so a teardown-race verdict cannot become an unhandled rejection. If a future version reached userauth before the verifier, transmitted credentials despite `verify(false)`, or stopped arming `readyTimeout` until after verification, re-evaluate: each is a security regression (credentials to an unverified host, or an unbounded probe). Also note `keyBlob` is a Buffer slice view with a meaningful `byteOffset`/`byteLength` (ssh2's `bufferSlice`); `hostKeyBlob` passes those through, because a bare `new Uint8Array(keyBlob.buffer)` would hash the whole pooled buffer and compute the wrong fingerprint. Assumption (4) and the slice view are driven in `apps/cli/test/integration/sftpStackPremises.test.ts`. Assumption (1) is driven in `apps/cli/test/integration/sftpConnection.test.ts` on the in-process backend: the no-pin refusal, the wrong-pin refusal and the first-use probe each dial a server that counts the userauth requests it receives, and fail unless that count is zero.
- ssh2 reports none of a peer's pre-identification bytes to the application, so a peer that answers the SFTP port without ever sending an SSH identification string cannot be told from one that sends nothing at all by anything the stack raises. Driven against a bare `net` listener answering with an HTTP error page, with a TLS alert record, and with a clean close having sent no bytes: ssh2's `debug` callback -- the one channel that could send them -- reads `Socket connected` then `Socket ended` for all three. All three reject identically with `Connection lost before handshake` (ssh2 sets `level: "protocol"` on it, which does not survive ssh2-sftp-client's `getConnection:` wrapper). ssh2 does report pre-identification lines on its `greeting` event, but only for lines followed by a valid `SSH-...` identification string, so a peer that never identifies itself emits nothing there either. A peer that resets at accept instead rejects with `connect ECONNRESET <host>:<port>`, and `code: "ECONNRESET"` does survive that wrapper. This is why the host-key probe's non-SSH-answer diagnosis (`apps/cli/src/connection/sftpPeerIdentification.ts`) reads the peer's first bytes itself, on one bounded credential-free TCP connection opened after the dial has failed, rather than threading them out of ssh2. The rejection wording is only the gate on whether to look, so a version that reworded it degrades to the undiagnosed failure and never to a wrong diagnosis. That the wording still arms it is a check rather than prose: `apps/cli/test/integration/sftpStackPremises.test.ts` dials the pinned client at three bare `net` peers -- one answering an HTTP error page, one closing having sent nothing, one resetting at accept with `resetAndDestroy` (an explicit RST: a plain `destroy()` there, with nothing left to read, arrives as the same clean close). It holds each rejection to the diagnosis's own gate, so a reword fails there rather than disarming the diagnosis unseen. The TLS-alert shape's stack-level rejection wording stays a measured assumption without a check of its own -- the unit suite drives that shape at the classifier, against a bare listener rather than through ssh2. A bump re-measures this: a version that reported those bytes -- on `debug`, on `greeting`, or on the error -- would make that second connection unnecessary. The port the diagnosis has to dial when the config sets none -- ssh2's own default, since core omits `port` from the connect options for a portless config -- is a check rather than prose in the same file. A portless dial of the pinned client at a closed loopback address is refused, the address the stack itself names in that refusal is the port it dialed (`connect ECONNREFUSED 127.0.0.1:22`), and the diagnosis's resolved probe target for the same portless config is held to it. Nothing there re-derives the default; a version that changed it fails the case rather than sending the diagnosis to a peer the dial never spoke to. Where something answers that port on the host running the suite the stack names no address, and the case skips with that reason rather than assuming one.
- Both halves of the stack route their own diagnostics to the one `debug` connect option, as plain strings, one call per rendered line: ssh2's handshake and packet lines, and ssh2-sftp-client's `CLIENT[...]` lines, arrive on the same callback. That is what the SFTP wire trace routes into Alcove's logger (`apps/cli/src/connection/sftpWireTrace.ts`), and the lines an operator dials for -- the peer's identification string, both sides' KEXINIT name-lists, the negotiated algorithms, and `Handshake completed` -- are among them. Which of those strings arrive already escaped is not uniform and is the reason Alcove escapes at its own sink rather than trusting the stack's: driven against a listener choosing every pre-key-exchange byte, ssh2 renders the peer's identification string through `inspect` and so escapes an ANSI sequence in it, which Alcove's own escape then reads as a backslash and doubles, while it renders the peer's KEXINIT name-lists verbatim, control bytes included. So an operator reads `\\x1B` on the identification line and `\x1b` on a name-list, and the difference is which side escaped first rather than anything the peer did. Both, and the credential silence -- no password reaches the callback on the password or the keyboard-interactive path -- are checks rather than prose in `apps/cli/test/integration/sftpWireTrace.test.ts`, which drives a real dial at the trace level and at the debug, info and warn levels below it, debug again under the highest `-v` count. The error and silent levels are held by the unit suite's level table (`apps/cli/test/unit/connection/sftpWireTrace.test.ts`), which resolves the trace against a logger at each level and dials nothing. A version that renamed the option, changed the callback's arity, stopped emitting the handshake lines, or moved a name-list behind its own escape fails there rather than degrading an operator's diagnostic unseen. The last of those lines arrive as the transport drains, after ssh2-sftp-client has answered a close it had no connection open for, and against the pinned stack none of them is emitted later than the ssh2 `Client`'s `close` event -- which is what the adapter's terminal close waits for, so they reach the operator's `--log-file` before a command closes its diagnostic sink. The wait is bounded, on a timer that holds the process alive because the socket it waits over may already be destroyed, and the trace detaches where that close returns rather than on the `close` event -- so a line the stack emits between the event and the close's return is still traced, and only one emitted after the close has returned is dropped rather than printed past the sink. The same test drives all three: a dial the server accepted and one it refused with an `SSH_MSG_DISCONNECT` held to their last line with nothing on stderr, and the bound measured in a child process with nothing else on its event loop.
- ssh2 authenticates the `keyboard-interactive` method by emitting a `'keyboard-interactive'` event on the `Client` with `(name, instructions, lang, prompts, finish)` and awaiting a `finish(answers)` whose `answers` count equals the `prompts` count (the SSH `num-responses == num-prompts` rule, RFC 4256, enforced by the server, not by ssh2's `authInfoRes`). Core sets `tryKeyboard` -- from `connection.server.keyboard_interactive`, only alongside a `password` -- and the adapter registers one persistent listener on `this.client` (`attachKeyboardInteractive`) that answers every prompt with that password, for a server that disables the direct `password` method but accepts the same secret over keyboard-interactive. Every prompt of the request gets the same answer, one answer per prompt: neither the prompt text nor its `echo` flag is consulted, so the count the rule above requires holds by construction rather than by a fixed answer list. The value is read when the request is answered, off the connect options the most recent dial stored, rather than captured when the listener was attached -- the listener outlives every dial and each dial replaces those options, so a re-dial answers with the credential of the dial it belongs to and never a stale one. Nothing is re-resolved at that point: a recovery or cycle-start re-dial reuses the options the last `connect()` was called with, so the configuration is not re-read, a `@path` reference is not resolved again, and the operator is not re-prompted; only a fresh `connect()` carrying different options changes the answer. Those retained options hold the credential for the adapter's whole life, teardown included, which is what lets a recovery re-dial authenticate at all and is why nothing clears it after an answer. Four ssh2 behaviors hold it up. (1) `'keyboard-interactive'` is offered only when `tryKeyboard === true`, and a server info-request reaches this listener only after userauth begins -- hence only after `verify(true)`, the same post-host-key-verification boundary the probe bullet above rests on, so the password never reaches an unverified host. (2) ssh2 auto-responds to a zero-prompt `USERAUTH_INFO_REQUEST` itself, before emitting, so the listener never sees an empty `prompts` (its `prompts.map` always yields at least one answer). (3) `Client.connect()` and `Client.end()` do not strip Client-level user listeners (only `sock.removeAllListeners('data')` on the socket), so the listener attached before the first connect survives every reconnect -- which is why it is attached exactly once behind a boolean guard, not the object-identity guard the recreated `SFTPWrapper`'s `'error'` listener needs. (4) `tryKeyboard` with no registered listener stalls the handshake to `readyTimeout` (the emit is a no-op, `authInfoRes` is never sent), so the adapter throws loud at connect if the `Client` no longer exposes `on()` rather than degrading to a silent timeout. If a future version reorders the emit args, stops auto-answering the zero-prompt request, begins stripping Client-level listeners on connect (the boolean guard would then leave the listener un-reattached and stall to timeout), or reaches userauth before host-key verification (a security regression -- credentials to an unverified host), re-verify. The zero-userauth-request assertions in `apps/cli/test/integration/sftpConnection.test.ts` named in the probe bullet above are what drive that ordering. The real-server integration test (`apps/cli/test/integration/backendAgnostic/keyboardInteractive.test.ts`) authenticates through this path against a server that refuses the `password` method, so a behavioral break fails it red.
- ssh2-sftp-client's constructor takes the `error`/`end`/`close` event callbacks as its second positional argument and runs them through `globalListener`, which invokes a callback only for an event the high-level client did not itself initiate (its `endCalled` / `*Handled` guard) and performs its own handled-flag bookkeeping and `this.sftp` teardown regardless of the callback body. The adapter passes explicit callbacks there to route those out-of-band ssh2-`Client` events to its project logger -- `error` at error level while a session is held and at trace otherwise, the benign first-use-probe / `verify(false)`-rejection `end`/`close` at trace -- instead of the library's default `console.error` / `console.log` (whose bare `Global ... listener` lines otherwise leak past the logger and the suite's log-level controls). The `error` message is server-controlled (ssh2 builds it from the `SSH_MSG_DISCONNECT` description), so it is rendered through `sanitizeErrorForDisplay` -- escaped against log injection and run through the PEM/key redaction safety check -- before it reaches the logger and any `--log-file`; on a bump, confirm no credential can ride a `Client`-level `error` to this sink (today none can). Which of the two levels an `error` takes turns on `this.sftp`: the library hands such an error over with `sftp` still set, measured for a reset that takes a live session, and a teardown the peer answers with a reset arrives the same way; it has already cleared `sftp` for one arriving behind a failed dial or a closed connection (measured against a real server through the adapter; both arms are held by `apps/cli/test/integration/outOfOperationClientError.test.ts`). The split is what keeps a refused key exchange to one reported failure: a real OpenSSH server writes its disconnect and closes, and the client's own disconnect -- written as it reaches the same verdict locally -- lands on a socket already closing, which answers with a reset the client reads as `read ECONNRESET` once the dial has already rejected (measured against the hardened-sshd harness's `restricted-crypto` profile, 39 of 40 dials; a bare `net` client that stops writing after its own KEXINIT sees a clean close 30 of 30 instead, which is what identifies the trailing write as the cause). The routing is observational only: it changes where the diagnostic goes, never control flow. If a bump changes the constructor signature, drops the second-argument callbacks, or makes a callback required (e.g. moves the `this.sftp` clear into the `close` body), re-verify; the worst case is the cosmetic console lines returning, not a correctness break.

### Key exchange, ciphers and delete of a missing path

- ssh2 builds its key-exchange offer once at module load and runs no capability probe over it, unlike its host-key formats: on a host whose OpenSSL provider does not offer X25519 it still advertises `curve25519-sha256@libssh.org` and `curve25519-sha256`, wins the negotiation against a server that offers them, sends `KEXECDH_INIT`, and only then dies on `crypto.generateKeyPairSync('x25519')`. `apps/cli/src/connection/sftpKexCapability.ts` subtracts the unperformable algorithms from that offer, and rests on four measured properties of the pinned `ssh2`, all decided by reading the client's own `SSH_MSG_KEXINIT` off the wire rather than from its source. (1) `algorithms.kex` accepts a modifier object as well as an explicit list -- the `append`/`prepend`/`remove` shape `@types/ssh2` declares as `AlgorithmList<T>` -- and `remove` matches a `RegExp` entry as well as a string, mid-string and honouring the `i` flag, which is what lets Alcove express "ssh2's own offer minus everything built on X25519" without enumerating a key-exchange list of its own. (2) `remove` is applied after `append`/`prepend`, so merging Alcove's removal into an operator's modifier cannot be undone by the entry beside it. (3) An empty explicit list is read as *unspecified* and falls back to ssh2's full defaults -- so an operator list filtered to nothing must be refused, never forwarded, or the refusal would restore the very algorithms it rejected. A value that is neither a list nor a modifier (a bare string, `null`) is likewise inert and falls back to the defaults, as is a list that arrives empty -- which drops nothing, so it is not the refusal's case but the inert one, and takes the removal modifier ssh2's own reading of it amounts to. (4) ssh2 appends `ext-info-c` and the Terrapin strict-key-exchange marker `kex-strict-c-v00@openssh.com` to whatever list is offered, and `remove` does not reach them, so constraining the offer cannot downgrade the handshake.
- A key-exchange negotiation that then finds nothing in common is reported through ssh2-sftp-client as `getConnection: Handshake failed: no matching key exchange algorithm` -- ssh2's structured `level: "handshake"` does not survive that wrapper, so the message fragment is what there is to match on, exactly as for `Host denied`. Two things key on that fragment, each conditioned on a non-empty capability verdict and never on the message alone. It adds a diagnostic naming the missing primitive, and it feeds one classifier that says the failure is permanent, which both dial paths consult. At `connect()` the retry predicate ends the dial at its first attempt, because a process that cannot perform the primitive puts the same withheld offer to the same server on every re-attempt, a second apart, for the whole reconnect budget, to arrive at the diagnostic the first attempt already had. In `connection_per_poll` mode `ensureConnected`'s `isFatalDialError` terminates the exchange instead of skipping the cycle, because that dial is re-attempted tick after tick until the peer-inactivity ceiling ends the run with a generic peer-silence error, in place of the diagnostic the first cycle already had. The two classify on opposite sides of the diagnostic -- the retry predicate reads ssh2's rejection, the cycle-start re-dial reads what `connectLocked` threw after the diagnostic replaced that message and kept ssh2's one cause link down. So the classifier answers for the diagnostic's own type as well as for the fragment, a value nothing outside `sftpKexCapability.ts` constructs and no party on the wire can write. One classifier over one verdict is what keeps the two paths from disagreeing about a single rejection. A reworded message therefore degrades to ssh2's bare text, to that spent budget, and to a `connection_per_poll` run spending its whole peer-inactivity ceiling on the same permanent failure -- the behaviour of a match that never fires -- never to a wrong diagnostic, a dial ended for the wrong reason, or an exchange ended for one. The fragment is not ssh2's own text alone: ssh2 renders a server's `SSH_MSG_DISCONNECT` description into that same message, so a server -- or an on-path attacker, since a disconnect precedes host-key verification -- writes the fragment verbatim and reaches the diagnostic at a stage where it does not apply (measured). What bounds that is the capability verdict every consumer is conditioned on, this process's own reading of its own crypto provider taken before the dial. On a host that can perform everything ssh2 offers, a written fragment decides nothing at all -- not the diagnostic, not the dial, not the exchange -- and on a host that cannot, the same party reaches the identical outcome with no message control by offering only algorithms built on the missing primitive. The residual is a misattributed diagnostic, a dial ended at the first attempt rather than after the reconnect budget, and -- in `connection_per_poll` mode -- an exchange ended at the first cycle rather than at the peer-inactivity ceiling. All three come from a party that could already deny the exchange outright, and one written disconnect suffices, since the classification reads each rejection alone rather than a pattern across ticks. That residual is bounded by the diagnostic's message being composed from constants, with the server's own text one cause link down where the display sink escapes it once.
- `apps/cli/test/integration/sftpKexOffer.test.ts` drives all of it against the installed ssh2. Each offer shape -- no operator `algorithms.kex`, an explicit list, a modifier whose `append`/`prepend` names an unperformable algorithm, and a list that arrives empty -- is decoded off the wire with the capability verdict forced, both appended markers surviving every one of them, and the empty-list and non-list fallbacks are measured against bare ssh2 rather than assumed. The constrained offer negotiates against the suite's real server on three of the four dial paths (a direct connect, core's host-key probe, and a recovery re-dial after a server-cut session, the last two read through a recording relay that also holds the re-dial's offer identical to the first dial's). The no-common-algorithm refusal is driven against a real `ssh2.Server` restricted to `curve25519-sha256`, with a listener that writes the failure description itself, holding its bytes out of the diagnostic. The terminal classification is driven at the connect loop -- a dial given a reconnect budget of 3 and accepted exactly once by a counting relay, against that `ssh2.Server` on every leg and against a real OpenSSH `sshd` on the `restricted-crypto` native profile -- so a bump that changed any of the four fails it red. Its limits: the fourth dial path, the `connection_per_poll` cycle-start reconnect (`reestablishSession`), is driven in `apps/cli/test/integration/sftpKexRedialPolicyFlip.test.ts` rather than here, its offer and its classification alike. A live connection-per-poll exchange whose endpoint accepts the handshake it opens on and then offers only `curve25519-sha256` ends at the first re-dial meeting that policy, with the diagnostic that names the primitive rather than the `TransportOperationStalledError` the peer-inactivity ceiling raises. The identical refusal under an empty verdict, though, skips the cycle, and the exchange survives to deliver on a later one. The verdict is the only difference between the two arms, the transient one withholding the same algorithms through an operator `algorithms.kex` of its own, which each arm reads off the wire rather than assuming: the exchange dials through the same recording relay the offer legs above read their packets from (`apps/cli/test/integration/kexOfferWire.ts`). Every cycle-start re-dial that completed a handshake there offered exactly what the dial the exchange opened on offered -- no X25519 algorithm, both appended markers -- so re-constraining the retained, already-constrained options is measured to be the no-op that the constraint's sitting at `connectLocked`, the single path to ssh2's `connect`, predicts of it. What that leaves inferred is the offer of the dial meeting the flipped policy, the one dial of the exchange that abandons its handshake. Such a client can have its socket destroyed with its own `SSH_MSG_KEXINIT` still unread (measured -- the same property that makes the dial counts below connections accepted), so the packets decoded are those of the re-dials that complete, and the refused dial's offer rests on its being built from those same retained options. That leg has limits of its own. The policy flip is a second listener that a relay in front of the exchange hands later dials to, rather than one server changing its own policy. That is because the pinned ssh2 reads a Server's `algorithms.kex` once, as the Server is constructed, and never again per connection (measured: an accessor on the config object fires before the first client arrives and not after). And it runs on the in-process backend alone, as the connection-per-poll coverage does throughout, a native `sshd` not being driven in that mode and the `restricted-crypto` profile accepting only what the forced verdict withholds, so no dial of such an exchange could complete against it.
- What the stubbed client in `apps/cli/test/unit/connection/sftpKexFastFail.test.ts` still holds is the cases no server produces on demand: a host-key rejection, an ordinary transient dial failure, and a dial the teardown settled. The capability verdict is forced rather than produced by a FIPS host, because the only lever this image has is `crypto.setFips(true)`, which is not a model of one. Measured on node 26.5.1 / openssl 3.5.7 it leaves OpenSSL with no usable algorithms (`createHash('sha256')`, `createCipheriv('aes-128-gcm', ...)` and `generateKeyPairSync('ec', {namedCurve: 'prime256v1'})` all throw `error:0308010C:digital envelope routines::unsupported`), where the Amazon Linux 2023 FIPS host measured in the next bullet keeps those three primitives and is short only the curve25519 kex pair; an unmeasured provider's behavior on them is not established. The no-common-algorithm refusal reaches a native `sshd` on one leg only, the `restricted-crypto` profile, whose server accepts only `curve25519-sha256`, exactly what the forced verdict withholds. So on that leg the two dials that must complete a handshake skip instead, and on every other leg the refusal and the classification are driven against the in-process `ssh2.Server` alone. That leg also determines which text reaches `error.message` there, which is a race rather than a reading. A real OpenSSH server describes its own `SSH_MSG_DISCONNECT` as `no matching key exchange method found` -- `method`, not the `algorithm` the fragment matches -- and the pinned ssh2's local negotiation failure wins the race. So a bump that let the server's text win would leave the fast-fail never firing against OpenSSH at all, which is the deployment, and fails that leg red. The dials are counted as connections accepted rather than as offers decoded, because a client that abandons a handshake can have its socket destroyed with its own `SSH_MSG_KEXINIT` still unread by the relay (measured). Both fast-fails rest on that same one leg for the text question, the cycle-start re-dial's no less than the connect loop's: it matches the diagnostic, which exists only where the fragment already matched, so a bump that let a server's own description win the race disarms both at once.
- The pinned `ssh2` does capability-probe the cipher list it offers, as it does its host-key formats and unlike the key-exchange list above, so the ciphers a FIPS runtime puts on the wire are constrained by the provider rather than by configuration. Measured on a real Amazon Linux 2023 host in kernel FIPS mode, running the FIPS variant image built from `Dockerfile.fips` on `aarch64` -- `OPENSSL_CONF=/etc/alcove/fips-only.cnf`, the certified module it pinned when the capture was taken, `3.0.8-d694bfa693b76001`, mapped with `crypto.getFips()` reading `1` and the image's own engagement probe returning `ENGAGED`, node `v26.7.0` on OpenSSL `3.5.7`, its startup report reading the host kernel's FIPS mode as enabled. The measurement decodes the client's own `SSH_MSG_KEXINIT` off the wire from a `probe-host-key` dial against a listener that reads that first packet and answers nothing. Both `encryption_*` lists contain `aes128-gcm@openssh.com`, `aes256-gcm@openssh.com`, `aes128-ctr`, `aes192-ctr` and `aes256-ctr`, and not `chacha20-poly1305@openssh.com`, with no `connection.provider_options` supplied at all (`probe-host-key` builds its connection from the URL alone). The control is the same stack off a FIPS provider -- same architecture, same node and OpenSSL, `ssh2@1.17.0`, a bare `ssh2.Client` with no `algorithms` -- whose offer is those five in the same order plus `chacha20-poly1305@openssh.com`. The provider is the only difference between the two offers, and Alcove configures `algorithms.kex` (`sftpKexCapability.ts`) and never `algorithms.cipher`, so the omission is the runtime's rather than Alcove's or an operator's. That is why the cipher list determines what the kex list cannot, the FIPS host's kex offer being short the curve25519 pair that Alcove's own removal above already accounts for. The same packet holds the host-key probe (`ssh-ed25519` absent from `server_host_key_algorithms` where the control offers it, the six remaining formats identical and in the same order) and shows the probing is per-algorithm rather than a blanket FIPS filter over the offer. Both `mac_*` lists still contain `hmac-sha1-etm@openssh.com` and `hmac-sha1`, identical to the control's, so the MACs stay the operator's `algorithms.hmac` to constrain. Its limits: the drop is read off the wire and not from the module -- the engagement probe exercises AES-256-GCM, HKDF, HMAC-SHA-256, SHA-256, MD5, RSA-1024 keygen and X25519, never ChaCha20-Poly1305 -- so what is measured is that the offer tracks the provider, not that the module refuses that cipher by name. The listener answers nothing, so the measurement is the offer, with no cipher negotiated to a completed handshake on that host. And whether the probe also filters an operator-supplied `algorithms.cipher` list or modifier is unmeasured, so a cipher an operator names and the provider lacks is not known to be withheld the way this default one is. Nothing in the tree drives it -- `apps/cli/test/integration/sftpKexOffer.test.ts` decodes offers off the wire but forces the capability verdict, and no runtime in CI has a FIPS provider to produce one -- so re-verify it on a bump by re-driving that capture on a FIPS-mode host.
- ssh2-sftp-client's `delete(path, true)` resolves rather than rejects when the path is already gone (`SSH_FX_NO_SUCH_FILE`), the `notFoundOK` contract the connection-per-poll cleanup drain's re-issue rests on. It is what makes the drain's re-issue safe to tear at an idle boundary (see [SFTP_SESSION_RECOVERY.md](SFTP_SESSION_RECOVERY.md#the-deferred-cleanup-delete-record)): a torn delete leaves the file either unlinked or present, and the re-issue that follows must read the first as the success it is rather than spending the record's re-issue budget on it and reporting a file left behind that is gone. This one does not need re-reading on a bump: it is driven against the real in-process server by a case in `apps/cli/test/integration/ephemeralSessionExchange.test.ts` that records a temp path never created on disk and measures the re-issue clearing the record, so a bump that changed the contract fails the suite rather than silently weakening the drain.

## Re-verification by test

**The dial-on-a-writable-socket assumption re-verifies itself.** The dial gates above rest on ssh2-sftp-client never clearing `this.sftp` while the transport is still live: a clear that outlives the transport would admit a dial into ssh2's deferring state, where no bound applies. `apps/cli/test/integration/dialDeferral.test.ts` is that assumption as a check -- it drives the three dial paths against a partner that never closes and censuses the socket beneath every dial -- so a bump that re-opened the deferring state fails it red rather than needing a hand-run procedure. It covers the same three paths the measurement did, and no more (see the note's caveats), with the recovery re-dial driven in both states a drop leaves behind -- a session still held over an ended transport, and a `'close'` still owed over a cleared one -- so a bump that adds a dial path adds a case there.

**The test backend's listing batches rest on a NAME-reply wall.** The in-process SFTP server every CLI suite drives (`apps/cli/test/sftpServer/inProcessServer.ts`) answers a READDIR by packing entries until the reply reaches `READDIR_BATCH_BUDGET_BYTES` and resuming the listing on the next round trip, because the pinned client refuses a wider reply outright. Measured against a real ssh2 server and the real client, a NAME reply the server declares at 262,144 payload bytes is delivered whole, while one declaring 262,145 raises a fatal protocol error on the client's `SFTPWrapper` naming that maximum and takes the SFTP session down with it. And the server that wrote it is told nothing either way, so a backend that wrote one would lose the session it was serving without seeing why. The budget is half the wall, the margin that lets the backend's per-entry byte estimate over-count without costing a reply. Both sides of the wall are checks in `apps/cli/test/integration/sftpStackPremises.test.ts`, driven at the width the server's own encoder declares for each reply rather than at one predicted for it, so a bump that moves the wall fails there and names the stack. A suite driving a wide listing would report the same break as its own batching having stopped working.
