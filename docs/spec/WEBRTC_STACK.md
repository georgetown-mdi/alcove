# WebRTC stack upgrade checklists

This document records the internal assumptions the web and CLI WebRTC transports make about `peerjs`, `peerjs-js-binarypack` and `werift`, the dependency source files to re-read, and the checks that re-verify them, so a version bump of any of the three packages is verified before it merges.
It does not cover how the other pinned stacks and the install-time policies are upgraded (see [DEPENDENCY_PINS.md](DEPENDENCY_PINS.md), [NPM_INSTALL_POLICY.md](NPM_INSTALL_POLICY.md) and [SFTP_STACK.md](SFTP_STACK.md)), the controls the transports implement on top of these assumptions (see [WEBRTC_TRANSPORT.md](WEBRTC_TRANSPORT.md), [TRANSPORT_BOUNDS.md](TRANSPORT_BOUNDS.md), [CHANNEL_SECURITY.md](CHANNEL_SECURITY.md) and [SIGNALING_SERVER_BOUNDS.md](SIGNALING_SERVER_BOUNDS.md)), or the dependency-review requirement (see [CONTRIBUTING.md](../../CONTRIBUTING.md#dependency-policy)).
Intended readers are maintainers upgrading a pinned dependency, security auditors, and developers.

## Upgrading the PeerJS Stack (peerjs / peerjs-js-binarypack)

The web WebRTC data-channel inbound bound specified in [TRANSPORT_BOUNDS.md](TRANSPORT_BOUNDS.md#webrtc-data-channel-inbound-bound) reaches past the public `DataConnection` API into PeerJS reassembly/unpack internals (`apps/web/src/psi/transport/boundedReassembly.ts`) and parses the `peerjs-js-binarypack` wire format directly (`packages/core/src/connection/binaryPackBounds.ts`), so it rests on assumptions about both packages' internal behavior that an upgrade can silently break. The outbound path does the same in the other direction: Alcove encodes every frame itself (`packages/core/src/connection/binaryPackEncode.ts`), because the library's packer recurses once per element and cannot encode a record-scaling frame at all, and the web app installs that encoder over the PeerJS connection's own send internals (`apps/web/src/psi/transport/iterativePacking.ts`). Re-verify the following on any `peerjs` or `peerjs-js-binarypack` version bump, before the bump merges.

A `peerjs-js-binarypack` bump is one edit across two declaration sites: `apps/web/package.json` (the web transport's decoder, and the packer its tests drive) and `packages/core/package.json` (a dependency: the unpacker the PeerJS framing in core decodes with, the real packer and unpacker both of core's differential suites oracle against, and the packer the shared frame fixtures both transports are driven through are built with, `packages/core/src/connection/webrtcInboundFrameFixtures.ts`). A site left behind puts the wire format the guards are measured against out of step with the one a partner decodes with.

The library is the ORACLE for Alcove's own encoder, not a runtime dependency of it: `binaryPackEncode.ts` does not import the library, and the encoder's differential suite requires byte equality against the real `pack` for every frame shape and marker. A bump that moves the encoding fails there rather than at a partner's browser. A scoped `no-restricted-imports` rule in `eslint.config.mjs` fails lint when `binaryPackEncode.ts` or `binaryPackBounds.ts` imports the library statically, covered by `scripts/eslint-binarypack-library-import-ban.test.mjs`; a dynamic `import()` is outside what it matches.

The internal assumptions the bound relies on:

- The binary/chunked `DataConnection` class -- the one `peer.connect` and an incoming connection use by default -- exposes `_handleChunk` (reassembling chunk slices keyed by `__peerData` into `_chunkedData`, deleting the entry on completion), `_handleDataMessage` (the sole point each frame is `unpack`ed: an unchunked frame directly, the reassembled buffer via the completion recursion), and `_chunkedData` (the per-id partial store). The bound replaces `_handleDataMessage` with its own `unpack` and a copy of the dispatch that follows it in PeerJS: a truthy `__peerData` whose `type` is `"close"` calls `close()`, any other truthy `__peerData` goes to `_handleChunk`, and anything else is emitted as a `data` event. A frame decoding to `null` or `undefined` is emitted too, where PeerJS's own dispatch throws, matching the CLI's receive dispatch. `assertChunkReassemblySupported` checks all three exist at install time, so a rename or removal fails loud. These three are specific to the binarypack (Binary) serializer class; the Cbor/MsgPack/JSON/None connection classes do not chunk and lack `_chunkedData`/`_handleChunk`, so a default-serializer change to a non-chunking class trips the assert. The residual to re-verify by hand, because the assert cannot catch it: a future serializer that also exposes these three names but uses a different (non-binarypack) wire format would pass the assert while the marker scan parses the wrong format -- confirm `peer.connect` still defaults to the binarypack Binary serializer. A marker misparse either refuses the frame early (fail-closed) or runs the cursor off the end (delegated to `unpack`, which errors); it never admits a frame it did not walk, but the chunk-byte accounting could mismatch, so this is a re-verify assumption, not a silent-safe one.
- The same class exposes the send path the outbound encoder replaces: `_send(data, chunked)` (packs one value, then chunks or buffers it), `_sendChunks(packed)` (splits an over-MTU frame and sends each envelope back through `send` already chunked), `_bufferedSend(packed)` (the point a datagram reaches the data channel, with PeerJS's own buffered-amount backpressure), and `chunker.chunkedMTU` (the 16,300-byte threshold). `assertIterativePackingSupported` checks all four exist at install time, so a rename or removal fails loud rather than leaving the recursive packer in place -- a failure that would otherwise show up only on an exchange large enough to reach it, after both parties had paid for the PSI compute. The replacement calls `_sendChunks` and `_bufferedSend` unchanged, so PeerJS keeps chunking, buffering and backpressure; only the encode step is Alcove's. It drops the fifth path the original `_send` has, `_send_blob(data)` (taken when `pack` returns a promise for a `Blob`): Alcove sends no `Blob`, and one handed to the replacement refuses with a `usage`-kind `ConnectionError` from the encoder rather than being packed asynchronously. That narrowing is intended and is driven by `apps/web/test/unit/psi/iterativePacking.test.ts`; a bump that made a `Blob` a frame shape Alcove needs would have to restore the path rather than assume it is still there.
- The `Packer`'s marker choices, which the outbound encoder emits byte for byte: the integer ladder (fixint, then the first unsigned or signed marker whose range holds the value, up to `int64`/`uint64`), the `double` layout taken from a logarithm and a truncating multiply rather than from the IEEE-754 bits, UTF-8 strings under `0xb0 + n`/`0xd8`/`0xd9`, byte strings under `0xa0 + n`/`0xda`/`0xdb`, arrays under `0x90 + n`/`0xdc`/`0xdd`, and plain objects as maps under `0x80 + n`/`0xde`/`0xdf` with keys packed as strings in `Object.keys` order. This is the one assumption here that a suite enforces exactly rather than approximately: `packages/core/test/connection/binaryPackEncodeDifferential.test.ts` compares Alcove's bytes against the real packer's for the four record-scaling frames and every marker at its boundaries, and `apps/cli/test/unit/connection/webrtcOutboundParity.test.ts` does the same over the shared fixture set. A bump that moves any marker choice reddens there.
- The chunk envelope shape `_handleChunk` consumes: `__peerData` (the message id shared by every chunk of a frame), `n` (chunk index), `total` (chunk count), `data` (slice bytes). The byte/chunk accounting keys on `__peerData`; a rename collapses every chunk to one in-flight entry -- which over-rejects (fail-safe), not fail-open -- but is unverified by the assert, so confirm the field names on a bump.
- The BinaryPack marker dispatch the scan mirrors (`peerjs-js-binarypack`'s `Unpacker.unpack`): fixint/fixraw/fixstr/fixarray/fixmap and the `0xc0`-`0xdf` markers, maps declaring two child values per pair, the raw-vs-str split at `0xa0`/`0xb0`, the fixed scalar skip widths and the `u16`/`u32` length-prefix widths, and `unpack_string`/`unpack_raw` advancing the buffer cursor by exactly the declared `size` regardless of how the payload decodes. A format change either refuses the frame early (fail-closed) or runs the cursor off the end (treated as malformed and delegated), so it weakens the scan's precision rather than disabling it, but re-verify the marker table on a `peerjs-js-binarypack` bump.
- The number markers wider than 16 bits (`float`, `double`, `uint32`, `int32`, `uint64`, `int64`) decode to JS numbers rather than a heavier boxed value, so each one costs an array slot and a heap number behind it at most -- inside the per-slot figure the measured amplification envelope in [TRANSPORT_BOUNDS.md](TRANSPORT_BOUNDS.md#webrtc-data-channel-inbound-bound) rests on. A version that decoded the 64-bit markers into a `BigInt`, say, would retain more per declared node than that figure admits. The retention suite drives both halves -- the decoded type per marker, and the bytes an array of a million of them retains per declared node (`packages/core/test/connection/binaryPackRetention.test.ts`) -- so read the source only to explain a failure.
- `unpack_raw` produces each `bin`/`raw` value as a fresh per-value copy through `slice(...)` of the unpacker's input -- a `Uint8Array` view when the input is one (the chunked-completion path and the CLI), a bare `ArrayBuffer` otherwise -- never a window sharing the frame's buffer. That copy's fixed cost is one of the per-value figures the measured amplification envelope in [TRANSPORT_BOUNDS.md](TRANSPORT_BOUNDS.md#webrtc-data-channel-inbound-bound) rests on, so a bump that made it heavier moves that figure. The retention measurement drives it (`packages/core/test/connection/binaryPackRetention.test.ts`), so read the source only to explain a failure.
- `unpack`'s past-the-end read returns `0` (a positive fixint) rather than throwing, so `unpack_array` retains the whole store its declared count reserved whether or not the wire backs it -- the per-slot half of the measured amplification envelope, and the reason the byte-backed-elements and cumulative-element rules tie a declared count to the wire. The length-prefixed `read()` path (raw/str payloads) does throw on underrun, the cursor-underrun-is-malformed path the scan catches and delegates. If a future version throws on the array zero-fill read instead, the reserved store shrinks to what the wire backs; if the length-prefixed path stops throwing, re-evaluate the delegate-on-underrun reasoning.
- `unpack_map` builds a plain object and assigns each pair through `map[key] = value`, so a key that is not already a string is retained as its coerced property name (and a container key as the joined string forms of the values below it, zero-filled descendants included). The scan's refusal of any non-string map key rests on that assignment form; if a future version keys a `Map` (or otherwise stops coercing), the refusal becomes a safety check rather than the rule that keeps a frame's retention tied to its wire size.
- `pack` emits a map only for a plain JS object, whose own keys are strings by construction, and throws on a `Map` or `Set` rather than encoding one. This is what makes the refusal above safe to apply to legitimate traffic, and it is the one assumption here that is enforced rather than only re-verified. The differential suite packs every value Alcove sends on the data channel with the real packer and requires the scan to accept each, so a bump that started emitting a non-string key would redden rather than silently break every exchange.

Dependency source files to re-read on an upgrade:

- `node_modules/peerjs/dist/bundler.mjs` (the bundled binary/chunked `DataConnection`): confirm `_handleChunk` still reassembles into `_chunkedData` keyed by `__peerData` and recurses into `_handleDataMessage` on completion; that `_handleDataMessage` is still the sole `unpack` point both the unchunked and reassembled paths flow through, and that what follows its `unpack` is still the close/chunk/`data` dispatch the bound copies; that `peer.connect`'s default serializer is still the binarypack Binary class (and that `_chunkedData`/`_handleChunk` remain specific to it); and that the chunk envelope still holds `__peerData`/`n`/`total`/`data`. On the send side, confirm `_send` still packs and then dispatches to `_sendChunks` or `_bufferedSend` on the `chunker.chunkedMTU` threshold, and that `_sendChunks` still routes each envelope back through the connection's own `send` with the chunked flag set.
- `node_modules/peerjs-js-binarypack/dist/binarypack.mjs` (`Unpacker.unpack`): confirm the marker table above, that `unpack_string`/`unpack_raw` advance the cursor by exactly the declared `size`, that `unpack_array` sizes its store from the declared count before reading an element, that `unpack_raw` still copies through `slice` rather than returning a shared window, and that `unpack_map` still assigns through `map[key] = value`. On the `Packer` side, confirm a map is still emitted only for a plain object with string keys -- the differential suite drives this, so read the source only to explain a failure.
- `packages/core/src/connection/binaryPackBounds.ts`: re-confirm `readValueHeader`/`scanFrameStructure` still mirror that marker table.
- `packages/core/src/connection/webrtcOutboundBound.ts`: the sender-side frame check charges each chunk at `PEERJS_CHUNK_MTU` plus the widest chunk envelope. A unit test holds the constant to the installed `util.chunkedMTU` (`apps/web/test/unit/psi/webrtcFrameLimit.test.ts`); re-confirm the envelope's four keys, since the charge counts their bytes.
- `packages/core/src/connection/binaryPackEncode.ts`: the differential suite is the check, so read the source only to explain a failure -- a bump that reddens it means the wire format moved, and the encoder must move with it.
- `apps/web/src/psi/transport/boundedReassembly.ts`: re-confirm `assertChunkReassemblySupported` still probes the three internals, that the wrap still applies the core constants at both of them, and that `dispatchDecodedFrame` still matches PeerJS's dispatch.
- `apps/web/src/psi/transport/iterativePacking.ts`: re-confirm `assertIterativePackingSupported` still probes the four send internals and that the replacement still hands an over-MTU frame to the connection's own chunker.
- `apps/web/src/psi/transport/signalingBounds.ts`: re-confirm `peer.socket.start`, `peer.socket._socket`, `peer._lostMessages` and `peer._storeMessage` all still exist; that `_storeMessage` is still the single entry point through which a message is held for a connection not yet set up; and that `socket.start` still creates `_socket` synchronously, since the guard reads it immediately after calling `start`, with no wait for the socket to open.

`assertChunkReassemblySupported` and `assertIterativePackingSupported` both run at install time on every connection in `openPeerMessageConnection`, and the live browser exchange test (`apps/web/test/browser/invitedPSI.test.ts`, run in CI) installs the guard on a real `DataConnection`, so a renamed or removed internal fails the install loud rather than running with no inbound bound. The unit tests pin the marker table and the bound constants (`packages/core/test/connection/binaryPackBounds.test.ts`), the fail-closed wrap bounds (`apps/web/test/unit/psi/boundedReassembly.test.ts`), and the scan's agreement with the real packer/unpacker from both sides. `packages/core/test/connection/binaryPackBoundsDifferential.test.ts` drives the scan alone, beside the source and against core's own pin, reading every frame the real `pack` produces and the value the real `unpack` returns from it. `apps/web/test/unit/psi/boundedReassemblyDifferential.test.ts` drives the same agreement through the web reassembly wrap. `packages/core/test/connection/binaryPackRetention.test.ts` measures what an admitted frame retains under `--expose-gc`, so a bump that changes how much `unpack` retains per reserved slot, per string character or per binary value reddens rather than widening the envelope the spec states. A purely behavioral change that keeps the names -- a different chunking serializer, a renamed chunk field, a marker-format change -- is not caught by the assert or the happy-path browser test, so the by-hand assumptions above must be re-verified against the source files on any bump.

**The clean close's delivery assumption re-verifies itself.** The web transport's clean close waits for the peer to close the data channel rather than returning once PeerJS's flush has queued the in-band close sentinel (`apps/web/src/psi/transport/waitForPeerClose.ts`, and [WEBRTC_TRANSPORT.md](WEBRTC_TRANSPORT.md#the-clean-close) for why the sentinel alone is not delivery). It rests on five behaviours, all measured in Chromium against the app's own broker rather than read off the source. An open `DataConnection` exposes the live `dataChannel` and `peerConnection` it declares on its public type. A flushing close leaves the local channel `open`, so it produces no channel close of its own. The receiving PeerJS peer closes its channel on reading the sentinel, which the ordered channel necessarily places behind every frame already handed to `send`. The peer connection under a channel that is starting to close is still live when the peer resets the stream, and already gone when this side's own teardown takes it. And `open` on the `DataConnection` itself is cleared by every path through `DataConnection.close()` -- the peer's close sentinel, this side's own close call, a broker-relayed leave, an echoed OFFER, an ICE failure, a send error, or the channel's own `onclose`. The pin's critical assumption is the ordering: PeerJS closes this side's peer connection and clears the flag synchronously, ahead of the channel's queued `closing` task, and a flushing close leaves that flag alone, since it only queues the sentinel and returns. Those last two together are what let the wait tell a receipt from a loss, since the healthy ending in which both parties close reaches `closing` on a link of this side's own closing. A completed close cannot be read that way at all: a link state read after a completed close no longer dates the death, so the wait does not try. `apps/web/test/browser/webrtcCloseDelivery.test.ts` drives all five on a real pair. The close must resolve no earlier than the peer's read of an 8 MiB final frame, and the same exchange with the wait disabled must resolve before it. A link torn down under a standing drain must report a loss rather than that receipt, and both parties closing a drained exchange must report the receipt on each side rather than that loss. So a bump fails there if it closed the local channel itself, stopped closing on the sentinel, moved either accessor, moved its own teardown ahead of the wait's reading, or changed when it releases `open`. That failure is what keeps such a bump from silently restoring a close that returns with the exchange's final frame still buffered, one that reports a lost frame as delivered, or one that doubts every healthy exchange. A bump that breaks the ordering reports that spurious loss on the drained-and-closed case above, and one that lets a flushing close clear the flag suppresses the loss the standing-drain case exists to catch.

**A repeated OFFER replaces the connection, and the CLI acceptor's re-send rests on it.** PeerJS 1.5.5, handed a second `OFFER` naming a `connectionId` it already holds for that peer, closes the existing `DataConnection` -- emitting no `close` while it is not yet open -- and builds and emits a new one under the same id (the `Offer` case of `Peer._handleMessage` in `node_modules/peerjs/dist/bundler.mjs`, which logs "Offer received for existing Connection ID"). The web app keeps the first connection it is handed, so a CLI data channel that opens on the second is one the app never reads. That is why the CLI acceptor never sends a copy of its offer while the broker may still hold the last one ([WEBRTC_TRANSPORT.md](WEBRTC_TRANSPORT.md#broker-socket)). No suite drives the PeerJS half: `apps/cli/test/unit/connection/webrtcNegotiation.test.ts` pins only the CLI half, against a scripted peer -- one offer until the broker's `EXPIRE` or the unreported-offer fallback, and one more on each, the one on an `EXPIRE` no sooner than the minimum offer re-send interval after the last send. Re-measure it on a bump by the run that established it: a CLI acceptor (`alcove exchange` on a `channel: webrtc` config) started more than 5 s before a browser inviter in Chromium, both through the broker the web app's dev server mounts (`npm run dev`), with `DEFAULT_UNREPORTED_OFFER_RESEND_MS` set below the broker's 5 s hold in a local build so the inviter is handed two copies of one `connectionId` when it registers. On 1.5.5 the browser's console shows that warning, the connection the web app took is closed before it opens, and the CLI's data channel opens on the replacement, which the app never reads. A bump that ignores or re-answers a repeated `OFFER` instead makes the rule a precaution rather than a requirement; one that does anything else re-opens the re-send design in [WEBRTC_TRANSPORT.md](WEBRTC_TRANSPORT.md#broker-socket). Then run the same exchange at the default budget and confirm it completes.

## Upgrading the CLI WebRTC peer (werift)

The CLI's WebRTC transport (`apps/cli/src/connection/webrtc/`) drives werift's `RTCPeerConnection` directly -- no PeerJS runs in Node -- and speaks the PeerJS DataConnection wire on the raw data channel. The library choice and the architecture are recorded in [docs/notes/cli-webrtc-stack.md](../notes/cli-webrtc-stack.md); what follows is the pin's own content: the behaviours the transport rests on that werift's published API does not state, and how to re-verify them before a bump merges. Every one was established by driving the library, not by reading it, which is also how each must be re-checked.

### The internal assumption: the SCTP send queues

The transport's flushing close reads `peerConnection.sctp.sctp.outboundQueue` and `sentQueue` -- chunks not yet transmitted, and chunks transmitted but not yet acknowledged. In werift 0.27.0 each is a `FifoQueue` object rather than an array, and the close reads only its `length`, which the class exposes as a getter. Both empty is the only observable point at which tearing the connection down cannot lose data, and there is no public API for it.

This is not a refinement of the data channel's `bufferedAmount`. That counter reaches zero while chunks are still unacknowledged, so a close gated on it loses them: measured at roughly one frame in three, nine datagrams of sixty-two, over a loopback channel with no packet loss at all. Gated on the queues, the same case delivered twelve times out of twelve. `assertSctpDrainSupported` checks on every session that both fields exist as objects with a numeric `length`, so a release that renames or restructures them fails loud rather than silently restoring that data loss.

The close is two-phase, and an upgrade must keep both halves. The frames are drained to acknowledgement; the PeerJS close sentinel that follows is drained only to transmission, because a peer closes the moment it reads the sentinel and therefore never acknowledges one -- waiting for that would spend the whole close budget on every clean close.

### The behavioural assumptions

- **An `iceServers` list holding a `stun` url replaces werift's built-in `stun.l.google.com:19302` default rather than adding to it.** This is what makes a configured `stun` list the list actually used. A list holding no `stun` url, whether empty, absent or holding only `turn` urls, means "use the default" (it does not mean "no STUN"), and `getConfiguration()` echoes its input, so it confirms pass-through but not suppression. Suppression is held by a separate check that hooks `dns.promises.lookup` -- the entry point werift resolves a STUN hostname through -- and asserts a peer built with `{}`, or with a list holding only a `turn` url, resolves `stun.l.google.com` while a peer built with a `stun` list does not (`test/integration/webrtc/transport.test.ts`). The default's endpoint is measured in the same suite rather than read off the library: the hostname is resolved to loopback and the real peer's STUN binding request is observed arriving on the port the endpoint names, so the host and the port are both driven. The transport warns when no list is configured, naming the default it is about to use; a list holding only `turn` urls uses the default without that warning. Setting werift 0.27.0's `iceUseDefaultStunServer` option to `false` turns the default off; the CLI leaves it at its default, `true`.

That endpoint is a confidentiality statement an operator reads before handing a recurring exchange's secret to a scheduler, and it is written by hand in more than one place: the CLI warning, the web app's command-line export panel (which may not import from another app), and the documents that state the default. It lives once, in `WERIFT_BUILT_IN_STUN_URI` (`apps/cli/src/connection/webrtc/weriftPeer.ts`), and `npm run check:stun-default-claims` holds every copy to it, so a bump that moved the default cannot leave one behind. The web app's own ICE list (`apps/web/src/psi/transport/rendezvous.ts`) is a different list and is not tied to it.
- **ICE candidates begin firing during `setLocalDescription`, before the local description can have reached the broker.** Browser PeerJS has no pre-remote-description candidate queue of its own and discards a `CANDIDATE` it cannot apply, silently from the sender's side, so the transport queues its own candidates until its description is on the wire. werift also inlines its candidates in the SDP, which masks a trickle loss entirely -- a broken queue therefore shows up as a connection that works until the inlined candidates are not enough, never as an end-to-end test failure. That is why the queue's ordering is pinned by a unit test against a scripted peer rather than by the live suite.
- **A peer that vanishes is detected in about thirty seconds, by consent freshness, and not before.** Until then `connectionState` still reads `connected`, the data channel still reads `open`, and `bufferedAmount` stays pinned at its peak. A partner whose peer connection is closed tells this side, which raises the data channel's `close` at once while `connectionState` still reads `connected`; a partner that crashes or drops off the network sends nothing, and that is the case consent freshness alone detects. So the transport watches `connectionState` to fail an exchange whose partner has gone; without it a party would wait out its hour-scale inactivity budget.
- **`send` accepts a `Buffer`/`Uint8Array` and `onmessage` delivers a Node `Buffer`**, and `pack` encodes a `Uint8Array`, an `ArrayBuffer` and a `Buffer` to identical bytes, so the framing is unambiguous in both directions.
- **`setRemoteDescription` and `addIceCandidate` accept plain objects** -- `{type, sdp}` and the browser-shaped `{candidate, sdpMid, sdpMLineIndex, usernameFragment}` -- which is what lets a broker payload be applied without reconstructing a library type. An unparseable candidate throws a `DOMException`, so a malformed one from a peer is catchable rather than fatal.
- **A remote host candidate named `<uuid>.local`, the form a browser gives its host candidates by default, is resolved by an mDNS query, and one no host answers costs 10 s.** Until the remote description has signalled end-of-candidates, werift 0.27.0's `addIceCandidate` settles at once, in about 2 ms, as 0.26.0's did whether or not the local description was set, and the query goes on running after it settles. A lookup still pending when its peer connection closes is cancelled by the close on 0.27.0: measured on a peer connection holding one such lookup, whose timer was armed at the close, the Node event loop drained 2 to 6 ms after the close. On 0.26.0 the lookup kept its timer, which held the loop until the 10 s were up: it drained about 10.0 s after the close on 0.26.0, and about 9.8 s on 0.25.0. werift 0.25.0's `addIceCandidate` instead did not settle until the query was answered or 10 s passed (after an `a=end-of-candidates` it skipped such a candidate without a query and settled at once); an unanswered candidate was then dropped without an error and never reached the ICE agent or `getStats`, and a candidate handed over after it was kept. The transport hands held candidates over without waiting on each ([WEBRTC_TRANSPORT.md](WEBRTC_TRANSPORT.md#negotiation-envelope)), so a release that waits on the lookup, as 0.25.0 did, cannot hold the candidates behind it: driven on 0.25.0 with two werift peers through the broker, the partner's description followed by two unresolvable `.local` candidates and then the one usable `srflx` candidate, the channel opened about 20 s after the description when each held candidate waited on the one before it, and about 0.2 s after it without (`test/integration/webrtc/heldRemoteCandidates.test.ts`, which passes on 0.26.0 and 0.27.0).
- **The negotiated SCTP `maxMessageSize` is 65,536 bytes** between two werift peers. The transport does not rely on it: PeerJS's own 16,300-byte chunking threshold is well below it, and the inbound bound refuses an over-cap datagram regardless of what the SDP negotiated.
- **werift 0.27.0 transmits an unpaced burst handed to the data channel without its cost per message growing with the burst, and its `bufferedAmount` falls as messages are transmitted.** Driven with two peers over loopback, 1,074 messages of 16,300 bytes (17.5 MB) arrived in about 2.0 s, 2,148 in about 3.7 s and 4,296 in about 7.4 s, where 0.26.0 on the same host took 1.9 s, 3.3 s and 6.3 s, the connection stayed connected throughout, and `bufferedAmount` fell 465 times over the 1,074-message hand-off. The send path does not rely on it:
  - The CLI paces to a window on `bufferedAmount` and the `bufferedamountlow` event ([WEBRTC_TRANSPORT.md](WEBRTC_TRANSPORT.md#outbound-pacing)). If the event stopped firing, a waiting send would still re-read the channel every 250 ms, so the failure is slower transfer rather than a hang.
  - The window exists because werift 0.24.4 did work on each acknowledgement that grew with the messages handed over and not yet transmitted: unpaced, a 17.5 MB frame took about 60 s and starved ICE consent until the connection failed, and a 35 MB set took about 344 s, where paced they took about 1 s and 2 s.
  - Re-check on a bump with the WebRTC completion run (`apps/cli/test/stress/webrtcCompletion.stress.test.ts`) at 1,000,000 records a side, timing each set transfer against the outgoing release on the same host, back to back. A regression shows as a set transfer of minutes or a lost connection.
  - Measured 2026-11-10 on one macOS host whose load came from other work, two pairs in alternating order, each set transfer timed on the sender from its first datagram to `bufferedAmount` reaching zero. 0.25.2 at a one-minute load of 31 and then 17: 317 s and 239 s to complete, 17.5 MB sets in a median 1.6 s and 1.3 s, 35 MB sets in 2.5 to 4.0 s. 0.26.0 at a load of 34 and then 46: 360 s and 232 s to complete, 17.5 MB sets in a median 1.1 s and 0.9 s, 35 MB sets in 1.9 to 6.6 s. No connection was lost in either.
  - Measured again for 0.27.0 the same way and on the same host later that day, in the order 0.26.0, 0.27.0, 0.27.0, 0.26.0, with 7.7 to 9.1 GB of swap in use. 0.27.0 at a one-minute load of 35 and then 39: 398 s and 254 s to complete, 17.5 MB sets in a median 2.4 s and 1.3 s, 35 MB sets in 2.5 to 4.8 s. 0.26.0 at a load of 16 and then 52: 292 s and 275 s to complete, 17.5 MB sets in a median 1.1 s and 0.9 s, 35 MB sets in 2.2 to 3.5 s. No connection was lost in either. 0.27.0's 17.5 MB sets were slower in both pairs, by 0.4 to 1.3 s in median.
- **A peer answers consent checks, and reads the answers to its own, only from the event loop of the thread that owns it, and two parties' holds of that thread add up.** A party whose main thread runs synchronous work neither answers its partner nor counts its partner's answers, and a party coming out of such a stretch does not start over: its partner's hold that follows is counted on top of its own. Measured on one host over loopback at 7,700,000 records a side, each party built its first cascade round's set in one stretch of about 27 s, the acceptor first and the inviter straight after it, and the acceptor's connection went from `connected` to `failed` about 29 s after its own stretch began, 2.4 s into the inviter's; with the set built in short stretches, the two parties' 26 s stretches resolving the round's matches, again one straight after the other, ended the connection the same way. The exchange therefore builds and resolves a cascade round in short stretches with the event loop run between them ([WEBRTC_TRANSPORT.md](WEBRTC_TRANSPORT.md#the-main-thread-on-an-open-channel)). Re-check on a bump with the WebRTC completion run (`apps/cli/test/stress/webrtcCompletion.stress.test.ts`) at its default 7,700,000 records a side on a host that can hold both parties: it completes in about twenty minutes, it holds each party's longest stretch on an open channel to a stated bound, and a regression shows as a lost connection in the first round.
- **`bytesSent` and `messagesSent` are counted at hand-off**, not as bytes leave, so neither is a progress gauge; there is no finer signal than the queues above.
- **`getStats()` resolves a `Map` whose entries name their fields as the W3C statistics dictionaries do**: a `type` of `local-candidate`, `remote-candidate` or `candidate-pair`, an `id`, a `candidateType`, and a pair's `localCandidateId`, `remoteCandidateId`, `state` and `nominated`. The ICE diagnostics an operator is shown are read entirely out of those names (`apps/cli/src/connection/webrtc/iceDiagnostics.ts`), and a rename would empty the report rather than fail it, so a live pair's report is asserted in the transport suite.
- **Closing the peer connection disarms a TURN allocation's refresh timer.** werift keeps an allocation alive by re-sending refresh on a timer armed from the lifetime the relay granted, and a timer left armed after the close holds the Node event loop for five sixths of that lifetime -- about 500 s where a relay grants the usual 600 s. werift 0.24.4 left it armed (8 min 19 s from close to the timer firing, measured against coturn), and nothing it exposed released it. On the pinned release the close disarms it: a peer connection that allocated against a scripted UDP relay granting 120 s let its event loop drain 1 ms after its close, where 0.24.4 held it 86 s. The relay still holds the allocation until the lifetime it granted ends, since the close sends no refresh releasing it ([WEBRTC_TRANSPORT.md](WEBRTC_TRANSPORT.md#budgets)). A release that leaves the timer armed again brings the held loop back, and the process then returns on the run's own budget rather than on the timer, naming the handle still armed.
- **werift refuses a DTLS certificate whose fingerprint the SDP did not name.** The CLI's `webrtc` channel applies the application-layer encryption ([CHANNEL_SECURITY.md](CHANNEL_SECURITY.md#which-channels-request-it)) above the DTLS session, which still protects the channel against the network path, so a session to any certificate other than the one a description's `a=fingerprint` line names must not complete. Driven with two real peers on loopback, one side's description handed over with its fingerprint value changed in one digit, werift 0.27.0 ends with a peer's `connectionState` at `failed`, no data channel opened and no message delivered, whichever of the offer and the answer is changed; the same pair with the descriptions unaltered opens both channels and delivers a message each way (`test/integration/webrtc/dtlsFingerprint.test.ts`).
- **werift answers an incoming ICE Binding request that carries no MESSAGE-INTEGRITY.** It verifies MESSAGE-INTEGRITY on the responses to its own connectivity checks, but answers a Binding request that arrives without it with a Binding Success Response, measured on 0.26.0 and 0.27.0. The same request switched a controlling agent to controlled, a request signed with a wrong password was answered the same way, and an agent that went on to connect added a peer-reflexive candidate for the sender and sent it checks, measured on 0.27.0. A party that can send to one of a CLI party's candidates during an exchange can so disturb that connection attempt; it cannot read or change exchange data, which the DTLS fingerprint check above and the application-layer encryption protect. Re-check on a bump by sending such a request to a peer's host candidate over loopback; once werift refuses it, this bullet goes.
- **werift gathers from every STUN and TURN url of the `iceServers` list it is given, so a CLI run gives it one of each.** A werift 0.27.0 peer given two STUN and two TURN loopback servers sends requests to all four while it gathers; 0.26.0 kept the first url of each kind and dropped the rest. A CLI run hands werift only the first STUN url and the first TURN url of the list it builds (`buildPeerConfiguration` in `apps/cli/src/connection/webrtc/weriftPeer.ts`), so it gathers relay candidates from the first TURN url it lists and server-reflexive candidates from the first STUN url, as [RELAY_CREDENTIALS.md](RELAY_CREDENTIALS.md#the-invitations-relay-locator) states. The unit test (`test/unit/connection/webrtcIceConfiguration.test.ts`) pins what the run hands werift and what `parseIceServers` keeps of it. The integration test (`test/integration/webrtc/firstTurnUrl.test.ts`) shows what a real peer contacts: given the list a run builds for two STUN and two TURN loopback servers, each answering with an error at once, it sends requests to the first of each kind only by the time its gathering completes, and given all four urls itself it sends requests to each.
- **werift sends a TURN request again under the new nonce when the relay answers it with `438 Stale nonce`, and the relay's 438 holds no MESSAGE-INTEGRITY.** coturn 4.18.0, the relay's image (`infra/relay/Dockerfile`), answers the first request after a nonce goes stale with a 438 holding only ERROR-CODE, NONCE, REALM and FINGERPRINT; at the relay's settings (no `stale-nonce` line, `max-allocate-lifetime=600`) that is the second round of refreshes, about 1,000 s after the allocation. werift 0.25.2 and 0.26.0 refused that answer for its missing integrity and sent the request again under the stale nonce until it timed out, so a relayed run lost its path about 1,000 s in. werift 0.27.0 sends it once more under the 438's nonce, as a new transaction: measured on 2026-11-10 with two werift peers relayed through coturn 4.18.0 over TURN on TCP, each 438 drew a retry the relay granted, and data kept flowing to the end of a 1,620 s hold. The unit test (`test/unit/connection/webrtcTurnStaleNonce.test.ts`) drives `TurnProtocol` against a scripted relay that answers a refresh with an unsigned 438, and holds that the refresh is sent again under the new nonce, signed, as a new transaction, and that the lifetime the relay then grants is kept; it fails on 0.25.2.

### Re-verification on a bump

- Run `npm run test:integration:webrtc -w apps/cli -- test/integration/webrtc/transport.test.ts`. It drives two real werift peers over loopback through the real vendored broker and covers the chunked round trip, the final-frame-before-close guarantee, the `iceServers` pass-through, the STUN-default suppression (observed through werift's DNS resolution, since no readable API shows it), the endpoint that default addresses, the inbound bound, the ICE statistics the diagnostics read by field name, and that a close still returns when the partner has vanished -- a partner cut off from the network before it closes, since its close would otherwise tell this side. A bump that moved the default reddens there first; `npm run check:stun-default-claims` then names every copy of the old endpoint still to be updated.
- Run `npm run test:integration:webrtc -w apps/cli -- test/integration/webrtc/dtlsFingerprint.test.ts` for the fingerprint check. A bump that accepted a certificate the description did not name reddens there.
- Run `npm run test:integration:webrtc -w apps/cli -- test/integration/webrtc/firstTurnUrl.test.ts` and `npm run test:unit -w apps/cli -- test/unit/connection/webrtcIceConfiguration.test.ts` for the one-TURN-url, one-STUN-url assumption. A bump through which a CLI run contacts a further url reddens in the integration test, and the stated limit in [RELAY_CREDENTIALS.md](RELAY_CREDENTIALS.md#the-invitations-relay-locator) is then updated with it; the other documents link to it.
- Run `npm run test:unit -w apps/cli -- test/unit/connection/webrtcTurnStaleNonce.test.ts` for the stale-nonce assumption. A bump that refuses an unsigned 438 again reddens there. It reaches `TurnProtocol` and not a relay: what a stale nonce costs a relayed run end to end is measured against coturn by hand, with a hold past the relay's second refresh round.
- Run `npm run test:integration:webrtc -w apps/cli -- test/integration/webrtc/heldRemoteCandidates.test.ts` for the `.local` assumption. It holds that a channel whose only working path follows two unresolvable `.local` candidates opens within 5 s of the description, in both roles; it does not time the lookup itself, so close a peer connection holding one unresolvable `.local` lookup by hand and time how long the Node event loop takes to drain, and a bump that changed the drain time goes back into the bullet above with its new value.
- Run `npm run test:unit -w apps/cli -- test/unit/connection/webrtcNegotiation.test.ts` for the orderings the live suite cannot show: no candidate before the local description, the offer retry and its stop condition, and the answer's payload shape.

It drives `TurnProtocol` against a scripted relay that grants one second, holds that a live allocation draws a refresh at five sixths of the grant, that the allocation arms one timer which the close removes from the timers Node counts as active (`process.getActiveResourcesInfo()`), and that no refresh arrives after the close; a bump that leaves the timer armed reddens there, and the bound goes back into the documents with it. It reaches the timer and not the process: what a held loop costs a run end to end is measured against a relay by hand.
- Re-drive the candidate-queue assumption by hand against a browser peer if the negotiation changes. The unit test pins the order this side emits in; only a real PeerJS peer shows what it does with one that arrives early.

The relay transports are present in the published API, the URL parser resolves the port-443 TLS case, and an allocation has been driven against a real relay for the refresh-timer assumption above, but no exchange here runs over a relayed candidate pair; drive one before any deployment relies on relayed connectivity.
