# Service fact sheet

This page is for an agency's counsel.
It lists the services the project runs for its hosted web application (`psi.data-bridge.org`, `staging.data-bridge.org` and `demo.data-bridge.org`) and states, for each, what it receives, what it stores, how long it keeps it, where it runs, and who operates it.
It states facts only and makes no determination under any law or regulation.
Each fact links the section that states it in full, and the check that keeps it true where one exists.

The container deployment (the command line app and the local console) uses these services only for a WebRTC exchange through them: inviting at the hosted site's address reads one public file from it, and the exchange then uses the project's coordination server, and the relay and registrar where the invitation names them ([PRIVACY.md, Container deployment](../PRIVACY.md#container-deployment-cli-and-local-console)).

| Service | What it receives | What it stores | How long | Where it runs, and who operates it |
| ------- | ---------------- | -------------- | -------- | ---------------------------------- |
| Hosted site (the application's pages) | Each page request: the client IP address, the path, and the time. The application runs in the browser, so no exchange data reaches it ([PRIVACY.md, Hosted web application](../PRIVACY.md#hosted-web-application)). | The project stores nothing: the pages are static files with no server-side code, and the project keeps no log of page loads, verified on the Cloudflare account on 2026-10-07. Cloudflare keeps its own request records ([PRIVACY.md](../PRIVACY.md#hosted-web-application); [DEPLOYMENT.md, What the deployment logs](DEPLOYMENT.md#what-the-deployment-logs)). | Cloudflare's request analytics: at least 31 days, with no maximum stated. Raw request logs: not kept unless turned on; whether they are on for this zone has not been checked ([PRIVACY.md](../PRIVACY.md#hosted-web-application)). | Cloudflare Pages, a third party, serves the pages; the project builds and uploads them ([DEPLOYMENT.md, The project's hosted web deployment](DEPLOYMENT.md#the-projects-hosted-web-deployment)). |
| Coordination server (`signal.data-bridge.org`) | The setup messages it passes between the two parties, the rendezvous identifiers derived for the exchange, connection times, client IP addresses, and the headers a browser sends, such as the user agent and origin. Not the exchange content, which is encrypted end to end under a key derived from the two parties' shared secret ([PRIVACY.md](../PRIVACY.md#hosted-web-application); [SECURITY_DESIGN.md, Channel security](SECURITY_DESIGN.md#channel-security)). | Log lines. The access log: time, the client IP address for a request to port 8443 and `127.0.0.1` for one through port 443, method, path without its query string, status, Upgrade header, bytes, and duration; no user agent and no rendezvous identifier ([`scripts/broker-front.test.mjs`](../scripts/broker-front.test.mjs)). The error log: warnings and errors, and a line can include the query string, which holds the rendezvous identifier. Which request headers an error-log line holds (Host, Referer, user agent, Origin) has not been measured. The server's own output: start-up and service lines ([PRIVACY.md](../PRIVACY.md#hosted-web-application); [infra/broker/README.md, Logging](../infra/broker/README.md#logging)). | Each log line: about 90 days after the newest entry in its file ([`scripts/relay-logging-posture.test.mjs`](../scripts/relay-logging-posture.test.mjs)). | A host the project runs, on Amazon Web Services (AWS) in `us-west-2`, behind a TLS front the project also runs. AWS hosts the machine and holds its disk. Cloudflare does not carry this traffic ([PRIVACY.md](../PRIVACY.md#hosted-web-application)). |
| TURN relay (`turn.data-bridge.org`) | Each party's IP address and port, connection times, and traffic volume. It learns the address of each party that lists it, whether or not traffic is relayed, and forwards encrypted packets without decrypting them ([PRIVACY.md](../PRIVACY.md#hosted-web-application)). | No relayed traffic. Log lines: a failed login, naming the credential's username (an expiry time and a fixed label); a refused peer address; and a socket error, naming the client's address and port ([webrtc-relay-deployment.md, What the relay host keeps](notes/webrtc-relay-deployment.md#what-the-relay-host-keeps); [`scripts/relay-logging-posture.test.mjs`](../scripts/relay-logging-posture.test.mjs)). | Each log line: about 90 days, as above. | The same host, run by the project. On `psi` and `staging`, an exchange uses it only where the user turned it on, the invitation names it, or the browser's relay setting names it; on `demo`, every browser exchange uses it; on any of them, the exchange's Allowed relays can leave it out ([DEPLOYMENT.md, The default relay](DEPLOYMENT.md#the-default-relay)). |
| WebSocket relay (on the same host, under a name of its own) | Each party's hello: the exchange id and a proof that the party holds the exchange's relay key ([WEBSOCKET_RELAY.md, The hello](spec/WEBSOCKET_RELAY.md#the-hello)). The host's port 443 front decrypts the connection's TLS and passes it to the relay ([infra/relay/README.md, The WebSocket relay](../infra/relay/README.md#the-websocket-relay)). Its operator sees each party's address, the fact and timing of the pairing, the volume each direction, the key-exchange frames, which hold no linkage identifier and no exchange data, and every later frame encrypted, with its sequence number and size. Not the key the proof is derived from ([web-websocket-transport.md, What the relay's operator sees](notes/web-websocket-transport.md#what-the-relays-operator-sees-stated-for-the-disclosure-documents)). | It reads the exchange keys from the relay's table and writes nothing to it ([WEBSOCKET_RELAY.md, The key table](spec/WEBSOCKET_RELAY.md#the-key-table)). Log lines: one at each start, a warning when the key table cannot be read, and its faults, each limited to one a minute; a fault about one exchange names its exchange id ([infra/relay/README.md, The WebSocket relay](../infra/relay/README.md#the-websocket-relay)). | Each log line: about 90 days, as above. | The same host, run by the project, under a DNS name that is neither `turn.data-bridge.org` nor `registrar.data-bridge.org` ([infra/relay/README.md, The WebSocket relay](../infra/relay/README.md#the-websocket-relay)). A hosted site names it only where its build sets `VITE_DEFAULT_RELAY_WEBSOCKET_URL`, which stays unset until the host runs the relay ([DEPLOYMENT.md, The default relay](DEPLOYMENT.md#the-default-relay)). A run that lists it opens a socket there as each rendezvous starts, whether or not WebRTC then carries the exchange, and sends the exchange through it only when no WebRTC path opens ([WEBRTC_TRANSPORT.md, Falling back to the WebSocket relay](spec/WEBRTC_TRANSPORT.md#falling-back-to-the-websocket-relay)). |
| Relay registrar (`registrar.data-bridge.org`) | From each party of an exchange that uses the relay, before it connects: an exchange id and a relay key, both derived from the shared secret, the party's IP address, and the time. Never the shared secret itself ([PRIVACY.md](../PRIVACY.md#hosted-web-application); [PROTOCOL.md, Enrolling at a default relay](spec/PROTOCOL.md#enrolling-at-a-default-relay)). | The exchange id and relay key, in the relay's table. One log line per request (method, path, and status) and one per enrollment (exchange id, time, and outcome); no line names an IP address or the key. The IP address is held in memory for rate limits and not written ([infra/relay/README.md, The registrar](../infra/relay/README.md#the-registrar); [`scripts/relay-exchange-keys.test.mjs`](../scripts/relay-exchange-keys.test.mjs)). | The table entry: 70 minutes after enrollment, then deleted within about 11 minutes ([`infra/relay/alcove-relay-sweep.timer`](../infra/relay/alcove-relay-sweep.timer)). Log lines: about 90 days, as above. The address in memory: until its 10-minute window or 70-minute entry has ended and a later enrollment arrives, or the registrar restarts. | The same host, run by the project. |

Every log above is kept in that host's system journal, which nothing copies off the host ([PRIVACY.md](../PRIVACY.md#hosted-web-application)).
The journal can also delete entries sooner when it reaches its size limits, which are journald's defaults.
The host's port 443 front, which routes connections to the coordination server, the TURN relay, the WebSocket relay and the registrar ([infra/relay/README.md, The 443 front](../infra/relay/README.md#the-443-front)), keeps no access log; its error log names a client's IP address when a service refuses, times out, or resets that client's connection.

Besides Cloudflare, two other third parties are involved: AWS, which hosts the project's host and can observe its network metadata, and Google, whose STUN server learns each browser's IP address where neither the browser's relay settings nor the invitation names a STUN server, with one exception stated in [PRIVACY.md](../PRIVACY.md#hosted-web-application).
`npm run check:egress-claims` fails the build when the shipped source gains an address naming a host outside a reviewed list, within the limits stated in [SECURITY_DESIGN.md, Egress hardening and its limits](SECURITY_DESIGN.md#egress-hardening-and-its-limits).
